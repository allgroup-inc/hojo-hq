# 家計のポっ(apo-kanri)

家計の見直しやさん(株式会社エンライフ)の対面営業向けアポ管理システム。
名称「家計のポっ」は2026-08-14 小柳さん決定。配色は公式ロゴ(同日受領)から抽出した
**黄 #F9C93F × 墨 #221D11**。ヘッダーのロゴは提供画像を元にSVGで描き起こした再現版
(公式の高解像度データを入手したら `src/apoPage.js` の `KAKEIPO_LOGO_DATA_URI` を1箇所差し替え)。

**正式表記は「家計のポっ」**——カタカナの「ポ」+**小さいひらがなの「っ」**。
誤字ではなく、ゆるさ・親しみやすさを狙った意図的な表記(「家計のポッ」は誤り)。
資料・Slack・周知文でもこの表記に統一すること。

設計書: `docs/superpowers/specs/2026-08-14-apo-kanri-console-design.md`
実装プラン: `docs/superpowers/plans/2026-08-14-apo-kanri-console.md`

## これは何か

**アポを組む人とアポに行く人が、一緒に予定を確認し、効率よくアポを回るためのスケジュール連携システム。**
アポ入れ担当と対面営業メンバー(7名以上)が、**アポ連携・申込み連携・急な変更・
前アポ長引きの遅れ連絡**を1つのスマホ画面とSlack通知で共有する。

### 守備範囲(ここを踏み越えない)

| このシステムが持つもの | 持たないもの(=対面営業マン物件管理システムの領分) |
|---|---|
| 日時・場所・担当営業・アポ入れ担当・ステータス・変更履歴 | 顧客/世帯情報・訪問履歴・**架電リストと結果** |
| 「今日は誰がどこへ行くか」「空きはどこか」「ずれたら誰に伝わるか」 | **リードソース(紹介・ご家族)・紹介元**・見込み度・提案商品 |

しまい、小柳さん指摘で撤去した。**架電・リード管理の要件が来たら、実装せず
`docs/連携メモ_YYYYMMDD_<件名>.md` で物件管理システム側へ渡すこと**
(引き渡し済み: `docs/連携メモ_20260819_対面営業マン物件管理システム.md`
/ 先方回答と本システムの回答: 同 `_回答.md`)。

### 5システムの中での位置づけ(❷)と共通の約束

本システムは5つの入口のうち **❷ 営業アポスケジュール管理システム**。
❶でアポが確定した時点で入り、**訪問した時点で❸へ移る**(面識のある相手は営業マンが
直接追うほうが効率が高いため)。訪問に至らなければ差し戻しで❶へ返す。

| 共通の約束 | 本システムの状態 |
|---|---|
| 【1】顧客データを自分の中に持たない | **一部保持**。`顧客名` のみ独自に持つ(電話番号・住所・生年月日は持たない)。台帳から氏名を引く手段が用意でき次第、参照へ寄せる |
| 【2】顧客の番号を自分で発番しない | 遵守。`顧客ID` は参照のみ(発番しない) |
| 【3】自前のログイン・ユーザー管理を作らない | **一部抵触**。パスワードは作っていない(Googleアカウント認証)が、`スタッフ` タブは自前。統合の認証基盤が決まり次第寄せる |
| 【4】ステータスの言葉を言い換えない | 遵守(2026-08-21 移行済み) |

### 名寄せキーと結果連携(2026-08-21 軸の裁定で更新)

- **正の参照キーは KM-000001 形式**。ただし名寄せの親統合で採番が動くため、**今は焼き付けない**。
  当面の保存は**アセンドの顧客id**(`アポ予定` の `顧客ID` 列)、KM- は読み取り時に
  resolve API で引く。カットオーバーで焼き付けてから不変にする
  → **resolve API の仕様待ち**(URL・認証・応答形式)
- **フォームには出さない**(営業に手入力させない)。自動連携が通るまでは空のまま
- **訪問結果(訪問済/申込)は❸❹が持つ**。❷は本来「読むだけ」。
  ❸からの結果連携が通るまでの暫定として `schema.js` の `RESULT_INPUT_MODE = "許可"` で
  ❷からの入力を通している。**❸連携を実装するリリースで "禁止" に倒すこと**
  (禁止にすると❸❹のステータスは❷から書き換え不可になる)
- **転換ファネルの数え方は軸が一元管理する**。❷と❸が別々に数えると必ずズレ、
  両方の数字が信用されなくなるため。`apoCore.js` の `VISITED_STATUSES` /
  `SIGNED_STATUSES` は**暫定**で、画面にも「この定義は暫定です」と出している
  → **正式定義待ち**

- 実データ(顧客名・アポ情報)は専用のGoogleスプレッドシート「アポ管理台帳」に保持し、
  このディレクトリにはGASのコードのみを置く。**実データは一切このリポジトリにコミットしない**
- **glow-ma(M&A台帳)とは完全に別のシステム**。スプレッドシートもWeb AppのURLも別。
  apo-kanri のコードから glow-ma のシート・コードを参照してはならない
  (シートIDのハードコード禁止。`SpreadsheetApp.getActiveSpreadsheet()` のみ使用)

## できること(MVP)

| 場面 | 操作 | 起きること |
|---|---|---|
| アポが取れた | ＋新規アポ → 保存(1フォーム) | 担当営業へSlack即通知+変更履歴記録 |
| 続けて何件も登録 | 「保存して続けて登録」 | 保存後もフォームが開いたまま。日付・担当営業・アポ入れ担当・形式は引き継ぎ、顧客名・場所・メモだけ空になり顧客名にカーソルが入る(1日100件入力向け) |
| 日時・内容の変更 | カード→編集→保存 | 差分つきでSlack通知+履歴記録 |
| 申込 | カード→🎉申込(2タップ) | 🎉通知+履歴記録。※本来は❹が持つ語。❸連携までの暫定 |
| 差し戻し(訪問に至らず❶へ返却) | カード→❌(顧客都合/自社都合) | ❌通知+履歴記録。**理由は別項目**で持つ(自社都合=訪問枠を捨てた損失なので顧客都合と必ず分ける)。**人事評価に使わないこと** |
| 前アポが長引く | カード→⏰遅れそう(+15/30/60分) | 本日の後続アポのアポ入れ担当へ自動通知(**時刻は変えない。調整の判断は人間**) |
| アポが切れた(代打) | 差し戻し操作をするだけ | 🧭その時間が空いている営業を、同日の前後アポの場所+Googleマップリンク付きでSlackに自動提示(**GPS・位置情報は不使用**。誰に行ってもらうかの判断・連絡は人間) |
| 今日やることの確認 | **開くだけ** | 画面の一番上に「手当てが要るもの」が出る。**探させない・検索させない**(下記) |
| 今日の全体確認 | 開くだけ(本日ビューが初期表示) | 全員分を時刻順に表示。現在時刻の線と1時間以上の空きを行間に挟む。「自分のアポ」「担当者チップ」で絞り込み |
| 空いている枠を探す | 本日ビューの下 | 明日から7日分・90分以上の空きを営業ごとに表示。全員終日空きの日は1行にたたむ |
| 全体を一目で見る(朝礼・夕礼) | 「全体」タブ | **営業×時間の帯**(誰がいつ動くか・いまの時刻の線つき)+**本日の結果表**(これから/結果待ち/訪問済/申込/差し戻し)。帯をタップでそのアポが開く |
| 先の予定確認 | 「週」タブ | 今日から7日分を日別表示 |
| 埋まり・生産性確認 | 「分析」タブ | 本日の埋まり状況(営業別バー)+過去30日の転換ファネル(結果が出たアポ→訪問に至った→申込に至った)+温度感別の申込率(高🔥/中⚡/低❄️)。いずれも母数併記・母数10件未満は参考値表示。**ファネルの定義は軸から届くまで暫定** |
| ダブルブッキング | 同一営業の時間帯重複を保存時に警告 | 警告表示→もう一度保存で登録(止めない) |

### 「手当てが要るもの」に出るもの(2026-08-21 追加)

**新しい入力は1つも増やしていない。**すべて既存の列から導いている
(共通の前提【1】入力は仕事の副産物・【4】放置されているものが自動で浮上する)。
緊急な順に最大8件。それ以上は件数だけ出す。

| 出るもの | 条件 | なぜ出すか |
|---|---|---|
| 結果待ち | 訪問終了から90分過ぎてもステータスが❷の持ち場のまま(14日前までさかのぼる) | 訪問したのか差し戻しか分からない状態が**最も埋もれる**。入力漏れと「本当に無い」の区別がつかなくなる |
| 重なり | 同じ営業の時間が重複(**まだ始まっていないものだけ**) | 過ぎた重なりは直しようがないので出さない |
| 未確定 | 訪問日が2日以内なのにスケジュール調整中のまま | 確定しないまま当日を迎える |
| 行き先なし | 訪問・来店なのに場所が空で、訪問日が2日以内 | 営業が行き先を知らないまま当日を迎える。オンラインは対象外 |
| 担当なし | 担当営業が空 | 通知が誰にも届かない |

閾値(90分・2日・14日・8件)は `apoCore.js` の冒頭に定数として置き、理由をコメントで
残している。**出しすぎると読み飛ばされて、埋もれるのと同じ状態になる**ため広げない。

### 「全体」タブの見かた(2026-08-21 追加)

朝礼・夕礼で1画面を見ながら段取りを決めるための面。**担当者チップは出さない**
(絞り込んだ状態を「全体」と読み違えるのを防ぐため)。

- **帯の見た目**は色だけに頼らない。これから=白枠 / 結果待ち=赤枠 / 訪問済=薄い灰 /
  申込=ブランド色 / 差し戻し=破線+取り消し線
- **アポゼロの営業も行として残す**(消すと「誰が空いているか」が分からなくなる)
- スタッフ表にない担当営業・担当が空の行も**黙って消さず**「(担当なし)」等で出す
- 表の**結果待ち**列だけ赤で立てている。ここが減っていれば、その日の記録は追いついている
- 横に広いので、**その枠の中だけ横スクロール**する(ページ本体は横に動かない)
- **評価目的では使わない**(v1.1三名体制裁定・軸の裁定③と同じ理由)

訪問済/申込の数え方は転換ファネルと**同じ定数**を使っている(`VISITED_STATUSES` /
`SIGNED_STATUSES`)。2つ持つと必ずズレて、どちらが正しいかの議論になるため。

### ステータス(5システム共通語彙・言い換え禁止)

❷が書き換えてよいのは自分の持ち場だけ。訪問済以降は❸❹が持ち、❷は読むだけ。

| ❷が持つ | ❸❹が持つ(❷は表示のみ) |
|---|---|
| スケジュール調整中 / アポ確定 / 差し戻し / 対象外 | 訪問済 / 追客中 / 申込 / 成立 / 保全中 |

- **スケジュール調整中は訪問枠を押さえる**(調整の途中で他アポに枠を取られると調整が
  破綻するため)。本当に流れたら**差し戻し**にして明示的に空ける
- 枠が空くのは **差し戻し・対象外の2つだけ**
- **対象外**(架電禁止・アポ禁)は持ち場と無関係に最優先で効く。❶からの連携が通るまでは
  ❷側で自動判定できないため、手動で設定する運用

通知は5種限定(新規・変更・差し戻し・申込・遅れそう)。リマインダー等は作らない
(通知過多で肝心の連絡が埋もれるのを防ぐ)。

## セットアップ(初回のみ・小柳さん向け手順)

1. **スプレッドシート新規作成**: Googleドライブで「アポ管理台帳」を新規作成する。
   共有相手はアポ管理のスタッフのみ(glow-ma台帳と共有設定を分ける)
2. **GASプロジェクト紐付け**: スプレッドシートの 拡張機能 > Apps Script でプロジェクト作成
3. **コード反映**: 次のどちらか
   - clasp: `npm install -g @google/clasp` → `clasp login` →
     `apo-kanri/.clasp.json.example` を `apo-kanri/.clasp.json` にコピーして scriptId を書き換え →
     `cd apo-kanri && clasp push`
   - コピペ: `apo-kanri/dist/apo-kanri-bundle.gs`(8ファイルを1つにまとめた自動生成物)を
     `コード.gs` に貼り、`src/appsscript.json` をマニフェストに貼る。計2回のコピペで済む。
     **src を変更したら `node scripts/build_apo_bundle.mjs` で再生成すること**
     (同期ずれは tests/apo_kanri_bundle.test.mjs がCIで検出する)
4. **タブ作成**: Apps Scriptエディタで `ensureApoTabs` を一度実行(冪等・何度でも安全)
5. **スタッフ登録**: 「スタッフ」タブに全利用者の 氏名 / Slack User ID / 有効✔ /
   メールアドレス / 役割(アポ入れ・営業・両方)を入力
   (Slack User ID: プロフィール→「その他」→「メンバーIDをコピー」)
6. **Slack Webhook**: 通知チャンネル用 Incoming Webhook を発行し、Apps Scriptの
   スクリプト プロパティ `SLACK_WEBHOOK_URL` に設定(コードに書かない。未設定時は通知スキップ)
7. **デプロイ**: 「デプロイ」→「新しいデプロイ」→種類「ウェブアプリ」。
   **実行ユーザー: 「ウェブアプリケーションにアクセスしているユーザー」** /
   アクセスできるユーザー: 「Googleアカウントを持つ全員」
   ※「自分」にすると個人Gmail運用ではアクセス者のメールが取得できず、所有者以外全員が
   ログイン不可になる(2026-08-17レビューで検出)。各スタッフは初回アクセス時に
   権限承認ダイアログを1度通る(「詳細」→「移動」→「許可」)
8. **URL共有**: デプロイURLをスタッフに共有(スマホの「ホーム画面に追加」推奨)。
   スタッフタブに登録されたGoogleアカウント以外はアクセス拒否画面になる

## 運用ルール

- **シートの直接編集は禁止**(すべてWeb Appから操作する)。変更履歴タブは
  「Web App操作の記録」であり、直接編集は履歴にも通知にも残らない
- 列の追加は `src/schema.js` の配列**末尾のみ**(途中挿入は既存データが列ズレして破損する)
- 遅れそう連絡は社内通知のみ。**顧客への連絡・後続アポの時刻変更は必ず人間が行う**
- アポ実績の数字を人事評価に使わない(設計書 Non-goals)。分析タブの埋まり率・転換率も同様
  (転換率はチーム全体のみ表示。営業マン別は評価誤用リスクのため実装していない)
- **GPS・位置情報は取得しない**。スタッフの位置情報取得(GPS連動の訪問メンバー最適化)は
  守り部審査+小柳さん正式決裁が出るまで実装禁止
  (v1.1設計書の三名体制裁定。GPSレスの近接候補提示が推奨代替案)
