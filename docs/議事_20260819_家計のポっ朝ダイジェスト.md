# 議事: 家計のポっに「朝ダイジェスト」を追加するか(2026-08-19)

起票: sales-appointment-management-appチャット / 裁定者: 部門長(AI側)→ **結論は保留・小柳さんへ上申**

## 背景

家計のポっ(apo-kanri)は実装完了・本番投入待ち。共有ツール最大の失敗パターンは
「誰も開かず、結局チャットで個別連携に戻る」こと。対策として、毎朝1回
「今日のアポ一覧+空き状況」をSlackへ自動投稿する案(朝ダイジェスト)が浮上した。

**重要な前提**: この案は v1設計(2026-08-14)の三名体制裁定④
「**通知を5種に限定しリマインダー系を作らない**」と正面から衝突する。
CLAUDE.md三名体制ルール8により、①ルールの変更 ②外部送信/配信 の両方に該当するため
議事必須。過去の裁定を覆す提案なので、AI側では決めず小柳さんへ上申する。

## 論点: 朝ダイジェスト(毎朝8時のSlack自動投稿)を追加すべきか

### スイシン(推進)

- 定着の一押しになる。全員がアプリを開かなくても、その日の動きがSlackで揃う
- 「開かない人がいて情報が届かない」失敗を、運用ルールではなく仕組みで防げる
- 実装は軽い(GASの時間主導型トリガー1本+既存の集計ロジックの再利用)。
  新しいデータも権限も増やさない
- 空き状況が毎朝出れば、アポ入れ係が「今日どこを埋めるか」を朝一で判断できる

### ウタガイ(懐疑・反対必須) ← 反対理由の記録

- **v1裁定④と衝突する**。あのとき「通知過多で肝心の遅延通知が埋もれる」と判断して
  リマインダー系を明確に禁じた。3日で前提が変わったわけではないのに覆すのは、
  裁定の軽視であり、同じ理屈で今後いくらでも通知が増える入口になる
- 毎朝必ず飛ぶ通知は、**中身が薄い日ほど無視の習慣を作る**。アポが0〜2件の日も
  投稿されると「ポっの通知は読まなくていい」という学習が起き、遅延通知の既読率まで下げる
- **未稼働の段階で定着対策を先回りするのは、存在しない問題への実装**。
  現場が実際に「開き忘れる」と分かってから足しても遅くない(むしろ根拠つきで設計できる)
- 朝8時固定はスタッフの出社・訪問リズムと合う保証がない。合わなければ雑音そのもの
- 時間主導型トリガーは無人自動化。失敗しても誰も気づかない経路が1本増える
  (resilient-agent-designの観点では、停止検知の設計まで含めないと「静かに止まる」)

### ベッカイ(別解・前提を疑う)

- そもそも「毎朝配信」ではなく**閲覧の動線**を作ればよいのでは。スマホのホーム画面に
  アイコンを置く(本日実装済み)+朝礼で1回開く運用ルールで足りる可能性がある
- 配信するとしても、毎日ではなく**条件付き配信**が筋: 「本日のアポが3件以上ある日だけ」
  「未確定のアポが残っている日だけ」など、読む価値がある日に限る
- あるいは**Slackのリマインダー機能**(`/remind`)でURLを流すだけなら、コードも
  トリガーも増えない。まずこれで試して、物足りなければ実装する

## 結論(部門長の裁定)

- 採否: **保留・小柳さんへ上申**(AI側では決めない)
- 理由: 効果は見込めるが(スイシン)、**3日前の自分たちの裁定を覆す提案**であり、
  かつ未稼働=根拠となる実測がない(ウタガイ)。ベッカイの「まずSlackリマインダーで
  URLを流す/条件付き配信」という段階案が、コストも副作用も小さく合理的
- 上申する選択肢(小柳さんが1つ選ぶ):
  1. **何もしない(推奨)** — 試運転1〜2週で「開き忘れ」が実際に起きるか観測してから決める
  2. **Slackの /remind でURLだけ流す** — 実装ゼロ。今日から試せる
  3. **条件付きの朝ダイジェストを実装** — 「本日3件以上」等の条件つき。v1裁定④の
     見直しとセットで決裁が必要
  4. 毎朝無条件で配信 — ウタガイの反対理由により推奨しない
- 見直し期限: 2026-11-19(本番稼働3ヶ月後。実測データが揃う時点で自動で再議論)
