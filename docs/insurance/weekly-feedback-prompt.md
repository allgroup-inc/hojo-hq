# 保険引き受け目安検索 — 週次フィードバック取り込みプロンプト

**実行頻度:** 毎週月曜 10:00 JST  
**所要時間:** 30～60分  
**実行者:** 検証部 + LINE部 + 現場営業（フィードバック提供）

---

## 📋 実行プロンプト

```
あなたは保険引き受け目安検索の品質監視チームです。
週次でユーザーからのフィードバックを回収し、緊急対応が必要な誤りを検出してください。

【状況】
- ツール: 保険引き受け目安検索（3社統合）
- ユーザー: 診断部・LINE部・現場営業・提携士業
- フィードバック源: Slack #検証-保険 / LINE グループ / メール
- 対応ルール: 重大誤り（実運用に影響）は即座に修正＆アラート

【STEP 1: フィードバック回収】

以下のチャネルから、今週（月～日）に寄せられたフィードバックをすべて回収してください:

① Slack #検証-保険
  - 「この判定は違う」
  - 「公式基準ではXXと書いてある」
  - 「利用者からこんな質問が来た」

② LINE グループ（なないろ営業・FWD営業・チューリッヒ営業）
  - 「この疾患、実は加入不可なんです」
  - 「基準が改定されました」

③ メール feedback@hojo-hq.example.com（外部から）
  - 「ツールの判定が正確ではない」
  - 「この特約は加入できないはずです」

④ GitHub Issues
  - bugs / question ラベル付きでフィードバック報告がないか確認

【集計フォーマット】

| # | 報告元 | 病名 | 保険会社 | ツール判定 | 報告内容 | 情報源信頼度 | 優先度 |
|---|---|---|---|---|---|---|---|
| 1 | 下地さん（営業） | 神経線維腫 | なないろ | △ 条件付き | 「実際には医療と死亡のみ。他は不可」 | ⭐⭐⭐⭐⭐（公式基準） | 🔴 高 |
| 2 | 患者相談 | XX病 | FWD | ✅ 可 | 「加入拒否されました」 | ⭐⭐⭐（実運用） | 🔴 高 |
| 3 | XX士業さん | YY症 | チューリッヒ | ❌ 不可 | 「実は条件付きで加入できるらしい」 | ⭐⭐（伝聞） | 🟡 中 |

【STEP 2: 情報源の信頼度を評価】

各フィードバックについて、以下で情報源を判定してください:

| 信頼度 | 判断基準 | 対応 |
|---|---|---|
| ⭐⭐⭐⭐⭐（確実） | 保険会社公式基準・公式サイト・営業から公式情報 | ✅ 即座に JSON 修正 |
| ⭐⭐⭐⭐（高） | 実運用報告（利用者からの実体験）・複数ソースの一致 | ✅ 即座に JSON 修正 + 情報源確認 |
| ⭐⭐⭐（中） | 業界レポート・他社事例・士業からの伝聞 | 🟡 要確認（月次チェックで扱う） |
| ⭐⭐（低） | 単一の伝聞・不確かな情報 | ❌ スキップ（月次チェック時に再評価） |
| ⭐（確実に偽） | 明らかに誤った情報・根拠不明 | 🚫 却下＆報告者に説明 |

【STEP 3: 緊急対応判定】

以下の場合は「🔴 高優先度」で即座対応:

条件 | 判定 | 対応例 |
---|---|---|
実運用で「加入拒否された」と報告 | 🔴 高 | 情報源確認後、即座に JSON 修正 |
公式基準が変わった | 🔴 高 | 公式URL確認→即座に修正 + 影響範囲確認 |
複数の保険会社から同じ指摘 | 🔴 高 | 即座に修正（複数社の一致＝確実） |
ツールの判定が「顧客不利」（加入可→不可の誤り） | 🔴 高 | 即座に修正＋謝罪メール送付 |

以下の場合は「🟡 中」で月次チェック時に扱う:

条件 | 判定 | 対応例 |
---|---|---|
士業からの伝聞「実は...」 | 🟡 中 | 公式確認を取った上で月次チェック対象に |
複数説が存在する | 🟡 中 | 三名体制で議論（STEP 3 参照） |

【STEP 4: 🔴 高優先度の場合、即座に JSON 修正】

```bash
# 新しいブランチを作成
git checkout -b fix/insurance-urgent-2026-08-21

# JSON を修正（修正方法は underwriting-schema.md 参照）
# 例: confidence_level を「中」→「高」に変更、condition_text を詳細化

git add docs/insurance/underwriting_full.json
git commit -m "fix(insurance): 神経線維腫（なないろ）の判定を緊急修正

報告元: 下地さん（営業）
報告内容: 公式基準で『医療・死亡のみ』と確認
修正内容:
  - judgement: '条件付き' → '条件付き' (変わらず)
  - confidence_level: '中' → '高' (公式確認できたため)
  - condition_text: 詳細化 → '医療・死亡特約のみ。他は不可'
  - data_completeness: 0.65 → 0.88

情報源: なないろ生命公式引き受け基準
対応時刻: 2026-08-21 14:30 JST"

git push origin fix/insurance-urgent-2026-08-21
```

PR を作成し、即座にマージ:
```bash
# GitHub CLI で自動 PR 作成
gh pr create --title "fix(insurance): 神経線維腫の緊急修正" \
  --body "公式基準確認により confidence_level を中→高に昇格。" \
  --assignee @検証部
  
# マージ
gh pr merge --merge
```

【STEP 5: 複数説が存在する場合、三名体制で議論】

例: 「加入可」と「条件付き」で説が分かれている場合

🎯 スイシン（推進）:
  「ツールは『条件付き』と表示。報告は『加入可』。
   実運用で加入できた実績があるなら『加入可』に修正すべき」

⚠️ ウタガイ（懐疑）:
  「ちょっと待て。1件の実績だけで判断できるのか。
   他の利用者から『加入拒否された』という報告がないか確認が必要」

💡 ベッカイ（別解）:
  「前提を疑おう。『加入可/条件付き』の定義を確認。
   もし『条件付き』＝『特定の医歴なら加入可』という定義なら、
   『条件付き』が正確で『加入可』は誤りかも」

結論の例:
```
決定: 『条件付き』で現状維持
理由: 
  - 1件の実績だけでは全体傾向と判断できない
  - 『条件付き』が正確（条件によっては加入可）
  - 他からの報告がないか月次チェックで追跡

但し、condition_text を詳細化:
  『XX経歴がない場合は加入可。YY経歴がある場合は要相談』
  （報告者からのヒアリングで条件を明確化）

次アクション: 月次チェック時に複数事例を集約
```

## 🚨 緊急時の連絡フロー

**ツール誤りで顧客に損害が発生した場合:**

1. 即座に JSON 修正＆PR マージ ← 技術対応
2. LINE部に緊急連絡 → 顧客対応
3. 小柳さんに報告 → 対外対応判断
4. 月次チェック時に「なぜこの誤りが検出できなかったか」を三名体制で議論

---

## 📌 重要な約束事項

✅ **情報源が確実（⭐⭐⭐⭐⭐）ならば迷わず修正**
  - 「本当にいいのか」という懸念は無用
  - データが間違っているより、遅れている方が害

✅ **情報源が低い場合は月次チェックに回す**
  - 「このフィードバックは本当か」を確認する時間を作る
  - 月次チェック時の三名体制で「いくつかの根拠」を集約する

✅ **フィードバック提供者には必ず結果を返す**
  - 「修正しました」「月次チェック対象に入れました」など
  - 信頼関係の構築＝継続的なフィードバック源の確保
