# 勝てるくん プロンプト設計ガイド v2(2026-08-12)

構想: 保険証券を写真に撮る → AIが内容を読み取る → 当社取扱3社(なないろ生命・FWD生命・チューリッヒ生命)の保障で良い案内ができる提案を見出すシステム。
担当チャット: kateterukun-prompt-design / 位置づけ: 出口3(法人保険・家計の見直しやさん)側の営業支援ツール。
※「沖縄企業のミカタ」本体のCV導線(LINE単一)とは別系統。ミカタのサイト・LINEには載せない。

更新履歴:
- v1(2026-08-12): 証券1枚の読み取り→比較→提案の3ステップ設計+三名体制議事
- v2(2026-08-12): **3類型対応**(❶個人1枚/複数枚 ❷夫婦 ❸世帯)+3社マッチング設計。**名称「勝てるくん」は社内限定で確定(2026-08-12 小柳さん決裁)**。残る決裁は守り部審査のみ

---

## 0. 結論と前提

- 証券写真の読み取り・保障マップ化・3社候補とのマッチングは、Claudeで**技術的に可能**。読み取りは今日から試せる
- 比較・乗換提案は保険募集の規制領域(比較表示・乗換時の不利益説明。適用条文は守り部→弁護士確認前のため要確認)。**AIの出力は下書きまで**。お客様に出す前に必ず募集人(人間)が確認する
- AIに3社の商品内容・保険料を**記憶から答えさせるのは禁止**(もっともらしい誤りが混ざる)。3社の資料は必ずこちらから渡す
- 「3社が勝つ結論ありき」にはしない。**勝ち筋がなければ正直に現状維持推奨**を出させる。これが信頼と法令対応の両方を守る(3社で埋められる穴が実際に多ければ、正直な比較でも自然に3社の提案が増える)

## 1. 全体像 — 共通パイプライン(3類型とも同じ流れ)

```
証券の写真(1〜N枚・家族の分も)
  ↓ プロンプトA: 読み取り(1枚ずつ → JSON)※名前は「夫」「妻」「長男」等に置き換え
  ↓ (人間が「要確認」項目を埋める・誤読チェック)
  ↓ プロンプトB: 保障マップ(人×保障分野の一覧表+重複+穴)
  ↓ プロンプトC: 穴分析+3社マッチング(渡した3社資料+引受目安と照合)
  ↓ プロンプトD: 提案下書き(勝ち筋4分類)
  ↓ 募集人が確認・修正 → お客様へ
```

| 類型 | 使うプロンプト | 備考 |
|---|---|---|
| ❶ 個人・証券1枚 | A → C → D | Bは省略可(1枚ならマップ不要)。乗換比較が中心 |
| ❶ 個人・複数枚 | A×N → B → C → D | 重複保障の発見が価値になりやすい |
| ❷ 夫婦 | A×N → B(夫婦) → C → D | 片方に保障が偏る「穴」が見つかりやすい |
| ❸ 世帯 | A×N → B(世帯) → C → D | 子・親も含む。保障の空白世代が見える |

ポイント: **類型ごとに別システムを作らない**。プロンプトBに「対象範囲(個人/夫婦/世帯)」を宣言するだけで3類型すべてに対応する。

## 2. 指示の出し方 7原則(共通の型)

1. **役割を1行で決める** — 「あなたは保険証券の読み取り担当です」
2. **出力の形を先に決める** — 欲しい項目をJSONや表の雛形で見せる
3. **手順は番号で書く** — 読み取る→束ねる→照合する→分類する、と順番を固定
4. **読めないものは「要確認」と言わせる** — 推測で埋めさせない。断定禁止
5. **3社の資料はこちらから渡す** — AIの記憶の商品知識を使わせない
6. **「勝てない」も言わせる** — 勝ち筋なし=現状維持推奨を正解の一つにする
7. **不利益もセットで出させる** — 解約返戻金・免責リセット・再告知・旧契約の高予定利率

## 3. プロンプトA: 証券読み取り(1枚ずつ・全類型共通)

```
あなたは保険証券の読み取り担当です。
添付した保険証券の写真から、契約内容を下のJSON形式で抜き出してください。

ルール:
- 写真に書いてあることだけを抜き出す。推測で埋めない
- 文字が読めない・写真に写っていない項目は "要確認" と入れる
- 金額・日付は原文の表記のまま書き写す(単位や和暦・西暦を勝手に変換しない)
- 個人名は書き写さず、私が指定する呼び名(例: 夫、妻、長男)に置き換える
- 氏名・住所・証券番号・電話番号・受取人名は、写真に写っていても**出力に一切含めない**(書き写さず無視する)
- 最後に「読み取りに自信がない項目」を必ず列挙する

この証券の被保険者の呼び名: 【ここに「夫」「妻」など記入】

出力形式:
{
  "被保険者(呼び名)": "",
  "契約者(呼び名)": "",
  "保険会社名": "",
  "商品名": "",
  "契約日": "",
  "被保険者の契約時年齢": "",
  "保険期間": "",
  "払込期間": "",
  "保険料": { "金額": "", "払込方法(月払/年払など)": "" },
  "主契約": { "種類": "", "保険金額": "" },
  "特約": [ { "名称": "", "保障内容": "", "金額": "" } ],
  "解約返戻金の記載": "",
  "読み取りに自信がない項目": []
}
```

使い方: 証券1枚につき1回。**撮影時に氏名・住所・証券番号の欄を付箋や指で隠す**(PII非取得原則)。写り込んでしまったら読み取り後すぐ写真を削除する。**返ってきたJSONは必ず原本と突き合わせる**(特に金額の桁・保険期間)。家族の証券もこれで揃える。呼び名置き換え+非取得ルールにより、以降の成果物に個人情報が残らない。

## 4. プロンプトB: 保障マップ(個人複数枚・夫婦・世帯)

```
あなたは保険の保障設計の整理担当です。
下に貼った契約JSON(プロンプトAの出力・複数件)を束ねて、「保障マップ」を作ってください。

対象範囲: 【個人 / 夫婦 / 世帯(夫・妻・長男・長女…)のいずれかを記入】
世帯の状況: 【年齢・職業・子の人数と年齢・住宅ローンの有無など、わかる範囲で記入】

ルール:
- 貼ったJSONに書いてあることだけで作る。保障内容を推測で補わない
- JSONに「要確認」が残っている項目は、マップにも「要確認」と表示する
- 保障分野は次の8分類で整理する:
  ①死亡(遺族の生活費) ②医療(入院・手術) ③がん ④三大疾病・八大疾病
  ⑤就業不能・収入保障 ⑥介護 ⑦老後資金・貯蓄性 ⑧その他(傷害・引受緩和など)

出力(3点セット):
1. 保障マップ表: 行=家族(呼び名)、列=8分野。セルには「保障額・期間(何歳まで)」を記入。無保障のセルは「─」
2. 重複の指摘: 同じ人に同じ分野の保障が重なっている箇所と、その保険料合計
3. 穴の指摘: 世帯の状況から見て保障が無い・薄い・期間が切れそうな箇所を、理由付きで列挙
   (例: 「妻: 就業不能が無保障。パート収入があるため収入減リスクあり」)
   ※穴の指摘は「検討候補」であり、必要性の断定はしない
```

使い方: 家族全員分のJSONをまとめて貼る。❶複数枚なら対象範囲=個人、❷なら夫婦、❸なら世帯。**この保障マップ自体が面談で使える成果物**(穴が見えた時点でお客様の納得感が生まれる)。

## 5. プロンプトC: 穴分析+3社マッチング

```
あなたは保険プランの候補整理担当です。
下の「保障マップ」の穴・重複に対して、下に貼った当社取扱3社
(なないろ生命・FWD生命・チューリッヒ生命)の商品資料の範囲で、
埋められる候補を整理してください。

ルール:
- 候補は、ここに貼った資料に載っている商品だけから選ぶ。あなたの記憶で商品を足さない
- 資料に保険料表があれば概算保険料も書く。無ければ「保険料は設計書で確認」と書く
- 3社で埋められない穴は、正直に「当社取扱では対応商品なし」と書く
- 健康状態の情報が下にある場合、引受目安データと照合し「引受に注意が必要な可能性」を付記する
  (最終的な引受可否は保険会社の審査によるため、断定しない)
- 乗換(既契約の解約を伴う提案)になる候補には【乗換】と印を付ける

出力形式: 穴・重複ごとに次の表
| 穴/重複の内容 | 対象者 | 候補商品(会社名+商品名) | 埋まる保障 | 概算保険料 | 引受の注意 | 乗換か上乗せか |

【保障マップ】
(プロンプトBの出力を貼る)

【3社の商品資料】
(パンフレット・商品一覧のテキストを貼る ← 空のまま実行しない)

【健康状態の情報(任意)】
(告知に関わる既往歴など。あれば呼び名ごとに)

【引受目安データ(任意)】
(docs/insurance/underwriting_full.json の該当疾病部分を貼る ※現在なないろ・FWDのみ)
```

使い方: 3社の商品資料(パンフ・商品一覧をテキスト化したもの)を貼るのが必須。「乗換」と「上乗せ(既契約はそのまま追加)」を分けるのが重要 — **上乗せ提案は乗換規制の論点が軽く、穴埋め型の営業と相性が良い**。

## 6. プロンプトD: 提案下書き(勝ち筋4分類)

```
あなたは保険提案書の下書き担当です。
下の候補整理表をもとに、提案ごとに「勝ち筋」を次の4つから1つ選び、提案の下書きを作ってください。

勝ち筋の分類:
- A: 保険料も保障も有利(両方で勝てる)
- B: 保険料は上がるが、その分保障がよくなる(補償で勝てる)
- C: 保障はほぼ同等のまま、保険料が下がる(料金で勝てる)
- D: 勝ち筋なし(現在の契約のほうが有利、または乗り換える意味のある差がない)

ルール:
- Dの場合は正直に「現在のご契約の継続がおすすめ」と書く。無理に乗換の文章を作らない
- 【乗換】の提案には「ご注意いただきたい点」を必ず入れる:
  ・解約すると解約返戻金や配当の扱いが変わること
  ・新契約では免責期間・待ち期間が最初からになること
  ・健康状態の告知をやり直すため、加入できない場合があること
  ・古い契約は予定利率が高く、数字の比較以上に有利な場合があること
- 上乗せ(追加加入)の提案は、世帯の保険料負担の合計がいくら増えるかを明示する
- 「絶対」「必ず得」「損はない」などの断定表現は使わない
- 夫婦・世帯の場合は、個々の商品説明の前に「世帯全体で何が変わるか」を3行で要約する
- 文章はお客様向けのやさしい言葉で(専門用語には一言の説明を添える)
- これは下書きであり、募集人の確認・修正を経てから使う前提で書く

【候補整理表】
(プロンプトCの出力を貼る)
```

出荷ゲート: お客様に渡す文面は `humanizer` を通す(AIっぽさ除去)+募集人の最終確認。正確性の考え方は hojo-accuracy-check に準拠(原本=証券・設計書と照合、断定しない)。

## 7. 操作フロー例(❷夫婦の場合)

1. 夫の証券2枚・妻の証券1枚を撮影 → **プロンプトA を3回**(呼び名: 夫/夫/妻)
2. JSON3件を原本と突き合わせ、「要確認」を埋める
3. **プロンプトB** に3件+「対象範囲: 夫婦」「世帯の状況: 夫42歳会社員・妻39歳パート・子2人(10歳/7歳)・住宅ローンあり」→ 保障マップ+穴
4. **プロンプトC** にマップ+3社資料(+あれば健康情報と引受目安)→ 候補整理表
5. **プロンプトD** → 提案下書き → 募集人が確認・修正 → 面談へ

## 9. 三名体制議事

### 議事1(v1・2026-08-12): 構想の導入可否 → 採用(段階導入)

- スイシン: 証券写真の構造化はClaudeの得意領域。既存資産 underwriting_full.json と連結可能。3ステップ分割で精度と法令対応を両立
- ウタガイ: ①乗換ありきの比較は比較表示規制・不利益事実説明義務に抵触のおそれ(条文は要確認)②誤読1つで誤提案・実測なしの実戦投入に反対 ③証券写真は濃い個人情報・保存ルールなき運用に反対 ④旧契約の高予定利率など単純比較は顧客不利益を生み得る ⑤名称「勝てるくん」の対外使用は比較優良誤認の印象
- ベッカイ: 「勝ち負け」でなく「保障の見える化」フレーム/最小構成(読み取りのみ)先行/世帯全体の保障マップの方が価値大
- 裁定: 採用(段階導入)。Phase 1=読み取りのみ社内テスト、比較・提案は守り部審査通過が解禁条件。見直し期限 2026-11-12
- **決裁反映(2026-08-12 小柳さん)**: 名称は社内限定で確定(⑤は解消)。3類型+世帯マップ(ベッカイ案)を正式採用

### 議事2(v2追記): 3類型+3社マッチング設計

#### スイシン(推進)
- 類型別に別システムを作らず、プロンプトBの「対象範囲」宣言だけで❶❷❸に対応する設計は、保守が軽く精度改善が全類型に効く
- 「穴埋め・上乗せ型」を比較・乗換型と分けたことで、規制の重い乗換を避けた提案ルートができる(営業上も自然)
- 保障マップ自体が面談成果物になる。提案前に「見える化」で納得感を作れる

#### ウタガイ(懐疑) ← 空欄不可
- **「3社の保障が良い案内」を目的に置くと、比較が結論ありきに傾く構造リスク**がある。プロンプトCの「3社で埋められない穴は正直に書く」・プロンプトDの「D分類(勝ち筋なし)」を外したら、このシステムは公正な比較ではなくなる。**将来の改修でもこの2つは削除禁止**とすべき
- 夫婦・世帯版は家族の健康情報まで扱い、個人情報の濃度がさらに上がる。呼び名置き換えだけでは不十分な場面(設計書作成時)が残る。保存/破棄ルールの守り部審査前に、実顧客データでの運用を開始してはならない
- 3社資料の整備(§8)が終わる前にプロンプトCを使うと、「資料が薄い会社の商品が候補に出ない」偏りが起きる。3社を公平に載せた資料が揃うまでCは社内テスト限定とすべき
- 保険料の「概算」表示は誤解のもと。設計書(正式見積)前の数字が独り歩きしないよう、下書きに「概算・設計書で確定」の明記を徹底する必要がある

#### ベッカイ(別解)
- 穴の「必要保障額」を厳密計算(遺族年金・生活費シミュレーション)まで踏み込む案もあるが、計算根拠の検証負担が大きい。v2では「穴の指摘+候補提示」までに留め、必要保障額の算出は募集人の面談に残すのが役割分担として健全
- 3社資料の整備を待たずに始めるなら、**まず「なないろ+FWDの2社版」で運用開始**し、チューリッヒは資料が揃い次第追加する段階案もある(引受目安DBも2社分は既にある)
- 保障マップだけを切り出して「保険の健康診断」として単体サービス化する道もある(提案なし=規制リスク最小)。ただしCV設計に関わるため、やるなら別途上申

#### 結論(部門長の裁定)
- 採否: **採用**。ウタガイの4点はすべて運用ルールに反映(§5・§6の正直条項は削除禁止/実顧客データは守り部審査後/3社資料が揃うまでCは社内テスト/概算明記)。ベッカイの2社先行案を実務ルートとして採用(チューリッヒは資料整備後に追加)
- 見直し期限: 2026-11-12(議事1と同時)

## 10. 運用上の禁止事項(v2で強化)

- **PII非取得原則(2026-08-12 小柳さん決裁・絶対前提)**: 個人に紐づく情報(氏名・住所・証券番号・電話番号・受取人名など)は**データとして一切取得しない**。撮影時は該当欄を付箋や指で隠す。一部写り込んでしまった写真は、読み取り後**即削除**する。保存してよいのは匿名化された設計データ(呼び名+年齢+契約内容)のみ
- 証券写真・読み取りJSON・保障マップ・提案下書きを **hojo-hq(公開リポジトリ)にコミットしない**(家族の健康情報を含み得るため特に厳格に)
- AIの出力をそのままお客様に渡さない(募集人確認なしの配布は禁止)
- AIに3社の商品情報を記憶から出させない(資料を渡していない商品を候補に挙げさせない)
