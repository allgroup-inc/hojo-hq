# 勝てるくん プロンプト設計ガイド v1(2026-08-12)

構想: 保険証券を写真に撮る → AIが内容を読み取る → 「勝てるプラン」の提案を見出すシステム。
担当チャット: kateterukun-prompt-design / 位置づけ: 出口3(法人保険・家計の見直しやさん)側の営業支援ツール。
※「沖縄企業のミカタ」本体のCV導線(LINE単一)とは別系統。ミカタのサイト・LINEには載せない。

---

## 0. 結論: 出来るか? → **出来る(条件付き)**

- 証券の写真から契約内容を読み取って構造化するのは、Claudeの画像読み取りで**技術的に可能**。今日から試せる
- ただし「比較して乗換を提案する」部分は**保険募集の規制領域**(比較表示・乗換時の不利益事実の説明義務。適用条文は守り部→弁護士確認前のため要確認)。AIの出力は**下書きまで**とし、必ず募集人(人間)が確認してからお客様に出す
- AIに「他社商品の保障内容や保険料」を記憶から答えさせるのは**禁止**(もっともらしい誤りが混ざる)。比較相手のプランデータは**必ずこちらから渡す**(絶対ルール1「正確性最優先」と同じ考え方)

---

## 1. 全体像 — 1つの巨大プロンプトにしない(3ステップ分割)

```
証券の写真
  ↓ ステップ1: 読み取り(写真 → 契約内容のJSON)
  ↓ (人間が「要確認」項目を埋める・誤読チェック)
  ↓ ステップ2: 比較(現在の契約 vs こちらが渡した候補プラン)
  ↓ ステップ3: 提案下書き(勝ち筋を4分類して文章化)
  ↓ 募集人が確認・修正 → お客様へ
```

分割する理由: ①誤読と誤提案を別々に検査できる ②途中で人間が確認を挟める ③1ステップずつ精度を上げられる。

---

## 2. 指示の出し方 7原則(勝てるくんに限らず使える型)

1. **役割を1行で決める** — 「あなたは保険証券の読み取り担当です」。役割が曖昧だと出力も曖昧になる
2. **出力の形を先に決める** — 欲しい項目をJSONの雛形で見せる。「いい感じにまとめて」は事故のもと
3. **手順は番号で書く** — 読み取る→照合する→分類する、と順番を固定する
4. **読めないものは「要確認」と言わせる** — 推測で埋めさせない。断定禁止(憲法・絶対ルール1と同じ)
5. **比較データはこちらから渡す** — AIの記憶にある商品知識を使わせない。「渡した資料の範囲だけで比較して」と明記
6. **「勝てない」も言わせる** — 勝ち筋がない時に無理に提案を作らせない。「現状維持がおすすめ」を正解の一つにする
7. **不利益もセットで出させる** — 乗換提案には解約返戻金・免責期間のリセット・再告知などの注意点を必ず入れさせる

## 3. マスタープロンプト(コピペ用)

### ステップ1: 証券読み取り

```
あなたは保険証券の読み取り担当です。
添付した保険証券の写真から、契約内容を下のJSON形式で抜き出してください。

ルール:
- 写真に書いてあることだけを抜き出す。推測で埋めない
- 文字が読めない・写真に写っていない項目は "要確認" と入れる
- 金額・日付は原文の表記のまま書き写す(単位や和暦・西暦を勝手に変換しない)
- 最後に「読み取りに自信がない項目」を必ず列挙する

出力形式:
{
  "保険会社名": "",
  "商品名": "",
  "契約日": "",
  "被保険者の契約時年齢": "",
  "保険期間": "",
  "払込期間": "",
  "保険料": { "金額": "", "払込方法(月払/年払など)": "" },
  "主契約": { "種類": "", "保険金額": "" },
  "特約": [ { "名称": "", "保障内容": "", "金額": "" } ],
  "解約返戻金の記載": "",
  "読み取りに自信がない項目": []
}
```

使い方: このプロンプト+証券の写真を送る。**返ってきたJSONは必ず原本と突き合わせる**(特に金額の桁・保険期間)。「要確認」「自信がない項目」は人間が埋めてからステップ2へ。

### ステップ2: 比較

```
あなたは保険プランの比較担当です。
「現在の契約」(下のJSON)と「候補プラン」(下に貼った当社取扱商品の資料)を比較してください。

ルール:
- 比較は、ここに貼った資料の範囲だけで行う。あなたの知識で商品情報を補わない
- 現在の契約に「要確認」の項目が残っている場合、その項目は「比較不能」と書く
- 有利・不利は項目ごとに判定する(全体の印象で決めない)
- 判定できない項目を無理に判定しない

出力形式: 次の5列の表
| 比較項目 | 現在の契約 | 候補プラン | どちらが有利か | 差の内容 |

最後に「保険料の差(月額)」と「保障の差の要約」を3行以内でまとめる。

【現在の契約】
(ステップ1のJSONを貼る)

【候補プラン】
(パンフレット・設計書の内容を貼る ← ここを空にしたまま実行しない)
```

### ステップ3: 提案下書き(勝ち筋の4分類)

```
あなたは保険提案書の下書き担当です。
下の比較表をもとに、まず「勝ち筋」を次の4つから1つ選び、その上で提案の下書きを作ってください。

勝ち筋の分類:
- A: 保険料も保障も有利(両方で勝てる)
- B: 保険料は上がるが、その分保障がよくなる(補償で勝てる)
- C: 保障はほぼ同等のまま、保険料が下がる(料金で勝てる)
- D: 勝ち筋なし(現在の契約のほうが有利、または乗り換える意味のある差がない)

ルール:
- Dの場合は正直に「現在のご契約の継続がおすすめ」と書く。無理に乗換の文章を作らない
- A〜Cの下書きには「ご注意いただきたい点」を必ず入れる:
  ・解約すると解約返戻金や配当の扱いが変わること
  ・新契約では免責期間・待ち期間が最初からになること
  ・健康状態の告知をやり直すため、加入できない場合があること
  ・古い契約は予定利率が高く、数字の比較以上に有利な場合があること
- 「絶対」「必ず得」「損はない」などの断定表現は使わない
- 文章はお客様向けのやさしい言葉で(専門用語には一言の説明を添える)
- これは下書きであり、募集人の確認・修正を経てから使う前提で書く

【比較表】
(ステップ2の出力を貼る)
```

## 4. 実際の指示の出し方(小柳さんの操作例)

1. Claudeに **ステップ1のプロンプト+証券写真** を送る
2. 返ってきたJSONを証券と見比べ、誤読・「要確認」を直す(ここが品質の生命線)
3. **ステップ2のプロンプト+直したJSON+候補プランの設計書/パンフ内容** を送る
4. 比較表を確認(「比較不能」が多ければ資料を足してやり直し)
5. **ステップ3のプロンプト+比較表** を送る → 下書きを募集人が確認・修正して使う

出荷ゲート: お客様に渡す文面は `humanizer` を通す(AIっぽさ除去)+募集人の最終確認。制度の締切系ではないので hojo-deadline-alert は対象外、正確性の考え方は hojo-accuracy-check に準拠(原本=証券・設計書と照合、断定しない)。

## 5. 三名体制議事(hojo-triangle-review)

## 論点: 勝てるくん(証券写真→勝てるプラン提案)のプロンプト設計と導入可否

### スイシン(推進)
- 証券写真の構造化はClaudeの画像読み取りの得意領域。商談の場で「比較の土台」が数分で出るのは営業速度に直結する
- リポジトリには既に docs/insurance/underwriting_full.json(なないろ生命・FWD生命の引受目安)があり、将来は「体況的に乗換できるか」の引受チェックまで連結できる
- 3ステップ分割+人間確認の設計なら、精度検証と法令対応を両立できる

### ウタガイ(懐疑) ← 空欄不可
- **「勝てる」前提の設計そのものが危険**。乗換ありきの比較は、保険募集の比較表示規制・乗換時の不利益事実の説明義務に抵触するおそれがある(適用条文の特定は要確認・守り部→弁護士確認前に対外運用しない)
- **誤読1つで誤提案になる**。保険金額の桁や特約の見落としは信頼失墜に直結。自社・自分の証券でのテスト(読み取り精度の実測)なしの実戦投入に反対
- **証券写真は極めて濃い個人情報**(氏名・生年月日・証券番号・健康関連)。写真と読み取り結果の保存場所・破棄ルールが決まる前の運用開始に反対。公開リポジトリ(hojo-hq)には写真もJSONも絶対に入れない(churn-pii-guardと同じ原則)
- 古い契約は予定利率が高く「数字では負けて見えるが顧客には有利」なケースがある。単純比較の自動化は顧客の不利益を生み得る
- 名称「勝てるくん」を対外(お客様向け)に出すと「他社に勝つための道具」という印象を与え、比較優良誤認の疑いを招く。対外名称としては不採用とすべき

### ベッカイ(別解)
- 「勝ち負け」フレームをやめ、**「保障の見える化ツール」**として設計する案。AIは読み取り+現在の保障の一覧化・穴の指摘までに徹し、比較・提案は人間の募集人が行う。法的リスクが大きく下がり、顧客の納得感はむしろ上がる
- 最小構成から始める案: **Phase 1=ステップ1(読み取り)だけ**を社内で使い始め、比較は当面人間がやる。読み取り精度の実測が貯まってからステップ2・3を解禁
- 世帯全体案: 証券1枚の勝ち負けより、顧客の**全証券を読み取って「世帯の保障マップ」**を作る方が、家計の見直しやさんの面談ツールとしての価値が大きい

### 結論(部門長の裁定)
- 採否: **採用(段階導入)+ 小柳さんへ上申2点**
- 理由: スイシンの通り技術的には即日試せるが、ウタガイの法令・PII・誤読リスクはどれも実害級。よって Phase 1(読み取りのみ・社内テスト・実測記録)を先行し、ステップ2〜3(比較・提案)は守り部審査の通過を解禁条件とする。ベッカイの「見える化」フレームは対外的な見せ方として採用候補(名称・訴求の決裁と併せて上申)
- 上申: ①構想の採否と位置づけ(社内ツール名か対外名か) ②守り部審査(比較規制・乗換規制・証券写真のPII管理ルール)
- 見直し期限: 2026-11-12(3ヶ月)

## 6. 運用上の禁止事項(Phase 1から適用)

- 証券写真・読み取り結果JSON・お客様の氏名入り比較表を **hojo-hq(公開リポジトリ)にコミットしない**
- AIの出力をそのままお客様に渡さない(募集人確認なしの提案書配布は禁止)
- AIに他社商品の情報を記憶から出させない(資料を渡していない商品の比較をさせない)
- 「勝てるくん」名を対外文面に使わない(小柳さん決裁まで)
