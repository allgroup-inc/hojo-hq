# 議事: glow-ma 企業マスタの書き込みを安全化する(2026-11-15)

CLAUDE.md 三名体制ルール8② の「技術的でも不可逆な変更(本番のデータを書き直す処理の変更)」に当たるため、議事を残す。
コードの修正・合成データのテスト・Draft PR の更新までは小柳さん承認済み(2026-11-15)。**マージ・本番反映は別の承認を待つ**ため status は `deferred`(決裁待ち)とする。

## なぜ(背景)

- 2026-11-11 の日次メンテナンスで、企業マスタを書き直す共通の関数 `writeCompanyRecords_`(`glow-ma/src/ImportRunner.gs`)が、2行目以降をすべて消してから全社分を一度に書き戻す途中に Google 側のエラーで止まり、約6割の会社の行が消えた(失敗台帳 FK-010)。小柳さんがバックアップから手で戻した。
- 同じ関数はスコア再計算・お断りの反映・取り込み・事前選定・過去記録の取り込み・試験用の計6か所から呼ばれており、どこからでも同じ事故が起きうる。
- Draft PR #612 で「先に消さずに上から500行ずつ上書きする」形に変えたあと、独立レビューで次の7点の指摘を受けた。
  1. 書いた後の照合そのものが失敗したとき、記録・通知・後続の停止が抜ける
  2. 後続の処理を止めるかどうかを、エラーの文言で判断している
  3. 企業IDが空の手入力の行を、余った行として消してしまう
  4. 書く前の確認で止めた場合と、書いている途中で止まった場合を区別せず、安全な処理まで止める
  5. 全33列の照合で、数値・文字・%・数式・先頭の0の扱いが粗い
  6. どんなエラーでもやり直しており、回数・時間の上限が弱い
  7. 議事が無い

## 前提

- 企業マスタは本番のデータであり、今回の作業では1セルも変更しない。テストはすべて架空の企業IDと合成データで行う。
- Apps Script の書き込みは、途中で失敗すると一部だけ(1行の途中まで)反映されることがある。
- 日次メンテナンスは、バックアップ → お断りの反映 → スコア再計算 → ダッシュボード → 今日の連絡先 → 世界の架け橋の週次KPI → 掘り起こしアラートの順に動く。
- 本リポジトリは公開のため、議事・失敗台帳に会社名・電話番号・正確な社数を書かない。

## 代替案

- A(採用): 書き込みの各段階に「どこで止まったか(書く前の確認/書き込み/書いた後の照合)」と「企業マスタが変わったか」を付けた構造化エラーを持たせ、日次メンテナンスはその2つで止める範囲を決める。照合中の失敗も必ず同じ経路で記録・通知する。
- B: 書き込みを別のタブに全部書いてから、タブを差し替える。途中で止まっても本体は無傷になるが、他のタブからの参照式・保護範囲・フィルタが切れるおそれがあり、影響を見切れないため今回は採らない。
- C: 企業マスタを書き直す処理を日次メンテナンスから外し、人が手で実行する。事故は減るが、お断りの反映が止まり、断った会社への再架電という一番避けたい事故が起きるため採らない。

## 三名体制の議論

- **スイシン(推進)**: 7点はどれも「止まったときに、誰も気づかない・安全な処理まで止まる・人の手入力を消す」のどれかで、FK-010 と同じ種類の事故につながる。構造化エラーにすれば、文言を直しても止める判断が変わらず、テストで機械的に確かめられる。照合中の失敗も記録・通知されるので、黙って壊れた企業マスタのまま後続が走ることがなくなる。
- **ウタガイ(懐疑・反対理由。必須)**:
  - 止める条件を増やすほど、正常な日でも止まる「止まりすぎ」が起きる。たとえば企業IDの空欄の行が1行でもあると、スコア再計算が毎日止まり、ランクが古いまま営業が動く。止まったことに気づいても、直す人がいなければ同じ。
  - 一時的なエラーかどうかを文言の正規表現で見分けている。Google がエラーの文言を変えると、本来やり直せるエラーで止まる(安全側ではあるが、止まりすぎにつながる)。
  - 数式のセルは照合しない(書いた式と読んだ値を比べられないため)。数式の列に別の会社の値が混ざっても見つけられない。
  - 書いている途中で止まった場合は、企業マスタは途中まで書き換わったまま残る。自動では元に戻さず、人がバックアップのタブから戻す必要がある。
  - 合成データのテストだけで、本番の3千社規模の台帳では試していない。本番反映の前に、本番と同じ規模でのドライランが要る。
- **ベッカイ(別解・前提を疑う)**: そもそも毎日全社を書き直す必要があるのか。スコア再計算は変わった行だけを書けば、書き込みの量も失敗の確率も大きく下がる。今回は書き方を変えずに安全化を優先し、差分書き込みは次の改善候補として残す。また、止まったときの復旧手順(どのバックアップのタブから、どの範囲を戻すか)を通知の文面に必ず載せ、「止まったが直し方が分からない」を無くす。

## 裁定

- 採否: 案Aを採用(コードと合成テストまで)。本番反映は小柳さんの別の承認を待つ。
- 7点の対応:
  1. 書いた後の照合の途中で読み書きが失敗しても、必ず「書いた後の照合」で止めたとして記録・通知し、例外を投げる。余った行は消さない。
  2. 例外に `companyWrite = { phase, dataChanged }` を付け、日次メンテナンスはこれだけで判断する(文言は見ない)。
  3. 企業IDが空なのに値が入っている行があれば、書く前に止める(1セルも変えない)。書いた範囲より下に、書いていない会社や手入力の行が残っていれば、消さずに止める。未チェックのチェックボックス(false)だけの行は空とみなす。
  4. 各手順に企業マスタを「書く/読むだけ/使わない」を付けた。書く前の確認で止めた場合は書く手順だけを止め、読むだけの手順(ダッシュボード・今日の連絡先・アラート等)は続ける。書いている途中・書いた後の照合で止めた場合は、企業マスタを使う手順をすべて止め、使わない手順だけ続ける。
  5. 照合では、日付(書き方の違い)・桁区切り・%・真偽値をそろえて比べる。先頭が0の番号は文字として扱い、0が消えたら止める。数式は照合しない(ウタガイの指摘どおり、これは残る弱点として明記する)。
  6. やり直すのは Google 側の混雑・タイムアウト等の一時的なエラーだけ。1かたまり3回まで、待ち時間は合計20秒まで。権限・保護範囲・範囲外などは、すぐに止める。
  7. 本議事。
- ウタガイの反映: 止まりすぎへの対策として、止めた理由と復旧の手がかり(バックアップのタブ名)を通知に必ず載せる。本番反映の前に、本番と同じ規模の合成データでのドライランと、止まったときの連絡先・復旧担当を決めることを、反映の承認の条件にする。数式の列の混入は検知できないことを残存リスクとして PR に明記する。
- ベッカイの反映: 差分書き込み(変わった行だけを書く)は次の改善候補として残す(今回の範囲外)。

## 追記: 本番反映前の最終安全審査(2026-11-15・小柳さん承認の範囲: 読み取り・コード改善・合成データ検証・Draft PR更新)

### 本番の企業マスタの読み取り点検(書き込みなし)
- 会社の行数は本番と同じ規模。数式のセルは0か所、企業IDが空なのに値が入っている行は0行、「=」で始まる文字は0か所。
- 電話番号はすべて先頭が0の文字で入っており、列の書式が文字(@)のため、書き直しても0は消えない。携帯番号・法人番号の列は空。
- 31〜33列目(LINE User ID・Instagramアカウント・QRコード URL)は見出しが空で、値も入っていない。書き直しても空を書くだけで、失う値はない(見出しの付け直しは今回の範囲外)。
- 実行記録: 11/15 の日次メンテナンスは、7つの手順がすべて同じ1分の中で完了した(今の書き方で1分未満。Apps Script の上限6分に対して余裕がある)。同じ日、音声ログの処理で Google 側の「サーバー エラー」が4回出ており、一時的なエラーは実際に起きている。

### 審査で足した安全策
- 数式のセルが企業マスタにあれば、書く前に止める(値で読んで値で書き戻すため、書き直すと数式が消える)。数式の有無を読めなかったときも、書かずに止める。
- 書き込む値に「=」で始まる文字があれば、書く前に止める(そのまま書くと数式として入り、元の文字が失われる)。
- どちらも「書く前の確認」での停止なので、企業マスタは1セルも変わらず、日次メンテナンスの読むだけの手順は続く。本番は今どちらも0か所のため、反映した日から止まることはない。

### 本番と同じ規模の合成データでの検証(架空の会社・33列すべてに本番と同じ型の値)
- 通常の再計算: 全社が残り、スコア以外の列は1セルも変わらない。書き込み7回・読み取り5回・待ち0秒。
- 書き込みの途中で失敗し続ける・1回の書き込みが前半だけ反映される: 会社は1社も消えず、まだ書いていない行は元のまま。
- 一時的な失敗が各かたまりで1回ずつ: やり直して最後まで書く(待ち合計14秒)。失敗が続くときは待ち合計20秒で止める。
- 名寄せの統合(行がずれる)が1行の途中で止まる: 統合した会社のほかは、どの会社の行も台帳のどこかに残る。混ざった行の数とバックアップのタブを知らせて止める。最後まで書けたときは全33列を照合して通る。

### ロックの時間(推定)
- 今の書き方は「読み取り1回・消去1回・書き込み1回」。新しい書き方は「読み取り5回(数式の確認を含む)・書き込み7回」で、Google への呼び出しが約10回増える。1回あたり1〜2秒とすると、ロックを持つ時間は10〜20秒ほど延びる。一時的なエラーが続いた日は、さらに最大20秒待つ。
- ロックを待つほかの処理は、音声ログ(2秒待って、だめなら次の回に回す)・管理画面の記録(10秒待って「混んでいます」を返す)・生存信号(次の回に回す)。日次メンテナンスは営業開始前の7時台に動くため、影響は小さいと判断する。本番の実測は反映の翌朝の実行記録で確かめる。

### 自動反映・停止・ロールバック
- 自動反映: `glow-ma/src/` を変えるコミットが main に入ると、glow-ma-deploy が `clasp push --force` で Apps Script の最新コードを置き換える(テストは反映の処理の中では走らない。PR の CI が通っていることがマージの前提)。時間で動く処理(日次メンテナンス・毎分の音声ログ処理から呼ばれる過去記録の取り込みなど)は、反映した直後から新しいコードで動く。
- 異常時の停止: 書き込みを止めたときは、稼働状況タブの「企業マスタの書き込み」に失敗として残し、Slack(未設定ならメール)で知らせる。通知は同じ処理につき1日1回。日次メンテナンスは、止めた段階に応じて後の手順を止める。過去記録の取り込みは取り込み表を残したまま、次の取り込みの時刻にもう一度試す(行がずれない書き込みのため、やり直すと同じ内容を書き直して終わる)。
- コードのロールバック: マージのコミットを main で取り消す(revert)と、glow-ma-deploy が前のコードを自動で反映する(数分)。取り消しも main への変更なので、小柳さんの承認を得てから行う。
- データのロールバック: 毎朝のバックアップ(14世代)と、インポート・事前選定が書く前に作るバックアップのタブから戻す。戻すのは人の操作。

### 本番反映を許可できる条件(案。決裁は小柳さん)
1. PR #612 の CI(glow-ma-ci・repo-scope・wikiskill-tests・fukugiiro-ci)がすべて成功していること。
2. 反映の直前に、企業マスタの社数が今朝のバックアップと一致し、数式のセル・企業IDが空の手入力の行が0であること(反映した日から止まらないことの確認)。
3. 反映は日次メンテナンス(7時台)と重ならない時間に行い、反映後に LINE の「反映完了」を確かめる。
4. 反映の翌朝、稼働状況に「企業マスタの書き込み: 成功」と日次メンテナンス「7件すべて完了」が出ることを確かめる。失敗が出たら、通知の文面に従って止めた段階を確かめ、必要なら取り消し(revert)を上申する。
5. 止まったときの一次対応者(稼働状況と通知を見る人)を決めておく。
6. 11/11 の復元で一部の列が戻っていない1社は、今回の反映と切り離して扱う(会社は非公開側の記録で特定する)。電話番号が空のため架電の対象外のままで、今回のコードはその行の空の列を空のまま書き直す(スコアの列だけ再計算される)。
7. その1社を人が貼り直す作業は、日次メンテナンス(7時台)・過去記録の取り込みの時刻と重ねない。書き込みはロックで他の処理とは重ならないが、人の手での編集はロックの外にあり、書き込みの最中に直した行は、書き込みが読んだ時点の値で上書きされうる(今の書き方でも同じ。新しい書き方ではロックを持つ時間が10〜20秒ほど延びる)。

## 見直し条件

- 見直し期限: 2027-05-11(失敗台帳 FK-010 の見直し期限に合わせる)。
- 本番反映後、「止めた」通知が月に2回以上出たら、止める条件が厳しすぎないかを再議論する。
- Google のエラー文言の変化で、一時的なエラーをやり直せずに止まった例が出たら、見分け方を見直す。
