# 体制総点検とやり切り計画(2026-08-01・小柳さん指示による全面見直し)

適用スキル: hojo-triangle-review / hojo-accuracy-check / hojo-deadline-alert

---

## 1. 体制の見直し(三名体制議事)

### 論点: KGI「12ヶ月でLINE登録1,000社」に対し、現行体制(6部門+統括+監査のエージェント組織)は十分か

### スイシン(推進)
- 自動運転は完成域: CI7系統(収集・照合・点検・E2E・Lighthouse・SNS投稿・週次レポ)+企業台帳+会話ボットが無人稼働。コンテンツ生産と品質管理は現体制で100点が出せる。
- 各部門エージェント(.claude/agents/ 17名)は役割定義済みで、議事・レビュー・生成の分業が機能している。

### ウタガイ(懐疑) ※反対理由の記録
- **反対①: 組織図は立派だが、KGIの実行主体が空白。** 1,000社の内訳は既存顧客基盤300+紹介200=**500社(半分)がオフライン・対人チャネル**なのに、実在の稼働人員は実質小柳さん1人。「提携部ムスブさん」はエージェント=電話も訪問もできない。たかしくんはFB管理者見送りで稼働範囲が不明確、嶺井さんの人脈稼働は8/5商談から。**バーチャル組織が人手不足を見えなくしている。**
- **反対②: ペースが既に危険水域。** 週20社目標に対し現状2社(公開10日)。3ヶ月マイルストーン100社(9月末)は、配布・紹介活動が今週始まらなければ未達がほぼ確定する。
- **反対③: 小柳さん一極集中。** 承認・配布・商談・テスター送付・決裁のすべてが1人に集まり、本人の可処分時間がKGIの上限になっている。テスター4通の送付すら数日滞留しているのが実証。
- **反対④: 「配る道具」が無い。** 催事・商談・既存顧客と毎日会っているのに、渡せるQRカード・紹介ワンシートが存在しない=接点がチャネル化されていない。

### ベッカイ(別解)
- 前提を疑う: 「デジタルで新規を集める」設計だが、GLOWグループの強みは**既に毎日経営者・世帯と会っていること**(保険・催事・回線・既存顧客)。主戦場は「集める」でなく**「会った人に配る」**。
- 組織は「部門」を増やすのでなく、**道具(配布キット)+週次アクション表(誰が・どこで・何件)**に落とす方が確実。エージェント組織は生産装置として維持し、人間は「配る・会う・決める」に限定する。

### 結論(裁定)
- 採否: **体制を2層に再定義して採用**
  - **L1 自動運転層**(維持): CI7系統+エージェント17名=生産・品質・監視。人手ゼロで回る。
  - **L2 人間実行層**(明確化): 小柳さん(決裁・商談・承認)/たかしくん(配布・SNSコメント対応 ※役割は小柳さんから本人へ依頼要)/嶺井さん(士業・金融機関・商工会リレー)。**新機能「くばる(配布)」は部門新設でなく配布キット+週次ルールで実装。**
- 理由: ウタガイの指摘通りボトルネックは技術でなく対人実行。道具と週次ルールで人間の1時間あたり配布効率を最大化するのが最短。
- 見直し期限: 2026-10-31(3ヶ月マイルストーン結果で再議論)

## 2. ルールの明文化(運用ルールブック v1)

### 承認フロー(SLA付き)
| 対象 | 承認者 | SLA | 放置時の扱い |
|---|---|---|---|
| SNS投稿(月水金) | 小柳さん | 当日18:00まで | 見送り(=意思決定として有効) |
| サイト文言・UI変更 | 技術部実装→事後報告 | — | CV設計・掲載方針・予算・提携に触れるものだけ事前決裁 |
| 対外送信(メール・LINE一斉配信) | 小柳さん事前承認 | — | 送信しない |
| GAS/ボットのコード変更 | 技術部が用意→小柳さん貼り替え | 1週間以内 | リマインド |

### 品質基準(全対外物の関門)
1. 対外文面 = `humanizer`(トーン) + `hojo-deadline-alert`(約1か月前から) + `hojo-accuracy-check`(断定禁止・原文照合) の3スキル通過必須
2. サイト変更 = 実ブラウザ検証+デプロイ後実測+E2E/healthcheckグリーン確認まで完了と呼ばない
3. 数値の掲載 = 原文URL照合できないものは「要確認」表示(見栄えのための断定化は禁止)

### エスカレーション条件(数値の階段)
| 条件 | アクション |
|---|---|
| LINE登録が2週連続で週目標の50%未満 | 三名レビュー招集→原因究明→チャネル再配分案を小柳さんへ上申 |
| healthcheck/E2EのERROR | 即日対応(LINE即時通知→当日中に原因特定) |
| 台帳への苦情・削除依頼 | 24時間以内にuserId検索→削除→守り部記録 |
| 週次レポートに「取得不可」 | 当週中にトークン等を再設定 |
| マイルストーン(8月末30社/9月末100社)未達 | 前提破壊レビュー(ベッカイ主導)を実施し計画自体を再設計 |

### 安全ルール(憲法の再確認・効率化で崩さない)
- 申請代行はしない(士業取次まで)/台帳は非公開・チャットにトークン非表示/クロールは守り部承認ソースのみ/CV=LINE登録単一

## 4. 実行指示(エージェント別)
- **収集部/検証部**: 現行自動運転を維持(変更なし)。
- **SNS部(ヒロメ)**: 承認ゲート運用継続。8月中にIG投稿の反応データが10件貯まったらテンプレA/B提案を作成。
- **LINE部(ツナグ)**: 月木配信ルール(T8)に従い下書き品質を毎回humanizer基準で。友だち30社到達時にステップ配信設計を提案。
- **提携部(ムスブ)**: T3紹介ワンシートの文面を保持し、嶺井さん経由の配布結果を台帳経路で計測。
- **守り部(マモリ)**: 削除依頼24h対応ルールの窓口をLINE運用設計に追記済み扱いとし、月次で台帳アクセスを点検。
- **統括(アカリ)**: 週次レポート(自動)に加え、数値の階段(8月30社/9月100社)との差分を毎週判定→エスカレ条件該当時に三名レビューを起票。
- **技術部(本チャット)**: T1/T2/T3/T4/T5前半を即日実行(本ドキュメントと同時にコミット)。
