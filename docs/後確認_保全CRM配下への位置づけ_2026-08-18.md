## 1. 共通の約束4つに対する適合状況

| 約束 | 適合 | 状況 |
|---|---|---|
| 【1】顧客データを自分の中に持たない | ✅ 適合 | `atokakunin_rules.py` は氏名・電話番号・住所・生年月日を**一切受け取らない**。同一番号の名寄せは仮名化キー(`tel_key`)のみ |
| 【2】顧客の番号を自分で発番しない | ⚠️ **要修正** | `order_id`(A-10431形式)は申込の識別子で顧客番号ではないが、**KM-への参照を持っていない**。レコードに `km_id` を必須で持たせる |
| 【3】自前のログイン・ユーザー管理を作らない | ⚠️ **要修正** | `atokakunin-console.html` は独自のナビを持つ**独立した画面**として作ってある。❹の中の1画面に畳む |
| 【4】ステータスの言葉を言い換えない | ✅ 適合(要明示) | 本機能の状態(未送信/送信済/承認_SMS/承認_電話/要確認/送信失敗/期限切れ)は**共通語彙の言い換えではなく、「保全中」の内側の作業状態**。リスト上の持ち場は変えない |

## 2. 見つけた欠陥と修正(2026-08-18 実施済み)

### 架電禁止を見ていなかった(重大)

共通仕様「**架電禁止は持ち場と無関係に最優先で効く。どこにいても発信しない**」に対し、
実装した電話リストは**架電禁止の方を平気で載せる状態**だった。

修正:
- `is_do_not_call()` を新設。`do_not_call` フラグと `list_status == "対象外"` の両方を見る
- `needs_call()` の**冒頭**で判定。経過日数・期限・状態を一切見る前に弾く
- `can_send()` でも弾く。**架電禁止の方へ機械が一斉SMSを送るのは、電話より始末が悪い**
- ただし黙って消すと「静かな脱落」になるため、`build_excluded_list()` で
  **「架電禁止だが後確認が未了」の一覧を必ず表に出す**。自動では触らず、保全部が人として判断する

テスト: ゴールデンセット 93件 → **103件**。変異テストで4種すべて検知を確認
(電話リストのガード除去 / 自動送信のガード除去 / list_statusを見ない / 除外一覧を空にする)。

## 3. 未解決の矛盾 — 後確認の起点は「申込」か「成立」か

**ここは決めずに上げる。**

| 出典 | 記述 |
|---|---|
| 最初の依頼(2026-08-14) | 「**申込み完了**したお客様には、後確認をいれて了承が必要になります」 |
| 共通認識・確定版(2026-08-18) | 放置検知の例に「**成立**から後確認が済んでいない契約」 |

共通語彙では **申込 ≠ 成立**(申込=書類提出 / 成立=保険会社の引受完了)と明記されている。
起点が変われば、後確認を始めるタイミングも、期限日数の意味も、
放置検知の対象も変わる。**推測で片方に寄せない**(絶対ルール1)。

→ 軸(総合管理システム)または小柳さんへ確認する。決裁キューに登録。

## 4. 作り直しが必要な箇所(前提6つに照らして)

### 【1】入力は仕事の副産物にする — **違反している**

`atokakunin-console.html` の「記録する」画面は、申込ID・受付日・契約者名・携帯番号・
送信予定・確認方法・返信内容・文面バージョン・備考の**9項目を手入力させる**設計。
共通認識が挙げる**悪い例(訪問後に報告フォームを開いて15項目を手入力)そのもの**。

さらに契約者名・携帯番号は**kakei-crmに既にある情報**で、【3】同じことを2回入力させない
にも抵触する。

**作り直しの方針**(パッチではなく再設計):
- 顧客情報の入力欄を**全廃**。KM-番号で引いて**表示するだけ**にする
- 手で入れるのは「電話の結果」だけ。それも**選択肢を押すだけ**にする
  (了承もらえた / 不在 / かけ直し希望 / 拒否)。自由記述は最後の手段
- 承認の証跡に要る「返信原文」は、SMS返信なら自動で入る。電話の場合のみ
  「了承の一言」を残す欄を1つ置く
- 理想は❺の音声ログと接続し、電話の録音から自動で記録が残る形

### 【2】開いたら「今日やること」が出ている — 部分的に適合

電話リストは「今日かける順」で出るので適合。ただし**❹の入口として**
「今日フォローすべき契約・放置されているもの」の中に、後確認未了が並ぶ形にする。
後確認だけの画面を開かせない。

### 【4】放置が自動で浮上する — 適合

「成立から後確認が済んでいない契約」は、まさに本機能が出す一覧。
`build_call_list()` と `build_excluded_list()` の2本がこれに当たる。

### 【5】スマホ前提 — 対象外

❹保全部は事務所で使う想定のため、❸のようなスマホ最優先の要件は適用しない。
ただし電話リストは片手で見る可能性があるため、行の詰まった一覧は維持する。

### 【6】待たせない — 未検証

判定ロジックは純粋関数のみで高速だが、台帳(kakei-crm)への問い合わせ速度は未測定。
1件3秒を超えないことを、台帳接続時に必ず測る。

## 5. 影響を受けない部分

方式の決定・判定ロジック・電話リストの並び順・self-test/変異テストの仕組みは、
❹配下になっても**そのまま使える**。捨てる必要はない。

作り直すのは**画面(入力のさせ方)**と、**顧客データの持ち方(KM-参照)**の2点。
