# 設計(調査): 診断ページ監視を、GitHub Actions の定時起動の遅れに依存せずに起動する

対象: もらいわすれ堂(株式会社フクギイロ・moradou.jp)の15分監視(`.github/workflows/diagnosis-monitor.yml`)。
状態: **調査・設計のみ**(実装・外部サービスの設定・トークンの発行はしていない)。小柳さんの指示(2026-11-04)で別課題として扱う。
関連: `docs/議事_20261103_診断ページ15分監視.md` / `docs/診断ページの外部監視_設計.md`

## 問題

15分監視は `schedule`(cron `*/15 * * * *`)で起動するが、このリポジトリの定時起動は大きく遅れ、飛ばされる。

- 直近14日の実測(8本・190回): 予定からの遅れ 中央値 約3.7時間・上位10% 約6.2時間・最大10時間。予定の回が丸ごと飛ばされる割合は、多いもので43〜48%(測定方法は `docs/診断ページの外部監視_設計.md` の「測定の方法」)
- 2026-11-04 の統合後、約2時間半たっても15分監視は一度も定時起動していない

`schedule` は GitHub 側の仕組みで遅れるので、間隔の設定(cron)や実行環境(ランナー)を変えても直らない。**起動のきっかけを GitHub の定時起動以外に移す**必要がある。

## 使える仕組み(GitHub の仕様)

- `workflow_dispatch`(手動実行のイベント)は、GitHub API(`POST /repos/{owner}/{repo}/actions/workflows/{file}/dispatches`)から起動できる。定時起動の待ち行列を通らないので、ほぼすぐに始まる
- 15分監視はすでに `workflow_dispatch` で `monitor` ジョブが動く(`if: schedule || workflow_dispatch`)。LINE 送信担当も `workflow_dispatch` 起動の完了を受け付ける
- API で起動するには、起動の権限(Actions: write)を持つトークンが要る。`GITHUB_TOKEN` で起こした `workflow_dispatch` は、例外として次の実行を作れる(GitHub の仕様)

## 案の比較

| 案 | 起動のきっかけ | トークン | 費用 | 良い点 | 懸念 |
|---|---|---|---|---|---|
| **1. Cloudflare Workers の定期実行から起動(推奨)** | Cloudflare の cron(最短1分・無料はアカウント全体で5本まで)が15分ごとに API を呼ぶ | fine-grained PAT(hojo-hq だけ・Actions: write だけ)を Worker の Secret に置く | 無料枠で足りる見込み | 起動の遅れがほぼ無い。トークンは Cloudflare の暗号化された Secret に置ける。C案の自前監視と同じ基盤にできる | トークンを外部に置く(漏れれば、第三者がこのリポジトリのワークフローを起動できる)。PAT は人に紐づき、期限切れで止まる。Cloudflare のアカウント管理が増える |
| 2. cron-job.org などの外部の定期実行サービスから起動 | 外部サービスが15分ごとに API を呼ぶ | 同じ PAT を外部サービスの設定に置く | 無料 | 設定だけで済む(コードが要らない) | トークンを第三者のサービスの設定画面に置く。規約(事業での利用)の確認が要る |
| 3. ワークフローが自分を次々に起動する(自己起動の連鎖) | 監視の最後に、14分ほど待ってから `GITHUB_TOKEN` で自分を `workflow_dispatch` する | 外部に置かない(`GITHUB_TOKEN` に actions: write を足す) | 0円(公開リポジトリ) | 外部サービスもトークンも要らない | ランナーを常に1台使い続ける。連鎖が1回切れると止まる(定時起動が再開の役になるが、それも遅れる)。GitHub Actions の利用規約が、リポジトリの開発と関係の薄い常時稼働を想定していない点の確認が要る |
| 4. GitHub App のトークンで起動 | 外部の定期実行(1 または 2)から | App の秘密鍵からその都度トークンを作る(1時間で切れる) | 無料 | PAT と違い人に紐づかず、権限を細かく絞れる | 秘密鍵を外部に置くことになり、仕組みが一番複雑 |
| 5. 監視そのものを外部で動かす(C案の強化) | 外部の死活監視(UptimeRobot)・Cloudflare Workers | 不要 | 無料 | GitHub に頼らない | 実ブラウザで診断を操作する検査(件数の誤差0件)は外部の死活監視ではできない(Cloudflare のブラウザ実行は別料金・別の確認が要る) |

**推奨: 案1(Cloudflare Workers から `workflow_dispatch`)+ 案5(C案の UptimeRobot)の組み合わせ。**
- UptimeRobot(C案)が、ページ・制度データ・判定ロジックの消失を5分おきに見る(主な監視)
- Cloudflare Workers が15分ごとに15分監視を起動し、実ブラウザでの件数照合を予定どおりに回す
- 定時起動(`schedule`)は消さずに残す(Cloudflare が止まったときの予備)

## 案1を採るときに直すところ

1. **停止検知(`diagnosis-monitor-watchdog.yml` / `scripts/diagnosis_notify.py` の `GitHub.runs`)**: いまは `event=schedule` の実行だけを数えている。`workflow_dispatch` の実行も数えるようにしないと、外部から起動している間も「起動なし」と誤って判定する
2. **重なりの扱い**: 外部からの起動と定時起動が重なっても、`concurrency`(`diagnosis-monitor-live`)で順番に動くので壊れない。ただし同じ時間帯に2回動くことがある(LINE の通数は送信担当の上限で守られる)
3. **起動の記録**: 外部から起動した実行を見分けられるよう、`workflow_dispatch` の入力(例 `source=cloudflare`)を足す
4. **A案(ハートビート)の期限**: 起動が15分ごとに安定すれば、期限と猶予を短くできる(例 期限30分・猶予30分)。実測で決める
5. **トークン**: fine-grained PAT を、対象リポジトリ hojo-hq のみ・権限 Actions: write のみ・有効期限つきで発行する。期限が近づいたら知らせる仕組み(停止検知に「外部起動が途絶えた」を足す)を用意する
