# 勝てるくん 実行キックオフプロンプト集(2026-08-12)

設計ガイド(docs/勝てるくん_プロンプト設計ガイド_2026-08-12.md)の実現に向け、**残タスクをAIに指示するためのコピペ用プロンプト**。
本体のプロンプトA〜D(読み取り/保障マップ/3社マッチング/提案下書き)は設計ガイド側にある。ここにあるのは「仕組みを組み上げるための作業指示」。

## 実行ロードマップ(この順で)

| 順 | タスク | 使うプロンプト | 決裁 | 担当想定 |
|---|---|---|---|---|
| 1 | 精度テスト(自分の証券で) | P1 | 不要・即日可 | 小柳さん・たかしくん |
| 2 | 商品ラインナップ表(なないろ・FWD先行) | P2 | ③着工指示のみ | たかしくん+収集部 |

| 4 | 保険料表のテキスト化 | P4 | 同上 | たかしくん |
| 5 | 守り部審査(法務+PII) | P5 | ②の指示 | 守り部 |
| 6 | 通しリハーサル(架空世帯) | P6 | 不要 | 全員 |
| 7 | 実顧客運用の解禁 | — | **P5通過が条件** | 小柳さん |

運用のコツ(共通):
- 1つのチャットに全部詰めない。**1タスク=1チャット**で始める(混ざると精度が落ちる)
- 資料はスクショよりテキスト(またはPDFそのもの)を渡す方が誤読が減る
- 各タスクの成果物は必ずファイルに保存させる(「やったのに記録がない」を作らない)。**実顧客情報を含むものは hojo-hq に入れない**

## P1: 精度テスト+実測ログ

> 用途: プロンプトAの読み取り精度を実測し、守り部審査に出せる「精度の根拠」を貯める。自分・家族(同意済み)の証券のみ使用。

```
あなたは社内システム「勝てるくん」(保険証券読み取り)の精度テスト担当です。
これから証券の写真を送るので、次の手順で進めてください。

手順:
1. 私が別途貼る「プロンプトA」(読み取りプロンプト)の通りに読み取り、JSONを出す
2. 私が原本と見比べて、誤りを指摘する
3. 指摘を受けて、次の形式で「実測ログ」を1行作る(個人名・証券番号は書かない):

| 日付 | 保険会社 | 商品種類 | 誤読した項目 | 金額の桁誤り(有/無) | 要確認と出た項目数 | 気づき(写真の撮り方・レイアウト起因など) |

4. 誤読の原因が「写真の写り」か「プロンプトの指示不足」かを分けて、プロンプトAの改善案があれば1つだけ提案する

このログは累積させます。過去のログを貼ったら、傾向(どの会社の証券が読みにくいか等)も更新してください。
```

## P2: 商品ラインナップ表の作成(なないろ・FWD先行 → チューリッヒ追加)

> 用途: プロンプトC(3社マッチング)に渡す土台資料を作る。**AIの記憶で書かせず、公式資料から作らせる**のが生命線。

```
あなたは保険商品資料の整理担当です。
添付(または下に貼付)する公式パンフレット・商品パンフの内容から、「商品ラインナップ表」を作ってください。

対象会社: 【なないろ生命 / FWD生命 / チューリッヒ生命 のいずれかを記入】

ルール:
- 渡した資料に書いてあることだけで作る。あなたの記憶にある商品知識で補わない
- 資料に無い・読み取れない項目は「要確認」と書く
- 各行に出典(資料名とページ)を必ず付ける(あとで原文照合するため)
- 販売停止・改定の可能性があるため、資料の作成年月を表の冒頭に明記する

出力形式:
| 商品名 | 保障分野(下の8分類) | 主契約の内容 | 主な特約 | 加入年齢範囲 | 保険期間 | 出典 |

保障分野の8分類:
①死亡(遺族の生活費) ②医療(入院・手術) ③がん ④三大疾病・八大疾病
⑤就業不能・収入保障 ⑥介護 ⑦老後資金・貯蓄性 ⑧その他(傷害・引受緩和など)

最後に「資料に載っていなかった重要情報」(保険料・引受基準・付加条件など)を列挙してください。
```

※完成した表は、代理店限定資料を含まなければ docs/insurance/ 配下へ。代理店限定資料由来の場合は置き場所を守り部審査(P5)の結論に合わせる。

## P3: チューリッヒ生命 引受目安のデータ化

> 用途: 既存の docs/insurance/underwriting_full.json(なないろ1,483件・FWD2,874件)にチューリッヒを追加し、3社体制にする。

```
あなたは引受目安資料のデータ化担当です。
添付するチューリッヒ生命の体況別引受目安資料を、以下のJSON形式に変換してください
(既存の underwriting_full.json のなないろ・FWDと同じ形式です)。

出力形式(1レコードの例):
{
  "page": <資料のページ番号>,
  "disease": "<疾病・状態の名称(資料の表記のまま)>",
  "state": "<経過期間・状態の条件(資料の表記のまま)>",
  "marks": { "<商品・特約名>": "○/×/△など資料の記号のまま" },
  "remarks": "<備考欄の内容>"
}

ルール:
- 資料の表記のまま書き写す(記号・疾病名を言い換えない)
- 判読できないセルは "要確認" と入れる
- 最後に「変換したレコード件数」と「要確認が入った件数」を報告する(検品用)
- 長い資料は章ごとに分割して送るので、そのたびに追記していく

検品: 変換後、無作為に10レコードを選んで元資料のページと突き合わせます。その10件のページ番号を教えてください。
```

## P4: 保険料表のテキスト化

> 用途: プロンプトCの「概算保険料」欄を埋められるようにする。概算はあくまで参考で、正式には設計書。

```
あなたは保険料表のデータ化担当です。
添付する保険料表(年齢別・性別)を、次の表形式に変換してください。

| 会社名 | 商品名 | プラン条件(保険金額・期間など表の前提) | 年齢 | 性別 | 月払保険料 | 出典(資料名・ページ) |

ルール:
- 表の前提条件(保険金額・口数・特約の有無)を必ず「プラン条件」に書き写す。前提が違う保険料は比較できないため
- 数字は資料のまま。判読できないセルは「要確認」
- 最後に件数と要確認件数を報告(検品用)
- この表の冒頭に「※概算参考値。正式な保険料は設計書で確定」と必ず記載する
```

## P5: 守り部審査キックオフ(実顧客運用の解禁条件)

> 用途: 決裁キュー②の実行。小柳さんの「指示する」の一言のあと、守り部チャットにこれを貼る。

```
守り部(マモリ)へ審査依頼です。社内システム「勝てるくん」(保険証券写真→読み取り→保障マップ→当社取扱3社の候補整理→提案下書き)の、実顧客データでの運用解禁に向けた審査をお願いします。
設計の全体像と三名体制議事は docs/勝てるくん_プロンプト設計ガイド_2026-08-12.md を参照。

審査対象は2点:

1. 法務(保険募集規制)
- 比較表示・乗換募集に関する規制(保険業法・監督指針)のうち、本システムに関係する条文・ガイドライン箇所を特定する(現時点の設計ガイドでは「要確認」のまま)
- 設計上の対応(勝ち筋なし=現状維持推奨の明示・乗換時の不利益4点の必須記載・募集人の最終確認・上乗せと乗換の区別)で足りるか、論点を整理する
- 弁護士確認に出す質問リストを作る(確認が要らない範囲/要る範囲を分ける)

2. 個人情報(PII)
- 証券写真・読み取りJSON・保障マップ・提案下書きの「保存場所・保存期間・破棄ルール」のv1案を作る
- 前提: 公開リポジトリ(hojo-hq)への保存は禁止。呼び名置き換え(実名を残さない)は実装済み。家族の健康情報を含み得る
- churn-pii-guard(既存の顧客データ管理原則)と同水準にそろえる

アウトプット: ①審査所見(OK/NG/条件付きの別) ②弁護士への質問リスト ③保存・破棄ルールv1案。
断定できない法解釈は断定せず「弁護士確認事項」に回してください。
```

## P6: 通しリハーサル(架空のモデル世帯)

> 用途: 実顧客解禁前の最終リハ。実在の人物・証券は使わない。

```
あなたは社内システム「勝てるくん」の通しテスト担当です。
まず、沖縄の典型的な架空のモデル世帯を1つ設定してください
(例: 夫45歳会社員・妻42歳パート・子2人。夫: 他社の定期保険と医療保険、妻: 共済のみ、など。実在の人物・実在の契約は使わない)。

その世帯の「架空の証券情報」をプロンプトAの出力JSON形式で3件作り、
そこから プロンプトB(保障マップ)→ C(3社マッチング・資料は別途貼る)→ D(提案下書き)を通しで実行してください。

終わったら、次の3点を自己点検して報告:
1. Dの下書きに断定表現(「絶対」「必ず得」等)が混ざっていないか
2. 乗換提案に「ご注意いただきたい点」4点が全部入っているか
3. 勝ち筋なし(D分類)にすべき候補を無理にA〜Cにしていないか

最後に、営業のたかしくん役として「この下書きのままお客様に出せない箇所」を3つ挙げてください。
```

## P7: 公開情報の深堀リサーチ(勝ち筋の材料集め)

> 用途: 各社が公式に開示している情報(商品ページ・パンフPDF・約款・ご契約のしおり)を深掘りし、「どの穴に・どの顧客に・どの商品が効くか」の材料を集める。**ウェブ検索が使えるAI**(claude.ai のリサーチ機能等)で実行する。

```
あなたは保険商品の公開情報リサーチ担当です。
社内の保障見直しツールの土台資料として、次の会社の公式開示情報を深掘りしてください。

対象会社: 【なないろ生命 / FWD生命 / チューリッヒ生命 のいずれか1社。1チャット1社】

調べる項目(すべて公式の一次情報のみ):
1. 現在販売中の商品一覧(商品名・保障分野・発売/改定時期)
2. 各商品の保障の細部: 支払事由 / 免責事項 / 待機期間(がん保険の90日等)/
   支払限度(日数・回数・通算)/ 更新の有無と更新時の保険料変動
3. 特約の一覧と付加条件(単体で入れない特約・中途付加の可否)
4. 引受緩和型・無選択型商品の有無と告知項目数
5. 健康割引・非喫煙割引などの割引制度(適用条件と割引幅)
6. 公式サイトの保険料シミュレーターがあれば、モデル年齢(30/40/50歳・男女)の
   試算例(試算条件を必ず書き添える)
7. 「よくあるご質問」「ご契約のしおり」から、営業現場で聞かれやすい注意点
   (解約返戻金の扱い・クーリングオフ・告知義務違反の扱い)

ルール(正確性最優先):
- 出典は会社公式サイト・公式PDFのみ。比較サイト・ブログ・まとめ記事は使わない
- すべての記載に出典URLと取得日を付ける
- 資料に書いていないことは書かない。曖昧な箇所は「要確認」と明記
- 「この商品が最強」などの断定はしない。事実(数字・条件)だけを集める
- 販売停止・改定の告知(ニュースリリース)も確認し、情報の鮮度を記す

出力の最後に「勝ち筋メモ」を付ける:
- この会社の商品が「効きやすい穴」(例: 就業不能が無保障の自営業者、がん家系で一時金重視 等)を、
  集めた事実にひもづけて箇条書き(1項目=事実の出典付き)
- 逆に「弱い分野」(この会社では埋めにくい穴)も正直に書く ← 比較の公正さと、
  他2社への振り分け判断に必要
```

使い方: 1チャット1社で3回実行 → 成果物は docs/insurance/ 配下に保存(公開情報のみなのでリポジトリ可)。**四半期に1回、同じプロンプトで更新**する(商品改定を見落とすと誤提案の元)。「弱い分野」まで集めるのがミソ — 3社のどれで埋めるかの振り分けと、勝ち筋がない時に正直に言うための材料になる。
