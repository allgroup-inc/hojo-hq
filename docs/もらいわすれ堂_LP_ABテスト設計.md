# もらいわすれ堂 LP A/Bテスト設計(実戦プラン)

目的: LPを「診断→LINE登録(❹)」へ最短で運ぶ形に、データで磨き続ける。
CVは LINE登録の1点のみ / 締切表現は「約1か月前」 / 事実は公式照合(変えない)。

---

## ⚠️ 最初に(いちばん大事な現実)

**いまの流入(1日約5人=週約35人)では、A/Bテストは統計的に成立しません。**
A/Bは「偶然の差」と「本物の差」を見分けるのに一定の人数が要ります。目安:

| 判定したい指標(基準値) | 20%改善を見抜くのに必要な人数 | いまのペースだと |
|---|---|---|
| ヒーローCTAクリック率(基準20%) | 約3,000人/パターン(計6,000人) | 約40か月 |
| 診断→LINE登録率(基準30%) | 約1,200人/パターン(計2,400人) | 約16か月 |

→ **結論: まず流入を増やす(Instagram)。テストはそのあと。** 少人数で結果を見て止めると「偽の勝ち」を掴み、判断を誤ります。

### だから、当面の進め方(2段構え)
1. **今すぐ:テストせず"高確度の改善"を入れる**(下の「A. 確定で入れる磨き」)。世界の高転換LPで実証済みのものは、少人数でも入れて損はない。
2. **流入が週300人を超えたら:A/Bを回す**(下の「B. テスト・バックログ」)。まずヒーロー見出しから。
   - 目安: 診断開始が **週150人×2パターン** 集まる規模になったら開始。

---

## A. 確定で入れる磨き(テスト不要・高確度)

少人数でも入れてよい、実証済みの改善。ICE(影響・確度・容易さ)が高い順。

1. **運営者の顔写真を物語ブロックに追加**(信頼↑・滞在+15%報告)。※写真の用意=小柳さん判断。
2. **「県民が取り戻したお金」カウンターを数字が出たら最上部近くへ**(社会的証明の最大化)。いまは「まもなく公開」で正直に。
3. **診断の"結果直下LINE"は実装済み** — 継続。`pos:result_top` で効き目を計測中。
4. **ファーストビューの画像最適化**(表示1〜2秒)。人物・生活の写真は滞在を伸ばす。
5. **市町村ページへの内部リンク強化**(SEO流入の受け皿)。

→ これらは「入れる/入れない」の判断だけ。テストで時間を使わない。

---

## B. テスト・バックログ(流入が増えたら・ICE順)

各テストは**1回に1要素だけ**変える。primary=主指標 / guard=悪化させてはいけない指標。

### B-1. ヒーロー見出し(最優先・ICE高)
- 仮説: 「損失回避(もらい忘れて損)」を強めると、診断開始率が上がる。
- 対照(現行): 「あなたの世帯、いくらもらい忘れてる?」
- 変化A: 「対象なのに、締切を逃していませんか。」(損失を直接提示)
- 変化B: 「もらい忘れの給付金、3分でわかる。」(成果+手軽)
- primary: **ページ表示→shindan_start**(診断開始率) / secondary: shindan_complete / guard: 直帰率
- 必要規模: 各3,000人前後(基準20%・20%改善を見る場合)

### B-2. ヒーローCTAの文言(ICE高)
- 仮説: 一人称+得の文言はクリックが増える。
- 対照: 「私の"もらい忘れ"を3分で調べる」/ 変化: 「無料で3分診断をはじめる」
- primary: CTAクリック→shindan_start / guard: 完了率

### B-3. 診断結果のLINE誘導=位置(ICE中・実装で計測準備済み)
- 仮説: 結果直下(`result_top`)は最下部より登録が多い。
- いまは両方に設置済み → `pos` タグの比率で観察。**将来はどちらか一方に絞ってA/B**。
- primary: line_add_click(pos別) / guard: 診断完了→離脱

### B-4. 損失回避セクションの有無(ICE中)
- 仮説: ヒーロー直後の「こんなもらい忘れ」具体例が、診断開始を後押しする。
- 対照: あり / 変化: なし
- primary: shindan_start / secondary: スクロール到達

### B-5. LINE特典の見せ方(ICE中)
- 仮説: 「締切を"約1か月前"に」の言い切りは登録を増やす。
- 対照: 現行(言い切り) / 変化: 特典を3点リストで強調
- primary: line_add_click / guard: ブロック率(あいさつ後)

### B-6. スマホ固定CTAの文言(ICE低〜中)
- 対照: 「私の"もらい忘れ"を3分で調べる(無料)」/ 変化: 「まず3分、対象かチェック」

## 計測(このサイトで実際に使えるもの)

既に `fgTrack()`(Plausibleカスタムイベント)が入っており、次を計測済み:
`shindan_start / shindan_step_q2..q5 / shindan_complete / shindan_zero / line_add_click(pos付き) / jukyu_report_click / kit_click`。

- A/Bの実装は**軽量なクライアント側分岐**でできる(下記ハーネス)。バリアントを `fgTrack` の props に付ければ、Plausible上でバリアント別に見える(APIなしでもダッシュボードで読める)。
- 主指標は **診断→LINE登録率(目標30%)** と **ページ→診断開始率**。

### 実装ハーネス(流入が増えたら有効化・雛形)
```html
<script>
// 50/50でバリアント割当(初回に決めて localStorage で固定=同一ユーザーは同じ表示)
(function(){
  var KEY="fg_ab_hero";
  var v=localStorage.getItem(KEY);
  if(!v){ v=(Math.random()<0.5?"A":"B"); try{localStorage.setItem(KEY,v);}catch(e){} }
  window.FG_AB={hero:v};
  // 表示反映(ちらつき防止のため、対象要素は最初 visibility:hidden にしておき、確定後に出す)
  document.addEventListener("DOMContentLoaded",function(){
    if(v==="B"){ /* 見出しBに差し替え */ }
    // 計測に必ずバリアントを付ける
    if(window.fgTrack) window.fgTrack("ab_expose",{test:"hero",variant:v});
  });
})();
</script>
```
※ 本番実装時は「対照/変化」を1要素だけ差し替え、`line_add_click` 等の主要イベントに `variant` を必ず付与する。

## 運用サイクル(流入が増えたあと)
- 週次: 走行中テストの技術チェック(早期に勝ち判定しない。ガードレール悪化時のみ停止)。
- 隔週: 完了テストを判定→勝ちパターンを playbook 化→次のテスト開始。
- 月次: 実験velocity(月4〜8本)・勝率(20〜30%)・累積リフトを確認。バックログ補充。

## まとめ(今日の意思決定)
- **A/Bは"流入が増えてから"**。いまはテストせず、A(確定の磨き)を入れるのが最短。
- **最優先は流入(Instagram)**。テスト設計・計測・ハーネスは準備済みなので、人が来た瞬間に回せる。
