# 議事: 診断ページの外部監視(A案・C案)

## なぜ(背景)

PR #566 で入れた15分監視・停止検知は、どちらも GitHub Actions のスケジュール起動で動く。2026-11-04 の統合後、リポジトリ全体で約2時間、定時起動が1件も来なかった。スケジュール起動が止まると監視と停止検知が同時に止まり、誰も気づけない。

小柳さん承認(2026-11-04): A案(監視の停止を外部から検知する。healthchecks.io 等を候補、正常終了時にハートビート、Secret をログ・Issue に出さない)を設計・実装する。C案(moradou.jp/shindan/ と診断用制度データを GitHub Actions に依存せず確認)は設計する。外部サービスの契約・アカウント作成・課金・本番監視の開始は別途承認。

## 前提

- 設計の詳細: `docs/診断ページの外部監視_設計.md`
- healthchecks.io の無料プラン(Hobbyist)は20件まで(公式の料金ページの検索結果。メール通知が含まれるかは契約前に確かめる)
- LINE Notify は 2025-03 に終了している。外部監視の通知はメールにする(顧客向けの LINE の通数を使わない)

## 代替案

1. 外部から定期的に監視ワークフローを起動する(cron-job.org など): 起動の権限を持つトークンを外部に預ける。漏れたときの影響が大きいので見送り
2. 停止検知を強化する: 停止検知も同じスケジュール起動で動くので、同時に止まる問題は解けない
3. **ハートビート(A)と外部の死活監視(C)(採用)**

## 三名体制の議論

- **スイシン(推進)**: ハートビートは外部サービスが「来ない」ことを数えるので、GitHub Actions が完全に止まっても気づける。Secret 未設定の間は何もしないので、統合しても挙動は変わらない。費用は無料プランで足りる
- **ウタガイ(懐疑・反対理由。必須)**:
  1. ハートビートのURLが漏れると、第三者が偽の「生存」を送って停止を隠せる。URLそのものが鍵になる
  2. GitHub の遅れが続くと、外部サービスが頻繁に Down を知らせ、運営が通知に慣れて見なくなる
  3. 外部サービスの規約・料金が変わると、黙って監視が止まりうる(UptimeRobot は事業での利用の扱いが情報源によって食い違う)
  4. 外部監視が増えるぶん、通知の経路が3つ(LINE・GitHub Issue・メール)になり、どれを見ればよいか分かりにくい
- **ベッカイ(別解・前提を疑う)**: スケジュール起動に頼らず、外部から起動する方式(代替案1)なら、監視の間隔そのものを守れる。ハートビートは「止まったことが分かる」だけで、止まっている間の監視の空白は埋まらない

## 裁定

採用する(A案は実装、C案は設計まで)。指摘1は、URLを Secret にだけ置き、ログ・Issue に出さないことをテストで確かめる。偽の生存を送られても、15分監視・停止検知・LINE の経路は別に動く。指摘2は、期限を Period 2時間・Grace 4時間から始め(最後のハートビートから約6時間で知らせる)、2週間の実測で見直す。直近14日の実測で、リポジトリ全体で定時起動が3時間以上止まることが24回あり、6時間を超えたことは0回だったため(期限30分+猶予15分や1時間+2時間では毎日誤報が出る見込み)。指摘3は、契約前に公式の規約を確かめ、決裁事項に入れる。指摘4は、メールは「監視そのものが止まった/外から見てページが落ちている」専用とし、ページの中身の異常は今までどおり Issue と LINE に残す(設計に書く)。ベッカイ案(外部からの起動)は、A案で途絶の実態を測ってから、トークンの扱いとあわせて別議題にする。

## 追記 2026-11-04: 初期値の変更

本番導入前の最終確認で、スケジュール起動の遅れを実測した(設計書の「期限と猶予の決め方」)。予定からの遅れは中央値約3.7時間・最大10時間、定時起動が丸ごと飛ばされる回も多い。初期値を Period 1時間・Grace 2時間から Period 2時間・Grace 4時間に改めた。healthchecks.io の無料プランの利用と設定準備は小柳さんが承認した(通知先メールアドレス・Secret の登録・外部への初回送信は別途確認)。

## 追記 2026-11-04(2回目): C案を主な監視、A案を補助にする

誤通知を14日分で試算した(設計書の「想定される誤通知」)。15分監視が、4時間おきのワークフロー並みにしか起動しない場合は、期限2時間+猶予4時間でも14日で約30回鳴る。A案は、定時起動の遅れそのものに左右されて「監視が止まった」の知らせとして当てにならない。そこで、GitHub Actions を使わずに moradou.jp を5分おきに確かめる C案を主な監視とし、A案は補助とした。A案の期限2時間+猶予4時間は暫定値とする。

- **ウタガイ(懐疑・反対理由。必須)**: C案はページの文字列しか見ないので、件数の誤差(判定ロジックと表示のずれ)や制度データの鮮度は見つけられない。主な監視にすると、そちらの見張りが手薄になる
- 裁定(部門長): C案を主な監視にするのは、利用者から見える「ページ・データ・ロジックの消失」を、起動の遅れと関係なく見つけるため。件数の誤差と鮮度は、引き続き15分監視(起動したとき)が見る。鮮度は、15分監視が6時間以上動かなければ停止検知と A案が知らせる

## 見直し条件

- 見直し期限: 2027-05-04
- 外部サービスの通知が週2回以上の誤報になったら、期限・猶予・間隔を見直す
- 外部サービスの規約・料金が変わったら再議論する
