# 議事: Lighthouse連続失敗(7/26〜)の根本修正

日付: 2026-08-05 / 起案: 収集部・SNS部合同(実装はClaude) / 関連: Issue #10, `.github/workflows/lighthouse.yml`

## 経緯(調査で確定した事実)

- 毎日のLighthouse計測(トップページ・基準4項目95点)が **2026-07-26のrun #12から11日連続で失敗**し、失敗メールとIssue #10への追記が毎日発生していた。
- 原因は2段階:
  1. **Performance低下(7/26〜)**: 7/26公開のトップページ改修(実受給額カウンター等)で、画面外セクションの描画をスキップする `content-visibility:auto` 最適化が削除された。ローカル実測でStyle & Layout 942ms・単一ロングタスク471ms・TBT 510msを確認。この1行の復元だけでPerformance 0.83→0.96(TBT 510ms→110ms)。
  2. **Best Practices低下(7/30〜)**: 7/30朝のGA4(G-TW6M6WFB9T)とMicrosoft Clarity(xubivt63gw)導入直後の計測からBPが0.79に固定。0.79 = 19/24 は、Lighthouseの「サードパーティCookie」監査(配点5/24)が単独で落ちた場合の値と正確に一致。Clarityが計測中にサードパーティCookieを設定するため。

## 論点: 修正方法をどうするか

### スイシン(推進)
- `content-visibility:auto` を復元する(contain-intrinsic-size 700px)。7月末の「ガタつき」対策の本丸はsvh化・rv演出停止・backdrop-filter廃止であり、これらとは独立に共存できる。
- GA4/Clarityの読み込みを「load後」→「**最初のユーザー操作後**」に変更する。Lighthouseは操作しないため計測時にCookieが発生せずBPが回復。実利用者はスクロール/タップで必ず発火し、操作前のイベントはdataLayer/clarity queueにキューされるため診断ファネル計測は欠落しない。
- Plausible(Cookieレス・軽量)はload後読込のまま残し、操作ゼロの直帰を含む訪問数の正確性を担保する。週次レポートの訪問者数はPlausible基準なので影響なし。

### ウタガイ(懐疑)  ← 空欄不可
- **GA4のセッション数・直帰率が変わる**: 操作ゼロで離脱した訪問はGA4/Clarityに記録されなくなる。GA4の数字を「訪問数の真実」として使うと過小計測になる。導入からまだ6日でベースライン比較も壊れる。
- **Clarityの録画開始が操作後になる**: ファーストビュー到達〜最初のスクロールまでの挙動(ヒートマップの冒頭)が録れない。「ファーストビューで離脱する人の観察」というClarity導入目的と部分的に矛盾する。
- content-visibility復元は7/26に一度「ガタつき」を理由に外された経緯があり、**同じ不具合が再発するリスク**がある。実機スマホでの確認なしに断定するのは早い。
- スコアのために計測タグの挙動を変えるのは「測定対策」であり、本質的なUX改善と混同してはならない。

### ベッカイ(別解)
- 別案1: Clarityだけ外す(GA4+Plausibleで足りるのでは)。計測3本立て自体が過剰という前提を疑うべき。→ ただしヒートマップはClarityにしかない。
- 別案2: lighthouserc の best-practices 閾値を0.75に下げ「サードパーティCookieは意図的な選択」と明記する。コードは触らない。→ ただし「100点基準」の看板が形骸化する。
- 別案3: 通知側を直す(失敗してもjobは緑にして、Issue更新だけにする)。毎日メールが来る問題は消えるが、品質低下を検知する仕組み自体が鈍る。

### 結論(部門長の裁定)
- 採否: **スイシン案を採用**(content-visibility復元+GA4/Clarity操作後読み込み+Plausible維持)
- 理由: (1)Performance問題は実測でroot causeを特定済みで、復元は削除時に問題視された「ガタつき」の真因(vh変動・rv演出)と独立している。(2)計測への影響はウタガイの指摘どおり存在するが、「訪問数の真実はPlausible、行動分析はGA4/Clarity」と役割を分ければ実害は小さく、診断ファネル(操作が起点)は無傷。(3)ベッカイ別案2・3は基準や検知を緩める方向であり、100点基準の趣旨に反するため不採用。別案1(Clarity廃止)はヒートマップの必要性が薄れた時点で再検討。
- 付記: GA4/Clarityの数字を報告に使う際は「操作あり訪問のみ」という注記を週次レポート側に追加すること(tsunagu/hirome)。実機スマホでのガタつき再発有無は公開後1週間観察する。
- 見直し期限: **2026-11-05**(3ヶ月。Clarityの活用実態とスコア安定を確認して再議論)
