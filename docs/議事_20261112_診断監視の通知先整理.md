# 議事: もらいわすれ堂 診断監視の通知先整理

## なぜ(背景)

- 2026-11-11、もらいわすれ堂の診断ページ監視の通知(「⚠️【もらいわすれ堂】診断ページの監視が動いていません」)が、**沖縄企業のミカタ(株式会社GLOW)の LINE 公式アカウント**から届いた。送信担当 `diagnosis-line-sender.yml` が、ミカタのトークン(`LINE_CHANNEL_ACCESS_TOKEN`)で管理者へ送っていたため(議事_20261103 の時点では、このトークンを管理者向け通知に共用する前提だった)
- もらいわすれ堂(株式会社フクギイロ)とミカタは別会社・別サービス。混同表記をしない(CLAUDE.md)
- 2026-11-12 06:56(JST)、小柳さんの承認で `diagnosis-line-sender` を一時停止した(Actions の状態 `disabled_manually`)
- 停止中も、15分監視と停止検知は障害Issueに LINE の送信要求(`<!-- line-want -->`)を書き続ける。**再開すると、たまった要求が(24時間3通の上限内で)まとめて送られる**。また停止検知は、要求が6時間以上残ると「送信担当の停滞」(`LINE_SENDER_STALLED`)を起票する
- 一方、障害Issueは GitHub Actions のボットが起票しており、**小柳さんに通知メールが届くかは確かめられていない**(リポジトリを Watch していれば届くが、設定はこの作業環境から読めない)。UptimeRobot(外部監視C案)・healthchecks.io(A案のハートビート)はどちらもまだ登録前で、`DIAG_HEARTBEAT_URL` は未設定(2026-11-12 の監視ログで「未設定のため送りません」を確認)

## 前提(2026-11-12 確認)

- 送信記録(`bot/diagnosis-line-state` の `diagnosis-line/state.json`): 10件すべて送信済み、送信中の予約なし。**いま再開しても送るものは無い**が、新しい障害が起きるたびに要求がたまる
- GitHub は、Issue に割り当てられた人へ「割り当て」と以後のコメントを通知する(受け取る側の通知設定でメールが有効な場合)。割り当てできないアカウントを指定しても、GitHub はエラーにせず黙って無視する
- 予定のスケジュール起動は遅れ・間引きがある(議事_20261103・外部監視設計の実測)。この変更は検知までの時間を変えない

## 代替案

1. **③ もらいわすれ堂の LINE 公式アカウントから送る** → トークンの発行・登録が先に要る(決裁キュー4)。顧客向け配信と同じ枠を使う。将来の選択肢として送信担当のコードは残す(`DIAG_LINE_REQUESTS=on` で再び要求を書く)
2. **② GitHub の通知メールに一本化し、UptimeRobot を補助にする** → 採用(本議事)。LINE のトークン管理と通知先の混在を減らし、障害の記録は Issue に残る
3. Slack・Webhook へ送る → 受け皿が決まっていない(`SLACK_WEBHOOK_URL` 未設定で黙ってスキップした前例: 議事_20261016)。不採用
4. 停止したまま何もしない → 通知の経路がゼロになる。不採用

## 三名体制

### スイシン(推進)
- LINE の送信要求を書かなければ、送信担当を止めている間に要求がたまらず、再開時のまとめ送りが起きない
- 障害Issueを担当者に割り当てれば、Watch の設定に関係なく「割り当て」の通知が届く。以後の症状の変化・復旧もコメントとして通知される
- 停止検知の「送信担当の停滞」は、送信要求を書かない間は意味が無い。代わりに「通知先が使えるか」(担当者の設定・割り当てできるアカウントか・開いている障害Issueに担当者がいるか)を毎回確かめ、使えなければ専用のIssue(`diagnosis-notify-route`)に残してジョブを赤にする

### ウタガイ(懐疑・反対必須)
1. **GitHub の通知メールは、受け取る側の設定で止まる。**「割り当て」の通知も、通知設定でメールを切っていれば届かない。割り当てが成功しても、届いたことにはならない。コードでは確かめられない
2. **担当者を変数にすると、未設定のまま統合されうる。**未設定なら誰にも知らせが届かない。また割り当てできないアカウントを GitHub は黙って無視するので、「割り当てた」つもりで誰にも届かない
3. **割り当ての処理を足すと、起票そのものを壊す危険がある。**割り当ての失敗で例外が出れば、障害の記録まで消える。予備ジョブ(`fallback`)は `set -euo pipefail` で動くため、`gh issue create --assignee` にすると割り当ての失敗で起票ごと止まる
4. **GitHub のメールに一本化すると、GitHub 自体の障害・スケジュール起動の停止と同時に止まる。**外部監視(UptimeRobot・healthchecks.io)はまだ登録前で、いま外から見ている仕組みは無い
5. 通知先のIssueやジョブの赤で、かえって知らせが増える(未設定のまま統合すると、2時間ごとにジョブが赤になる)

### ベッカイ(別解・前提を疑う)
- そもそも「人に届ける経路」を GitHub の中に作るのは限界がある。外部監視(UptimeRobot のメール)を先に登録すれば、GitHub が止まっても届く。通知の主経路は外部監視、Issue は記録、という分担もありうる
- 担当者の割り当てではなく、Issue 本文で担当者をメンションする方法もある。ただし公開リポジトリの本文にアカウント名が毎回残り、メンションの通知も同じく受け取る側の設定に左右される
- LINE をやめるのではなく、③(もらいわすれ堂の LINE)に切り替えるまでの「つなぎ」として扱う考え方もある

## 裁定(部門長)

- 採否: **採用(Draft PR まで)**。統合・本番反映・変数の登録・受信テストは、小柳さんの別承認のあと(frontmatter の status は、統合の承認まで deferred)
- ウタガイへの対応:
  1. 指摘1は、コードでは確かめられないことを前提にし、**統合の前に実際の受信テストを必須**にする(下の「統合の前に要ること」)。停止検知のジョブ要約にも「メールが届くかは確かめられない」と書く
  2. 指摘2は、停止検知が毎回「担当者が設定されているか」「割り当てできるアカウントか(`GET /repos/{repo}/assignees/{login}`)」「割り当てが実際に反映されたか(応答の担当者一覧で判定)」を確かめ、だめなら `diagnosis-notify-route` のIssueに残してジョブを赤にする。担当者の名前は英数字とハイフンだけを受け付ける
  3. 指摘3は、**起票が先・割り当てが後**にする。割り当ての失敗(例外を含む)は捕まえて、Issueに「通知メールで知らされていない可能性」と1回だけ書き残す。その注記も書けない場合でも起票は止めない。予備ジョブも `gh issue create` の後に `gh issue edit --add-assignee` を別に行い、失敗は警告だけにする。合成データの試験で確かめる
  4. 指摘4は、この PR では解消しない。外部監視の登録(UptimeRobot・healthchecks.io)は別承認として残し、統合と同時期に進めることを推奨する
  5. 指摘5は、通知先が使えない状態は実際に「誰にも届かない」異常なので、赤にするのが正しい。同じ問題ではIssueを増やさない。統合と同時に変数を登録すれば赤は出ない
- ベッカイ案のうち「外部監視を主経路にする」は、外部監視の登録後に見直す。メンション案は、公開リポジトリにアカウント名が繰り返し残るため不採用。③はつなぎではなく別の選択肢として残す(送信担当のコードは消さない)
- 見直し期限: 2027-05-12(外部監視の登録後、または③のトークン登録後は、その時点で見直す)

## この変更でやること(Draft PR)

- `scripts/diagnosis_notify.py`
  - LINE の送信要求を既定で書かない(`DIAG_LINE_REQUESTS=on` のときだけ書く。ワークフローでは設定しない)
  - 障害Issue(診断ページの障害・監視システムの故障・制度データの注意)を、起票の後で担当者(`DIAG_ALERT_ASSIGNEE`)に割り当てる
  - 停止検知: 送信要求を書かない間は「送信担当の停滞」を見ない。代わりに通知先を確かめ、割り当て漏れのIssueを割り当て直す。問題があれば `diagnosis-notify-route` に起票して赤にする。GitHub API の失敗で確かめられない回は判定しない(断定しない)
- `.github/workflows/diagnosis-monitor.yml` / `diagnosis-monitor-watchdog.yml`: 変数 `DIAG_ALERT_ASSIGNEE` を渡す。予備ジョブは起票の後で割り当てる
- `diagnosis-line-sender.yml` は変えない(停止したまま)
- 試験: 合成データのみ。LINE・メールは送らない。既存の試験(LINE の送信要求を書く設定での動き)はそのまま残す

## 統合の前に要ること(別承認)

1. リポジトリの変数 `DIAG_ALERT_ASSIGNEE` に、通知を受け取る GitHub アカウントを登録する(Settings → Secrets and variables → Actions → Variables。秘密ではないが、本番設定の変更)
2. 受け取る側の GitHub の通知設定で、「Participating(参加しているもの)」のメール通知が有効かを確かめる
3. **受信テスト**: テスト用のIssueを1件作って同じアカウントに割り当て、通知メールが届くことを確かめてから閉じる(実際の通知の送信になるため、別承認)
4. 統合後、`diagnosis-line-sender` は停止したまま。削除するか、③で再び使うかは別に決める
