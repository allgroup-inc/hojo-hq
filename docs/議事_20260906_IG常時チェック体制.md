# 議事 2026-09-06 もらいわすれ堂Instagram 常時チェック体制の構築

発端: 小柳さん指示「しっかり直接常にチェックが出来る体制にしてください」
(背景: Claude Codeの実行環境は egress proxy が instagram.com / graph.facebook.com への接続を
遮断しており、セッションからの直接閲覧が不可能。遥さんのスクショ頼みでは「常に」が満たせない)

## 論点: Instagram(@moradou.okinawa)を毎日自動でチェックする体制をどう作るか

### スイシン(推進)
- Instagram Graph API(Meta公式API)+ GitHub Actions の日次cronで、投稿一覧・キャプション・
  プロフィールを毎朝取得し、機械検査(禁止表現・タグ数・投稿停滞)にかける
- 違反・停滞・トークン失効を検知したら GitHub Issue で通知(Lighthouse運用と同型)
- 公式APIなのでIG利用規約上も問題なく、遥さんの作業を増やさない。実行はGitHubランナー上
  なので、セッションのネットワーク制限と無関係に動き続ける

### ウタガイ(懐疑)
- **トークンは約60日で失効する**。失効すると体制が静かに死ぬ → 対策: API認証エラーを
  検知したら「トークン期限切れの可能性」Issueを自動起票し、無音停止を防ぐ
- **公開リポジトリに運用データを蓄積する懸念** → 保存するのはIGで誰でも見られる公開情報
  (投稿・キャプション・公開カウント)のみ。インサイト系の内部数値は保存しない
- Meta開発者アプリの作成・Facebookページ連携は人的作業で、ここで止まるリスクが最も高い
  → 手順書を1ステップずつ用意し、Secrets未設定の間もCIが赤くならない設計にする
- cronはmainブランチにマージされるまで動かない。ブランチに置いただけでは「体制」にならない

### ベッカイ(別解)
- 別解1: 遥さんが週次でスクショを送る運用 → 人依存で「常に」が満たせず、確認漏れが再発する
- 別解2: Claude Code環境のネットワークポリシーを変更してセッションから直接閲覧
  → instagram.comは未ログインだとほぼ見えないため、許可しても信頼できる確認にならない
- 別解3: 有料のSNS監視SaaS → 現段階の投稿数(立ち上げ期)には過剰。まずは自前APIで十分

### 結論(部門長の裁定)
- 採否: **採用**(スイシン案。ウタガイの4点を対策込みで組み込む)
- 理由: 「常に・直接・機械的に」を満たすのは公式API+CIのみ。別解はいずれも
  「常に」か「信頼性」が欠ける。実装は可逆(ワークフロー削除で撤去可)
- 稼働条件(人間タスク・小柳さん/遥さん): ①Metaトークン発行とGitHub Secrets設定
  ②本ブランチのmainマージ。手順: docs/人間タスク_IG常時チェック_トークン設定.md
- 見直し期限: 2027-03-06(投稿数が増えたら検査項目とインサイト取得の拡張を再検討)
