# 議事 2026-11-21: glow-ma の反映承認の一本化と、毎分処理の読み取りの使い回し

## なぜ(背景)
- 小柳さんから「開発のスピードを格段に上げたい」「すべて承認」の指示(2026-11-21)。
- glow-ma の反映は、main への PR のマージで自動的に行われる(glow-ma-deploy。テストは反映の中では走らない)。
  承認は PR のマージそのもので、反映のたびに別の承認を取る決まりになっていた(11/16 の決裁の条件)。
- 毎分の処理は、録音シートの全件読み取りを1回の実行で4回行っていた(定常の形。確認待ちの録音が無い日も同じ)。

## 前提
- 本番の処理時間は、この作業では測っていない。読み取り回数は、コードを読んで数えた値。
- 承認切れで自動処理は停止中(11/18〜)。反映しても、小柳さんの復旧操作の後まで毎朝の処理は動かない。

## 代替案
1. 承認を、PR ごとに「チェックリストの全項目」を満たした時の1回にまとめる(今回の案)。
2. 反映を、マージ後に人が確認してから行う別の承認(環境の保護)を GitHub に入れる。
   本番の GitHub 設定の変更になるため、小柳さんの操作が要る。今回は見送り。
3. 毎分の処理の読み取りを、時間で間引く。録音の反応が遅れるため採らない。

## 三名体制の議論
- **スイシン**: 承認を1回にまとめると、確認の手数が減り、反映までの日数が縮む。PR のテスト・CI・合成試験・チェックリストの記録が残れば、承認の中身は揃う。
- **ウタガイ**: マージ=即反映なので、承認を1回にまとめると、見落としが本番に直接出る。特に、承認切れのように本番側が止まっているときに反映すると、直したかどうかを確かめられない。
  → 反映の前に、承認切れが解消していること・日次メンテナンスが直近2日完了していることを、チェックリストに入れる。
- **ベッカイ**: 承認の仕組みを変えるより、反映の前後の確認を機械で行うほうが、人の手間が減る。今回は、反映前の確認の機械化は次の候補とする。

## 裁定
- 採否: 採用(案1)。承認の単位は「1つの PR(テスト・CI・合成試験・チェックリストが揃ったもの)」とする。
- 反映の前提: 承認切れの解消と、日次メンテナンスの2日連続完了(ウタガイの指摘を反映)。
- 毎分処理の読み取りの使い回し: 採用(実行の中だけ。書き込みの後は読み直す。実行の外は変えない)。
- 本番の GitHub 設定(環境の保護)は変えない(案2は保留)。
- 見直し期限: 2027-05-21(最長6か月)。

## 見直し条件
- 承認を1回にまとめた反映で、見落としによる障害が1回でも起きたら、案2(環境の保護)を再議論する。
- 毎分処理の時間が、実測で増えたら、読み取りの使い回しを見直す。
