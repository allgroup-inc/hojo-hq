- 親議事: docs/議事_20260828_独自ドメインmoradou.md(2026-08-28 小柳さん決裁・moradou.jp採用)
- 本議事で決めるのは「決裁済みの移行を、どの範囲でどう組み立てるか」だけ。採否は蒸し返さない

## 前提の確認(2026-09-23 時点の実態)

親議事の Phase A(自動ミラー workflow)は 8/28 に入っているが、**26日間で11回 success のまま

moradou.jp も未取得(= 小柳さんの4手順が未着手)。

加えて、親議事のあとに構成が変わっており、当時のミラー定義のままでは配信内容が壊れる。

|---|---|

## 三名体制の議論

### スイシン(推進)
- 書き換えは**配信時の1箇所**で足りる。公開ページが使っているURL基底は3種類しかない
  (`/hojo-hq/fukugiiro`・`/hojo-hq/yamanashi`・`/hojo-hq/go`。全5,835箇所を数えて確認)。
  ジェネレーター約40本を触らずに済み、旧URL側の挙動は一切変わらない = **可逆**。
- 山梨版も `/go/` も同じ仕組みで載る。ブランドは同じ「もらいわすれ堂」なので
  moradou.jp/yamanashi/ が自然な置き場所。
- トークン未設定でも**組み立てと検査だけは毎回走らせる**ようにすれば、小柳さんの4手順が
  終わった瞬間に「動くことが既に確認済みの仕組み」が起動する。

### ウタガイ(懐疑・反対)
1. **一括置換は事故の温床**。ミカタ(株式会社GLOW)のページや `/go/site` `/go/ig` 等の
   ミカタ用チャネルが紛れ込めば、フクギイロのドメインで他社ブランドを配信することになる
   (CLAUDE.md「混同表記をしない」に正面から抵触)。→ **採用条件: 配信ツリーに
   「沖縄企業のミカタ」の文字列が1つでも残っていたら配信を止める検査を必須にする。**
2. **書き換え漏れは緑で通る**。置換し損ねた旧URLが残っても、ページは普通に開いてしまうので
   誰も気づかない。8/28 の Phase A が26日間気づかれなかったのと同じ形。→ **採用条件:
   旧URL(ホスト名だけの記述を含む)が残っていたら配信を止める。検査が本当に落ちることを
   自己テストで毎回確かめる。**
3. **同じ内容が2つのドメインで出る**期間ができる。検索評価が割れるので、旧URL側の
   canonical 付け替え(Phase B)を放置してはいけない。
4. 年額の自動更新請求は続く。解約条件の把握は親議事どおり小柳さんの持ち物。
5. 山梨版を moradou.jp に載せると、**山梨の利用者に沖縄のドメイン名**…とはならないか。
   → moradou は「もらいわすれ堂」であって沖縄を指していないので、ドメイン名自体は問題なし。
   **ただし確認したところ、山梨版の3箇所が `instagram.com/moradou.okinawa`(沖縄のIG)へ
   リンクしていた。** これは独自ドメインとは別の既存の取りこぼしだが、moradou.jp に
   載せることで「山梨の公式サイトが沖縄のアカウントへ送る」形が固定されるため、ここに記録する。
   選択肢は ①山梨版からIGリンクを外す ②山梨用IGを作る ③そのまま(沖縄の投稿も役に立つと割り切る)。
   **本議事では決めない**(IG運用は遥さんの担当範囲であり、③でない場合は運用負荷が増えるため
   小柳さん決裁)。決裁キューに起票する。

### ベッカイ(別解・前提を疑う)
- **別解A: 生成側(約40本のジェネレーター)を直す。** 本筋ではあるが、テンプレート内に
  JSのオブジェクトリテラル `{pos:'header'}` が混ざっており f-string 化は危険。さらに
  手書きの静的ページ(index/shindan/privacy等)は生成物ではないので結局取りこぼす。
  効果は同じで危険だけ大きい。不採用。
- **別解B: 独自ドメインを hojo-hq の Pages に直接当てる。** 1つの Pages サイトに当てられる
  独自ドメインは1つだけで、そこには「沖縄企業のミカタ」のトップも同居している。
  moradou.jp を当てるとミカタがフクギイロのドメインに載る。**採れない**。
  → この制約こそが配信専用リポジトリを分ける理由で、親議事の設計は正しい。
- **別解C: 山梨版は github.io に残す。** ブランドが二股になり、山梨版だけ検索評価が
  積み上がらない。移行の目的に反するので不採用。
- **前提を疑う: そもそも今やる意味があるか。** ある。訪問者が少ない今が引っ越しコスト最小で、
  むしろ「ページを増やしてから移す」ほど損が増える。

## 裁定(部門長)

- 採否: **採用**(ウタガイ1・2を採用条件として実装に組み込む)
- 配信範囲:
  - `site/fukugiiro/` → `https://moradou.jp/`(沖縄版=トップ)
  - `site/yamanashi/` → `https://moradou.jp/yamanashi/`
  - `site/go/fg-*` `site/go/ymn-*` → `https://moradou.jp/go/`(**ミカタのチャネルは載せない**)
  - sitemap はもらいわすれ堂の437件だけに絞って出し直す。robots.txt・404.html・CNAME・
    README は配信先用に生成する(404はミカタのトップへ誘導しない)
- 実装: `scripts/deploy_moradou.py`(自己テスト31件)+ `moradou-deploy.yml` の作り直し。
  **トークンの有無にかかわらず、毎push・毎PRで組み立てと検査を実行する**(ウタガイ2)。
  検査に引っかかれば赤で止まる。スキップするのは push だけ。
- 理由: ウタガイが挙げたブランド混入と書き換え漏れは、どちらも「起きても緑で通る」種類の
  事故だった。機械が止める形にしない限り採用できない、という条件付きでの採用。
- **見直し期限: 2027-03-23**。それ以前でも、moradou.jp 公開後30日の時点で旧URL側の
  canonical 付け替え(Phase B)が終わっているかを点検する。

# 追補: 越境トークンをやめ、配信先が自分で取りに来る形にする(同日)

小柳さんから「残り4手順を完全に自動化してほしい」との指示。**どこまで本当に自動化
できるかを実際に叩いて確かめた上で**、手順を減らす設計変更をしたので記録する。

## 確かめたこと(推測ではなく実行結果)

| 手順 | 自動化できるか | 根拠 |
|---|---|---|
| 1. moradou.jp 取得 | **できない** | 年額費用の決済手段が要る。加えて .jp は登録者の氏名・住所・電話の**実在情報**の登録が必須で、こちらで作ることはできない |
| 2. リポジトリ作成 | **できない** | 実際に `create_repository` を叩いて `403 Resource not accessible by integration`。このGitHub App権限ではorgにリポジトリを作れない |
| 3. トークン発行+Secrets登録 | **設計変更で不要にした**(下記) | PATの発行にAPIは無い(あれば権限昇格の穴になる)。Secretsの書き込み権限もApp側に無い |
| 4. DNS設定 | **できない** | 手順1の取得先の管理画面。手順1に従属する |

なお `moradou.jp` は 2026-09-23 時点で**取得可能**(registrar APIで確認)。

## 三名体制の議論: 手順3をどうするか

### スイシン(推進)
- hojo-hq は **Publicリポジトリ**。ならば配信先(moradou)が自分で hojo-hq を読みに行けば、
  認証は一切要らない。moradou 自身の `GITHUB_TOKEN` は自分のリポジトリへ書けるので、
  **PATもSecretsも不要**になり、手順が1つ丸ごと消える。
- 副次効果として、**Publicリポジトリのワークフローに長期の越境書き込みトークンを
  置かずに済む**。漏洩・失効・権限過多のリスクがまとめて無くなる。

### ウタガイ(懐疑・反対)
1. **即時反映が失われる**。pushごとの配信ではなく定期実行になるので、最大で数時間遅れる。
   → 制度データ自体が収集cron(1日4回)でしか変わらないため、実害は無い。収集の30分後に
   走らせれば実質同じ。即時が要るようになったら `repository_dispatch` を足せばよい(口は開けてある)。
2. **配信先のworkflowを、配信そのものが消す**。組み立てスクリプトは出力先を
   `.git` 以外まっさらにするので、`.github/workflows/build.yml` が1回目の配信で消え、
   **2回目以降は何も起きないまま静かに止まる**。しかも1回目は成功して見える。
   → **採用条件**: `.github` を保護対象に入れ、CIで「配信後もworkflowが残っていること」を
   毎回検査する。実際に .github を置いた状態でビルドして残ることを確認した。
3. **失敗したときに壊れたものが公開されないか**。
   → 検査に引っかかればコミット自体をしないので、前回の正しい内容が残る。
4. **手順が2→3画面に増えていないか**。リポジトリ作成に加えてworkflowファイルの貼り付けが要る。
   → PAT発行(複数項目のフォーム)+Secrets登録(別画面)の2画面が消え、ファイル貼り付け1画面が
   増えるので、差し引きで減っている。かつ**扱う秘密情報がゼロ**になる。

### ベッカイ(別解・前提を疑う)
- **別解A: Netlify / Vercel へ載せ替える。** 両アカウントとも実在を確認した
  (Netlify=小柳さん個人アカウント・1サイト / Vercel=LOTEチーム)。APIでサイト作成まで
  できる可能性はあるが、①継続的な更新には結局 hojo-hq 側に配信用トークンを1本置く必要があり
  手順3が復活する ②Vercelは別事業(LOTE)のチームなので費用と権限が混ざる
  ③8/28決裁のGitHub Pages構成を変える話になる。**今回は採らない**。
  ただし「まず動いているものを見たい」場合の選択肢としては有効なので記録に残す。
- **別解B: GitHub App の権限を足してもらい、リポジトリ作成をAIにやらせる。**
  権限付与という操作自体が人の手で必要な上、組織全体に効く強い権限を恒久的に足すことになる。
  1分の作業を省くために権限を広げるのは割に合わない。不採用。
- **前提を疑う: 手順1を省けないか。** 省けない。独自ドメインを持つことが目的なので、
  ドメインの購入者(=契約主体)が株式会社フクギイロである必要がある。

## 裁定(部門長)

- 採否: **採用**(ウタガイ2を採用条件として実装済み)
- 変更点:
  - 配信は `allgroup-inc/moradou` 側の `build.yml` が行う(hojo-hq からは配信しない)
  - hojo-hq の `moradou-deploy.yml` は**検査専用**にする。`MORADOU_DEPLOY_TOKEN` は不要になり、
    8/28 の Phase A にあったPAT前提のミラー処理は削除
  - 配信スクリプトは `.git` と `.github` を保護する。CIで「配信後もworkflowが残ること」を検査
  - 貼り付け用のファイルと手順書を `deploy/moradou/` に置く
- 理由: ウタガイ2は「1回目だけ成功して以後静かに止まる」典型で、このリポジトリが繰り返してきた
  失敗と同じ形。保護と検査をセットにすることを条件に採用した。トークンを1本減らせるのは
  Publicリポジトリでは無視できない利点。
- **見直し期限: 2027-03-23**(本体議事と同じ)
