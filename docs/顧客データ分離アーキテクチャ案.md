# 顧客データ分離アーキテクチャ案(公開と機密の分離)

作成日: 2026-07-26 / 起案: Claude(churn-pii-guard 準拠)/ 裁定・決裁: 守り部＋監査＋小柳さん
位置づけ: 実データ投入の**前提**となるセキュリティ設計。これは提案であり、採否は守り部審査＋小柳さん決裁。

---

## 1. 現状の問題(なぜ分離が要るか)

- リポジトリ `allgroup-inc/hojo-hq` は **公開(public)**。GitHub Pages の公開サイトと、顧客個人情報を扱う保全システム(`scripts/churn/`)のコードが**同居**している。
- いま顧客データを守っているのは「gitに上げない(`private/` gitignore)」という**運用の1点**だけ。公開リポジトリ上でPIIを扱うと、人為ミス1回(誤コミット・Issue/PR貼付・gitignore崩れ)で**即・全世界公開&実質恒久**の事故になる。
- 保険=規制業種の顧客情報として、この配置は「最高レベルのセキュリティ」とは呼べない。**公開と機密を物理的に分ける**必要がある。

## 2. 目標とする3ゾーン設計

```
┌─────────────────────────┐   ┌──────────────────────────┐   ┌───────────────────────────┐
│ ① 公開ゾーン(現状維持)   │   │ ② 保全システムのコード     │   │ ③ 顧客データゾーン(機密)   │
│ hojo-hq(public)         │   │ 非公開リポジトリへ隔離     │   │ 閉じた社内環境のみ         │
│ ・GitHub Pages 静的サイト │   │ allgroup-inc/hojo-churn    │   │ ・別システムのCSXエクスポート │
│ ・SNS/LINE 導線          │   │ (private)                  │   │ ・churn CLI 実行           │
│ ・PIIゼロ                │   │ ・scripts/churn のコードのみ │   │ ・カルテ/一覧/コンソール生成 │
│                         │   │ ・PIIゼロ(コードだけ)      │   │ ・権限管理された保管        │
└─────────────────────────┘   └──────────────────────────┘   └───────────────────────────┘
      世界に公開してよい            社内メンバーのみ閲覧            ネット非公開・アクセス制御
```

- **①公開ゾーン**: 今の `hojo-hq` のまま。制度情報の公開サイト。顧客個人情報は一切置かない。
- **②コードゾーン**: 保全システムのコードを**非公開(private)リポジトリ**へ移す。コードにPIIは無いが、公開リポジトリから外すことで「誤コミットが世界公開になる」最悪ケースの blast radius を消す。
- **③顧客データゾーン**: 実データ(申込み・接触履歴)・モデル・カルテ出力は、**アクセス制御された閉じた社内環境**でのみ扱う。手元PC任せにしない。ネットに露出させない。

## 3. 選択肢

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A(推奨)** | コードを非公開リポジトリ `hojo-churn` に隔離＋データ処理は閉じた社内環境 | 誤コミットが公開にならない・公開/機密が物理分離・最小権限を敷きやすい | リポジトリ運用が2本になる・移行の手間 |
| B | コードは公開のまま、データ処理環境だけ閉じる | 移行が軽い(環境運用だけ) | 公開リポジトリにPII処理コードが残り、誤コミットが公開になる risk が残る |
| C | GitHub を使わず、コードも内部 git/配布で完全非公開化 | 露出面が最小 | 開発・レビューの利便が落ちる・過剰になりやすい |

## 4. 三名体制の議事(この選択の裁定)

### スイシン(推進)
- A案。誤コミット=公開事故という最悪ケースを構造から消せる。公開サイトと機密処理を物理分離でき、②③に最小権限・監査ログを敷きやすい。保険=規制業種として説明責任が立つ。

### ウタガイ(懐疑)  ← 反対必須
- **リポジトリを private にしても、データそのものを守るのは"実行環境"であって repo 可視性ではない**。②を private 化しても、③の社内環境がザル(共有ドライブ全開・端末暗号化なし)なら意味がない。分離を"やった気"になって環境統制を怠るのが最大のリスク。
- リポジトリ2本運用は、同期漏れ・権限設定ミスなど**新たな人為ミスの面**を増やす。
- そもそも B(コードは公開のまま)でも、PIIがコードに無い以上、現行の gitignore 運用＋環境統制で足りるという主張も成り立つ。

### ベッカイ(別解)
- 「repo をどうするか」より先に、**③顧客データゾーンの要件(誰が・どの端末で・どこに保管・保持期限・ログ)を先に固める**べき。器(repo)の議論は環境要件が決まってから。
- ファイルベース(CSV/HTML in private)自体を見直し、**アクセス制御・監査ログが標準装備された社内データ基盤**に載せる選択もある(将来)。

### 裁定(保留・小柳さん＋守り部へ上申)
- 方向性は **A案(コード隔離＋閉じた環境)** を推奨として上申。ただしウタガイの指摘どおり、**本丸は③環境統制**。よって:
  1. **③顧客データゾーンの要件を先に確定**(守り部審査チェックリストで洗い出す=別紙)。
  2. その上でコード隔離(②private化)を実施。
- これは予算・体制に関わるため**小柳さん決裁事項**。AI・エージェントは判定しない。

## 5. 実施順(決裁後)

1. **③環境要件の確定**(別紙:守り部審査チェックリスト)。アクセス制御・保管場所・保持/削除・ログ・端末を決める。
2. **②コード隔離**: `scripts/churn/` を非公開リポジトリ `hojo-churn`(private)へ移設。`hojo-hq`(公開)からは保全システムのコードを外す(公開サイトはそのまま)。
3. **データ運用の固定**: 別システムのエクスポート → 閉じた環境で churn CLI 実行 → 生成物は権限管理された保管先。ネット非露出。`churn-pii-guard` を全作業で適用。
4. **守り部審査＋小柳さん決裁の通過を確認してから、初めて実データ投入**。
