## ① social-post.yml: べき等性が無かった(修正)

`scripts/post_social.py`は、投稿を「日付ローテーション」で選ぶことで
*同じ投稿を選ぶ*再現性はあったが、*実際にAPIへ投稿する*処理そのものには
べき等性が無かった。

**具体的な失敗シナリオ**: Facebook投稿が成功→Instagram投稿がAPI障害で失敗
→jobを再実行(workflow_dispatch、または承認のやり直し)→Facebookへ**同じ内容が
二重投稿される**(Instagram公開の3回リトライが尽きたあとSystemExitするため、
再実行は「最初から」になる)。

**修正**: `data/social_post_state.json`に`{date, stem, facebook, instagram}`を
記録し、同日・同素材で既に投稿済みのチャネルはスキップする設計に変更。
投稿jobに`Commit post state (always)`ステップを追加し、投稿の成否に関わらず
state を必ずコミットする(片方だけ成功した状態を正しく残すため)。

## ② fukugiiro-fetch.yml / fukugiiro-audit.yml: push retryが無かった(修正)

`update.yml`・`weekly-report.yml`は「pull --rebase→push」を最大3回試行する
リトライ処理を持つが、この2ワークフローは`git push`一発のみだった。
この環境では複数セッションが同時にmainへpushする競合が実際に頻発しており
(このセッション中も複数回発生)、競合時にジョブが無条件で失敗する状態だった。
`update.yml`と同じリトライパターンに揃えた。

## 要観察(修正見送り): fukugiiro-weekly-report.yml

`weekly-report.yml`が起こした重複LINE配信事故(2026-08-03、push+scheduleの
二重トリガーが原因)と同じ「push時にも本処理が走る」構成を持つが、この
ワークフローは外部送信(LINE等)を一切行わず`reports/fukugiiro/*.md`への
書込のみのため、重複実行してもcommitがdiff-quietガードで無害化される。
**現時点では実害なし**と判断し変更を見送るが、将来ここにLINE配信等の
外部送信を追加する場合は、必ずpush時はdry-run化すること(weekly-report.yml
の対応を参照)。
