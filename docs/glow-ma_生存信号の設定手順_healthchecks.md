# glow-ma 台帳の自動処理を見張る設定手順(監視C+D方式)

2026-11-06 作成。この方式は小柳さんの承認を得ています。
ただし、次の作業は**まだ承認待ち**で、手を付けていません。

- healthchecks.io に本番のチェックを作ること
- GASへの反映(mainへのマージ)
- 通知設定の変更

この文書は、承認後に進める順番と確かめ方をまとめたものです。

## なぜ必要か

台帳の自動処理が止まったことに気づく手段は、今は GitHub の3時間おきの点検(glow-ma-gcp-api)だけです。
ところがこの repo では、GitHub の定期実行が予定の半分ほどしか動かない日があります(11/5〜11/6 は5回の予定のうち1回)。
そのため、止まってから気づくまでに半日以上かかることがあります。FK-008 では、承認切れに2日間気づけませんでした(`docs/失敗台帳.md`)。

そこで、GitHub に頼らない見張りを2つ足します。

| 方式 | しくみ | 知らせが来るまで |
|---|---|---|
| **C 生存信号** | 毎分の処理が最後まで正常に終わったときだけ、1時間に1回 healthchecks.io へ「生きています」と送る。信号が途切れると、healthchecks.io がメールで知らせる | 止まってから最大でおよそ2時間 |
| **D トリガーの失敗通知** | Apps Script の「トリガーの失敗通知」を「今すぐ」にする。承認切れなどで処理が失敗すると、Google からメールが届く | 数分〜1時間ほど |

GitHub の3時間おきの点検は、原因を調べる手段としてこのまま残します。

## しくみ(コード)

| ファイル | 役目 |
|---|---|
| `glow-ma/src/heartbeatPing.js` | 送るかどうかを決める。送り先の形を確かめる(`https://hc-ping.com/` のUUID形式、または ping key とスラッグの形式だけ)。前回の結果を記録する。ログに出す文からURLを消す |
| `glow-ma/src/HeartbeatRunner.gs` | 毎分のトリガーの入口 `processQueuedVoiceLogs`。本体 `processQueuedVoiceLogsCore_` を呼んだあと、送る時期なら送る |
| `glow-ma/src/LineVoiceLogRunner.gs` | 本体の名前を `processQueuedVoiceLogsCore_` に変えた。台帳の処理が失敗した数を `VOICE_RUN_STEP_ERRORS` で数える |
| `tests/glow_ma_heartbeatPing.test.mjs` / `tests/glow_ma_heartbeatRunner.test.mjs` | 合成データのテスト。GAS のサービスは偽物で、本物の台帳・本物の healthchecks.io にはつながない |

送る条件は、次の5つが全部そろうときです。

1. 本体が最後まで終わった。本体が例外で止まったときは送らず、例外はそのまま上へ投げる(D方式のメールが届くようにするため)
2. この実行で、台帳の処理が1つも失敗していない。数える処理は次の5つ
   - 自己点検
   - 過去記録の取り込み
   - 録音ファイルの受け付け
   - 放置分の取り消し
   - 止まった録音の再開

   BlueBean の同期は数えない。外の会社の都合で止まることがあり、「台帳が止まった」という知らせと意味がずれるため
3. 前回うまく送れてから60分たっている。送れなかったときは10分あけて送り直す
4. 実行が始まってから4分たっていない(6分の上限に近づけないため)
5. スクリプトプロパティ `HEALTHCHECKS_PING_URL` が正しい形で入っている。未設定なら何も送らず、これまでどおり動く

守っていることは次のとおりです。

- 送るのは中身の無い GET だけです。台帳の中身・顧客情報・録音は送りません
- 送れなくても、例外はすべて `sendHeartbeatIfDue_` の中で受け止めます。台帳の処理は止めません
- 毎分の実行が重なっても、同じ信号を2回は送りません。送る前に、ロックの中で「送信中(失敗扱い)」を先に書いて番を取ります
  - 使うのは UserLock です。台帳の書き込みや録音の送信が使うロックとは別のものです
  - ロックが取れなければ待たずに諦め、次の実行に回します
  - 通信はロックの外で行います
  - 通信の途中で実行が打ち切られても、状態は失敗扱いのまま残るので、10分後に送り直します
- 送り先のURLは、ログにも稼働状況タブにも書きません。URLを知っている人は誰でも信号を送れるためです
- 結果は台帳の「稼働状況」タブに「生存信号(healthchecks.io)」の行として残します。書き込むのは送ったときだけで、1時間に1回ほどです

## 承認後の手順(この順番で)

### 1. コードを反映する(要承認: mainへのマージ)
- マージすると glow-ma-deploy が自動で反映します
- `HEALTHCHECKS_PING_URL` が未設定のうちは、信号は送られません。変わるのは、失敗を数える処理が増えることだけです。このため、先に反映しても安全です
- 確かめ方: 反映の後も毎分の処理が動いていることを、稼働状況タブと実行記録で見る

### 2. healthchecks.io にチェックを作る(要承認: 小柳さんの操作)
1. healthchecks.io にアカウントを作る。無料プラン(Hobbyist)で足ります。台帳の持ち主のアカウントで作ってください
2. 「Add Check」で、次の内容のチェックを作る
   - 名前: 例「GLOW台帳 毎分の処理」
   - Schedule: Simple / **Period 1 hour / Grace Time 1 hour**
3. Integrations でメールの通知先を確かめる(既定はアカウントのメールアドレス)。「Test!」を押すと、届くかどうかを試せます
4. チェックの画面にある Ping URL を控える

**Ping URL は、チャット・メール・GitHub に貼らないでください。**

### 3. 送り先を設定する(要承認)
1. 台帳の Apps Script エディタを開き、「プロジェクトの設定」→「スクリプト プロパティ」を開く
2. プロパティ `HEALTHCHECKS_PING_URL` を足し、値に手順2の Ping URL を入れる
3. 数分待ってから、エディタで `showHeartbeatStatus` を実行し、次の2つが出ることを確かめる
   - 「送り先: 設定済み(形は正しい)」
   - 「前回の送信: … 成功」
4. healthchecks.io の画面で、チェックが「up」(緑)になったことを確かめる
5. 台帳の稼働状況タブで、「生存信号(healthchecks.io)」の行が「送信済み」になっていることを確かめる

### 4. トリガーの失敗通知を「今すぐ」にする(D方式・要承認)
1. Apps Script エディタの左の「トリガー」(時計の印)を開く
2. 次のトリガーについて、それぞれ鉛筆の印 →「エラー通知設定」で「**今すぐ通知を受け取る**」を選んで保存する
   - `processQueuedVoiceLogs`(毎分)
   - `syncCtiCallHistory`
   - `runDailyMaintenance`
   - `sendDailyReport`
3. 通知は、トリガーを作った人(台帳の持ち主)に届きます

**注意**: 自己修復(6時間ごと)やメニューの操作でトリガーが作り直されると、通知の設定は既定(1日1回)に戻ります。作り直したことが稼働状況タブに出たら、この設定をもう一度確かめてください。

## 知らせが来たら
- 「GLOW台帳 毎分の処理 is DOWN」というメールは、1時間以上、正常に終わった処理が無いという意味です
  - まず台帳の「稼働状況」タブと、Apps Script の「実行数」を見る
  - 承認切れ(「その操作を実行するには承認が必要です」)なら、台帳のメニュー「GLOW台帳 → 自動処理を復旧する(権限の再許可)」を押す(FK-008 と同じ)
- 信号が戻ると、healthchecks.io から「is UP」のメールが届きます

## 戻し方
- 信号を止める: スクリプトプロパティ `HEALTHCHECKS_PING_URL` を消す。コードは何もしなくなります。あわせて healthchecks.io のチェックを Pause にする(止めたことを知らせるメールが来ないように)
- コードごと戻す: 反映したPRを revert します。入口の名前 `processQueuedVoiceLogs` は変えていないので、トリガーを作り直す必要はありません

## 承知しておく危険
- 知らせが来るのは、止まってから最大で約2時間後です(60分ごとの信号+猶予1時間)。もっと早くしたいときは Period を短くする。ただし送る回数も増やす必要があり、コードの変更が要ります
- 自己点検や録音の受け付けなどが1時間以上続けて失敗すると、録音の処理そのものは動いていても知らせが来ます。これは狙いどおりの動きです
- Gemini の支払いエラーで録音の処理を待っている間も、信号は送ります。この状態は別に知らせているため、「処理が止まった」には数えません
- healthchecks.io が止まっていると、知らせが来ないことがあります。そのときも GitHub の点検と D方式のメールは残ります
