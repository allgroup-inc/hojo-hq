# 議事: スキル改善プロジェクト開始

**日時**: 2026-10-04  
**形式**: 三名体制レビュー (スイシン/ウタガイ/ベッカイ)  
**主題**: スキル改善プロジェクト開始承認及び実行方針確定  
**決定者**: 小柳さん  

---

## プロジェクト概要

**目的**: 沖縄企業のミカタ・もらいわすれ堂の品質向上を実現するため、15個のカスタムスキル改善と、全13リポジトリへの段階的配布

**スコープ**:
- 対象スキル数: 15個
- 実装期間: 4週間（第1段階: 基盤整備 / 第2段階: スキル改善 / 第3段階: ロールアウト）
- 改善後の拡大計画: カスタマイズ層10個へも段階展開

**3本柱**:
1. **手順化**: スキル改善の標準フロー化
2. **失敗通知**: 異常検知・自動起票の仕組み化
3. **ローカル検証**: 各リポジトリでのテスト実行の自動化

---

## スイシン（推進）の見解

### 強み・推進根拠

**KGI達成への必須性**  
LINE登録1,000社達成のボトルネック（SNS・LINE・提携部の品質不安定性）を15個スキルの改善で抜本的に解決。

**段階的ロールアウト方式の効率性**  
13リポジトリへの一括配布ではなく、段階的に`update-skills.sh`で同期することで、失敗時のリスク最小化と改善の並列化が実現可能。

**4週スケジュールの実現可能性**  
- 週1: 基盤（GitHub Actions・検証パイプライン・エラーハンドリング）
- 週2〜3: スキル改善の並行実装（週2本ペース）
- 週4: ロールアウト・運用体制の立上げ

カスタマイズ層10個への拡大もその先のロードマップとして位置付け可能。

**品質の一括向上**  
個別改修ではなく、全13リポジトリに統一基準を適用することで、hojo-lighthouse-triage等の監視スキルも機能向上する相乗効果あり。

## ウタガイ（懐疑・反対）の見解

### 反対理由と懸念点

**1. 4週スケジュール + 全リポテスト は急すぎないか**

- 実装: 4週間は体感的に「可能に見える」が、テスト・修正・再テストのサイクルが圧縮されている
- **懸念**: 検証部・守り部との並行作業の調整がつかない。特に第2段階で15個スキルを「週2本」実装しながら、各リポジトリで「全テスト」を回すのは実務レベルでは無理
- **提案**: マイルストーン・明示的な「責任者・対象リポ」のマトリックスが必要。スイシン案だけでは誰が何をいつまでにするのか不明確

**2. Gemini並行検証(マルチAI連携)による token コスト増加**

- 2026-08-06決裁で verify-sources型のサンプリング検証が承認済みだが、スキル改善でコード生成品質が上がれば確認件数も増える可能性
- **懸念**: ROI測定なしに運用開始した verify-sources がまだ軌道に乗っていない状況で、さらにコスト増を引き込むのは早すぎる
- **提案**: Gemini検証は改善前後の「品質比較」段階（4週の最終週）に限定し、本運用は見直し期限後に再検討してはどうか

**3. update-skills.sh 一括配布のロールバック対応が複雑**

- 13リポジトリへ同時に配布すると、1つのスキルファイルにバグがあれば全リポが影響
- **懸念**: 「週1の基盤整備」で自動化ガード(linter・構文チェック)を入れるというが、実際にはカスタマイズ層ごとに異なる要件がある(musubu.md等)。一括配布で全スキルに統一ガードを当てると、部門の工夫が潰される
- **提案**: 配布の「段階性」を明確に（第1段階: 3リポのみ本番 → 観察 → 残り10リポ）。且つロールバックのテスト(Git rollback + ワークフロー再実行)を事前に実行確認する

## ベッカイ（別解・前提を疑う）の見解

### 前提の再検討と代替案

**1. スキルの優先度は「作成順」ではなく「実装影響度」で再順位付けすべき**

- スイシン案では「15個スキル」と並列に並べているが、実装インパクトに差がある
- **別解**: 
  - Tier 1 (即座に影響): データ正確性に関わるもの(kensho.md等)・KPI計測(analytics関連)
  - Tier 2 (副次的): 情報公開・ガイダンス(humanizer等)
  - Tier 3 (最後): UI/UX最適化(review等)
  - 段階的に実装すれば、4週でも全15個は無理でも Tier 1・2を完全化できる

**2. Issue自動起票の「誰が・どこから」が不明確**

- 「失敗通知」で「GitHub Actions で Issue自動起票」と書いているが、起票者が「Bot」か「実行ユーザー」かで権限や通知ルートが変わる
- **別解**: 起票は「特定のサービスアカウント」に限定し、かつ起票対象を「システムエラー限定」にしないと、日常のエラーで Issue が溜まる
  - 例: 503エラーで Issue起票 → 翌日修復 → Issue は自動close されない → Issues が生ゴミ化

**3. ローカル検証は「各スキル独立テスト」か「13リポ統合テスト」かで負担が全く違う**

- スイシン案「ローカル検証の自動化」は曖昧。各スキル内で単体テストするのか、全13リポでの実装テストをするのか
- **別解**:
  - **各スキル内テスト** (推奨): スキルファイル自体の文法・ロジックチェック。所要時間: 数分 × 15個
  - **統合テスト**: 実際に13リポで skills command を実行。所要時間: 1時間 × 13リポ以上 。4週に詰め込めない
  - **折衷案**: Week 1-2 に各スキル内テスト + 3リポでの統合テスト。Week 3-4 で残り10リポのテスト

## 実装上の注意事項

1. **責任者とマトリックス** (Week 1 中に確定)
   - スキル名 / Tier / 担当者 / 対象リポ / テスト計画 の表を作成
   - 重複実装・漏れを防ぐため、統括(アカリさん)経由で整理

2. **マイルストーン報告** (毎週 木曜)
   - 進捗: 完成スキル数 / テスト完了数 / 配布済みリポ数
   - ボトルネック: テスト時間超過 / 統合テスト失敗 等を明文化
   - 見直し判断: 2週目末で「予定比 70% 以上」の達成見込みを評価

3. **ロールバック手順** (Week 1 中にテスト実施)
   ```
   git revert <commit> && git push
   ./update-skills.sh --sync-all  # スキルをロールバック版に統一
   ```

4. **Gemini 検証の実施タイミング**
   - 改善前: 対象スキル 3個をサンプリング
   - 改善後: 同じ 3個を改善版で再検証
   - 結果: 改善効果の「Claude vs Gemini」比較表を `docs/` に記録

5. **見直し期限後の対応**
   - 条件達成 → 残り Tier 2-3 への拡大を承認
   - 条件未達成 → スコープ削減または期間延長を小柳さんへ上申
