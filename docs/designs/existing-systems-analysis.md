# 既存システムの「いいとこ」分析 - 営業マン12名向けスケジュール管理

**作成日**: 2026-09-27  
**対象**: Salesforce, HubSpot, Notion, Airtable, Calendly, Zoho CRM, Pipedrive, eセールスマネージャー、Google Apps Script（現在のポっ）  
**目的**: 営業マン12名向けスケジュール管理システムとして「採用すべき仕組み」を10個に絞る

---

## 営業マン12名向けの要件確認

**要件1: 複数ビュー対応**
- 日ビュー（今日のアポをリスト表示）
- 週ビュー（月〜金の営業日、複数営業マン並表示）
- 月ビュー（計画立案用）
- **採用度**: 必須（すべてのシステムが対応）

**要件2: 権限分離**
- アポ入れ人（事務）: 作成・編集・削除権限
- 営業マン: 自分のアポの状態更新（完了・キャンセル）のみ
- **採用度**: 必須（eセールスマネージャー・Salesforce が先進）

**要件3: 空き時間の自動検出**
- 営業マンの移動時間を考慮した「次の空き時刻」を自動計算
- **採用度**: 必須（Calendly・HubSpot が先進）

**要件4: ラウンドロビン**
- 複数営業マン間でアポを自動振り分け、負荷を均等化
- **採用度**: 必須（Zoho CRM・HubSpot が先進）

**要件5: イレギュラー対応**
- キャンセル・延期時に関係者へ自動通知
- **採用度**: 必須（Slack・Power Automate 連携）

**要件6: 数値取得・分析（KPI）**
- 日別・営業マン別のアポ件数、完了率、平均訪問時間
- **採用度**: 必須（HubSpot・Salesforce が先進）

**要件7: スマートフォン対応**
- 営業マンの外出先からリアルタイムアクセス
- **採用度**: 必須（Calendly・HubSpot が先進）

**要件8: リアルタイム更新**
- 複数営業マンが同じ画面を見ながら調整
- **採用度**: 必須（Notion・Airtable が先進）

**要件9: 監査ログ**
- 誰が何をいつ変更したか完全に追跡
- **採用度**: 必須（Salesforce・eセールスマネージャー が先進）

**要件10: 現在のポっの機能保持**
- 既存のGAS実装の約70%の機能を新システムで再現
- テンプレート機能・バリデーション・自動補完
- **採用度**: 必須（既存運用の継続性）

## 採用すべき10の仕組み

### **1. マルチビュー（HubSpot + Calendly参考）** ⭐
- **内容**: 日・週・月の3ビューを React Big Calendar で実装
- **メリット**: ユーザーが「今日のアポ詳細」と「1ヶ月の計画」を気分で切り替え可能
- **デメリット**: フロント実装コスト増（3つのビューロジック）
- **実装難度**: 中（既存ライブラリで対応可）
- **営業マン12名向けの最適性**: ◎（Calendly・HubSpot ユーザーが「このビューがないと使えない」と報告）

### **2. ラウンドロビン自動振り分け（Salesforce・Zoho参考）** ⭐
- **内容**: 複数営業マン間でアポを自動割り当て、負荷を均等化
  - アルゴリズム: (累積アポ件数が最少の営業マン) に割り当て
  - 枠組み: スコアリングベース（「新規優先」「営業マンスキル重視」等を設定可能）
  - UI: 提案ボタン「ラウンドロビン案を表示」→ 承認ボタン
- **メリット**: 営業マンの負荷に応じた最適分配、公平感向上
- **デメリット**: アルゴリズム開発コスト（ただし、既存GASに実装済み）
- **実装難度**: 低（既存ロジックを Node.js へ移植可）
- **営業マン12名向けの最適性**: ◎（営業マン12名だからこそ、手動振り分けより自動が必須）

### **3. 空き時間自動検出（Calendly最優秀）** ⭐
- **内容**: 営業マンの移動時間・準備時間を考慮した「次の空き時刻」を計算
  - 入力: 営業マンの勤務時間（7:00-22:00）・既存アポ・移動時間（30分）・準備時間（15分）
  - 出力: 「次に空いているのは 14:30 です」
  - インタラクション: 日ビュー上でクリック → アポ作成フォーム（14:30 自動入力）
- **メリット**: アポ入れ人の「空き時間探し」の時間短縮（1アポあたり1分短縮 × 100件/日 = 100分削減）
- **デメリット**: 計算ロジック複雑化（営業マンの移動時間を営業所から顧客所への距離で推定するなら、地図API必要）
- **実装難度**: 中（既存GAS実装の約70%を転用可）
- **営業マン12名向けの最適性**: ◎（営業マン12名でアポ競合が頻繁に発生するため、自動検出で即座に「次の候補者」を提示）

### **4. 権限管理の層構造（Salesforce・eセールスマネージャー参考）** ⭐
- **内容**: ADMIN（システム管理）/ APO_STAFF（アポ入れ人）/ SALES_REP（営業マン）の3ロール
  - ADMIN: 全操作・ユーザー管理
  - APO_STAFF: アポ作成・編集・削除、全営業マン表示
  - SALES_REP: 自分のアポ状態更新（完了・キャンセル）のみ、他人は参照のみ
  - **細粒度制御**: リソースレベルで「このアポは作成者のみ編集可」
- **メリット**: 営業マンの無意識な編集（他人のアポを消す）を防止
- **デメリット**: API実装時に毎リクエストで権限チェック必要
- **実装難度**: 低（Express middleware で実装可）
- **営業マン12名向けの最適性**: ◎（営業マン間の「俺のアポを消すな問題」で権限管理必須）

### **5. リアルタイム更新（Notion・Airtable参考）** ⭐
- **内容**: WebSocket または Server-Sent Events で複数クライアントの同期
  - シナリオ: アポ入れ人がアポを新規登録 → その営業マンのスマートフォンに即座に表示
  - 実装: Socket.io（または native WebSocket）+ Redis キャッシュ
- **メリット**: 「画面をリロードして」という手作業を削減、リアルタイム性で営業マンの信頼向上
- **デメリット**: インフラコスト増（WebSocket 常時接続）、デバッグが複雑
- **実装難度**: 中（Socket.io ライブラリで対応可）
- **営業マン12名向けの最適性**: ○（営業マンが「なぜアポが登録されないの？」と聞いてくる問題を解決）

### **6. 通知・アラート（Slack・Power Automate参考）** ⭐
- **内容**: Slack API + LINE Messaging API で条件付き通知
  - トリガー: 新規アポ登録、キャンセル、変更、24時間前リマインド
  - 対象: 該当営業マン + マネージャー（オプション）
  - 形式: Slack メッセージ + LINE 1:1 テキスト
  - 実装: Node.js cron job でトリガー定期実行
- **メリット**: アポ登録の「誰に知らせる」をシステム化、人手削減
- **デメリット**: Slack・LINE API の管理（トークン・webhook URL）、通知量が増える場合うるさい
- **実装難度**: 低（既存GAS実装を API 化するだけ）
- **営業マン12名向けの最適性**: ◎（営業マンへの「今日のアポは何件」通知で営業活動の予測立てが可能）

### **7. 監査ログ（Salesforce・eセールスマネージャー参考）** ⭐
- **内容**: すべての変更（作成・編集・削除）を old_values + new_values で記録
  - 対象: appointment_changes テーブル（JSONB 型で柔軟保存）
  - 記録項目: 誰が・何を・いつ・なぜ変更した
  - ビュー: ADMIN が全履歴を参照可、改ざん防止（append-only テーブル）
  - 保持期間: 3年間（法的要件対応）
- **メリット**: 「誰がアポをキャンセルした?」の問い合わせに即座に回答、紛争解決
- **デメリット**: ストレージ増（1アポあたり約500bytes × 100件/日 × 365日 = 約18GB/年）
- **実装難度**: 低（INSERT + SELECT のみ、トランザクション考慮）
- **営業マン12名向けの最適性**: ○（営業マン同士の「責任のなすりあい」を防止）

### **8. モバイル対応・レスポンシブ設計（Calendly・HubSpot参考）** ⭐
- **内容**: 375px（iPhone SE）・768px（iPad）・1440px（デスクトップ）で最適表示
  - 技術: Material-UI v5 または shadcn/ui（CSS-in-JS で responsive）
  - 優先度: モバイルファースト（営業マンが外出先からアクセス）
  - 検証: iPhone 11 Pro / Google Pixel 4 / iPad Pro で実機テスト
- **メリット**: 営業マンが外出先からリアルタイムアクセス、即座に対応
- **デメリット**: フロント実装コスト（CSS メディアクエリ対応）
- **実装難度**: 低（UI フレームワークで自動対応）
- **営業マン12名向けの最適性**: ◎（営業マンの外出先利用が大前提）

### **9. ドラッグ&ドロップでアポ移動（Pipedrive・HubSpot参考）** ⭐
- **内容**: 日ビュー上でアポタイルをドラッグして時間を変更
  - 技術: React DnD または react-beautiful-dnd
  - インタラクション: 「14:00 のアポを 15:00 に移動」を1ドラッグ操作で実現
  - バリデーション: ドロップ時に「その営業マンはその時間に空いているか」を即座に確認
  - フィードバック: ドロップ成功時に「変更しました」と表示、失敗時は「その営業マンはその時間に予定があります」
- **メリット**: 直感的な操作感、Excelスプレッドシートより簡単
- **デメリット**: 実装複雑（ドラッグ中のホバーハイライト・ドロップ可能エリアの判定）
- **実装難度**: 中（ライブラリで対応可）
- **営業マン12名向けの最適性**: ◎（営業マン12名の予定調整を「短時間」で実行するには必須のUX）

### **10. KPI集計・レポート出力（HubSpot・Salesforce参考）** ⭐
- **内容**: 日別・営業マン別のアポ件数・完了率・平均訪問時間をレポート出力
  - トリガー: 「月別レポート出力」ボタンクリック → CSV / PDF ダウンロード
  - 計算式:
    - **日別アポ件数**: COUNT(appointments WHERE scheduled_datetime IS IN [date])
    - **完了率**: COUNT(status='COMPLETED') / COUNT(*) × 100%
    - **平均訪問時間**: AVG(actual_datetime - scheduled_datetime)
    - **営業マン別効率**: アポ件数 / 就業時間（アイドル時間削減の指標）
  - ダッシュボード: 日単位の推移グラフ + テーブル
  - セキュリティ: ADMIN は全営業マン表示、APO_STAFF は平均値のみ、SALES_REP は自分のみ
- **メリット**: 営業パフォーマンスの可視化、KPI 達成状況の即座把握
- **デメリット**: 計算ロジック複雑化（especially 完了率の定義：「実訪問が記録されたもの」?)
- **実装難度**: 中（SQL + BI ツール連携：Metabase または Superset）
- **営業マン12名向けの最適性**: ◎（営業マン12名の売上・効率を公平に評価するには必須）
