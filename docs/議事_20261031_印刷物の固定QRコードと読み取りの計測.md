# 議事 2026-10-31 印刷物の固定QRコードと読み取りの計測

- 起案: ❶システム関係全般(本セッション)
- 決裁: 小柳さん(2026-10-30「福田からメールが来てます。対応してください」→ 福田さんの確認事項④への対応。2026-10-31「QRコードをスマホで読めるかの確認…自動で対応して完了させてください」)
- 区分: ①掲載方針(新しい導線の追加)
- 実装: PR #546(QR・中継ページ・週次レポ欄)、#554(毎日の点検)

## 背景
- 福田さんから(10/30 メール): チラシ・QRスタンド・企業説明で使う、各サイト・SNSの固定QRはあるか。QRを固定にすると、QRからの流入はどこでわかるのか。
- 対象: 沖縄企業のミカタ(サイト・LINE公式)、ゆんたく経営相談室、世界の架け橋、Instagram、Facebook。

## 論点: 固定QRをどう作り、流入をどう数えるか

### スイシン(推進)
- QRは行き先を直接指さず、`/go/<チャネル>/` の中継ページを指す。中継ページがGA4にイベントを送ってから転送する。
  - 行き先が変わっても、印刷したQRはそのまま使える(`scripts/generate_go_pages.py` の転送先を変えるだけ)。
  - チャネルごとに読み取り回数を数えられる。
- LINE以外へ転送するQR(サイト・ゆんたく・世界の架け橋・Instagram・Facebook)は、イベント名を `qr_redirect` にする。ミカタのLINEへのQRは既存の `/go/card/`(紙配布)を使う。
- 週次レポに「固定QRの読み取り(LINE以外)」を別欄で出す。
- QR画像と中継ページが配信されているかを、毎日の点検(`scripts/healthcheck.py`)で確かめる。

### ウタガイ(懐疑)
- **LINE以外へ送るQRは、CV単一(絶対ルール4: 導線はLINE登録のみ)に反しないか。**
  → QRは新しいCV(申込・購入)を足すものではなく、既存のサイト・SNSへの入口。サイト側のCVはLINE登録のまま。LINE登録に数えないよう、イベント名を `line_redirect` から分けた(CLAUDE.md 再発防止メモ: 導線クリックと完了を同じイベント名で数えない)。
- **ゆんたく経営相談室・世界の架け橋は、他のチャット(❸・❻)の担当。** 向こうで別のQRを作ると、同じ用途のQRが2種類出回り、数字が割れる。
  → 連携メモで知らせる(docs/連携メモ_20261031_固定QRコードとメールでの案内.md)。用途別に分けたいときは、❶へ依頼してチャネルを足す。
- **中継ページを挟むと、表示が一瞬遅れる。** スキャン後に転送されず離脱する人が出る。
  → 既存の /go/ と同じく、計測が遅れても0.4秒で必ず転送する(計測より転送を優先)。
- **用途(チラシ・スタンド・企業説明)ごとの回数は分からない。**
  → 今回は行き先ごとに1枚。福田さんは「流入経路が増えたら追加で依頼する」と回答済み。

### ベッカイ(別解)
- 各サイトのURLにutmを付けて、そのままQRにする案。中継ページが無いので速いが、行き先を変えると印刷物を刷り直すことになり、SNSのようにutmを数えられない行き先もあるため採らない。
- 外部のQR作成サービス(動的QR)を使う案。計測が外部サービスに分かれ、有料化や終了のリスクがあるため採らない。

### 結論(裁定)
- 採否: 採用。
- 実装の内容:
  - `scripts/generate_go_pages.py` にチャネル qr-mikata・qr-yuntaku・qr-world・qr-ig・qr-fb を追加(event: `qr_redirect`)。
  - QR画像は `site/assets/qr/*.png`(作り直しは `scripts/generate_go_qr.py`)。
  - 週次レポは `scripts/weekly_report.py`、毎日の点検は `scripts/healthcheck.py` の `check_fixed_qr`。
- 確認: 6枚ともQRを読み取ると正しい中継ページを指すこと、公開サイトで画像と中継ページが取れることを確認した(2026-10-31 点検で全件OK)。実機のスマホでの読み取りは未確認(機械では代われない)。
- 見直し期限: 2027-04-30(読み取り回数と、用途別QRの要否を見て再評価)。
