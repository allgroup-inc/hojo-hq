## 論点①: 管理本部連携システムに着手すべきか(資源配分)

営業が獲得した後に管理本部が対応している業務を棚卸しし、自動化するシステムを作る件。

### スイシン(推進)

- CLAUDE.mdの4本柱で、②営業管理システム(glow-ma)は「将来的に4つすべての顧客を一元管理する計画」と明記済み。管理本部連携はその延長線上にあり、憲法と矛盾しない。
- 真のKPI(出口への相談・面談転換 月10件)が動き出した瞬間、獲得後の処理が人手のままだと管理本部がボトルネックになる。詰まってから作ると、詰まっている間の機会損失がそのまま出る。
- `docs/組織_現在地.md` は真の制約を「意思決定レイテンシと**人間実行**」と裁定している。管理本部の定型作業が小柳さんの時間を食っているなら、それを自動化した分だけKGI側に時間が還る。間接的にKGIへ効く。
- 棚卸しそのものは低コスト(実案件1件を獲得から完了まで追跡するだけ)。棚卸しで止めて、構築するかは後から決められる。

### ウタガイ(懐疑)

- **LINE友だち数8人**(2026-08-15実測)。1,000社目標の0.8%。公開から24日で8人なので、このペースの単純外挿は12ヶ月で約120社。**目標未達が確定的に近い状態**。この局面で新システムを起こすのは、数字が動かない苦しさから「作れる仕事」に逃げる典型パターンに見える。
- 管理本部の自動化は獲得が増えてから効くもの。獲得がほぼゼロの今は**処理する案件が存在せず、効果測定すらできない**。
- `docs/組織_現在地.md` は「**この数字が動き出すまでは、他の施策より北極星の開通を最優先すること**」と明示的に裁定している。本件はその裁定の上書き提案であり、上書きの根拠が「将来詰まるから」では弱い。
- 既に「作ったが決裁されず動いていない在庫」がある(`docs/決裁キュー.md`: 商品設計5件・note収益3軸・Kindle白書・ノビシロ掲載承認)。在庫が捌けていない状態で作るものを増やすのは、在庫を積むだけ。
- 前段のglow-ma自体、Phase 18bまで作りながら7000件リストの実投入が未完。**前段が動いていないのに後段を作る**という順序の問題がある。

### ベッカイ(別解・前提を疑う)

- そもそも「システムを構築する」が答えかを疑う。管理本部の業務が月に何件発生しているのか、誰も数字を持っていない。月3件なら自動化の投資対効果はマイナスになる。
- **別解A: 棚卸しだけやって、システムは作らない。** 結果が「チェックリスト1枚」で足りる可能性は十分ある。紙1枚で回るものをシステム化するのは過剰。
- **別解B: 問いを立て直す。** 「管理本部の効率化」ではなく「**獲得後の事務が、営業の新規開拓時間をどれだけ奪っているか**」を問う。奪っているなら、それはKGI直結の課題になり北極星と衝突しない。同じ棚卸し作業で、得られる答えの価値が変わる。
- **別解C: 統合先を決めるのが先。** 4本柱の一元管理という将来像に対し、既に glow-ma がある。管理本部連携を単体で起こすと3つ目の別システムになり、統合先未定のまま作るのは負債。

### 結論(裁定案)

- **採否: 条件付き着手 — 棚卸しのみGO、システム構築は保留(小柳さんへ上申)**
- 理由: ウタガイの「処理する案件がゼロ」「在庫が捌けていない」は事実であり重い。一方、ベッカイBの問い直しは北極星と衝突せず、むしろKGIに効く可能性がある。棚卸しは低コストで、結果が「紙1枚で足りる」なら構築せずに終われる。**作らずに済む可能性を残したまま調べられる**のが決め手。
- 実行条件:
  1. 棚卸しの問いを「自動化対象の洗い出し」ではなく「**獲得後の事務が営業の新規開拓時間をどれだけ奪っているか**」に設定する
  2. 方法は口頭ヒアリングではなく、**直近の実案件1件を獲得から完了まで実物(メール・チャット・シート・紙)で追跡**する(`log-analysis-playbook`)
  3. 月あたりの発生件数を必ず数える(件数が出ないなら構築判断はできない)
  4. 棚卸し結果を見て、システム化の要否を改めて三名体制で裁定する
- 上申事項: 棚卸し実施のGO、および「北極星最優先」裁定との関係の確認
- 見直し期限: 2026-09-17(棚卸し完了時点で再議論)

## 論点②: 三名体制の議事なしで決定したglow-ma案件4本の扱い

対象4本(いずれも「ウタガイ」の記載ゼロ、ペアとなるtriangle-reviewファイルなし):

- `docs/superpowers/specs/2026-08-09-glow-ma-partner-development-design.md`
- `docs/superpowers/specs/2026-08-09-glow-ma-partner-pipeline-view-design.md`
- `docs/superpowers/specs/2026-08-13-glow-ma-admin-console-v2-design.md`
- `docs/superpowers/specs/2026-08-13-glow-ma-letter-qr-fulfillment-design.md`

規程3は「ウタガイ役の反対理由が記録されていない議事は無効(結論ごと差し戻し)」。

### スイシン(推進 — 遡及して議事を作る)

- 書いてあるルールを運用しないなら規程が形骸化する。規程3を適用し、4本の議事を今から作成して記録を揃える。
- 4本とも実装済みで動いているため、記録を足すだけなら実務への影響がない。

### ウタガイ(懐疑)

- **実装完了後に書くウタガイは、結論を知った上での後付け**であり、本来の機能(実装前に止める)を一切果たさない。形式だけ整って中身が空になる。
- それは「議事はあるが機能していない」という**より悪い前例**を作る。規程6が警戒する「視点の同化」の、さらに退化した状態。
- 規程どおり差し戻すなら、既に動いている機能を止めることになる。コストが効果に見合わない。
- そもそも4本が「悪い決定だった」証拠は無い。**議事が無いことと、決定が間違っていることは別**。混同すると、記録の不備を実装の不備として処理することになる。

### ベッカイ(別解・前提を疑う)

- 問題の所在が違う。過去4本ではなく、**8/06までは3本すべて通っていた議事が8/09以降ゼロになった、その原因**のほうが問題。原因を潰さずに過去分だけ処理しても再発する。これはニドナシ機構(fukabori=真因)の担当領域。
- 真因の仮説: **議事が重い**。glow-maの実装が加速した時期と一致しており、「急ぐと省略される」形式は形式のほうに問題がある。だとすれば軽量版(3行でよい)を用意するのが対処になる。
- 規程3の「無効」の解釈自体に見直し余地がある。**実装前**の議事欠落は差し戻し、**実装後**に発覚した場合は「欠落の記録+再発防止」で足りる、と条件を分けるほうが実務に合う。

### 結論(裁定案)

- **採否: スイシン案は不採用(遡及作成しない)/ 代替措置を採用**
- 理由: ウタガイの「後付けウタガイは機能を果たさず、形骸化の前例を作る」が決定的。記録を揃えることが目的化して、規程の趣旨(実装前に止める)を損なう。ベッカイの真因指摘のほうが再発防止に効く。
- 代替措置:
  - (a) 4本の設計書に「三名体制の議事なしで決定(2026-08-17の点検で検出)」と1行追記し、**改竄せず事実を残す**
  - (b) 議事の軽量版フォーマット(3役×各1行でも有効とする)を用意し、「重いから省略」の逃げ道を塞ぐ
  - (c) ニドナシ機構(fukabori)に、8/09以降の議事欠落の真因分析を依頼する
  - (d) 規程3に実装前/実装後の条件分けを入れるかは、(c)の結果を見て判断
- 上申事項: (a)〜(c)の実施可否、および(d)の規程改訂の要否
- 見直し期限: 2026-11-17

## 論点③: スキル・コマンドの自発適用ルールと、38コマンドの本店配置

2026-08-17の点検で `CLAUDE.md` に「スキル・コマンドの運用」節を追加し、`scripts/update-skills.sh` に配布経路を足した件の是非。

### スイシン(推進)

- 95スキルを vendoring しながら、憲法にはスキルの語が1つも無かった。**使用規定が無ければ使われない**。今回追加した場面別表は既存の絶対ルールと矛盾しない範囲に留めている(広告系は絶対ルール4により明示的に除外)。
- コマンドの配布経路がそもそも存在しなかった(`update-skills.sh` は `.claude/skills` のみ同期)。経路の追加自体は、本店に実体が無い間は完全なno-opでリスクがない。
- `ALLGROUP_SKILL_NAMES` の配列漏れ(go-link-discipline / explainer-video-production)は**バグ**であり、意思決定ではない。放置すると再実行しても永久に配られない。

### ウタガイ(懐疑)

- 「場面に合致したら自発適用」は**運用が難しく、検証もできない**。合致の判定が主観なので、実務が変わらないまま「使わなかった」を後から責める材料が増えるだけになりうる。
- 表に10場面を書いたが、全部通すと1作業あたりのオーバーヘッドが跳ね上がる。特に対外文面は日次生成しており、**humanizerを毎回通すコストを検証していない**。
- 38コマンドの中身を1つも確認していない。**中身を見ずに配布経路を作ったのは順序が逆**。このリポジトリの絶対ルールと衝突するもの(広告系・LINE以外のCV誘導)が混ざっている可能性がある。
- 最大の問題: **CLAUDE.mdへの追記を、この三名体制を通す前に実行した**。手順違反であり、本議事は事後承認を求める形になっている。憲法の改訂こそ議事を先に置くべきだった。

### ベッカイ(別解・前提を疑う)

- 「自発適用」(人の意識に頼る)より「**特定の成果物には必ず通す**」というゲート方式のほうが検証可能。例: 対外文面を含むPRには humanizer 適用済みのチェックを入れ、CIで担保する。意識ではなく仕組みで守る。
- 場面表を憲法(CLAUDE.md)本体に置くべきかも論点。**憲法は長くなるほど読まれなくなる**。別ファイルに出して憲法からは1行参照にする選択肢がある。
- 38コマンドは全部要るのか。既存95スキルと機能が重複するものは、選択肢を増やして判断を遅くするだけになる。**配る前に取捨選択**すべき。

### 結論(裁定案)

- **採否: 一部採用・一部保留・1点は手順違反として自認**
- 採用(実施済み・意思決定を含まないため):
  - `update-skills.sh` の配列漏れ修正(バグ修正)
  - `.claude/commands` の同期機構追加(本店に実体が無い間はno-op、既存を消さない実装)
  - Lighthouse自動起票Issueへの `hojo-lighthouse-triage` 導線追記
- 保留・要検証: **場面別表の「自発適用」ルール**。ウタガイの「実効性未検証」が正当。1ヶ月運用し、実際に適用された/されなかった件数を記録する。機能していなければベッカイのゲート方式(CIで担保)に切り替える。
- 手順違反の自認: CLAUDE.md追記を議事より先に実行した。**以後、憲法の改訂は必ず議事を先に置く**。今回分は事後承認をお願いする形になる。
- 上申事項:
  1. CLAUDE.md「スキル・コマンドの運用」節の事後承認(不承認なら差し戻す)
  2. **38カスタムコマンドの実体の所在**。中身を確認せずに配布はしない(ウタガイ指摘を採用)
  3. go-link-discipline / explainer-video-production の実体も本店(hojo-hq)に未配置。配置元の確認
- 見直し期限: 2026-09-17(1ヶ月運用後に実効性を再議論)
