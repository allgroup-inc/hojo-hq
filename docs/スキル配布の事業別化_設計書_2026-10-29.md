## 3. 目的と範囲

- **目的**: ある事業専用のスキルが、別の事業のリポジトリに届かないようにする。そのうえで、承認された共通スキルだけを全事業で使い回せるようにする。
- **範囲外**: 各リポジトリが自分で持つスキルの中身、`.claude/settings.json`・hook・CI、Superpowers・marketingskills の外部スキルの中身(配る先の選び方だけを扱う)。

## 4. 新しい配り方の設計

### 4-1. 配布台帳(1枚)

hojo-hq に **配布台帳** を1つ置きます(置き場所の案: `skills/配布台帳.json`)。書く項目は次のとおりです。

**リポジトリの一覧**: リポジトリ名 / 事業(ミカタ・フクギイロ・GLOW・保険・SKL・hikari など)/ 公開か非公開か

**スキルの一覧**: スキル名 / 区分(共通 / 事業専用 / 配らない)/ 持ち主の事業 / 配ってよい事業 / 承認した人 / 承認日 / 理由 / 取り消した日(取り消したときだけ)

### 4-2. 配る判断(決まりは3つ)

1. **台帳に載っていないスキルは配らない**(載せ忘れは「配られない」側に倒す)
2. **「共通」は全事業へ配る。「事業専用」は、配ってよい事業のリポジトリにだけ配る**
3. **事業がわからないリポジトリには、共通スキルも配らない**(台帳にリポジトリを登録してから配る)

### 4-3. 配る前の検査(採用済みの #23 をここに組み込む)

配布のたびに、次の順で検査します。1つでも引っかかれば、そのスキルは配らず、理由を報告します(全体は止めない。議事 2026-10-06 のウタガイ③「誤検知1件で全部止まる」への対策)。

1. スキルの形式の検査(既存の `tests/skill_validation`)
2. 公開範囲の検査(既存の `scripts/check_repo_scope.py`。家計側のシステムの言葉)
3. **事業の混入検査(新規)**: 配布先と違う事業の言葉(事業名・サービス名・担当者の名前)が本文にあれば止める。言葉の一覧は、禁止語の書き方の決まりにならい **一覧のファイルを参照する** 形にして、文書には実際の語を書かない
4. 秘密情報らしい文字列の検査

### 4-4. 取り消し

- 台帳で「取り消した日」を入れると、次の配布で **そのスキルを配布先から消します**。
- 消してよいのは **台帳に載っていて、この仕組みが配ったもの** だけです。配布先リポジトリが自分で作ったスキルには触れません(名前が台帳に無いものは消さない)。

### 4-5. 配布先への反映の仕方

- いまは配布先の main へ直接 push しています。これを **配布先ごとにブランチを作って PR を出す** 形に変えることを提案します。
  - 長所: 配布先の持ち主が中身を見てから取り込める。履歴が残る。間違えても PR を閉じれば済む
  - 短所: 取り込みの手間が配布先ごとに増える
- 折衷案として、**共通スキルの「中身の更新」だけは直接 push、「新しいスキルの追加・事業専用の配布・削除」は PR** にする案もあります(9章で決裁をお願いします)。

### 4-6. 応答スタイルのコマンド(38個)

- いまは全部が一般的な内容なので、**共通** として台帳に1行で載せます。
- フォルダごと上書きする今の作りは、配布先に固有のコマンドがあると消してしまいます。**台帳に載っている名前のファイルだけを置き換える** 形に変えます。

## 6. 三名体制での検討(この設計を採用するかどうか)

- **スイシン(推進)**: 台帳を1枚置くだけで、事業専用のスキルが別事業へ行く道を止められる。採用済みの検査(#23)も同じ場所に組み込めるので、手間が1回で済む。自動配布が止まっている今が、作り直しの最も安全な時期。
- **ウタガイ(懐疑・反対理由)**:
  1. 台帳の手入れを怠ると、新しいスキルが「どこにも配られない」まま放置される。配られないことに誰も気づかない(静かな失敗)
  2. 事業の混入検査の言葉の一覧が古くなると、新しい事業(例: 世界の架け橋)の言葉を見落とす
  3. PR 方式にすると、13リポジトリぶんの取り込み待ちが溜まり、結局だれも取り込まなくなるおそれがある
  4. すでに配られた事業専用スキルの片付け(配布先からの削除)は、配布先の作業中のセッションに影響しうる
- **ベッカイ(別の案・前提を疑う)**: そもそも「本店から配る」をやめ、各事業が共通スキル置き場から **必要なものを自分で取りに行く** 形もある。配る側の台帳がいらなくなる代わりに、古い版が使われ続けやすい。また、事業専用スキルは本店の hojo-hq ではなく **その事業のリポジトリ自身** に置けば、そもそも配布の対象にならない。

**裁定(案)**: 台帳方式を採用する。ウタガイ①には「台帳に無いスキルの一覧を毎回の配布結果に必ず出す」、②には「事業の言葉の一覧を台帳と同じ PR で更新する決まり」、③には 4-5 の折衷案、④には「片付けは事業ごとに PR を出し、持ち主の取り込みを待つ」で答える。ベッカイの「事業専用スキルは自分の事業のリポジトリに置く」は、90日の分離計画で GLOW 営業管理のコードを移すときに合わせて行う。
→ 配布のルールそのものを変えるため、実装の前に `docs/議事/` へ議事として正式に残す(CLAUDE.md 三名体制ルール8の②)。

## 8. 試験(設計のみ・まだ実行しない)

テスト用に、架空の事業 X・Y のリポジトリ(合成データのみ)を使います。

**通るべき試験**
1. 共通スキルは X と Y の両方に届く
2. X 専用のスキルは X にだけ届き、Y には届かない
3. 台帳で取り消したスキルは、次の配布で X から消える。X が自分で作ったスキルは残る

**止まるべき試験**
1. 台帳に載っていないスキル → 配られず、「未登録」として報告される
2. Y の言葉を含む X 専用スキル → 事業の混入検査で止まる
3. 事業が登録されていないリポジトリ → 何も配られない
4. 禁止語を含む共通スキル → そのスキルだけ止まり、他のスキルは配られる
5. 実体の無いスキル(go-link-discipline のような)→ 「実体なし」と報告される
6. 秘密情報に似せたダミーの文字列 → 止まる

**検査そのものの試験**: 検査をわざと壊した写し(メモリ上の文字列)に当てて、落ちることを確かめる(kakei-crm 再発防止メモ 2026-10-16 の決まりにならい、本物のファイルは書き換えない)。
