# アポ管理アプリ 指示プロンプト設計ガイド(2026-08-14)

対象: 対面営業メンバー+アポ入れ(インサイドセールス)メンバーが、アポ連携・申込み連携・急な変更・
前アポ長引きによる後ろ倒し・イレギュラーを全員で管理できるアプリを作りたい、という小柳さんの構想。
このファイルは「そのアプリをAIに作らせるとき、どう指示を出すか」のガイド+コピペ用プロンプト。

三名体制議事は末尾。決裁が要る2点は docs/決裁キュー.md に追加済み。

---

## 1. 結論: 「アプリ作って」と一発で言わない。3段階で指示する

| 段階 | 指示の目的 | 出すプロンプト |
|---|---|---|
| 第1弾 | 要件のすり合わせ(質問させる) | §3のプロンプトA |
| 第2弾 | MVP(最小版)の実装 | §4のプロンプトB |
| 第3弾 | 使ってみた不満を1つずつ直す | 「実際に使ったら○○が困った。直して」でよい |

理由: アポ管理は「急な変更」「イレギュラー」が本体。最初に全部を仕様化するのは不可能で、
一発指示だとAIが勝手に前提を埋めて、現場が使わないアプリができる。
まず質問させ、小さく作り、現場の声で直すのが最短。

## 2. 指示に必ず入れる7要素(これが抜けると手戻りする)

1. **誰が使うか**: 人数・役割(アポ入れ係○名/対面営業○名)・PC or スマホどちらで見るか
2. **場面(ユースケース)**: 箇条書きで具体的に。「アポが取れたら営業に渡す」ではなく
   「アポ入れ係が電話でアポ獲得→日時・企業名・温度感を登録→担当営業のスマホに即通知」まで書く
3. **絶対要件(Must)と、あったら嬉しい(Nice)を分ける**: Mustは5個まで
4. **やらないこと(Non-goals)**: 例「顧客管理(CRM)は作らない=glow-ma台帳側の仕事」
   「給与・評価への利用はしない」
5. **データとPIIの扱い**: 企業名・担当者名・電話番号は個人情報。
   **公開リポジトリ(hojo-hq)には実データを一切入れない**。glow-ma方式
   (実データはスプレッドシート/コードだけリポジトリ)を指定する
6. **技術と既存資産の指定**: ゼロから作らせない。glow-ma(スプレッドシート+GAS+Slack/LINE通知+
   Web管理画面Phase 18a)と同じ構成を土台に、と明示する
7. **完成の定義(受け入れ条件)**: 「アポ登録→担当営業への通知→変更→再通知が、
   スマホだけで1分以内にできたら合格」のように動作で書く

## 3. プロンプトA(第1弾・要件すり合わせ用/コピペ可)

```
営業アポ管理の仕組みを作りたい。ただし実装はまだしないこと。
まず brainstorming スキルを使い、要件を確定させるための質問を私にすること。

背景:
- アポ入れ担当が日々アポを獲得し、対面営業の担当に連携している
- 困りごと: ①アポ連携が口頭・チャットでバラバラ ②申込み(成約)の連携漏れ
  ③お客様都合の急な日時変更 ④営業の前アポが長引いて後ろの予定がずれる
  ⑤ダブルブッキング等のイレギュラー。これらを全員が同じ画面で見たい

制約(必ず守る):
- 実データ(企業名・担当者名・電話番号)は公開リポジトリに入れない。glow-ma方式
  (データはスプレッドシート、コードのみリポジトリ)を土台にする
- 既存の glow-ma(スプレッドシート+GAS+Slack通知+Web管理画面)と将来つながる設計にする
- 通知は現場が今使っているチャネルに出す(チャネルは私に確認すること)

質問は「これが決まらないと作れない」順に5個以内。私の回答後、
Must要件5個以内のMVP案を三名体制(ウタガイ反対必須)でレビューして提案すること。
```

## 4. プロンプトB(第2弾・実装指示用テンプレ/【 】を埋めて使う)

```
プロンプトAで合意したMVPを実装すること。

利用者: アポ入れ係【○】名+対面営業【○】名。営業は外出先スマホ閲覧が主
Must(この5個だけ):
1. アポ登録(日時・企業名・場所orオンライン・温度感・メモ)→担当営業へ即通知
2. ステータス管理(予定/確定/実施済/申込み/キャンセル/日時変更)。変更履歴が残ること
3. 「遅れそう」ボタン: 営業が前アポ長引きをワンタップ報告→後続アポの関係者へ自動通知
4. 当日の全員分アポ一覧(誰が・いつ・どこで・ステータス)を1画面で
5. 申込み(成約)になったら【glow-ma対応履歴/担当者】へ連携される

Non-goals: 顧客マスタ管理(glow-ma側)・数値評価/人事利用・外部公開
データ: 実データはスプレッドシートのみ。リポジトリにはコードとダミーデータだけ
通知チャネル: 【Slack / LINE WORKS / LINE公式 ○○】
受け入れ条件: 登録→通知→変更→再通知がスマホで1分以内。self-test必須、
UIはスクリーンショット目視確認。完了したらセットアップ手順書を docs/ に残すこと
```

## 5. イレギュラー要件の書き方のコツ

「イレギュラーに対応して」では作れない。**起きること→誰が→何をしたら→誰に何が届く**の形で書く。

- 前アポ長引き: 「営業が『30分遅れ』を押す→次のアポのアポ入れ係と(登録があれば)顧客連絡担当に通知が届く」
- 当日キャンセル: 「ステータスをキャンセルにする→理由を1つ選ぶ(顧客都合/こちら都合/再調整中)→枠が空きとして一覧に出る」
- ダブルブッキング: 「同じ営業に時間帯が重なるアポを登録しようとしたら警告を出す(登録は止めない)」

## 6. 三名体制議事

### 論点: アポ管理アプリを新規に作らせるべきか。作るならどう指示するか

### スイシン(推進)
- 連携漏れ・急な変更は失注に直結。全員が同じ一覧を見る仕組みの価値は明確
- glow-maの資産(スプレッドシート+GAS+通知+Web画面)を土台にすれば、開発も運用も既存パターンの流用で速い
- 指示は3段階(質問→MVP→改善)にすれば手戻りが最小

### ウタガイ(懐疑)  ← 空欄不可
- **新アプリはglow-maと二重管理になる恐れ**。企業・担当・履歴が2か所に分かれたら連携漏れはむしろ悪化する。CLAUDE.mdの計画(顧客はglow-maで一元管理)と矛盾しかねない
- **現場が使わないリスク**が最大。営業メンバーが移動中に入力してくれなければただの置物。Googleカレンダー+チャットの運用ルール整備だけで足りる可能性がある
- アポ情報は企業名・担当者名を含む**個人情報**。公開リポジトリのhojo-hqに実データが混入する事故が最も怖い(過去にPII非コミットを繰り返し明文化している事業)
- 「遅れそう」通知は顧客への連絡まで自動化すると誤送信リスク。社内通知に留めるべき

### ベッカイ(別解)
- そもそも「アプリ」ではなく**glow-maの新Phase(アポ管理タブ+通知)として増築**すれば、二重管理問題が消え、将来の一元管理計画とも一致する。これを第1候補にすべき
- もう1つの別解: 作る前に1週間、**スプレッドシート手運用**(共有シート1枚+固定書式のチャット連携)で回し、本当に困る点だけをMVP要件にする。要件が実地で採れる

### 結論(部門長の裁定)
- 採否: **採用(指示ガイドとして)**。ただし実装の置き場所は「独立アプリ」と決めつけず、
  **glow-ma増築を第1候補**としてプロンプトAの質問段階で検討させる(ベッカイ採用)。
  実データのリポジトリ非コミット・顧客向け自動連絡は当面やらない(ウタガイ採用)
- 理由: 課題の実在は明確(スイシン)だが、二重管理と現場定着がリスクの本丸(ウタガイ)。
  段階指示+既存資産流用なら両立できる
- 見直し期限: 2027-02-14(最長6ヶ月。MVP稼働後は利用実績で再議論)

## 7. 決裁が要るもの(決裁キューに追加済み)

1. アポ管理の置き場所: glow-ma増築(推奨)か独立アプリか
2. 通知チャネルの確定(Slack/LINE WORKS/LINE公式 等、現場が毎日見るもの)
