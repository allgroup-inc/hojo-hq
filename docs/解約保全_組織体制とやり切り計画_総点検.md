## 0. このチャットの目標(KGI/KPI)を先に定義する

「システムを作る」が目的ではなく、**早期解約を減らし継続率を上げる**が目的。ゼロベース見直しの前に、測る対象を明確化する。

**KGI(最重要目標):** 保険等の契約の **早期解約率(申込から6ヶ月以内)を下げ、継続率を上げる**。
- 具体目標(実データのベースライン確定後に数値を確定): 例)早期解約率をベースライン比 **▲X%**、13ヶ月継続率 **+Y pt**。

**KPI(支持指標):**
| KPI | 目安(実データで較正) |
|---|---|
| モデルの当たり(バックテストAUC) | **≥ 0.65** で本番投入可(< 0.5 は不可) |
| 高リスク先への保全接触率 | **100%**(要フォローの放置ゼロ) |
| 保全の効果(実施群 vs 非実施群の早期解約率差) | **有意にマイナス**(効いている) |
| データ鮮度 | 別システム書き出しの取込遅延 短く保つ |
| セキュリティ事故 | **ゼロ**(PII誤コミット・漏えい) |

> ※ 業界ベンチマーク(13ヶ月継続率・早期失効率の水準)はリサーチ結果を反映して確定する(本書末尾「業界エビデンス」)。

## 1. 体制のゼロベース見直し(三名体制・ウタガイ必須)

### 現状の体制(これまで設計したもの)
最高統括QCM → 実務統括ミマモリ → 3部門(データ基盤ソナエ/分析モデルミトオシ/保全運用テアツ)＋独立監査(テキホウ/ダトウ/コウヘイ)＋セキュリティ運営体制。各部門に専門家3名の壁打ち。

### 論点: この体制で「早期解約を減らす」を100%達成できるか?

**スイシン(推進):**
- データ→モデル→採点→保全→監査→セキュリティまで役割が網羅され、システムを"作る"体制としては充実。専門家壁打ちで品質も担保。三名体制で意思決定の質も確保。

**ウタガイ(懐疑・反対)** ← 空欄不可:
- **致命的な穴①: 「保全を実際に実行する人」の当事者が不在。** 体制の大半が"作る/分析する/監査する"役で、**高リスク先に実際に電話・案内する現場の実行オーナー**が定義されていない。システムは「誰に手厚くするか」を出すが、**それを毎日実行し、継続率で評価される人**がいなければ、ただのダッシュボードで終わる。目標(解約を減らす)は"実行"でしか達成されない。
- **致命的な穴②: データ供給の責任者が不在。** 別システムからの書き出し(申込・接触履歴・保全実施フラグ)を**誰が・いつ・どの品質で**渡すかのオーナーがいない。データが止まれば全部止まる。
- **致命的な穴③: 効果検証と学習ループの回し手が不在。** 月次で効果測定→改善→再投入を回す当事者と定例がない。分析役はいるが「回す人」が未定義。
- **構造の歪み: 作りすぎ・回し不足。** 精緻な部門・専門家を並べたが、まだ導入前・小規模の実態(現場推進はたかしくん、決裁は小柳さん)に対し、**役職の数が実行力に見合っていない**。役割図の厚さ=実行力ではない。
- **人間へのマッピング欠如。** 架空エージェント体制が、実在の責任者(たかしくん=現場推進、嶺井さん=公庫/保険知見、小柳さん=決裁)にひも付いていないと"体制ごっこ"になる。

**ベッカイ(別解):**
- 部門を増やすのではなく、**「解約保全スクワッド」= 単一責任者(single-threaded owner)を数名だけ置く**最小構成に畳む。①データ供給 ②モデル品質 ③保全実行(現場) ④セキュリティ/守り ⑤効果検証、の5オーナーを名指しで置き、各に実在の人間をマッピング。精緻な専門家群は"壁打ち助言"に格下げし、**意思決定の当事者は少数・名指し**にする。規模に合わせる(2人会社的な現実に合わせた統制=ソロバン部トウセイの視点)。

**結論(QCMさん裁定):**
- 採否: **ベッカイ採用(最小・当事者明確なスクワッド化)＋ ウタガイの3穴を必ず埋める**。
- 具体体制(改訂):

```
                    小柳さん(最終決裁)
                         │
              QCMさん(最高統括=品質・統制・KGI進捗)
                         │
        ┌──────────┬──────────┬──────────┬──────────┐
   ①データ供給     ②モデル品質   ③保全実行(現場)  ④守り/セキュリティ  ⑤効果検証
   オーナー: 別システム  オーナー: 分析    オーナー: たかしくん   オーナー: 守り部    オーナー: 統括付
   連携担当             (ミトオシ/ベイズ)  (現場推進)＋保全担当  (マモル/コジン)     (スウジ/ケンテイ)
        │                                                    ＋外部専門家
   独立監査(テキホウ/ダトウ/コウヘイ)= 全体を指揮系統外から点検・小柳さん直
   専門家壁打ち(既存スペシャリスト群)= 各オーナーの助言役(当事者ではない)
```

- **ウタガイの3穴への手当て(必須):**
  - 穴①→ **③保全実行オーナー=たかしくん(現場推進)を明記**し、**継続率/保全接触率で評価**する。保全担当(人間)が要フォローを毎日消し込む。
  - 穴②→ **①データ供給オーナー**を置き、書き出しの頻度・品質・非識別化に責任を持たせる。
  - 穴③→ **⑤効果検証オーナー**＋**月次レビュー定例**(§ルール参照)で学習ループを回す。
- 見直し期限: 2026-11-01、または実データ運用開始時。

## 2. ルールの明文化(曖昧さを残さない)

### 2.1 判断基準(品質ゲート)
- **モデル本番投入**: バックテストで **AUC ≥ 0.65 かつ 較正(予測平均≒実績平均)** を満たす時のみ。**AUC < 0.5 は投入禁止**。満たさなければ要因追加・データ量・掛け合わせを見直す(churn-model-quality-gate)。
- **リスク帯**: 高=平均×2.0(天井0.9)。初期値。実データのバックテストで較正、変更は§2.2の変更管理。
- **放置検知**: 高リスク×直近14日接触なし=要フォロー。初期値。
- **表示**: リスク%は[0.1,99.0]にクランプ、100/0を出さない。少件数(<MIN_RELIABLE_N)は「参考」明示(断定しない)。
- **効果測定**: 母数不足は「参考」、解約後の接触は保全実績に数えない(免疫時間バイアス除去)。

### 2.2 承認フロー
- **実データ投入ゲート(不可逆・最重要)**: ①守り部審査チェックリスト全可 → ②独立監査点検 → ③外部専門家レビュー → ④QCM取りまとめ → **⑤小柳さん決裁** → 投入可。未通過は合成/非識別化のみ。
- **変更管理**(閾値・公開範囲・環境・連携先): 三名体制で議事化(ウタガイ反対理由必須)→ 守り部確認 → 小柳さん決裁。無断でパラメータを変えない。
- **コード変更**: TDD→タスクレビュー→(重要時)全体レビュー→PR。誤コミット検知(churn-pii-guard)を必ず通す。
- **マージ権限**: 通常のコード/ドキュメントPRはレビュー通過で可。**顧客データ・本番運用・外部送信に関わるものは小柳さん決裁**。

### 2.3 品質基準
- 全テスト通過(現行 100+ tests)。新規機能はテスト必須。
- 正確性最優先: 締切・金額・要件は原文照合、不明は「要確認」(hojo-accuracy-check)。
- 対外文面は humanizer 通過(AIっぽさ除去・事実は変えない)。

### 2.4 エスカレーション条件(即・上申/停止)
- **PII事故・誤公開** → 即時停止・遮断、48時間以内に3役レビュー(セキュリティ統括→小柳さん)。
- **AUC ≈ 0.5(当たらない)** → 本番停止、モデル見直し。
- **効果測定がマイナス**(保全した方が解約が多い)→ アクションの型を停止・再設計。
- **要フォロー件数が処理能力超過** → 閾値/トリアージを再設定(小柳さん)。
- **三名体制で割れて確信が持てない** → 統括経由でたかしくん・小柳さんへ上申。

## 3. やり切るためのタスク洗い出し(タスクレベル)

「作った」から「解約が実際に減る」までに足りないもの:

### A. データ(①データ供給オーナー)
- [ ] 非識別化CSVの定常運用(生年月日→年代・住所→市町村・直接識別子削除)を確立
- [ ] column_map 確定(現ステータス/年月日/申込日/チャネル/営業担当の対応)
- [ ] 顧客ID/名寄せキーの解決(無ければカルテは保留、リスク予測のみ先行)
- [ ] 別システムからの定期書き出し(頻度・品質・保全実施フラグ含む)

### B. モデル(②モデル品質オーナー)
- [ ] 実データで fit → **バックテスト(実AUC)** → 較正
- [ ] リスク帯・放置閾値を実データで決定(→小柳決裁)
- [ ] 重要な掛け合わせ要因の個別ルール化(検証部で確認)

### C. 保全実行(③現場オーナー=たかしくん)
- [ ] 手厚い保全アクションの型を**現場SOP(誰が・いつ・何を話す)**に落とす
- [ ] 要フォロー一覧の**毎日の消し込み運用**(放置ゼロ)
- [ ] 保全接触の記録を別システムに入力(効果測定の素材)

### D. 効果検証(⑤オーナー)
- [ ] 保全実施フラグの取得経路確立
- [ ] **月次効果レビュー**(実施群 vs 非実施群の解約率差)→ 改善→再投入

### E. セキュリティ/守り(④オーナー)
- [ ] 顧客データゾーン(閉域環境)の決定 → 実データ投入ゲート運用
- [ ] コード隔離(hojo-churn private)実行 → 私が代行
- [ ] 守り部審査＋外部専門家 → 小柳決裁
- [ ] GitHub設定(公開の是非・Actions有効化・push protection)

### F. 運用/可視化(QCM)
- [ ] 週次(要フォロー消し込み・データ鮮度)/月次(KGI・効果)カデンス
- [ ] KGI/KPIダッシュボード(継続率・早期解約率・保全接触率・効果)
