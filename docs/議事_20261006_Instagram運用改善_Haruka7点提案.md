# 議事: もらいわすれ堂 Instagram運用改善 — Haruka 7点提案(2026-10-06)

## 背景
Haruka(Instagram運用・投稿実装)から2026-10-05 06:11 UTC に送信された「投稿提案プロセスの改善」フィードバック。
投稿重複・データ精度低下・検証不足の3つの根本原因により、提案受領から実装までの流れが不効率化している。

---

## 論点: Instagram投稿プロセスの改善体制構築

### スイシン(推進) — 実装の利点と期待効果
**推進理由**:
1. **重複防止**: 投稿台帳システムにより、既投稿制度の重複提案を機械的に排除
2. **データ品質向上**: 公式ソース照合を提案時に必須化し、後発的な精度低下を防止
3. **工程削減**: 承認者の修正指示を減らし、最初から正確な提案を受け取れる
4. **スケール対応**: Haruka一人で10案以上を検証する作業を、自動・分散化できる
5. **信頼性**: 「対象になる可能性があります」等の慎重表現を機械的に担保

**実行案**:
- 投稿台帳(docs/もらいわすれ堂_投稿台帳.md)を運用開始
- 投稿提案時のチェックリスト5項目(Duplicate/Verify/Accuracy/URL/Citation)を必須化
- 検証スクリプト(verify_ig_urgent_items.py型)で自動検証→✓/⚠️判定
- 週次投稿スケジュール(月水金候補)で祝日・季節考慮

---

### ウタガイ(懐疑) — 必須の反対理由・リスク・懸念
**反対理由・リスク**:
1. **運用負担が重くなる可能性**: 提案者側(検証部)が5項目チェック→Haruka検証→小柳さん承認と、工程が増える。スケジュール遅延が発生するか？
2. **「検証済み」信仰の陥穽**: 機械判定で✓を付けても、人間の見落とし(「あかりの島」の200制度claim 根拠なし等)は検出できない。最終確認が属人的になる
3. **公式ソース変動への追従**: 厚労省・県サイトが急に変わっても、検証日が古いままだと無意味。定期的な再検証が必須か？
4. **データ正確性の責任所在**: 投稿精度が低下した場合、「検証部が見落とした」と「提案者の文面選択」どちらが原因か明確にしにくい
5. **ユーザー向けの信頼失墜**: Instagram上で「出産育児一時金」の言語が不正確だったという指摘は、ユーザーの離脱につながる。一度失った信用は取り戻しにくい

---

### ベッカイ(別解) — 前提への疑問・別案
**前提の疑問**:
1. **「投稿提案→承認→実装」の流れそのものが重い**: 7件の提案が週に積まれると、その確認だけで数時間。Haruka一人では限界では？
2. **「制度DB」と「IG投稿案」の二重管理**: 制度マスタは検証部が常に最新化しているのに、IG投稿案だけが旧情報を使い続ける。そもそも連動させるべき？
3. **投稿スケジュールの現実性**: 「月水金」「週2〜3件」という目安は、実際の業務量・Harukaの時間・設計稿の納期（デザイナー側）が考慮されているか？

**別案**:
- **案A: 「投稿承認機能」を自動化する**: 検証部が ig_neta.json を毎週更新 → 検証スクリプトで ✓判定されたもの → 小柳さんは「却下」ボタンだけ押す（今の「承認」を「却下」に反転）。デフォルト投稿方針を転換するか？
- **案B: 投稿案「一度作ったら修正なし」ルール**: 「偶数月」「詳細は〇〇ページ参照」等の修正は、次の同一制度投稿サイクル(3〜6か月後)に反映。修正作業の頻度を減らす（精度低下は許容）
- **案C: 社外(士業・商工会)からの「ネタ提供」制度**: 提案者を Haruka だけに絞らず、提携先から「今月はこの制度が注目」という情報をもらい、台帳に集約。負担の分散

## 結論(小柳さん裁定)

### 採否: **採用（段階実装）**

### 理由
1. **スイシンの工程削減効果は大きい**: Haruka の負担軽減と精度向上は両立可能。ウタガイの「最終確認が属人的」という懸念は、小柳さんのリバイュー時間で補う
2. **ベッカイの別案C(提携先ネタ提供)は並行実装**: 投稿スケジュール圧力を減らすため、提携部(ムスブさん)から「月1〜2件」の提案を受ける仕組みを同時進行。ただし責任は投稿台帳で明記する
3. **別案A(承認反転)は見送り**: デフォルト投稿方針は小柳さん判断。自動実装への転換は、3か月運用後に再上申（見直し期限 2027-01-06）

### 見直し期限: 2027-01-06（3か月試行後）
