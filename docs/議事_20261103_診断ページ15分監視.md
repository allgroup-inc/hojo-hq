# 議事: もらいわすれ堂 診断ページの15分監視

## なぜ(背景)

2026-11-02〜03、moradou.jp の診断ページ(`/shindan/`)が、moradou.jp に存在しないパス(`../../data/fukugiiro/seido.json`)を読みに行き、利用者が制度を検索できない状態になった(commit 8288f04250 で修正)。既存の監視はどれもこれを捕まえられない。

- `healthcheck.yml`(日次)の `check_fukugiiro()` は GitHub Pages 側の `data/fukugiiro/seido.json` を見ており、moradou.jp もページの読み込み先も見ていない
- `e2e.yml`(日次)は企業向け(ミカタ)トップページの診断だけを見ている

小柳さん決裁(2026-11-03): 監視間隔15分 / 件数の誤差0件 / 通知は既存のLINE+GitHub Issues / ローカル検証のあと段階的に導入。

## 前提

- hojo-hq・moradou とも Public(2026-11-03 GitHub API で確認)。GitHub-hosted の標準ランナーは Public リポジトリで無料
- 費用(試算): 1回あたり約2分(Playwright導入を含む。ランナーでは未実測)× 96回/日 × 30日 = 約5,760分/月。Public のため **0円**。仮に Private でも (5,760−2,000)分 × $0.006(Linux 2コア、2026-01-01 改定後の公式単価)= 約 $23/月
- **訂正**: 2026-11-03 の報告で「Private なら月 $8,140」としたのは誤り。①年間の実行回数 34,560回を月の分数として計算し、②実在しない単価 $0.25/分を使っていた
- docs.github.com はこのセッションのネットワーク設定で読めず、無料枠・分の切り上げ規則は公式文書を直接読んで確認していない
- **制度データが届いていなかった**: moradou 側の組み立て(`deploy/moradou/.github/workflows/build.yml`)は hojo-hq の `site/` と `scripts/` しか取得しないため、診断ページが読む `/seido.json` の元は `site/fukugiiro/seido.json`。これは 2026-11-03 06:55(UTC)に一度置いたコピーのままで、収集(`fukugiiro-fetch.yml`)が更新するのは `data/fukugiiro/seido.json` だけだった。同じPRで、収集が両方へ同じ内容を書き、`git add` の対象に足す(正本は `data/` のまま。`data/` を読む約20本のスクリプトは変更なし)
- **スケジュール起動の実態(2026-11-03 実測)**: このリポジトリでは GitHub の schedule が大きく遅れ・間引かれる。4時間おきの `moradou-cutover` は1日約3回(予定6回)・最大約12時間空き、1日4回の `update` は約3回・遅れ最大約3.5時間。15分間隔で書いても15分ごとには動かない前提で設計する
- **検知時間は保証しない**: 15分間隔は設定値。GitHub のスケジュール起動は遅れ・間引きがあり、実測で4時間おきの別ワークフローが最大約12時間空いた。停止検知(2時間ごと)も同じスケジュール起動のため遅れうる。実際の起動回数と最大間隔は停止検知のジョブ要約に毎回残す
- **LINE**: `LINE_CHANNEL_ACCESS_TOKEN` / `LINE_ADMIN_USER_ID` は設定済み(2026-10-22 の healthcheck 失敗時に送信成功の記録)。公式アカウントの無料枠は月200通で、顧客向けの締切アラートと共用(`docs/技術ロードマップ.md`)。このトークンは31本のワークフローの管理者向け通知でも使われている

## 三名体制の議論

- **スイシン(推進)**: 今回のP0は「ページが読みに行く先」が壊れた障害で、ページを実際に操作しないと見つからない。設定上は15分ごとに検査する。Public なので費用は0円(検知までの時間は保証しない。前提の「検知時間」を参照)
- **ウタガイ(懐疑・反対理由。必須)**:
  1. GitHub の schedule は混雑時に遅れたり間引かれたりする。15分間隔を前提にすると、監視停止の誤報が出る
  2. 現状の main では seido.json の自動更新が入っていないため、統合すると約1日で確実に鳴る。原因を知らない人には誤報に見え、監視の信用を落とす
  3. 障害が Public リポジトリの Issue に自動で載り、外部から見える
  4. Playwright やランナーの更新で監視側が壊れると、診断ページは正常なのに通知が来る
- **ベッカイ(別解・前提を疑う)**: 外から症状を見張るより、壊れた状態を配信させない方が根本的ではないか。今回のパスずれは、PR の時点で実ページを操作する検査があれば止められた。moradou の build.yml が配信前に同じ検査を走らせる案もある

## 裁定

採用。ウタガイの指摘は次のとおり実装に組み込む。

- 指摘1: 監視の停止判定は「6時間起動なし」とする(実測の間引きで誤報しない値。`diagnosis-monitor-watchdog.yml`、2時間ごと)。ワークフローの無効化(手動・60日無活動)、直近4回とも検査まで届かない状態(準備失敗・中断)、直近4回とも障害Issueの更新に失敗している状態も見る。実際の起動回数・最大間隔を毎回記録し、試験運用で閾値を見直す
- 指摘2: seido.json の自動更新の修正を、監視と同じPRに入れる
- 指摘3: 既存の `healthcheck`・`e2e` と同じ扱い(Public Issue)とする。Issue には URL・エラーの種類だけを書き、個人情報は扱わない
- 指摘4: 監視システムの故障(準備失敗・checkout失敗・停止)は `diagnosis-monitor-system` の Issue に「監視が動いていません(ページの状態は不明)」として起票し、診断ページの障害(`diagnosis-monitor`)とは分ける。Playwright の版は固定し(1.56.1)、対応する Ubuntu 24.04 のランナーで動かす
- ベッカイ: 検査本体・診断ページを変える PR では、ローカル配信で自己テストを走らせる(`selftest` ジョブ)。moradou 側の配信前ゲートは別議題とする

追加の安全策(2026-11-04 改定。下の2つの「追記」を参照): LINE は監視からの通知全体で**24時間3通・30日15通まで**。送るのは**ただ1つの送信担当**(`diagnosis-line-sender.yml`)で、送る前に LINE の送信枠を確認し、**残り50通以下・取得失敗・上限が読めない・形式が想定外**のときは送らず Issue に記録する。送れなかった通知は、復旧通知も含めて送れるようになった時点で送る(7日を過ぎたものだけ取りやめ、理由を記録する)。

通知の規則(LINE は状態が変わったときだけ送る): 初回の異常で起票+LINE / 同じ症状が続く間は何もしない / 症状が変わったら追記+LINE / 4時間以上続いたら追記+LINE(1回だけ)/ 正常に戻ったら継続時間を書いてクローズ+LINE。同じ症状のたびに追記する当初案は、1日最大96件の追記になるため採らない。

段階導入:
1. 作業ブランチに置き、自己テスト(正常1件・異常15件・再試行2件)をローカルで全件合格させる(2026-11-03 完了)
2. seido.json 自動更新の修正とあわせて main に統合し、15分監視を開始する(Draft PR。小柳さんの統合承認が必要)
3. 2週間運用し、誤報・見逃し・実際の起動間隔を見て、閾値(6時間・4回・30時間・4時間・24時間3通・30日15通・残り50通)を見直す。15分ごとに起動しない状態が続くなら、外部からの起動(別議題)を検討する

## 追記 2026-11-04(2回目): 送信担当の一本化・LINE応答の厳格化・公開用データの欠落防止(小柳さん承認)

本番導入前の最終確認で、次の3点が分かった。①15分監視と停止検知が別々に送るため、GitHub の API の反映が遅れると24時間の上限を1通超えうる(偽のGitHubで再現)。②LINE の使用量が真偽値・負の値でも「送る」と判定していた。③「シードの過半が取れなければ停止」は、262件中215件が到達性の確認を省くため効かず、ネットワーク全断でも欠けたデータ(258件→215件)が公開されうる。あわせて、**児童扶養手当(fk-kuni-jidofuyoteate)が 2026-10-14 以降の収集40回すべてで取得に失敗し、公開データから欠けている**ことが分かった(シードの原文URLは沖縄県のページ。原因は未確認)。

対応:
- A: 送信要求を障害Issueに永続的に書き(`<!-- line-want -->`。障害の記録と同じ1回の書き込み)、送るのは送信担当1本だけにする。送信記録は `bot/diagnosis-line-state` ブランチの `diagnosis-line/state.json` に置き、Contents API の sha 一致を条件に書き換える(比較交換)。上限の判定と送信の予約を同じ書き換えで行い、競合した・書いた内容を読み直せないときは送らない(Actions の concurrency は補助)。要求IDを LINE の再試行キー(`X-Line-Retry-Key`)に使い、送った直後に落ちても二重に届かない。そのため送信は既存の `line-notify` ではなく送信担当が直接呼ぶ(既存の部品・顧客向け配信は変えない)
- B: 使用量・上限値は0以上の整数だけを受け付け(真偽値・負数・欠落・文字列は送らない)、`type` は公式仕様の `none`(上限値なし)と `limited`(0以上の整数の上限値)だけを認める。送信担当を `mode=check` で手動実行すると、送らず・記録も書き換えずに送信枠・使用量・送信待ちを確認できる(LINE確認モード)
- C: 公開用 `site/fukugiiro/seido.json` は、前回の公開データと制度IDで比べ、次のどれかに当たれば更新しない(前回の公開データを残す)。(1) 前回の公開データに載っている制度の取得失敗(件数に関係なく)、(2) 理由なく3件以上が消えた、(3) 必須制度(国の制度 `fk-kuni-`)が1件でも理由なく消えた。正当な理由(締切終了・一時非公開・`RETIRED` に記録した廃止)は根拠を `data/fukugiiro/publish_status.json` に残す。保留と、必須制度が公開データに無い状態は、停止検知が `diagnosis-data-hold` の Issue と LINE で知らせる。`data/` 側の処理・終了コードは変えない
- C の解釈(小柳さんの確認待ち): 「取得失敗があれば保留」は、**前回の公開データに載っている制度**の取得失敗に限った。児童扶養手当のように前回の公開データにも無い制度の取得失敗まで保留にすると、毎回失敗している児童扶養手当のために公開用データが二度と更新されなくなるため。この欠けは「必須制度が公開データに無い」として知らせる

三名体制:
- **スイシン(推進)**: 比較交換は GitHub の API で唯一の確実な排他で、Actions の concurrency に頼らずに上限超過を防げる。再試行キーで、落ちたときの二重送信も防げる。公開用データは「欠けたら前のまま」にしたので、利用者が見る診断が黙って減ることはなくなり、欠けは30時間後の「データが古い」と制度データの注意で人に届く
- **ウタガイ(懐疑・反対理由。必須)**:
  1. 送信担当に `contents: write` を渡すことになる。誤りがあれば main など他のブランチを書き換えうる
  2. 送信記録のためのブランチと、15分ごとの送信担当の実行が増え、仕組みが複雑になる。送信担当そのものが止まると、どの通知も届かない
  3. 「取得失敗があれば保留」は、1か所の自治体ページが落ちただけで公開データの更新が止まる。止まっている間、新しく増えた制度や締切の更新も診断に出ない
  4. 監視からの LINE を既存の `line-notify` 以外の経路で送ることになり、送り方が2通りになる
- **ベッカイ(別解・前提を疑う)**: 取得失敗の多くは一時的なものなので、「取得失敗の制度だけ前回の内容を残し、他は更新する」(制度ごとの差し替え)にすれば、更新を止めずに欠けも防げる。ただし前回の内容が古いまま残る制度の扱い(締切の更新など)を別に決める必要がある

裁定(部門長): 採用する。指摘1は、送信担当が書き換えるのは `bot/diagnosis-line-state` の `diagnosis-line/state.json` だけで、コード上も対象を固定する。他の2本(15分監視・停止検知)は `contents: read` のまま。指摘2は、送信待ちが保留でもなく6時間以上残れば停止検知が「送信担当の停滞」として Issue に残す。指摘3は、保留が続けば30時間で監視の「データが古い」が鳴り、制度データの注意も出るので、人が原因(取得できない制度)を直す。ベッカイ案(制度ごとの差し替え)は、2週間の運用で保留の頻度を見てから別議題とする。指摘4は、再試行キーを渡せるのが送信担当の呼び出しだけのためで、既存の部品は変えない。児童扶養手当の取得失敗は、検証部が原文URLを確かめる(本PRの範囲外)。見直し期限は本議事と同じ。

## 追記 2026-11-04(3回目): 送信担当の権限分離・通知の優先順位・児童扶養手当の調査(小柳さん承認)

C の解釈(前回公開していた制度の取得失敗だけを保留の理由にする)は小柳さんが承認した。前回の公開データに無い制度の取得失敗は、公開用の更新を止めず、判定記録(`failed` の `in_previous_public: false`)と収集ログの警告に残す。

調査で分かったこと:
- 児童扶養手当が取れない原因は、2026-09-24 の出典の差し替え(`59a6269329`。Instagram 投稿⑨の出典を直すため、こども家庭庁のページから沖縄県のひとり親家庭支援の一覧ページ `…/1008226/1008243/index.html` へ)。このページは別の制度 `fk-ken-hitorioya-sodan` が8月の時点で「到達性の確認を省く」としていたもので、収集では取れない。9/24〜30 は別の不具合で収集が止まっており、データから消えたのは差し替え後の最初の収集(10/1)から。前回の追記の「10/14以降」は、調べた範囲の始まりで、正しくは「10/1以降」
- 収集は到達できなかった理由を捨てていた(`reachable()` が真偽値だけを返す)。403(遮断)と404(消滅)を見分けられない
- 制度データの注意は、保留と公開が入れ替わるたびに LINE を送り、監視の上限(24時間3通)を使い切ると診断ページの障害の通知が翌日まで遅れうる(偽の GitHub で再現: 保留が1回起きただけで3通)

対応:
- 送信担当を3つのジョブに分ける。予約(`contents: write`・LINE のトークンなし)→ 送信(`contents: read`・LINE のトークンあり)→ 記録(`contents: write`・LINE のトークンなし)。ジョブ間で渡すのは要求ID・結果の種類・短い理由だけで、文面は送信記録の予約から読む。checkout は `persist-credentials: false`。送信・記録の途中で止まれば予約が残り、次の起動が同じ再試行キーで送り直す。送信枠で送れなかったときは予約を取り消し、通数に数えない。1回の起動で送るのは1通まで
- 送る順は、診断ページの障害 → 監視システムの故障 → 制度データの注意(同じ種類なら古い順)。制度データの注意は、24時間・30日の上限の最後の1通を診断ページの障害のために残す。上限(24時間3通・30日15通)は変えない
- 制度データの注意の LINE は、欠けている必須制度の組み合わせが変わったときと、保留が始まったときだけ。保留の解除は Issue に書くだけ。欠けていた必須制度が戻ったときは、LINE で知らせていた場合だけ解消を知らせる
- 解消して閉じた Issue の、まだ送れていない通知は取り下げる(解消した後に「異常」「動いていません」だけが遅れて届くのを防ぐ。復旧の知らせは送る)
- `reachable()` は HTTP ステータス(または例外の種類)を返し、取得失敗の理由として判定記録と収集ログに残す
- 児童扶養手当の出典URLは変えない。県の専用ページ(`…/1036501/1036529/1036522.html`。題名「児童扶養手当｜沖縄県公式ホームページ」)が検索で見つかり、令和8年4月分からの額と、手続きは市町村であることが検索結果に出ている。ただし、この作業環境は `pref.okinawa.lg.jp` と `cfa.go.jp` に接続できず、本文・更新日・収集での取得可否を原文で確かめられなかったため(絶対ルール1)。関連する2制度(`fk-ken-hitorioya-sodan`・`fk-ken-kouto-shokugyo-kunren`。`…/1008243/` 配下)も、検索でページが見つからず、確かめられないので変えない

三名体制:
- **スイシン(推進)**: 書き込みの権限と LINE のトークンが同じジョブに無くなり、送信のジョブが乗っ取られても記録やリポジトリを書き換えられない。優先順位と「最後の1通」で、通知の増えた日にも診断ページの障害が先に届く
- **ウタガイ(懐疑・反対理由。必須)**:
  1. ジョブが3つになり、起動ごとに3台のランナーを使う。1回の起動で1通しか送れないので、同時に複数の通知があると、2通目以降は次の起動(15〜30分後、遅れればそれ以上)まで待つ
  2. 「最後の1通」は、制度データの注意を24時間に2通までに減らす。必須制度の欠けが続いた日には、注意の通知が翌日に遅れる
  3. 優先順位を付けても、LINE の送信枠(顧客向けと共通の月200通)が尽きれば、診断ページの障害も送れない。優先順位は監視の上限の中での順番にすぎない
  4. 児童扶養手当は統合後も欠けたまま。URL を直さない限り、診断で児童扶養手当が出ない
- **ベッカイ(別解・前提を疑う)**: 送信記録を別の非公開リポジトリに移せば、hojo-hq 側の書き込みの権限そのものを無くせる(GitHub App か、そのリポジトリだけに権限を持つトークンが要る)。児童扶養手当は、県の専用ページとこども家庭庁のページの両方をシードに持たせ、片方が取れれば載せる方式もある

裁定(部門長): 採用する。指摘1は、監視からの通知は上限が24時間3通のため、1回1通でも詰まらない(優先順位で重要なものから出る)。指摘2は、制度データの注意は Issue に残り、停止検知の Issue でも見えるので、LINE が翌日になっても失われない。指摘3は残る制約として PR と初回確認手順に明記する(確認モードで残り通数を見る)。指摘4は、検証部が原文を確かめてから URL を直す(作業環境で `pref.okinawa.lg.jp`・`www.cfa.go.jp` への接続を許可するか、人が確かめる)。ベッカイ案の別リポジトリ化は、新しいリポジトリと Secret が要るので小柳さんの決裁事項として別議題にする。2つのページを持たせる案は、検証部の確認の後に検討する。見直し期限は本議事と同じ。
