# 議事 2026-11-23: 自律開発の包括承認(代表者)

## 決裁
- 決裁者: 代表者(小柳さん)。2026-11-23 の正式包括承認。
- 内容: 「限りなく開発が自動でできる所まで進めてください。推奨で進める事を承認します。またその際に承認が必要なものも承認します。」
- 目的: GLOW全体のシステムを、代表者の個別指示・個別承認なしで、開発・改善・試験・運用できる状態まで進める。安全性を維持し、完成までの時間を最大限短縮する。

## 包括承認の範囲(個別承認を不要とする作業)
調査、課題の発見、優先順位の決定、要件整理、設計、コード実装、バグ修正、リファクタリング、合成データ試験、回帰試験、セキュリティレビュー、PR の作成・更新、CI 確認、安全基準を満たした PR のマージ、安全基準を満たした低リスク変更の本番反映、反映後の読み取り確認、異常検知、安全停止の設計と自動化、ドキュメント更新、知識の蓄積、担当間の連携、開発工程の改善。

**包括承認が及ばないもの**: 既存の保護ルール、権限制約、法令、本人同意、外部サービスの利用条件を無効化するものではない。

## 自動マージ・本番反映の条件(すべて満たすときだけ。1項目でも不合格・未確認なら、そのPRの自動反映を禁止)
① 最新 main との整合 ② 必須 CI の全件成功 ③ 既存機能の回帰試験の成功 ④ 独立したレビューによる安全性の確認 ⑤ 個人情報・顧客情報・秘密情報の漏えいなし ⑥ 本番データの欠落・破壊・意図しない更新のリスクなし ⑦ 連絡不要企業の保護が維持される ⑧ 重複架電・重複処理の防止が維持される ⑨ 他担当の変更との競合なし ⑩ 必要な最新バックアップの確認 ⑪ 障害時の安全停止・復旧方法の確認 ⑫ 反映後の正常稼働確認の実施 ⑬ 既存の本番反映禁止条件への抵触なし。
- 本番反映を伴うマージは、マージ時点で本番反映として判定する。
- 古い危険な実装に戻ることでデータ消失が再発しうる場合は、無条件の自動 revert を行わない。
- **現在の OAuth 承認切れとバックアップ停止が解消されるまで、それらに依存する本番反映は保留する**(条件 ⑩・⑫ が満たせないため)。開発・試験・Draft PR 作成は継続する。

## 代表者の関与が引き続き必要な事項
代表者本人の Google 認証操作、新規の権限付与と秘密情報の登録、顧客データの削除と重大な変更、個人情報の新たな外部提供、契約・支払い・発注、本人同意が必要な写真・プロフィールの掲載、公開内容や対象者が未確定のコラム公開・DM・LINE 実配信、安全基準を満たさない本番変更、経営方針に関わる重大な判断。

## 絶対保護事項
- 公開リポジトリへの顧客情報・個人情報・秘密情報の保存をしない。
- `.claude/experience/` を commit・push しない。
- C001213 は変更せず、架電対象外を維持する。
- 連絡不要企業への架電防止を弱めない。
- バックアップ、監査記録、安全停止機能を無断で無効化しない。
- 権限制約・既存の安全装置を迂回しない。
- 他担当の作業を無断で上書きしない。
- 試験・本番確認を実施していないものを成功と報告しない。未確認事項を確認済みとして扱わない。

## 三名体制の議論
- **スイシン(推進)**:包括承認により、個別の承認待ちで開発が止まらなくなる。安全基準を明文化すれば、低リスクの改善は速く反映できる。
- **ウタガイ(懐疑・反対)**:包括承認は、自動で本番を変える範囲を広げる。特に、独立したレビューが実際に行われないまま「条件を満たした」と判定される危険がある。また、本番の状態(承認切れ・バックアップ停止)を確認しないまま反映すると、データ欠落が再発しうる。
  → 反映: 条件④は、別の視点のレビュー担当による記録を必須とする。条件⑩・⑫は、確認できなければ禁止とする。「試験していないのに成功と報告しない」を絶対保護事項に入れる。
- **ベッカイ(別解)**:自動化の速さより、安全停止と早期検知を先に整えるほうが、事故の型には合う。反映の判定を「自動で決める」ことより、「判定の根拠を残す」ことを優先する。
  → 反映: 反映の判定は、各 PR の本文に13条件の結果を書く形で根拠を残す。安全停止と異常検知は P0・P2 で先行させる。
