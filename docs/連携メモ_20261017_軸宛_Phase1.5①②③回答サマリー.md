## § 3️⃣ 認証・権限管理のフロー

**期限**: 2026-10-15 (**本日**) → 2026-10-17 (2日超過)

### 📊 現時点での確認状況

#### A. KAKEHASHI アプリ内での認証方式

| 確認項目 | 現時点での推定 | 確信度 | 備考 |

| **セッション/トークン管理** | ？ネイティブアプリ → Local storage / Secure storage | 🟡 低 | 推測（確認未） |
| **認証の生存期間** | ❌ 不明 | ❌ | Session timeout / Token expiry の仕様未確認 |

#### B. 既存 admin.html の権限チェック

**推定フロー:**
```
1. KAKEHASHI ユーザーがログイン
2. admin.html を Web ビューで表示
3. admin.html 側が「このユーザーは admin か？」を確認
4. admin でない場合 → 403 Forbidden or 別ページへ遷移
```

**現在の実装（推定）:**
```javascript
// kakei-crm/apps/site/admin.html 内で想定される処理
// - Session Cookie を参照
// - または URL パラメータでトークンを受け取り
// - admin 権限をチェック
```

#### C. kanri_system UI への権限情報の渡し方

**複数の可能性を検討:**

| 方式 | 実装例 | メリット | デメリット |
|---|---|---|---|
| **URL パラメータ** | `customer_detail.html?token=xxx&user_id=yyy` | シンプル | Token が URL に見える（セキュリティ） |
| **Session Cookie** | KAKEHASHI が kanri_system と同一ドメイン配下 | 安全 | 配置先の制約（同一ドメイン必須） |
| **HTTP Header** | admin.html からの iframe/Web ビュー で透過的に Header 送信 | 安全 | ブラウザの制約（CORS） |
| **POST データ** | form submit で渡す | 安全 | 初期表示時のデータ渡しが限定的 |
| **API 呼び出し** | kanri_system UI 起動後、API で認証情報を検証 | 柔軟 | API 実装の複雑さ |

### 💡 暫定的な実装案

**推奨パターン（①②③ の軸チーム確認待ち）:**

```
【パターン A】Web ビュー + Session Cookie の場合
├─ kanri_system UI を kakei-crm/apps/site/ 配下に配置
├─ KAKEHASHI Web ビュー内で同一ドメイン → Cookie 自動送信
├─ kanri_system UI が Cookie から user_id を取得
└─ 権限チェック実施 → 403 or データ表示

【パターン B】iframe 埋め込みの場合
├─ kanri_system UI を別ドメイン配置（Azure Blob など）
├─ KAKEHASHI 側が postMessage で token 送信
├─ kanri_system UI が token をローカルストレージに保存
└─ 権限チェック実施

【パターン C】ネイティブアプリ + Web ビューの場合
├─ ネイティブアプリが token/session を保持
├─ Web ビュー から JavaScript Bridge で token を取得
├─ kanri_system UI に token を渡す（Header or Storage）
└─ 権限チェック実施
```
