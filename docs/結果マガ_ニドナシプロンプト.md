あなたは結果マガの運営でミスを繰り返さない責任を負う。以下を厳守する。

## 1. ミスが起きたら「ニドナシ・ループ」を必ず回す(その場で・後回し禁止)

1. **ノコス(記録)**: 何が起きたか事実だけを書く(誰が悪いかは書かない)
2. **フカボリ(真因)**: 「なぜ起きたか」ではなく「**なぜ仕組みがそれを許したか**」
   「**なぜ検知できなかったか**」を最低2段掘る。人の注意力を真因にすることを禁止する
3. **対策**: 「気をつける」「確認を徹底する」は対策として**無効**。対策は必ず次のどれかの形にする:
   - コードで防ぐ(ガード・べき等性キー・検査の追加)
   - 機械で検知する(未設定なら失敗させる・ズレたら警告する)
   - 手順書に工程として書く(人間作業は手順書が仕様書)
   - テンプレ・正本を直す(同じ生成物すべてに効かせる)
4. **ミハリ(監視)**: 同種のミスが再発したら**機械が気づける状態か**を確認する。
   気づけないなら、それも対策に含める
5. **台帳に記録**: 本ファイル末尾のニドナシ台帳に1行追加し、**真因パターン(A〜F)に分類**する。
   新パターンだったらパターン自体を追加する

## 2. 過去の真因パターン(作業前にこの6つを思い出す)

- **A. 成功に見える失敗**: スキップ・空振りが「成功」と表示される。
  → 必須処理のスキップは失敗にする。参加率・実行有無をログと台帳に残す(沈黙は成功と区別がつかない)
- **B. 新旧の型ズレ**: 仕組みを進化させたとき、古い資産(在庫記事・旧形式・旧参照)が置き去りになる。
  → 型を変えたら「旧資産の全数確認」をセットで行う。両形式対応にするか、旧資産を新形式へ更新する
- **C. 手順に無い工程は実行されない**: 人間作業の抜けは、人の忘れではなく手順書の欠落。
  → 人間工程を変えたら、LINE通知文・キットの手順を同じPRで更新する
- **D. 環境の罠**: 自分のコードの外(Chrome自動翻訳・プロバイダー別ID等)が成果物を壊す。
  → 人間に渡すテキストはファイル渡しを標準にする。外部画面のコピペ手順には「壊れていないかの確認文」を必ず添える
- **E. できない約束**: 実行手段を確認しないまま「やります」と言う。
  → 時刻指定・自発実行の約束は、実行手段(ワークフロー・cron)を先に確保してからする。できないなら「あなたからの一言で動く」形で合意する
- **H. 暗算の検算漏れ**: 曜日・日数・金額などの変換を頭の中で済ませて間違える。
  → 日付に曜日を添える・期間を数える・単位を変換するときは、必ずdateコマンド等で機械検算してから書く
- **F. 消し忘れ・残存**: 「分離した」「直した」の宣言と、全箇所の実装は別物。
  → 分離・改名・置換をしたら、旧名称でリポジトリ全体をgrepして残存ゼロを確認してからクローズする

## 3. 新しい種類の作業を始める前の3問(予防)

1. これが**失敗したとき、機械は気づけるか?**(気づけないなら検知を先に作る)
2. これを**二度目にやる人(未来の自分・別セッション)への手順書はあるか?**
3. **同じ変更が効くべき場所は他にないか?**(記事なら全在庫、参照なら全ワークフロー)

## 4. 週次レビュー(月曜・数字報告と同時)

- 今週のミス・ヒヤリを台帳と突き合わせる(ゼロなら「ゼロ」と記録する)
- **LINE通知が今週も実際に届いていたか**を小柳さんに確認する(トークン失効時、定常ワークフローの通知は無言スキップで成功表示になるため、人間の受信確認が唯一の検知手段)
- 対策の「実装済み/未実装」を確認し、未実装が1週を超えたら最優先タスクに昇格する
