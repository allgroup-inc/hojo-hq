# 議事: 出荷ゲートの通過記録をどう仕組みにするか — 三名体制

日付: 2026-08-17 / 発端: 小柳さん「お願いします」(点検レポート⑤の提案を採用)
適用スキル: hojo-triangle-review / resilient-agent-design / humanizer / go-link-discipline
関連: `docs/点検_20260817_スキル適用と完成度.md` ⑤ / `docs/運用規程_やり切り実行計画_2026-08.md` 1-3

## 背景

運用規程1-3で、対外文面は `hojo-accuracy-check` → `hojo-deadline-alert` → `humanizer` の3スキル通過が出荷条件。
しかし `posts/` `outbox/` を検索しても通過の痕跡が**1件も無く**、通したかどうかを誰も検証できない状態だった。
独立監査を週次に立ち上げても(週次レポ§4)、この領域だけは見ようがない。

## 論点: 通過記録をどこに、どう残し、どこで止めるか

### スイシン(推進)

- 記録は**生成物のmarkdown内**に `## 出荷ゲート` 節として持つ。人間もAIも同じものを読める
- 強制は**投稿直前**(`post_social.py`)。記録が無ければ投稿しない=フェイルクローズ
- 通過記録があれば、週次レポ§4の無作為点検で「いつ・誰が通したか」を外から確認できる。監査が初めて成立する
- 生成器側に `GATE_CHECKED` 定数を置き、文面を書き換えたら更新する運用にすれば、記録の更新忘れが出荷停止として顕在化する

### ウタガイ(懐疑)

- **スタンプは自己申告にすぎない。**生成器が日付を吐くだけなら「通したことにする」のは簡単で、記録が増えるだけで品質は1ミリも上がらない
- **90日で自動投稿が止まるのは事故に見える。**ある朝いきなり投稿されなくなり、原因が分からず放置される
- **検査対象がホワイトリスト**(`TARGET_GLOBS`)なので、新しい出力先を作った人が登録を忘れると素通りする。`/go/` のチャネル追加忘れと同じ構造の穴
- **対象範囲が狭い。**今回はInstagram/Facebook投稿とカルーセルだけ。LINE配信・note・メールは手つかずのまま「ゲートを実装した」と言うと、実態より安全に見える
- **文面は毎日再生成される。**ファイルに書いたスタンプは次の生成で消える。手でスタンプを貼る運用にすると必ず破綻する

### ベッカイ(別解・前提を疑う)

- そもそもゲートは「ファイル」ではなく**テンプレート(生成器のコード)**に紐づくべきでは。毎日変わるのは差し込まれるデータで、文体・訴求は生成器の中にある
- 別解: CIで毎回AIに humanizer 相当のチェックをさせる。ただし出力が非決定的で、同じ文面が日によって通ったり落ちたりする。**CIの判定は決定的であるべき**
- 別解: 記録を一切持たず、機械チェックだけにする。ただし「自然な日本語か」は機械で測れないため、humanizerゲートが丸ごと消える

### 結論(裁定)

**採用。ただし単純なスタンプ方式ではなく、二層構造にする。**

| 層 | 何を見るか | 誰が保証するか |
|---|---|---|
| **機械が検査する層** | 禁止表現(「締切7日前」「必ずもらえる」等の断定)/ lin.ee直貼り / 記録の鮮度 | コード。**申告があっても違反なら落とす** |
| **申告する層** | humanizerの自然さなど人の判断が要る部分 | 生成器の `GATE_CHECKED`。週次レポ§4の無作為点検で拾う |

ウタガイの指摘への対応:

1. **自己申告の穴** → 機械層を上に置いた。スタンプがあっても「締切7日前」が本文にあれば出荷停止する(実ファイルで動作確認済み)。ただし**humanizerの自然さは依然として申告**であり、これは仕組みでは埋まらない。限界として明記する
2. **突然止まる** → 76日で警告、90日で停止の二段。停止時は `post_social.py` が異常終了し、`social-post.yml` の失敗時LINE通知が飛ぶ(黙って止まらない)
3. **ホワイトリストの穴** → CLAUDE.md 再発防止メモに1行追加。加えて `TARGET_GLOBS` のコメントに明記
4. **対象範囲** → 今回はミカタのSNS投稿(Instagram/Facebook/カルーセル)とX告知のみ。**LINE配信・note・メールは未適用**。実装したと言い切らず、下の「残り」に明記する
5. **毎日再生成される** → ベッカイ案を採用し、スタンプは**生成器が出力**する。手貼り運用にしない

- 見直し期限: **2026-11-17**(3ヶ月。適用範囲の拡大可否をここで再判断)

## 実装したもの

- `scripts/shipping_gate.py`(新規): 記録の組み立て・読み取り・検査・一括検査。自己テスト20チェック
- `scripts/generate_sns.py` / `scripts/generate_carousel.py`: `GATE_CHECKED` 定数と記録の出力を追加
- `scripts/post_social.py`: 投稿直前にフェイルクローズ。`--preview` は `gate=ok|ng` を先出し
- `scripts/post_x_announce.py`: X本文はファイルを持たないため機械層のみ適用
- `.github/workflows/social-post.yml`: 投稿ジョブに全件検査ステップを追加(当日以外の素材の腐りも拾う)

## 追記(2026-08-17 同日): LINE配信へ適用

面談予約の導線でLINE文面を作ることが決まっており、未適用のままだとその文面が第1号の検査漏れになるため、
先にLINE配信(締切アラート下書き)へ広げた。**配信するのは人**なので、機械が止められるのは下書きの見え方まで。

- 違反があれば通過記録を付けず、**人が最初に読む先頭**に「⚠️ この下書きは配信しないでください」を挿入する
- データ更新・サイト公開まで巻き添えで止めないよう、`update.yml` に**別ジョブ** `shipping-gate` を追加(`needs: fetch-and-deploy`)
- 同じ理由で検査を**配信経路ごとのグループ**に分割(`--check-group sns` / `line`)。
  LINE下書きの違反でInstagram投稿が止まるのは筋が悪いというウタガイの指摘に対応
- 疑似違反を注入して経路を実測: 先頭に警告が入り、通過記録は付かず、`--check-group line` が exit 1 になることを確認
