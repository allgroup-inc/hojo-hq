## 返してほしいこと(4つ)への回答

### 1. 使う人は誰で、1日に何回開くか

| 誰 | 人数 | 頻度 |
|---|---|---|
| アポ入れ担当 | 数名 | **開きっぱなし**(1日100件の登録を想定した連続入力ボタンを実装済み) |
| 対面営業メンバー | 7名以上 | **1日5〜10回**・スマホ。朝に今日の訪問を確認 → 訪問前後にステータス更新 |

**ただし現時点で本番稼働しておらず、実測はゼロです。**コードはv2.3まで完成、テスト85件パス、独立レビュー済み。
残るのは本番投入(スプレッドシート作成〜デプロイの約30分の手作業)のみで、8/17から未実施です。

### 2. 手で入力させていること / 自動化できそうなもの

**いま手入力**: 顧客名 / 日付 / 開始時刻 / 所要分 / 形式 / 場所またはURL / 担当営業 / アポ入れ担当 / 温度感 / アポ種別 / 紹介元 / メモ
(形式・温度感・種別・担当はプルダウン。自由記述は顧客名・場所・メモの3つ)

**自動化できるもの(❶❺が繋がれば)**:

| 今 | 繋がった後 |
|---|---|
| 顧客名・場所を毎回手打ち | ❶から `KM-` 参照で引く → **入力ゼロ**。1日100件なら効果が最大 |
| 訪問後にメモを手入力 | ❺(音声→書き起こし→要約)から自動反映 |
| ステータスを人がタップして「実施済」に | ❺が音声を受信した時点で自動遷移できる余地あり |

### 3. 開いたときに最初に出るべきもの

共通認識では ❷ は「今日調整すべきアポ、埋まっていない訪問枠」。

**現状との差分**:
- 初期表示は「本日ビュー(全員分を時刻順)」。**埋まっていない訪問枠は分析タブの中**にあり、開いた瞬間には出ていない
- 営業マンは「自分のアポ」チップを1タップしないと自分の今日にならない。**開いた瞬間に自分の今日が出るべき**

いずれも直せます。ただし後述の分割の整理が先です。

### 4. 現場の手間が増える箇所(正直に)

1. **顧客名の手入力** — ❶から連携されない限りアポ入れ担当が毎回打つ。1日100件なら最大の手間
2. **ステータスの手動更新** — 「実施済」に変える動機が営業マンにない(本人の仕事は終わっているため)。放置されると分析タブの数字が嘘になる
3. **ダブルブッキング警告が止めない** — 警告後にもう一度保存すれば通る。速度優先の設計だが二重予約は成立する
4. **スタッフタブの手動メンテ** — 入退社のたびに手で編集。共通の権限基盤に寄せれば消える
5. **そもそも未稼働** — 手間以前に、まだ1度も使われていない

## 全システム共通の約束との差分(重要・4件)

家計のポっは共通認識より前(8/14)に作られており、**単独で完結する前提**で設計されています。
そのため約束と食い違う箇所があります。責任の所在ではなく事実として記録します。

| 約束 | 現状 | 差分 |
|---|---|---|
| 【1】顧客データを自分の中に持たない | 「アポ予定」タブが **顧客名** と **場所またはURL(訪問先住所)** を独自に保持 | **抵触**。`KM-` 参照に置き換える必要がある。ただしGAS+スプレッドシートでの都度参照は速度(約束【6】待たせない)と衝突しうるため、**表示用のキャッシュをどこまで許すかを軸に決めてほしい** |
| 【2】顧客の番号を自分で発番しない | 発番しているのは **アポID**(アポの管理番号)で顧客番号ではない | 発番自体はOK。ただし **`KM-` への参照列が存在しない**。列は末尾追加のみ可なので、追加は安全にできる |
| 【3】自前のログイン・ユーザー管理を作らない | 「スタッフ」タブ(氏名/Slack ID/有効/メール/役割)+ Googleアカウント照合の**自前の許可リスト** | **抵触**。パスワードは増やしていない(Googleアカウント認証)が、共通の権限基盤には乗っていない |
| 【4】ステータスの言葉を言い換えない | 7種: 予定 / 確定 / 実施済 / 申込み / キャンセル(顧客都合) / キャンセル(自社都合) / 再調整中 | **4語が共通語彙と不一致**(下表) |

### ステータスの不一致

| 家計のポっ | 共通語彙 | 備考 |
|---|---|---|
| 確定 | **アポ確定** | 言い換え |
| 再調整中 | **スケジュール調整中** | 言い換え |
| 実施済 | **訪問済** | 言い換え。しかも共通語彙では **❸が持つ** |
| 申込み | **申込** | 送り仮名違い。しかも共通語彙では **❹が持つ** |
| 予定 | (該当なし) | 「アポ確定」前の状態をどう呼ぶか要定義 |
| キャンセル(顧客都合/自社都合) | **差し戻し** / **対象外** との対応が未定義 | 訪問に至らず❶へ返すのは差し戻し。架電禁止は対象外。この2つとキャンセル2種の関係を軸に決めてほしい |

## いちばん大きな論点(軸への質問)

**家計のポっは、現状 ❷ の範囲を超えています。**

「実施済」「申込み」まで1つの画面で持っており、共通認識の分割で言えば **❷+❸+❹の一部**にあたります。
アポ入れ担当と営業マンが1画面で完結することを狙って作ったので、当然そうなっています。

移行のタイミング(❷→❸=訪問した時点、❸→❹=申込になった時点)を守るなら、選択肢は2つです。

- **A: 家計のポっを❷に絞る** — 「実施済」以降を❸へ渡す。分割は綺麗になるが、
  営業マンが「訪問した」と押した瞬間に別システムへ飛ぶ体験になる。約束【6】と衝突しないか要検証
- **B: 家計のポっを❷+❸として扱う** — 移行の理由(「一度会った人は営業マンが追うほうが効率が高い」)は
  **同じ画面の中でも担当が切り替われば満たせる**。5つの入口の数え方を1つ見直すことになる

**私からはBを推しますが、これは軸が決める話**なので勝手に決めません。
Aなら分割作業、Bなら共通仕様側の記述調整が必要になります。
