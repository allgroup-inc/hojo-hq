# ❶ アポ架電チャット向け

**報告期限**: 9/30 17:00

## 🎯 検証の目的
アポ架電システムが、軸台帳から顧客データを正常に受け取り、  
管理画面・架電・ログ送信が全て正常に動くことを確認する。

---

## ✅ 確認項目

### 1. ログイン・認証
- [ ] ログイン画面が軸の統一フォーム（OAuth or トークン認証）
- [ ] 認証に成功して管理画面が表示される
- [ ] 無効なトークンは 401 エラーで拒否される
- [ ] 期限切れトークンは 401 エラーで拒否される

**テスト手順**:
```bash
1. ブラウザで管理画面にアクセス
2. 統一フォームが表示される → 認証トークンを取得
3. 正常なトークンでログイン → 成功
4. トークンを無効にしてリロード → 401 エラーで拒否
5. 期限切れトークンを使用 → 401 エラーで拒否
```

### 2. 顧客一覧・検索
- [ ] 軸から受け取った顧客が一覧に表示される
- [ ] 顧客検索（電話番号・名前）が動く
- [ ] ページネーション（1000件制限）が正常
- [ ] フィルタ（scope / data_class）が効く

**テスト手順**:
```
1. 顧客一覧ページを開く
   → LINE Webhook で受け取った顧客が表示されているか
2. 検索ボックスで電話番号を入力して検索
   → 正しい顧客が絞り込まれているか
3. 複数ページをスクロール
   → ページネーションが正常か
4. フィルタ（例：data_class="real"のみ）を適用
   → 分類が正しく反映されているか
```

### 3. 架電ログ（call-log）送信
- [ ] 架電を記録すると、軸への送信が自動実行される
- [ ] メタ情報（who / when / duration / result）が記録される
- [ ] API エラー時もシステムが停止しない（非同期キューで後送信）
- [ ] ネットワーク遮断・復帰時のリトライが動く

**テスト手順**:
```
1. 管理画面から顧客を選択して「架電開始」をクリック
2. 架電ログが記録される（ローカル）
3. 軸への送信が開始される（ネットワークをサニタイズして送信確認）
4. 送信に失敗した場合、自動リトライが開始される
5. ネットワークを復旧させる
   → 待機中のログが軸へ送信される
```

### 4. 読み取り専用化（必要な場合のみ）
- [ ] LAYER_VIEW（閲覧のみ）のトークンで、編集ボタンが無効化される
- [ ] PUT / POST / DELETE メソッドが 403 Forbidden で拒否される
- [ ] 読み取り専用ユーザーが意図せず編集できない

**テスト手順**:
```
1. 読み取り専用権限のトークンでログイン
2. 「編集」「削除」ボタンが grayed out されているか
3. 編集を試みると 403 エラーで拒否されるか
4. (確認: 実装が LAYER_VIEW 対応しているか)
```

# ❂③ 保全CRMチャット向け

**報告期限**: 10/01 23:59（詳細テスト）  
**語彙統一期限**: 10/15

## 🎯 検証の目的
保全CRMが、軸台帳・後確認システムと連携して、  
顧客の状態遷移（pending → ack → settle）を正常に管理できることを確認する。

---

## ✅ 確認項目

### 1. Retention系API（pending/ack/settle）
- [ ] pending 状態の顧客が取得できる
- [ ] ack（確認）操作が軸に記録される
- [ ] settle（終了）操作が軸に記録される
- [ ] 不正な状態遷移（例：settled → pending）が拒否される

**テスト手順**:
```
1. GET /api/customers/pending で pending 顧客を取得
2. ある顧客を選んで「確認完了」を送信
   → ack が軸へ送信される
3. その顧客の状態が ack に変わることを確認
4. 「終了」を送信
   → settle が軸へ送信される
5. 既に settled な顧客に ack を送信しようとする
   → 400 Bad Request or 409 Conflict で拒否されるか
```

### 2. SMS雛形・送信フロー
- [ ] SMS雛形が軸の共有フォーマットに統一されている
- [ ] SMS送信トリガー（ack / settle など）が正しい
- [ ] SMS本文に変数（顧客名・確認内容など）が正しく埋め込まれる
- [ ] SMS送信エラー時の再試行フロー

**テスト手順**:
```
1. SMS雛形を確認（テンプレートファイルなど）
   → 用語が他チームと統一されているか
2. 顧客に SMS を送信テスト
3. SMS 本文を確認
   → 顧客名・内容が正しく反映されているか
4. SMS 送信に失敗した場合、リトライが実行されるか
```

### 3. CSV引き渡し仕様 v0.2
- [ ] CSV ファイルフォーマットが v0.2 に統一されている
- [ ] カラム名・順序が仕様通り
- [ ] 数値・日付形式が統一（例：YYYY-MM-DD）
- [ ] 文字エンコーディングが UTF-8（BOM なし）

**テスト手順**:
```
1. CSV 引き渡しファイルをダウンロード
2. 以下を確認
   - 1行目：カラムヘッダ
   - 2行目以降：データ行
   - 日付形式：YYYY-MM-DD
   - 金額：カンマなし（123000）
3. エクセルなど外部ツールで開いても文字化けしないか
```

### 4. 語彙統一（ズレ#5/12/13対応）
- [ ] 解約理由の区分値が統一されている
- [ ] 後確認結果の区分値が統一されている
- [ ] 他チーム（⑦など）と値が一致しているか

**テスト手順**:
```
1. 解約理由の list を取得（GET /api/choices?category=cancellation_reason など）
2. ④⑦など他チームの choices と比較
   → 値・表示名が一致しているか
3. DB の enum / 設定ファイルでも統一されているか
```
