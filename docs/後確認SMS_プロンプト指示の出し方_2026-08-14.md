# 後確認SMSシステム — プロンプトの指示の出し方(2026-08-14)

小柳さんからの相談:
> イメージシステム。申込み完了したお客様には、後確認をいれて了承が必要になります。その内容をお客様の携帯番号にショートメールで送り、その後に後確認の承認返信メールが届いて、それを持って後確認完了として本体システムに連動されるもの

このファイルは**そのシステムの作り方ではなく、AIへの指示の出し方**をまとめたもの。
先例: docs/勝てるくん_プロンプト設計ガイド_2026-08-12.md(同じ「指示の出し方」形式)

---

## 0. 結論(先に3行)

1. 上のイメージ文をそのままAIに渡すと、**それらしいコードは出てくるが必ず作り直しになる**。「後確認完了」の定義と「返信をどこで受け取るか」が決まっていないため、AIが勝手に決めてしまう
2. だから**1通目の指示は「作って」ではなく「作る前に、決めるべきことを質問にして出して」**にする。これが一番効く
3. 携帯番号・申込内容は個人情報。**この公開リポジトリでは実データを一切扱わない**。実装先と保存先を先に決めるまで、コードも実データも書かせない(憲法 絶対ルール2/運用規程1-1の2番目)

## 1. なぜイメージ文のままだと失敗するか

いただいた文には、AIが埋めてしまう空欄が7つある。埋めた内容が間違っていても、AIは自信満々で完成品を出してくる。

| # | 空欄 | AIが勝手に決めてしまうこと | 決めるのは誰か |
|---|---|---|---|
| ① | 「本体システム」が何か | 適当なDB/スプレッドシートを想定して設計する | 小柳さん |
| ② | 「後確認」で何を了承してもらうのか | 「申込内容でお間違いないですか」程度の文面を作る | 小柳さん+守り部 |
| ③ | 「承認返信メール」の正体 | SMSの返信/メール/Webフォームのどれか1つを勝手に選ぶ | 小柳さん(要業者確認) |
| ④ | 返信が来ないときどうするか | たいてい**何も設計しない**(黙って未完了のまま溜まる) | 小柳さん |
| ⑤ | 「はい」以外の返信の扱い | 「承認」と誤判定するコードを書きがち | 小柳さん+守り部 |
| ⑥ | 携帯番号の置き場所 | 平文でファイルに書く実装を出す | 守り部 |
| ⑦ | 返信=了承と扱ってよいかの法的根拠 | 「問題ありません」と言い切ってしまう | 守り部→弁護士 |

**③が最大の落とし穴。** 「ショートメールを送る」と「その返信を受け取る」は別の機能で、送信専用のSMS配信サービスでは返信を受け取れない場合がある(サービス・番号の種別により異なる・**要確認**)。ここを確認しないまま設計すると、システムの土台ごと作り直しになる。

## 2. 指示の出し方 7原則

1. **「完了」を先に1行で定義する** — 「後確認完了とは、○○が××した状態を指す」。ここが曖昧なままだと全部曖昧になる
2. **登場する物に固有名を付ける** — 「本体システム」ではなく実際の名前(例: glow-ma / スプレッドシート / 保険会社の申込システム)。名前が書けないものは、まだ設計できない
3. **ものの流れを矢印で書く** — 誰が→何を→どこへ。文章より矢印1行のほうが正確に伝わる
4. **正常系より先に異常系を渡す** — 「返信が来ない/文字が違う/番号が間違っている/二重に送った」を先に書く。AIは言われないと異常系を作らない
5. **個人情報の置き場所を先に指定する** — 「携帯番号はこのリポジトリに書かない」と明示。書かないと平文で書いてくる
6. **AIに決めさせない所を名指しする** — 法的有効性・お客様に出す文面の最終版・送信時間帯は人間(守り部・小柳さん)の担当だと宣言する
7. **出力の形を先に指定する** — 1通目は「質問リスト」、2通目は「設計表」、3通目でようやく「コード」。いきなりコードを頼まない

## 4. 設計の下敷き(4層に分けて考える)

`resilient-agent-design` の型に当てはめると、この仕組みはこうなる。第2便でAIが違う形を出してきたら、この表と見比べる。

| 層 | この仕組みでの中身 |
|---|---|
| Trigger | 申込み完了(本体システム側のイベント、または1日数回の定期チェック) |
| Workflow | 対象抽出 → 重複チェック → SMS送信 → 返信待ち → 返信の記録 → 本体システムへ反映 → 通知 |
| Agent(AIに任せる部分) | **原則なし。** 強いて言えば曖昧な返信文の下読み(分類案の提示)まで。**承認の最終判定はAIにさせない** |
| Guardrail | 1日の送信上限・再送3回まで・送信可能時間帯・二重送信防止キー(申込ID)・「はい」完全一致以外は人へ回す・実データは非公開領域のみ |

**この仕組みでAIが賢く判断する場所はほとんどない**、というのが重要な点。お客様の了承という法的な意味を持つ記録なので、判定は機械的な一致確認にして、迷ったら人に回すのが正しい。AIに任せる場所を探さないこと。

## 5. 三名体制議事

## 論点: 「SMSの返信をもって後確認完了とする」仕組みの是非と、指示の出し方

### スイシン(推進)
- 後確認は現状おそらく電話・手作業。SMSなら送信の手間が消え、お客様も好きな時間に返せる
- 「いつ送って、いつ返ってきたか」が自動で記録に残るのは、手作業の後確認より証跡として強い
- まず質問リスト→設計→段階実装の3便に分ければ、作り直しのコストを最小にできる

### ウタガイ(懐疑)
- **「承認返信メール」が技術的に成立するか未確認。** 送信専用のSMSサービスでは返信を受け取れないことがあり、ここが崩れると設計全体が作り直しになる(要確認)
- **本人性が担保されない。** 携帯番号にSMSを送っても、返信したのが契約者本人とは限らない(家族が代わりに返す・番号の入力ミス・番号の再割当)。「了承を得た」証拠として弱い可能性がある
- **法的有効性を誰も確認していない。** 後確認が業法上の確認義務に紐づくものなら、SMS返信で代替してよいかは弁護士確認が要る。ここを飛ばして作ると、動くけれど使えないシステムになる
- **返信が来ないケースが必ず大量に出る。** SMSの返信率は電話より低い。未返信の山を誰がいつ拾うかを決めないと、後確認が実質止まる
- 携帯番号を扱う以上、実データ投入前の守り部審査・外部専門家確認(決裁キュー既存項目)を通す必要がある。**この仕組みは既存の審査待ちの列に入る**
- SMSは文字数の制約がある(70文字前後で分割される仕様が基本。長文対応の可否は業者・キャリアによる・要確認)。確認内容の全文はSMS本文に入らない前提で考える必要がある

### ベッカイ(別解)
- 返信を「SMSの返信」にせず、**SMSにはURLだけ載せて確認ページで承認ボタンを押してもらう**方式にすれば、返信受信の技術問題・文面の揺れ判定・文字数制限が同時に消える。ワンタイムのリンクにすれば本人性も少し上がる。ただしページ実装が要る
- そもそも本体システム(申込元)に後確認機能が既にある可能性がある。**自作する前に、今使っているシステムの標準機能を確認する**のが最短
- 「AIに作らせるシステム」として考える前に、**まず1週間、手作業でSMSを送って返信率を見る**という手もある。返信率が低ければ、そもそも設計が変わる(電話併用が前提になる)
- 後確認は保険・金融領域なら業界標準のツールがあるはず。自作と既製品の比較を先にすべき

### 結論(裁定)
- 採否: **保留・上申**(指示の出し方=本ファイルは採用。仕組みの実装着手は決裁待ち)
- 理由: 指示の出し方そのものは今日から使えるので採用する。ただしウタガイの指摘のうち「返信を受け取れるか(技術)」「返信を了承とみなせるか(法務)」の2点は、どちらが崩れても設計が全部作り直しになる**前提条件**であり、これを確認する前に実装を始めるのは順序が逆。ベッカイの「URL+確認ページ方式」は、ウタガイの懸念3つを同時に解消するため、第1便の質問リストで必ず選択肢に含めること。憲法の判断順(正確性→法務→…→速度)に照らし、速度より前の2項目が未確定のため保留とする
- 見直し期限: 2026-11-14(小柳さんの回答が先に来た場合はその時点で再開)
