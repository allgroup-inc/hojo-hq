- 分類: 議事必須類型②(**不可逆な変更**=公開範囲の変更)。公開リポジトリへのコミットは git 履歴に残り、取り消せない。
  週次売上額を公開するかどうかは掲載方針にも関わるため、類型①として**小柳さん決裁**を要する
- 起票: 2026-09-30(Task 4 レビュー C3 を受けて)/ 状態: **小柳さん決裁待ち**
- 関連: `scripts/collect_weekly_metrics.py`、`.github/workflows/kekka-weekly-collect.yml`、`data/kekka_weekly_metrics.json`、
  計画書 `docs/superpowers/plans/2026-09-30-kekka-sales-automation-impl.md`(Task 5・Task 8)

## 前提の確認(2026-09-30 時点の実態)

- note API クライアント(Task 1・`scripts/note_api.py`)は、週ごとに `buyer_ids`(購入者ID)と `buyer_profiles`(購入者属性)を返す。
- Task 4 の初版は、このうち `buyer_profiles` だけを buyer_id に絞った。**`buyer_ids` は未加工のまま**、公開ファイル
  `data/kekka_weekly_metrics.json` と、`main()` の標準出力(= 公開 Actions ログ)に出す作りだった。
- **実害はまだ出ていない**。集約ワークフローは作業ブランチ上にしかなく、main に入っておらず、Secrets も未投入。
  `data/kekka_weekly_metrics.json` の `weeks` は、git 履歴を通して一度も値が入っていない(`git log -p` で確認)。
- 本リポジトリ(allgroup-inc/hojo-hq)は **PUBLIC**。note の購入者IDは note の公開プロフィールと照合できる。
  「どの週に誰が有料記事を買ったか」が誰でも読める形になる。ハッシュ化しても、ID が列挙できるため元に戻せる。
- 後続タスクの需要:
  - Task 5(facts 生成)が使うのは集計値だけ(売上・ビュー・スキ・セグメント別の率)。購入者単位は要らない
  - Task 8(セグメント判定)は `user_purchases`(利用者単位の購入履歴)を入力に取る。**購入者単位のデータは将来必要になる**

## 三名体制の議論

### スイシン(推進)
- 公開ファイルに残すのは集計値だけにする。note は `week / views_by_article / total_likes / total_sales_jpy` の4項目と、
  `buyer_count`(ユニーク購入者数)だけを書く。**ホワイトリスト方式**にし、NoteMetrics に項目が増えても、
  許可していない項目は公開されない。
- 標準出力も集計サマリ(件数・合計)だけにする。公開 Actions ログに ID を出さない。
- これで Task 5 の需要は満たせ、週次のふり返りも止まらない。すでに実装し、回帰テストを入れた
  (`test_no_buyer_ids_in_public_file` / `test_stdout_has_no_buyer_ids`)。

### ウタガイ(懐疑・反対)
1. **週次の売上額そのものが、公開してよい数字か**。`total_sales_jpy` と記事別ビュー数が毎週公開リポジトリに積み上がると、
   競合や第三者が結果マガの収益の推移を正確に追える。購入者IDを外しても、この点は解消しない。
   → **反対理由として記録する。集計値の公開可否は、エージェントでは決めず小柳さんへ上申する。**
2. **少人数の週は、集計値でも個人に近づく**。`buyer_count = 1` の週に、本人が SNS で「買った」と書けば、
   その週の売上額が誰のものかがわかる。k-匿名性の観点では、集計しても安全とは言い切れない。
3. **非公開側へ移す作業が宙に浮く**。「将来 glow-docs-private に置く」とだけ書いて、Task 8 で結局公開側に書き足されると、
   今回の修正が無駄になる。→ 採用条件: **購入者単位のデータを公開リポジトリに書く変更は、今後すべて議事を必須にする**
   (CLAUDE.md 機密区分・`churn-pii-guard` と同じ扱い)。
4. 購入者IDを「取得しているのに捨てている」状態は、データの見落としに見える。後任が善意で公開ファイルへ戻す恐れがある。
   → コード内のコメントとモジュールの docstring に、本議事への参照を残した。

### ベッカイ(別解・前提を疑う)
- **別解A: ファイルごと非公開リポジトリ(allgroup-inc/glow-docs-private)に置く。** ウタガイ1・2 を根本から解消できる。
  ただし Task 5 以降の facts 生成・記事ドラフト生成は本リポジトリの Actions で動くので、クロスリポジトリの読み取り権限
  (デプロイキーか PAT)が要る。Secrets が1つ増え、運用が複雑になる。**小柳さんの判断材料として提示する。**
- **別解B: ハッシュ化(salt 付き HMAC)した ID を公開する。** salt を Secrets に置けば、列挙しても元に戻せない。
  しかし、公開して得るもの(週をまたいだ同一人物の追跡)は Task 5 では不要で、リスクだけが残る。不採用。
- **別解C: 購入者単位のデータは note の管理画面にしかないものとし、どこにも保存しない。** Task 8 のセグメント判定を
  集計値ベースで組み直せるなら、これが最も安全。Task 8 の着手時に再検討する。
- **前提を疑う: 購入者IDは、そもそも note API から取る必要があるか。** Task 1 は仕様(設計書 §5.1「購入者属性を自動抽出」)
  どおりに取得している。取得をやめるかどうかは Task 8 の設計しだいで決まるので、ここでは取得は残し、公開だけを止める。

## 裁定(部門長)

- 採否: **スイシン案を採用**(公開ファイルと標準出力は集計値だけ。購入者ID・属性は書かない)。ウタガイ3 を採用条件とする。
- 購入者単位のデータの置き場所: **公開リポジトリには置かない**。必要になったら(Task 8 着手時)、守り部の審査を経て
  **非公開リポジトリ allgroup-inc/glow-docs-private** で扱う。そのときは別途議事を書く。
- **上申事項(小柳さん決裁)**: ウタガイ1・2(週次売上額・購入者数を公開リポジトリに毎週コミットしてよいか)。
  - 案1: 集計値は公開のまま(現実装)
  - 案2: ファイルごと非公開リポジトリへ(別解A。クロスリポジトリの読み取り権限を追加)
  - 決裁が出るまで、**集約ワークフローの本番投入(main への統合・Secrets 投入)は行わない**
- 理由: 購入者IDの公開は git 履歴に残って取り消せないため、実害が出る前に止める。売上額の公開は事業判断なので、
  エージェントの裁量の外にある(絶対ルール5)。
