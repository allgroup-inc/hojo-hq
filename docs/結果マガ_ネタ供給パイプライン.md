# 結果マガ・note・SNS ネタ供給パイプライン(Mindshareアービトラージ適用)

**ドラフト(小柳さん決裁前)**

- 基準: `.claude/skills/mindshare-arbitrage/SKILL.md`(発見→レビュー→生成→スライド化→承認投稿→分析の6段)
- 目的: 結果マガ(単発記事・毎月8/22日)、note週刊・白書、SNS投稿の**ネタ切れ防止**を仕組み化する
- 原則: 人が関わるのは「②レビュー」と「⑤承認投稿」の2ゲートだけ。他は仕組み(resilient-agent-design準拠)

## 1. 6段パイプラインの当てはめ

| 段階 | 本事業での実装 | 状態保存先 |
|---|---|---|
| ①発見 | 下記ソース群から候補収集→スコア化(新しさ×反応)→重複除去 | data/neta_candidates.json(新設・status: pending) |
| ②レビュー(人) | たかしくん週1・10分。キープ/スキップ/お気に入りの3択 | キープ分を data/tanpatsu_topics.json へ昇格 |
| ③生成 | 既存 tanpatsu-draft / note-draft が担当。writer→humanizer→criticの3段ループ。制度データは hojo-accuracy-check 必須 | posts/note/tanpatsu 等 |
| ④スライド化 | generate_sns.py / generate_images.py のカルーセル型へ流用 | posts/images |
| ⑤承認投稿(人) | SNS=social-postの承認ゲート(sns-approval)/ note=人間コピペ+publish-record | 承認履歴=Actionsログ |
| ⑥分析・学習 | data/kekka_kpi.json・note_kpi.json の反応データを①のスコア重みへ月次反映 | KPI台帳 |

## 2. 発見ソース(海外・他業界の型→沖縄向け翻訳。ネタ切れ防止の底)

| # | 元(どこで伸びている型か) | 沖縄向け翻訳の仕方 |
|---|---|---|
| 1 | **英語圏の中小企業向けgrant解説**(米SBA・grant writing系ニュースレター/YouTube) | 「海外では補助金をこう獲りにいく」→沖縄の申請準備術(gBizID・1か月前準備)に置換 |
| 2 | **他県の補助金メディア・士業の発信**(補助金ポータル、診断士・行政書士のX/YouTube) | 他県で反応が良かった切り口を、沖縄の同種制度+県内事例で先回り記事化 |
| 3 | **英語圏のAI活用事例**(X/YouTube/プロダクトchangelog。`last30days`スキルで収集) | 「沖縄の中小企業がAIで◯◯」型へ翻訳。結果マガの実例研究シリーズと相性が良い |
| 4 | **異業種の全国成功事例**(飲食・観光・農業の業界紙・事業再構築の採択事例集) | 「この業種はこの型で通った」→沖縄の同業種向け仮説記事に変換 |

| 6 | **noteの他ジャンル人気記事の「構成の型」**(docs/note販売テンプレ12_黄金構成・note多ジャンル_世界事例リサーチ集と接続) | 構成だけ借り、中身は補助金データで独自化(丸パクリ禁止・価値を足す) |
| 7 | **Reddit/HNの経営者スレ・海外中小企業の失敗談** | 「もらい損ね」「申請あるある」を沖縄の経営者の言葉に翻訳(humanizer仕上げ) |

差をつける5点(スキル準拠): 最初に見つける/自分の言葉で翻訳/価値を足す/一貫した声(CLAUDE.mdのトーン)/品質で勝つ。

## 3. 既存note自動化との接続(1節)

- **接続点は data/tanpatsu_topics.json のお題キュー**。②レビューでキープした候補を `pending` として追記すれば、既存の workflows/tanpatsu-draft.yml(毎月8/22日 09:35 JST)が自動で下書き化→LINE通知する。**生成系ワークフローの改修は不要**
- 週刊定点観測(note-draft.yml)・白書(monthly-report.yml)は⑤内製一次情報の恒常出口としてそのまま維持。新設するのは**①発見ジョブのみ**:
  - `neta-discovery.yml`(週1・月曜06:00 JST)を新設。ソース1〜4,6,7を巡回→スコア順候補を neta_candidates.json にコミット→たかしくんへLINEで「今週の候補N件」通知
  - resilient-agent-design 準拠: 状態は data/ のJSON+Gitコミット / べき等キー `neta:{source}:{url_hash}` で重複除外 / 収集失敗時は failure() LINE通知(無言停止させない) / concurrency 設定
- 公開後は publish-record.yml がX告知+キューを `published` に更新(既存のまま)。⑥の反応データ反映は月末の「前提破壊レビュー」と同時に実施

## 4. 運用ルール

1. CVはLINE登録の1点のみ(絶対ルール4)。翻訳記事でも他CVを混ぜない
2. 締切に触れる文面は締切3層ルール(hojo-deadline-alert)に従う。SNS掲載は残り30日以上のみ
3. 収集は robots.txt/規約の守り部承認済みソースに限る(絶対ルール2)。新ソース追加は守り部審査を先に通す
4. 翻訳元の明示: 海外・他業界由来のネタは「参考にした型」への言及で信用を守る(丸パクリは信用を失う)
5. 三名体制: 月1回、キープ/スキップ判断のサンプル3件をスイシン/ウタガイ/ベッカイで再点検(選定バイアスの検知)

- 見直し期限: 2027-02-06(6ヶ月。発見ソースの当たり外れをkekka_kpi実績で判定し入替)
