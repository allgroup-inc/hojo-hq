### この5件から読めること

**「3割以上でやり取りが発生する」が最大の手がかり。** 返戻(差し戻し)は少ないのに往復は3割
起きているということは、**書類の不備ではなく、確認・照会・調整の往復**が本体である可能性が高い。
不備チェックの自動化では効かない種類の負荷なので、往復の中身を分類するのが棚卸しの核心になる。

**「一切システム化されていない」は、裏を返すと基準線がゼロということ。** 台帳を1枚作るだけでも
効果が出る一方、効果測定の比較対象も無い。着手前に現状の数字を取っておかないと、後から
「良くなったのか」を言えなくなる(§5で先に測る理由)。

**3名という規模は、システム化の投資対効果が成立しにくい水準。** 判断ゲートを厳しめに置く根拠。

## 2. 置き場所の制約 — 着手前に解消が必要(重要)

**対象事業が保険に確定したため、扱うデータは保険契約の個人情報になる。**

- 本リポジトリ `allgroup-inc/hojo-hq` は**公開(public)**。コミットした瞬間に全世界へ公開され、
  git履歴・フォークに実質恒久で残る(`churn-pii-guard` の「事実として押さえておくこと」)
- したがって**保険の管理本部業務システムを、このリポジトリに実装することはできない**
- 既存の受け皿候補: **`hojo-churn`(非公開リポジトリ)**。ただし作成決裁が
  **2026-07-31から止まったまま**(`docs/決裁キュー.md` 決裁済みログ 2026-07-31 の行)

**この棚卸し(調査)自体は、PIIを持ち込まなければ本リポジトリで進めてよい。** 工程名・所要時間・
件数だけを扱い、氏名・生年月日・証券番号・契約明細は一切持ち込まない。マスク済みのものだけ。

**構築に進む場合は、hojo-churn の作成決裁が前提条件になる。** ここが開かないと着手できない。

## 3. 統合先の見直し(v1からの変更)

v1では「システム化するなら glow-ma に統合」と書いたが、対象が保険に確定したため**これは誤り**。

- `glow-ma` は GLOW の **M&A・不動産・法人保険の企業リレーション**基盤。管理対象は企業
- 保険の申込受領〜計上が扱うのは**個人契約**。データの粒度も法規制も別物

**保険側の統合先は、早期解約リスク保全システム(`scripts/churn` / hojo-churn)**。理由は、
すでに同じ顧客の同じ申込データを扱っているため。

| 保全システムが既に持っているもの | 管理本部連携との関係 |
|---|---|
| 顧客カルテ・申込み/解約/接触データ | **申込データが同一**。二重管理になる |
| 営業マン別の傾向 | 管理本部の往復も営業別に出る。同じ軸 |
| 要フォロー(放置検知) | 「申込後に止まっている案件」の検知と同型 |

**3つ目の独立システムを作らない**という方針は維持する。統合先を glow-ma から保全システムへ
差し替える。

### 営業時間の金額化(§A5)

`月あたり申込件数 × 1件あたりの営業関与時間 = 営業が事務に取られている月間時間`

これを「新規開拓に回せる時間」として表す。**機会費用であってキャッシュ削減ではない**ことを
必ず併記する(§A5の注記を削らない)。仮定単価を置く場合は前提として明示する。

## 6. 判断ゲート(先に決めておく — 後から動かさない)

結果を見てから基準を作ると、作りたい方に基準が寄る。先に置く。

| 実測 | 判断 |
|---|---|
| 月あたり申込件数が **3件未満** | **どの数値でも作らない**(投資対効果が成立しない) |
| 営業の関与が **月5時間未満** | **作らない**。チェックリスト1枚で終える |
| 月5〜20時間 | **コードを書かない対処を優先**(受付台帳1枚・往復の定型文・チェックリスト) |
| 月20時間以上、または待ち時間が総リードタイムの50%超 | システム化を三名体制で再裁定。**前提条件: hojo-churn の作成決裁**(§2)。統合先は保全システム(§3) |

管理本部3名という規模では、真ん中の「コードを書かない対処」で足りる可能性が相応にある。
そこで足りるならそれが正解であって、負けではない。
