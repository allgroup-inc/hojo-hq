# 連動アイデア：保全ログ × 未収データ で解約抑止の精度を上げる（2026-08-17）

徳元さんの保全ログ（済＝案内済／●＝コンビニ発送／実際の架電・対応記録）と、Ⅳ列の未収履歴・
現ステータス・初回引落結果を**連携**させ、早期解約を3%未満へ近づける具体案。各案は
「対象データ × 連動の仕組み × 期待効果 × 検証方法 × リスク」。既存モジュールを名指しで拡張する。

既存モジュール: `status`（分類）/`unpaid`（Ⅳパーサ）/`triggers`（予防・初動）/`triage`（今日の要接触）/
`timing`（ハザード・架電適期）/`experiment`（uplift）/`effect_learning`/`playbook`/`cohort`/`snapshot`。

---

## 観点1: 検知の精度（新トリガー／特徴量）

### 1a. 未収連鎖トリガー（未払消滅の“一歩手前”を捕まえる）★最有力
- **対象データ**: `unpaid_count`・未収の連続月（`unpaid_months`）・現ステータス（まだ成立済＝継続中）。
- **仕組み**: `triggers.py` に `unpaid_trigger` を追加。直近の未収連続月数 streak を出し、
  streak≥3＝「未払消滅目前」（4ヶ月連続で消滅）、streak==2＝「未収2連続」。継続中のみ。
- **期待効果**: **未払消滅（4ヶ月連続未払で契約消滅）を消滅前に止める**＝防げる解約の核心を先回り。
- **検証**: 合成で未収連続数と解約率の単調関係を確認し、トリガー該当者の実解約率をbacktestで裏取り。
- **リスク**: Ⅳの記法誤読（`parse_ok`監査で担保）。年跨ぎの連続判定に注意。

### 1b. 口座不備の確定判別（★＋管理ステータス①）
- **対象データ**: `unpaid_account_issue`（★）＋ 管理ステータス①「口座不備」。
- **仕組み**: ★かつ管理ステータス①=口座不備 → 「口座確認」トリガーを**昇格**（確定口座不備）。
  残高不足（★なしの未収）とは別ラベルにして打ち手を分ける。
- **期待効果**: 口座設定さえ直せば継続する層を確実に救う（打ち手が明確）。
- **検証**: 口座不備群と残高不足群で、口座確認/入金案内の効き（uplift）を別々に測る。
- **リスク**: 管理ステータス①の意味は徳元さんに要確認（下記データ依頼）。

### 1c. 初回引落失敗の即日検知
- **対象データ**: 現ステータス「不成立【引受後未入金】」＋初回引落予定日。
- **仕組み**: `status`で早期churn判定済み。加えて「引落予定日直後×未入金×継続中」を`triggers`で当日拾う。
- **期待効果**: 最速の前兆を初日に保全へ。**払込経路＝口座振替に限定**（クレカは不成立＝対象外）。
- **リスク**: 予定日の自由記述ゆらぎ（parse耐性は実装済み）。

## 観点2: 打ち手の最適化（効果測定連動）

### 2a. 済/●を保全アクションとして効果測定へ
- **対象データ**: Ⅳの済（案内済）・●（コンビニ発送）。
- **仕組み**: `effect_learning`/`playbook` に「済で救えた率」「●の後の継続率」を層別に集計。
- **期待効果**: 口座不備★→口座確認、残高不足→入金案内/●コンビニ、と**根拠づけて**打ち手を割り当て。
- **検証**: `experiment.uplift` の段階導入（0.7）で因果を確認。単純比較は参考。
- **リスク**: **Ⅳの済/●は月粒度で“接触日”が無い**→正確な因果には接触日つき保全ログが要る（データ依頼）。

### 2b. playbook を「未収理由 × 一手」に
- **仕組み**: `playbook.segment_playbook` の軸を、現ステータス由来の理由に加え **未収理由（★/残高）** で切る。
- **期待効果**: 「この理由にはこの一手」がより現場の実感に一致。

## 観点3: タイミング（ハザード × 保全ログ）

### 3a. 未収ステージ別の架電適期
- **対象データ**: 未収ステージ（1/2/3ヶ月目）× `timing`のハザード。
- **仕組み**: `timing.call_timing` に未収ステージの重みを足す。3ヶ月目＝消滅目前＝即日最優先。
- **期待効果**: 「今日動くべき人」を消滅タイムラインで正確化。

### 3b. キャパ最適配分
- **仕組み**: `triage` の並びを「守れる金額 × 未収ステージ × 架電適期」に。未払消滅目前を最上位。
- **期待効果**: 30件/日のキャパを、失う金額が大きく期限が近い順に確実に充てる。

## 観点4: クローズドループ（自動連動）

### 4a. 現ステータス遷移の追跡（救えた／失った）★有力
- **対象データ**: 月次スナップショット間の現ステータス変化 ＋ その間の保全アクション（済/●/架電）。
- **仕組み**: `snapshot` 差分で「引受OK・未収 → 成立済＝救えた」「未収 → 未払消滅/失効＝失った」を判定。
  保全アクションの有無と突合し、**保全の効果が自動で積み上がる**。resilient-agent-design（状態は
  スナップショット＝外部保存・月キーでべき等・読み取り最小権限）。
- **期待効果**: 効果測定の母数が保全ログから毎月自動で増える＝学習が回る。
- **検証**: 合成で2ヶ月分スナップショットを作り、遷移集計が正しいことをTDD。
- **リスク**: スナップショット取得が滞ると遷移が欠測（健全性監視が要る）。

## 観点5: CRM／営業連携

### 5a. 営業画面に統合トリガー
- **対象データ**: unpaid × timing × playbook の合成。
- **仕組み**: `today`/`karte` に「この人は未収2ヶ月・架電適期・口座不備 → 今日この一手」を1行で。
- **期待効果**: 営業がその日の最適行動を迷わない。**人事評価への転用は禁止**（churn-retention-ops）。

## 上位3案の具体化

### 【1位】1a 未収連鎖トリガー
```python
# schema: レコードに unpaid_months を保持（既存 unpaid_count に加える）
# triggers.py
def _recent_streak(unpaid_months, as_of):
    """as_of 直近から連続する未収月数。年跨ぎ対応。"""
    idx = {y * 12 + (m - 1) for (y, m) in unpaid_months if y}
    cur = as_of.year * 12 + (as_of.month - 1)
    s = 0
    while (cur - 1 - s) in idx:   # 直近月から遡って連続
        s += 1
    return s

def unpaid_trigger(record, as_of):
    if not record.get("is_scoreable"):
        return None                       # 継続中のみ（成立済で未収進行中）
    streak = _recent_streak(record.get("unpaid_months", []), as_of)
    if streak >= 3:
        return "未払消滅目前"             # 4ヶ月連続で消滅 → 最優先
    if streak == 2:
        return "未収2連続"
    return None
```
- **データフロー**: `unpaid.parse_unpaid` → `schema`(unpaid_months追加) → `triggers.unpaid_trigger` →
  `triage.classify`(PRIORITYに組込) → `today.html`。
- **決裁事項（小柳さん）**: 新PRIORITY順の提案＝**未払消滅目前 > 不着 > 遅延 > 未収2連続 > 口座確認 > 初動 > 高リスク**。
  未収の連続閾値（2/3ヶ月）と「未収1は当面トリガーにしない」も決裁。
- **三名体制**: ウタガイ＝「消滅目前を最上位にすると不着より優先で本当に良いか（不着も失効直結）」→
  ベッカイ＝両方を最上位帯に置き守れる金額で並べる。裁定は小柳さん決裁で確定。

### 【2位】4a 現ステータス遷移（救えた／失った）
```python
# transitions.py（新規）
def status_transitions(prev_rows, curr_rows, key=("customer_id", "apply_id")):
    prev = {tuple(r[k] for k in key): r["status"] for r in prev_rows}
    out = {"救えた": 0, "失った": 0, "変化なし": 0, "cases": []}
    for r in curr_rows:
        k = tuple(r[k2] for k2 in key)
        was, now = prev.get(k), r["status"]
        if was in ("不成立【引受後未入金】",) or "未収" in (was or ""):
            if now == "成立済":
                out["救えた"] += 1
            elif now in ("未払消滅", "失効中"):
                out["失った"] += 1
```
- **データフロー**: `snapshot`(月次) → `transitions.status_transitions`(前月×当月) ＋ 期間中の保全アクション →
  「保全あり群の救えた率 vs なし群」→ `cohort`/レポートへ。resilient-agent-design準拠。
- **決裁事項**: 「救えた／失った」の定義（どの遷移を成功とみなすか）。
- **三名体制**: ウタガイ＝「保全ありなしは無作為でない→救えた率は生存者バイアス」→ ベッカイ＝
  `experiment`の段階導入と併用し因果は別途。集計は参考として明示。
