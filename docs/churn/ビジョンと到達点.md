# 早期解約 保全システム ビジョンと到達点（北極星）

## 北極星（小柳さん 2026-08-12）
過去にわたる**全ての既契約者データを保管**しつつ、**現状ステータスを更新**しながら、
**早期解約を3%以下**に抑え、**様々な顧客に保全**を行う。**営業マンがCRM上で使い**、
**「誰に・いつ架電すれば効くか（有効な架電時期）」**まで分かるシステムを目指す。

## システム定義（小柳さん 2026-08-18・再確認）
過去**半年〜1年以内に解約になったデータから、解約の推移・傾向を算出**し、**新しく成立した契約が
入ってきたら、解約確率が高い案件を即時に発見**、**早い段階で保全して解約を阻止・継続**につなげる。
あわせて**既契約者のデータを継続的に保管・管理**するシステム。

| 定義の要素 | いまの実装 | 位置づけ |
|---|---|---|
| 解約の推移・傾向を算出（過去の解約データから） | 解約ハザード曲線・第2の山（`timing.churn_hazard_by_tenure`/`peak_windows`）＋要因別リスク（`fit`） | ✅ 実装（合成・要実データ） |
| 新規の高リスクを**即時発見** | 成立属性でのリスク採点（`score`）＝**予測の核・モデル（AUC）が要る**／併せて不着・未収の反応検知 | ✅ 実装／**モデルは実データ実行で確定** |
| 早い段階で保全 | 初動・口座確認（引落前）＋未払消滅目前・不着・再発（`triggers`/`triage`/`relapse`） | ✅ 実装 |
| 解約を阻止・継続 | 効いた一手・段階導入で因果（`playbook`/`experiment`/`imminent-uplift`/`relapse-uplift`） | ✅ 実装 |
| 既契約データを継続保管・管理 | 月次スナップショット＋保持6年＋削除監査（`snapshot`/`retention`） | ✅ 実装 |

**要点**：「反応（未収・不着）」は手作業のExcel抽出でも今すぐ拾える（フェーズ1）。だが**「新規の
即時発見＝解約確率の予測採点」はモデルが担う部分**で、これは実データを1回通して精度（AUC）を
見てから本番化する（フェーズ2＝簡単ツール/統制環境）。両輪でこの定義を満たす。

## 残る山：「有効な架電時期」をどう出すか（設計案＝強化6）

いまのトリガーは「起きた/近づいた事象」への反応。北極星が求めるのは、それに加えて
**「この顧客は今が架電の効く時期」**というデータ駆動の“いつ”。3つの部品で作れる（既存データで可能）。

1. **解約ハザード曲線（いつ解約が起きるか）** — `timing.py`
   - 成熟した早期解約者の「契約→解約の日数」分布を、経過日数バケツ（例15日刻み）で集計。
   - 出力: 「解約は契約後◯〜◯日に集中」→ **その手前が架電の勝負どき**。商品/営業/チャネル別に出せる。
   - 純・記述統計（モデル不要・断定しない）。

2. **架電適期フラグ（この顧客は今が効く時期か）** — 顧客カルテ／今日の要接触に付与
   - 継続中の顧客の現在の経過日数が「ハザードのピーク直前（＝手前で効く窓）」に入っていれば
     「架電適期」を立てる。既存の着金前・初動とも束ねる。
   - 営業マンのCRM画面に「◯◯さん：契約後△日＝今が架電適期（次のヤマは□日）」と出す。

3. **架電時期別の効果（どの時期の架電が効いたか）** — `timing.py`
   - 保全ログの「接触時点の経過日数」でバケツ分けし、早期解約率を比較。
   - 「効く時期」を過去実績から当てる。母数不足は参考、因果は段階導入（`experiment.py`）で確認。

### 営業マン（CRM）への出し方
- 顧客ごと: 「契約後○日／次の解約ヤマは△日／**今が架電適期**（or ×日後が適期）」
- チーム全体: 「架電が効く時期＝契約後◯〜◯日」ボード（商品別）。

### データの前提（既に満たしている）
- 契約日・解約日・接触日は取込済み（`schema.py`／`contact_log.py`）。
- 現状ステータスの更新＝月次スナップショットで蓄積（半年で学習可能に）。
- 顧客名は持ち込まずID管理（門前で強制）。
