## これが効く理由（モデル・運用への含意）
1. **現ステータス「引受OK」= 初回引落失敗** は、早期失効の**単独で最強の前兆**。実データで最初に狩るべき対象。
   我々の「不着」トリガー（`triggers.py`）にそのまま一致する。
2. **Ⅳ列の過去未収履歴**は強力な予測特徴量。**「未収回数」を新しい要因（factor）に追加**する価値が高い
   （繰り返し未収の顧客は解約リスクが高い）。
3. **「済」「●」は既に保全接触の記録**。徳元さんは**すでに手作業で保全している**＝効果測定（`effect_learning`／
   `experiment`）の母数が初日から存在する。過去の「済で救えたか」を測れる。
4. **理由で打ち手が分かれる**（`playbook` 直結）:
   - **★（口座不備）** → 口座確認・再設定（我々の「口座確認」トリガー）
   - **残高不足** → 入金案内・減額提案・コンビニ用紙（●）

## column_map への反映（要点）
- `debit_result` は「初回引落結果」列そのものではなく **現ステータス**から導く（引受OK→不着／成立済→成功）。

## 徳元さんへの確認事項 → 回答（2026-08-17 確定）
1. **現ステータス18種**: 全種の意味が判明。**成立済＝継続**、離脱系の分類は `現ステータス分類ルール.md` に確定。
2. **解約日**: 専用列は無く、**初回保険料着金日を解約日として使用**。ただし**成立済のときは無視**（着金日であって解約ではない）。
3. **契約開始日**: 保障開始は受注日だが、**保険料発生の起点＝契約日**。早期解約は保険料/未収の事象なので**契約日を起点**に6ヶ月を数える。
4. **Ⅳの記法**: ●＝コンビニ用紙発送／済＝未収案内で話した／○囲み数字＝該当月／**○の前の26・25＝年（2026/2025）**。
   **★＝口座不備＋口座設定が間に合わない人**。うち**口座不備は管理ステータス①に「口座不備」**と入り判別可。
5. **クレジットカード**: **初回決済失敗＝そもそも成立しない**ため保全対象外。**Ⅳの未収は口座振替が前提**。
   → 初回引落失敗の保全は **払込経路＝口座振替** に限定する。

## Ⅳ列パーサ（実装済み 2026-08-17）
`scripts/churn/unpaid.py`（`parse_unpaid`）で Ⅳ を分解 → schema に統合。
- **抽出**: unpaid_count（未収月のdistinct数）・unpaid_contacted(済)・unpaid_konbini(●)・unpaid_account_issue(★)。
- **記法**: 未＝未収／ASCII2桁 26・25＝年／○囲み①〜⑫＝月／●済★＝各フラグ。未知トークンは parse_ok=False で監査に残す。
- **要因追加**: `unpaid_band`（0／1／2+）を FACTOR_FIELDS に追加＝**繰り返し未収を予測因子に**。

### 三名体制（unpaid_band を要因に追加する決定）
- **スイシン**: 繰り返し未収は解約の最強クラスの前兆。要因に入れて採点に効かせる。
- **ウタガイ（反対）**: Ⅳの記法が複雑で誤読リスク。未知トークンで壊れると全読込が止まる恐れ。
  合成/従来データには Ⅳ が無く、常に "0" バケツになり**実データでしか効かない**＝バックテストで検証しづらい。
- **ベッカイ**: distinct集合で数え重複計上を避ける。未知トークンは parse_ok=False で拾える分だけ拾い、
  止めない。合成データにも「未収あり」を仕込めば効果を検証できる（gen_synthetic 拡張の余地）。
- **裁定**: unpaid_band を要因に追加。未知トークンは監査フラグで安全側。合成データでのfactor検証は
  gen_synthetic 拡張時に行う（次段）。
