# 予防トリガー設計 — 初回引落“前”確認 ＋ 支払い挙動ウォッチ

目標: 契約後6ヶ月以内の解約 <3%。
狙い: **早期失効の最大要因＝初回引落の失敗を「起こる前に」潰し、以降も毎月見張る**。
これは「当てるモデル」より確実で速い“予防”で、3%への最有効の一手（改善レビュー §6-A/B）。

## 前提データ（いつ揃うか＝正直に）
- **口座“普段使い”フラグ**（はい/いいえ/未確認）… 小柳さん承認済。**記録開始は守り部審査(#142)通過後**。過去は遡及せず今から積む。
- **引落予定日** … 契約日＋オフセット、または顧客管理画面の予定日。徳元さん実務では「初回引落＝翌月」＝契約から約30日。
- **引落結果**（成功/遅延/不着）＋日付 … 直近半年ぶんが出せる（徳元さん回答）。月次スナップショットで積む。

→ したがって本機能は**データ保存が積み始めてから**フル稼働。実データ投入は審査＋決裁の後。合成データでの型づくりは先行可。

## 2つの見張り

### A. 初回引落“前”確認トリガー（予防・先回り）
- **いつ**: 引落予定日の X 営業日前（例: 3営業日前）。
- **誰を**: 継続中で、口座が「いいえ／未確認」の契約。
- **何を**: 「引落は普段お使いの口座ですか」を確認し、必要なら口座変更を案内（＝徳元さんが既にやっている確認を、**失敗が起こる前に**先回り）。
- **効き方**: 不着そのものを発生させない。最大要因への“予防接種”。

### B. 支払い挙動ウォッチ（早期発見・毎月）
- **いつ**: 各月の引落日以降。初回だけでなく **2・3回目…6ヶ月窓の毎月**。
- **何を**: 引落結果が**不着→最優先で即接触／遅延→高優先**。**連続不着はエスカレーション**（帯を上げる・上長へ）。
- **効き方**: 失効の直前予兆を、毎月取りこぼさず拾う（初回だけ見て2回目落ちを見逃す、を防ぐ）。

## resilient-agent-design 4層
| 層 | 中身 |
|---|---|
| Trigger | 毎日1回。各契約の「引落予定日−Xの到来」「引落結果の更新」を検知 |
| Workflow | 口座フラグ照合→A候補抽出／引落結果照合→B候補抽出→守れる金額で並べ→今日の要接触に統合→通知 |
| Agent | なし（決定的ルール。AI判断は不要） |
| Guardrail | PIIはprivate限定・**顧客連絡は人の承認**・キャパ（30件/日）内でトリアージ・読取専用 |

## 優先度（今日の要接触への統合）
1. **不着**（Bの最優先・即接触）
2. **遅延**（B・高優先）／**連続不着**はさらに上位・エスカレーション
3. **口座 未確認/いいえ ×引落前**（Aの予防枠）
- 各バケット内は **守れる金額（リスク%×年間保険料）順**。既存「今日の30件」に統合し、キャパ内で回す。

## 現場カレンダーに乗せる（徳元さんの型を壊さない）
```
契約後3営業日: 申込内容の確認（既存）
 → 引落予定日−3営業日: 口座確認（A・新）
   → 引落後 即: 不着/遅延フォロー（B）
     → 2・3回目引落: 毎月ウォッチ（B）
       → 応当月ほか: 継続の後押し
```

## 効果測定（正直に・churn-retention-ops）
- 予防接触あり/なしで **初回引落成功率**・**6ヶ月継続率**を比較。
- **段階導入（先行/後発）で因果**を測る。**解約後接触は数えない（免疫時間除外）**。母数不足は「参考」。0/100%を断定しない。

## 規律・関門
- 実データ投入・口座フラグの記録開始は **守り部審査(#142)＋小柳さん決裁の後**。
- 営業担当別の数字は教育・型改善が目的（人事評価に使わない）。
- 統制環境（非公開hojo-churn）で運用。公開リポでは動かさない。合成では数字に意味を持たせない。

## 合成での型づくり（審査前でも可能な範囲）
現行の合成生成器に「口座普段使いフラグ・引落予定日・毎月の引落結果」を足せば、A/Bの抽出ロジックと
「今日の要接触」への統合を合成データで実演できる（実PIIは扱わない）。実装は次段で。
