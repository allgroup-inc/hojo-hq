## 位置づけ
- これは既存 `docs/守り部審査チェックリスト_実データ投入前.md` への**追補**。今回の保存決定が**特に触れる/新しく生む**論点だけを扱う。総合判定・実データ投入の可否は**既存チェックリストの関門に従う**。
- 各論点に 可 / 不可 / 条件付き可 と、確認者・根拠・期限を記録する。**未確認・不可が残る間は、スナップショットに実データを入れない**(合成データ検証は継続可)。
- 「利用目的の適合」「保持期限」「口座フラグの要否」は**外部専門家(弁護士・個人情報保護士)レビュー必須**領域。

---

## 1. 利用目的の適合(既存A) ★重点
- [ ] 「解約リスク予測・保全」のために**過去データを蓄積・保持**することが、取得時の利用目的の範囲内か。範囲外なら**利用目的の追加公表(法21条)/同意取得**を検討。
- [ ] 【リクナビ事件の教訓】契約時データを「解約リスク分析」に転用する構図の再確認(既存Aと同旨)。**蓄積によって分析が高度化する**ぶん、本人が予測できる範囲かをより厳格に。

## 2. データ最小化との整合(既存I) ★重点
- [ ] 「消さずに残す」は一見**最小化に反する**。正当化できるか＝**特定目的(モデル学習・保全)に必要な範囲・期間に限定**し、無期限・無目的に溜めないこと。
- [ ] スナップショットに**不要な個人情報を含めない**(氏名不使用・年代ビン化・ID運用は維持。生年月日など未使用列は取り込まない)。

## 3. 保持期限・削除(既存F) ★重点
- [ ] スナップショットを**何ヶ月/何年保持**し、**いつ確実に削除**するか。学習に必要な期間(例: 直近◯年)を守り部・専門家と設定。
- [ ] 期限切れスナップショットの**確実な削除手順**(バックアップ含む)。

## 4. 口座“普段使い”フラグの新設(既存A・I)
- [ ] この項目の**取得・記録が利用目的の範囲内**か(保全業務の一環として整理できるか)。
- [ ] **要配慮個人情報ではない**ことの確認(口座の利用習慣=健康情報等に当たらない)。
- [ ] **最小化**: 記録は「はい/いいえ/未確認」のみ。**口座番号・残高などの明細は持ち込まない**。

## 5. アクセス制御(既存D)
- [ ] 蓄積が増える=影響も増える。スナップショットの**閲覧・書出しの権限者を限定**し、最小権限・個人アカウント・多要素。共有ドライブ全開にしない。

## 6. 暗号化(既存E)
- [ ] スナップショット**保存先の暗号化**、および**エクスポート/転送時の暗号化**。

## 7. 監査ログ(既存G)
- [ ] **誰がいつスナップショットを取得・閲覧したか**の記録。`snapshot.py` の manifest(行数/sha256)に加え、アクセスログを残す。
- [ ] 監査(テキホウさん)が独立に点検できる証跡。

## 8. 保管場所・公開分離(既存C・F)
- [ ] 保管は**統制された社内環境(非公開)・ネット非露出**。公開リポジトリ hojo-hq とは分離。出力は `private/` 限定(gitignore・誤コミット検知が有効)。

## 9. 委託・エクスポート経路(既存H)
- [ ] 顧客管理画面からの**エクスポート経路の安全性**(暗号化・アクセス制御)、保管先の委託契約・安全管理措置。
