# 早期解約保全システム 日次運用設計（壊れにくい自動化）

`resilient-agent-design` スキルを `scripts/churn` に適用した運用設計。
手動CLIデモを、無人で回る日次運用へ載せるための設計図。

> 大原則（resilient-agent-design）: 最強のAIエージェント＝止まらないAIではない。
> **異常時に安全停止し、原因を残し、正しい地点から再開できる**ことを優先する。

## 動かす場所（最重要）

- **非公開リポジトリ hojo-churn（統制環境）で動かす。公開リポジトリ hojo-hq では動かさない。**
- 実データの本番投入は、守り部＋個人情報（コジンさん）＋監査（テキホウさん）の審査と
  小柳さん決裁の後。それまでは合成データのみ（`churn-pii-guard`）。
- 「公開と顧客データ処理を分離」という規律を、文章ではなく**環境で**担保する。

## 4層で設計する

| 層 | 内容 |
|---|---|
| **Trigger** | 毎朝1回、または顧客管理画面のCSVエクスポート着信時に起動 |
| **Workflow** | 取込 → スキーマ検証 → fit → **backtest(AUC)** → score → 初回引落アラート → 守れる金額一覧 → カルテ生成 → 通知（すべて決定的なコード処理） |
| **Agent** | 最小限。モデルは決定的なのでAI判断は不要。将来「最初の一手」の個別最適化にだけ限定して使う |
| **Guardrail** | AUC未達→公開停止／PIIは公開リポに出さない／顧客連絡は人の承認／読取専用 |

## 7原則の churn への当てはめ

1. **AIへ渡すのは判断だけ** — 取込・検証・学習・採点・集計・出力は全部コード。AIは原則ゼロ。
2. **完了条件はシステムで判定** — 取込件数・スキーマ適合・**AUC≥閾値**・出力行数を機械で確認。「できました」で進めない。
3. **状態は外部保存** — `job_id` / `status` / `current_step` / `last_error` を `private/` 配下のJSONへ。実行履歴が監査ログになる。
4. **べき等性で二重実行防止** — `idempotency_key = score:<YYYY-MM-DD>`。同じ日の再実行は何もしない。副作用（顧客連絡）には必須。
5. **リトライは上限つき** — 一時エラーのみ最大3回（30秒→2分→10分）。認証・権限・入力不正は再試行せず停止して通知。
6. **権限は最小から** — CSVは読取専用・顧客への自動送信なし・書込は出力先ディレクトリのみ。
7. **ルールは環境で守る** — 「PIIを出すな」と書くだけでなく、非公開リポ・読取権限・PIIガードHook（`churn-pii-guard`）で強制する。

補足: 分業は慎重に。1本のワークフローが順番に進める形で十分。無理にAIを増やさない。

## 止める仕組み（品質と信頼の要）

- **AUCゲート**（`churn-model-quality-gate`）: バックテストのAUCが閾値未満なら、一覧・カルテ・アラートを **publishしない**。当たらないモデルを現場に出さない。
- **PIIガード**（`churn-pii-guard`）: 出力（カルテ／一覧／モデル）は `private/` 限定。公開リポへの混入はHook＋CIで機械的に停止。
- **顧客連絡は人の承認**（`churn-retention-ops`）: アラートや一覧は「提示」まで。実際の架電・LINEは保全担当が判断して実行。締切アラートとは別系統。

## 実行方式と段階導入

- **方式**: 非公開リポの GitHub Actions（このグループの標準・AI判断が少なく決定的な処理向き）。試作は `/loop`、安定運用は Actions。
- **段階（権限は最小から上げる）**:
  1. 読取のみで採点・一覧・アラート生成 → 保全担当が見るだけ
  2. 効果測定（接触ログ）を貯める → 免疫時間を除外・母数不足は「参考」で正直に測る
  3. 効いた型が見えたら、承認つきで一部を自動化（ガードレール内で少しずつ）

## 決裁・設計事項（人が決める）

- 実行環境・スケジュール・権限・保持ルールは守り部と設計し、**最終決定は小柳さん**。
- AUCの本番閾値、放置検知の日数、リスク帯などの業務定数は小柳さん決裁（勝手に変えない）。
- 数値はすべて合成データ。本番の精度は実データのAUC確認後に判断する。
