# 顧客データ保存設計（消さずに残す仕組み）

## 決裁の記録
- **2026-08-07 小柳さん承認**：早期解約保全のため、上書きで消えている予兆データを「消さずに残す」運用への切替と、口座確認結果を1列で記録開始することを承認。
- ただし**実データの本番投入は、守り部＋個人情報（コジンさん）＋監査（テキホウさん）の審査（保持期限・アクセス制御の確定）の後**（`churn-pii-guard` ルール4）。本設計はその審査に上げるための土台。

## 背景（なぜ必要か）
保全責任者・徳元さんのヒアリングで判明：
- 「初回引落の結果（不着・遅延）」「引落口座が普段使いか」は早期失効の最強の予兆で、現場は把握している。
- しかし顧客管理画面は**古い契約を上書き**するため、過去分が消え直近半年しか残らない。
- 「どんな契約がやめやすいか」を学習するには過去実績が必要だが、その予兆が消えている＝**蓄積の逆**。

→ 上書きをやめ、**月次スナップショットで履歴を積む**。半年後には予兆つきの決着履歴が貯まり、モデルが学習できる。

## 何を残すか（スナップショット対象）
顧客管理画面から月次でエクスポートし、**上書きせず日付つきで保存**する：
1. 申込台帳（契約日・商品・保険料・営業担当・現ステータス 等）
2. **初回引落結果**（成功／遅延／不着）とその日付
3. 接触ログ（いつ・種別・担当・内容）
4. **口座“普段使い”確認結果（新設・下記）**

## 口座“普段使い”フラグの新設
- 徳元さんが初回引落案内時に既に口頭確認している内容を、**「はい／いいえ／未確認」の1列**として記録開始。
- **過去分は遡及しない**（一元管理されていないため）。**今から積む**方針。半年後から学習に効き始める。

## どう残すか（月次スナップショット方式）
- 命名：`private/snapshots/<YYYY-MM>/`（統制環境の private 配下・gitignore）。
- **べき等**（`resilient-agent-design` ④）：同月のスナップショットが既にあれば上書きしない（履歴保護）。
- 各スナップショットに manifest（`snapshot_id` / `as_of` / 行数 / 元ファイルのハッシュ）を添え、**取得の事実を監査可能**にする。
- スナップショット自体が「状態の外部保存」（同③）であり、履歴＝監査ログになる。

## 保存場所・権限・保持（守り部と確定する項目）
以下は**守り部＋個人情報＋監査で確定**（本設計では枠だけ提示、数値・期限は審査で決める）：
- **場所**：公開リポジトリではなく、統制された社内環境（非公開）。公開と顧客データ処理を分離。
- **アクセス制御**：最小権限（`resilient-agent-design` ⑥）。閲覧・書出しの権限者を限定し、監査ログを残す。
- **保持期限**：個人情報保護法・保険業の監督指針に沿って設定（保持しすぎない・目的外に使わない）。
- **暗号化・分離**：保存時の暗号化、バックアップの扱い。

## 段階（安全に積み上げる）
1. **今から**：月次スナップショットを開始（＝履歴の起点）。口座Y/N列の記録も開始。
2. **貯まり次第**：初回引落・接触ログを学習特徴に追加できるか検証（本番はAUC確認後）。
3. **効果測定**：接触ログで、免疫時間を除外・母数不足は「参考」で正直に測る（`churn-retention-ops`）。

## 残る関門（人が決める）
- 保持期限・アクセス制御・暗号化の具体は**守り部審査**で確定。
- 保存対象・列の追加など仕様変更は**三名体制議事（`hojo-triangle-review`）**でウタガイの反対理由を残して決裁に上げる。
- **実データ投入は上記審査とご決裁の後**。それまではこの仕組みを合成データで検証する。
