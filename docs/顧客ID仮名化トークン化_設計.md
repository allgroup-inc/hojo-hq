# 顧客IDの仮名化/トークン化 設計(データ最小化・最高水準)

作成日: 2026-07-26 / 起案: Claude(churn-pii-guard 準拠)/ 決裁: 守り部＋監査＋小柳さん
目的: 直接識別子(氏名・連絡先・生年月日など個人を直接特定できる情報)を分析・保全の処理系から切り離し、
万一 分析データや出力が漏れても**それ単体では個人を特定しにくく**する。最高水準の要件「データ最小化・仮名化」を満たす。
関連: `docs/顧客データ_セキュリティ運営体制_最高水準.md` / スキル `churn-pii-guard`

---

## 1. 用語(先に揃える)
- **直接識別子**: 氏名・電話番号・メール・住所・生年月日(フル)・保険証番号など、単体で個人を特定できるもの。
- **準識別子**: 年代・性別・地域・商品など、単体では特定できないが**組合せで再識別され得る**もの。
- **仮名化(トークン化)**: 識別子を、意味を持たない値(トークン)に置き換えること。鍵がなければ元に戻せない。
- **本人台帳**: トークン ↔ 氏名等 の対応を持つ、最小権限・暗号化された別管理の台帳。

## 2. 方針(2層に分ける)

```
┌───────────────────────────┐        ┌──────────────────────────────┐
│ 本人台帳(別管理・最小権限)   │        │ 分析・保全の処理系(churn)      │
│ token ↔ 氏名/連絡先/生年月日  │  ──▶   │ token(仮名ID)＋準識別子だけで回す │
│ 暗号化・限定者のみ・監査ログ  │  照合   │ 氏名等の直接識別子は持ち込まない  │
└───────────────────────────┘        └──────────────────────────────┘
        鍵を持つ限定者だけが                 万一漏れても単体では特定困難
        token→本人を引ける
```

- **原則(ベッカイの最小化):** 氏名・連絡先・生年月日フルなどの**直接識別子は、分析系(churn)に一切取り込まない**。取込の入口で落とす。分析に要るのは token(仮名ID)＋準識別子(年代・性別・地域・商品・金額帯・チャネル・担当)だけ。
- **顧客IDのトークン化(スイシン):** 別システムの顧客IDは、他システムと横断照合されるリスクに備え、churn 側では**決定的トークン**(HMAC-SHA256、鍵つき)に置換する。同じ顧客IDは常に同じトークンになるので、**複数申込みの名寄せ・接触履歴の束ねは不変**。
- **鍵の管理:** トークン化の鍵(secret)は `private/` の**外**(環境変数/シークレット管理)。リポジトリにもデータにも置かない。鍵が漏れなければトークンから顧客IDの復元は困難。
- **出力の最小化:** カルテ・一覧・コンソールには氏名等の直接識別子を載せない(token＋準識別子のみ)。現場が本人照合を要する場合は、**権限のある人だけが本人台帳で token→氏名を引く**。

## 3. 実装スケッチ(環境非依存で先行可能)
- `scripts/churn/tokenize.py`(純標準ライブラリ `hmac`/`hashlib`):
  - `tokenize(customer_id, secret) -> str`: `HMAC-SHA256(secret, customer_id)` の先頭を16進で切り出した決定的トークン。
  - 鍵 `secret` は環境変数 `CHURN_TOKEN_SECRET`(private・非コミット)。未設定なら明示エラー(黙って弱い既定値を使わない)。
- 取込の入口(`intake`/`interactions`)で、`customer_id` を token に置換するオプションを足す(既存の束ね・採点はそのまま=token を customer_id として扱う)。
- 直接識別子の列(氏名・連絡先等)は `column_map` で**取り込まない**(マップしない=読み捨て)。
- ※実装は本設計の承認後。今は設計まで。

## 4. 三名体制の議事(仮名化方式の裁定)

### スイシン(推進)
- 顧客IDを HMAC で決定的トークン化＋直接識別子は非取り込み。名寄せを保ったまま、漏えい耐性を大きく上げられる。実装は入口の変換だけで最小。鍵を環境シークレットにすれば復元困難。

### ウタガイ(懐疑)  ← 反対必須
- **顧客ID空間が小さい/連番だと、鍵を知らなくても総当たり(辞書攻撃)でトークン→IDを逆引きできる恐れ**。HMACでも入力空間が狭いと仮名化の意味が薄れる。
- **鍵管理を誤れば全部無意味**(鍵がデータと同じ場所に漏れたら即復元)。鍵ローテーション時に過去トークンとの整合も要る。
- **準識別子の組合せ(年代×地域×商品×担当)で再識別されるリスクは、仮名化では消えない**(k-匿名性は別問題)。「トークン化したから安全」と誤認するのが最大の罠。

### ベッカイ(別解)
- そもそも**直接識別子を分析系に一切入れない**のが最も単純で安全。トークンすら要らず、別システムの顧客IDをそのまま使い、氏名等を持ち込まないだけでよいケースも多い。トークン化は「顧客IDが他所と紐づく/連番で推測可能」な場合の**追加防御**と位置づける。
- 準識別子の再識別対策は、仮名化ではなく**出力の最小化・営業スコアの公開範囲・アクセス制御**で対処する(k-匿名化は将来課題)。

### 裁定(小柳さん＋守り部へ上申)
1. **直接識別子は分析系に取り込まない**(ベッカイの最小化を基本方針に採用)。
2. 顧客IDは、横断照合・推測リスクに備え **churn 側で HMAC トークンに置換**(スイシン採用)。鍵は環境の外部シークレットで管理し、ローテーション手順を用意。
3. **「トークン化=安全」と誤認しない**(ウタガイ)。準識別子の再識別は、出力最小化・公開範囲・アクセス制御で別途対処し、k-匿名化を将来課題として残す。
- 鍵の管理主体・ローテーション運用・本人台帳の管理は**小柳さん決裁事項**。見直し期限: 最長6ヶ月。
