# 議事_20260819_BlueBean CTI連携

## 背景
CLAUDE.md体制決定(2026-08-19)により、glow-ma配下のシステム変更は❶(本セッション)に一本化された。
本論点は「架電情報をこのシステム(glow-ma)に連動できないか」という小柳さんの要望(3.手紙→架電→訪問→ログ蓄積)
のうち、CTI(BlueBean/ソフツー)からの架電履歴自動取り込みを扱う。

外部システムからの定期取得結果を企業マスタと自動突合し、対応履歴ログへ自動書き込みする「本番設定」の
新規追加にあたるため、CLAUDE.md三名体制ルール②(不可逆な変更: 外部送信/配信・本番設定の変更)に該当し、
議事化する。

外部接続情報(ドメイン `bbw2960-g-low2.softsu.com`、campaign_id 8002「返信用封筒記載・GLOW管理番号」、
admin認証情報)は本番接続テストで確認済み(2026-08-19、小柳さん実施)。認証情報はGAS Script Propertiesにのみ
保存し、リポジトリにはコミットしない(既存のLINE/Gemini/Claude/Slackキーと同じ運用)。

## 論点: BlueBean通話履歴の取得・企業マスタ突合・対応履歴ログ自動記録の方式

### スイシン(推進)
- BlueBeanは架電システムとして既に現場で稼働中。手紙(QR/GLOW管理番号)→架電→訪問という導線の「架電」区間のログが
  これまで完全に手動転記(またはログなし)だったため、自動化すれば入力漏れ・遅延がなくなる
- BlueBeanの`顧客発着信履歴出力API`は取得専用(pull型)で、認証・campaign_idともに動作確認済み。プッシュ型
  webhookが存在しないため、GASの時間主導トリガーで定期ポーリングする以外に選択肢がない
- 電話番号での突合は`GlowDedupe.normalizePhoneNumber`が既存(DNC伝播で実績あり)。対応履歴ログへの重複防止つき
  自動追記も`ShippingRunner.gs`の`appendShippedInteractionLogIfNew_`に前例があり、同じ設計パターンを再利用できる

### ウタガイ(懐疑)
- 電話番号一致だけでは「電話機で直接発信した場合はコール履歴と顧客データが紐づかない」(BlueBean仕様書の制約)、
  誤発信・共有電話番号(親子会社・代表電話の共用)による誤マッチのリスクがある。誤って他社の対応履歴ログに
  書き込まれると、担当者が誤った前提で次のアクションを判断しかねない
- BlueBeanのcall_type=0(内線)を除外しても、call_status="キャンセル"(不通・出なかった)まで「電話」種別で
  対応履歴ログに記録すると、実態は「架電したが接続できなかった」のに正式な対応実績として計上されてしまう
- 認証情報は現状「admin」という人間の管理者アカウントと同一で、API連携専用アカウントではない(ユーザーへの
  確認は「確認中」のまま)。人間の管理者がパスワードを変更した瞬間に自動連携が無言で止まる

### ベッカイ(別解)
- 自動書き込み対象を「マッチ成功 かつ call_status=完了」のみに限定し、それ以外(未マッチ・キャンセル)は
  「CTI通話履歴」タブに記録は残すが対応履歴ログへは書き込まず、人間のレビュー対象として一覧化する方式にすれば、
  ウタガイの誤記載リスクを抑えられる
- 突合は「電話番号」「携帯番号」どちらも既存の複数企業でヒットした場合(同一電話番号を複数企業が持つケース)は
  自動マッチさせず未マッチ扱いにする(単純な最初の1件ヒットで決め打ちしない)

### 結論(裁定)
- 採否: 採用(ベッカイの限定方式を採用)
  1. 対応履歴ログへの自動書き込みは「電話番号が企業マスタと一意にマッチ」かつ「call_status=完了」の場合のみ
  2. call_type=0(内線)は取得対象から除外
  3. 全件(マッチ有無・ステータス問わず)は「CTI通話履歴」タブに記録し、`group_callid`で重複取得を防止する
     (再実行しても二重記録しない)
  4. 認証情報はScript Propertiesにのみ保存。「API連携専用アカウントかどうか」は小柳さんへの確認事項として
     README/TODOに明記し、人間の管理者アカウントと共用のまま運用する場合のパスワード変更時の影響を注記する
- 理由: 自動化の効果を得つつ、ウタガイが指摘した誤記載リスク(共有電話番号・不通コールの実績計上)を
  限定条件で防止できる。未マッチ・キャンセル分はタブに残るため人間の確認導線も確保される
- 見直し期限: 2026-11-19(3ヶ月後。実運用でのマッチ精度・誤記載有無を見て要件を見直す)
