# もらいわすれ堂 診断ページの外部監視 設計(A案・C案)

対象: もらいわすれ堂(株式会社フクギイロ・moradou.jp)の診断ページ。沖縄企業のミカタとは別の事業。
関連: `docs/議事_20261103_診断ページ15分監視.md`(15分監視・停止検知・LINE 送信担当)

## なぜ

PR #566 で入れた15分監視・停止検知は、どちらも GitHub Actions のスケジュール起動で動く。2026-11-04 には統合から約2時間、リポジトリ全体で定時起動が1件も来なかった。過去2週間の実測でも、4時間おきのワークフローが2〜9時間おきにしか起動していない。**スケジュール起動が止まると、監視も停止検知も同時に止まり、誰も気づけない。** そこで、GitHub Actions の外に見張り役を置く。

| 案 | 見張るもの | GitHub Actions が止まったとき | このPRで |
|---|---|---|---|
| A | 15分監視が動いていること(ハートビート) | 外部サービスが「ハートビートが来ない」ことで運営へ知らせる | **実装**(Secret 未設定の間は何もしない) |
| C | moradou.jp の診断ページと制度データの公開URL | 外部サービスが直接 moradou.jp を確かめる | **設計のみ** |

外部サービスの契約・アカウント作成・課金・本番監視の開始は、別途小柳さんの承認を得てから行う。

## A案: 監視が止まったことを外から知らせる(ハートビート)

### 仕組み

- 15分監視(`.github/workflows/diagnosis-monitor.yml` の `monitor` ジョブ)の最後に、`scripts/diagnosis_heartbeat.py` が外部サービスのハートビートURLへ1回送る
- 外部サービスは「最後のハートビートから一定時間たっても次が来ない」ことを自分で数えて、運営へ知らせる。GitHub Actions が止まっていても気づける

| 状況 | 送るもの | 外部サービスの動き |
|---|---|---|
| 監視が診断ページを検査し、障害Issueの更新まで終えた | 成功(本文に「正常」または「異常あり(症状)」の要約) | 正常(Up) |
| 診断ページに異常がある | 成功(監視は動いている。ページの異常は障害Issue と LINE が知らせる) | 正常(Up)。本文に異常の要約が残る |
| 監視が動いたが、検査まで届かなかった(準備の失敗・結果が壊れた) | 失敗(`/fail`) | すぐに Down として知らせる |
| 障害Issueの更新に失敗した | 失敗(`/fail`) | すぐに Down として知らせる |
| 監視ジョブが途中で落ちた(checkout の失敗など) | 予備ジョブ(`fallback`)が失敗(`/fail`)を送る | すぐに Down として知らせる |
| スケジュール起動が来ない・Actions が止まった | 何も届かない | 期限+猶予を過ぎたら Down として知らせる |

- ハートビートのURLは Secret `DIAG_HEARTBEAT_URL` で渡す。**URLそのものが鍵**なので、ログ・Issue・例外文面に出さない(テストで確かめている)
- 未設定なら何もしない(「未設定のため送りません」とだけ出す)。https 以外のURLは送らない
- 送れなかったときも監視ジョブは赤にしない(`continue-on-error`)。外部サービス側が「来ない」ことで気づく
- 送るのは15分監視の1か所だけ。停止検知・LINE 送信担当は対象外(15分監視が動いていれば、停止検知が送信担当の停滞を見る)

### サービス候補と費用

| 候補 | 費用 | 備考 |
|---|---|---|
| **healthchecks.io(推奨)** | 無料の Hobbyist プラン(20件まで・各100件の記録)。有料は月20ドルから | ハートビートのURL形式(成功は `<URL>`、失敗は `<URL>/fail`)にそのまま合う。本文を記録に残せる。メール通知が無料プランに含まれるかは、契約前に公式の料金ページで確かめる |
| Cronitor・Better Stack など | 無料枠あり(条件は各社で異なる) | `/fail` の形式が違う場合は `diagnosis_heartbeat.py` を合わせる |

### 外部サービスの設定(承認後に小柳さんが行う作業)

1. healthchecks.io のアカウントを作る(無料の Hobbyist プラン。クレジットカードは不要とされる)
2. チェックを1つ作る
   - 名前: 「もらいわすれ堂 診断ページ監視」
   - 期限: **Period 1時間・Grace 2時間から始める**(最後のハートビートから約3時間で知らせる)。15分にすると、GitHub のスケジュール起動の遅れで誤報が続く。2週間の実測を見て縮める
3. 通知先を設定する: 運営のメールアドレス(決裁事項)。LINE Notify は 2025-03 に終了しているので使わない
4. チェックのハートビートURLをコピーし、GitHub の hojo-hq の Settings → Secrets and variables → Actions に `DIAG_HEARTBEAT_URL` として登録する。URLを Issue・チャット・メールに貼らない
5. **登録した直後に、ハートビートURLを1回だけブラウザで開く**(計測を始めるため)。healthchecks.io は最初のハートビートが来るまで「New」状態で通知しないので、15分監視が一度も定時起動しないと永遠に知らせない

### 動き(初回起動前・初回通知・復旧)

| 段階 | 状態 | 通知 |
|---|---|---|
| Secret 登録前 | 監視は今までどおり。ハートビートは送らない | なし |
| チェックを作った直後(ハートビート0件) | New | なし(手順5で1回送ると計測が始まる) |
| 15分監視が動いている | Up | なし |
| 期限を過ぎた(猶予の間) | Late | なし |
| 期限+猶予を過ぎた / 失敗が届いた | Down | **メールが1通**(以後、Up に戻るまで同じ内容は送られない) |
| 次の成功が届いた | Up | **復旧のメールが1通** |

### 残る制約

- 外部サービス自体が止まると知らせは来ない(15分監視・停止検知・LINE とは独立した経路なので、同時に止まる可能性は低い)
- 期限と猶予を長くすると知らせが遅れ、短くすると GitHub の遅れで誤報が出る
- ページの中身が正しいかは見ない(それは15分監視の役目。監視が止まっている間の中身は C案で補う)

## C案: moradou.jp を外から直接確かめる(設計のみ)

### 確かめるもの

`scripts/deploy_moradou.py` で組み立てた配信ツリーを手元で確かめ、本番と同じパスで次の3つを見る。

| # | URL | HTTP | 含まれていること(文字列) | 何を見つけるか |
|---|---|---|---|---|
| C1 | `https://moradou.jp/shindan/` | 200 | `3分でもらい忘れ診断` と `fetch("../seido.json")` | ページの消失・差し替え。**11/2 の障害**(制度データを読みに行く先が `../../data/fukugiiro/seido.json` に変わった)も、後者の文字列が消えることで見つかる |
| C2 | `https://moradou.jp/seido.json` | 200 | `"fk-kuni-jidoteate"`(必ず載る国の制度の1つ) | 制度データの消失・空・壊れ(件数0件のときもこの文字列が無くなる) |
| C3 | `https://moradou.jp/shindan/logic.js` | 200 | `matchSeido` | 診断の判定ロジックの消失 |

- 文字列は、診断ページ・判定ロジックを作り変えると変わりうる。作り変えるPRでは、この表と外部サービスの設定を一緒に直す(15分監視の自己テストと同じ扱い)
- データの鮮度(30時間以内の更新)と、件数が判定ロジックと合うか(誤差0件)は、外部の死活監視では見られない。そこは15分監視の役目のまま

### 誤検知を防ぐ

- 間隔は5分。**2回続けて失敗したら知らせる**(確認期間を設定できるサービスを選ぶ)
- タイムアウトは30秒。ページの大きさや応答時間ではなく、HTTP の応答コードと文字列だけで判定する
- 監視サービスは JavaScript を動かさないので、GA4・Plausible の利用実績には混ざらない
- moradou.jp の配信(GitHub Pages)は差し替えが一度に切り替わるので、組み立て中に壊れて見える時間は無い。それでも誤報が続く場合は、組み立ての時刻(03:30 / 09:30 / 15:30 / 21:30 JST の前後)と照らす

### 異常時の運営通知

- 通知先は運営のメールアドレス(A案と同じ宛先にする。決裁事項)
- 1回の Down で1通、復旧で1通。続いている間は送らない
- 顧客向けの LINE とは別の経路(LINE の通数を使わない)

### サービス候補と費用

| 候補 | 費用 | 注意 |
|---|---|---|
| UptimeRobot | 無料プラン(50件・5分間隔・文字列の確認あり) | 無料プランを事業に使ってよいかの規約が、情報源によって食い違う(2024-10 以降は非商用に限るとする記事と、2026-05 に商用可へ戻ったとする記事がある)。契約前に公式の規約を確かめる |
| Better Stack など | 無料枠あり | 確認期間(連続失敗で知らせる)を設定できるかを確かめる |
| 自前(Cloudflare Workers の定期実行など) | 無料枠あり | 作る・保守する手間がかかる。通知の仕組み(メール送信)も自前になる |

### 承認後に必要な作業

1. サービスを決め、規約(事業での利用)を確かめる
2. 3つのURLを、上の表の文字列で登録する(間隔5分・連続2回で通知・タイムアウト30秒)
3. 通知先(運営のメール)を設定する
4. 1週間、誤報と見逃しを記録して、間隔・確認期間を見直す
