## 8. 止めたいとき・戻したいとき

### コードを変えずに止める(Actions 画面の「Disable workflow」。元に戻すのは「Enable workflow」)

| 止めたいもの | 止めるワークフロー | 止めた後に起きること |
|---|---|---|
| 監視からの LINE だけ | `diagnosis-line-sender` | Issue は今までどおり作られる。送信要求は Issue に残り、再開すると重要度の高い順に送る(7日を過ぎた要求・解消済みの障害の未送信の通知は取り下げる)。6時間を過ぎると停止検知が「送信担当の停滞」を Issue に1件残す |
| 監視全体(誤報が続くときなど) | `diagnosis-monitor-watchdog` → `diagnosis-monitor` → `diagnosis-line-sender` の順 | 停止検知を先に止めないと、監視の無効化を「監視が動いていません」として起票する。開いている Issue は手で閉じる |

- 送信記録は `bot/diagnosis-line-state` ブランチにある。消すと上限の数え直しが0から始まり、送りかけの予約も消える(同じ通知を二重に送るおそれ)ので、送信担当が動いている間は消さない
- 顧客向けの LINE 配信(`line-notify` を使う既存のワークフロー)は、これらを止めても影響を受けない

### 公開用の制度データ(`site/fukugiiro/seido.json`)

- **保留が続く**(Actions のログに「公開用 seido.json の更新を保留しました」が続く): 利用者には前回の公開データが表示され続ける(件数は減らない)。理由は `data/fukugiiro/publish_status.json` の `reasons` と `failed`(HTTP ステータス付き)を見る。正当に終わった制度ならシードから外して `RETIRED` に根拠を書く PR を出す。取得の失敗なら出典を直す
- **誤ったデータが公開された**(判定をすり抜けた場合): `site/fukugiiro/seido.json` を直前の正しい版へ戻す PR を出す(自動コミット `auto: fukugiiro seido update …` を revert する)。moradou.jp には次の組み立てで反映される
- main への直接 push はしない(修正も PR で行う)
