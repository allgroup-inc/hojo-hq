## 1. 責任分界の提案(ここが本メモの主題)

2つのシステムが同じ「営業活動」を扱うため、境界を決めないと二重管理になります。提案は次のとおり。

| | 家計のポっ(apo-kanri) | 対面営業マン物件管理システム |
|---|---|---|
| ひとことで | **予定を回す** | **誰に会うかを作る** |
| 持つもの | 日時・場所・担当営業・アポ入れ担当・ステータス・変更履歴 | 顧客/世帯情報・訪問履歴・架電リストと結果・リードソース・見込み度・提案商品 |
| answers | 「今日は誰がどこへ行くか」「空きはどこか」「ずれたら誰に伝わるか」 | 「次に誰へ架電するか」「この顧客は何をどこまで提案済みか」 |
| 持たないもの | 顧客の連絡先・架電履歴・リードソース | アポの当日運用(遅れ・代打・ダブルブッキング) |

**接点は2か所だけ**にするのが健全だと考えます。

1. 架電などでアポが取れた → **家計のポっに1件登録される**(誰が登録するかは §4)
2. 家計のポっで「実施済」「申込み」になった → **結果が物件管理側へ戻る**

## 2. こちらで作ってしまった、そちらに属する仕様

家計のポっから外す予定の2項目です。**そのまま採用せず、物件管理システムの文脈で再設計してください。**

### アポ種別(4区分)

```
再訪(既存) / 新規(紹介) / 新規(ご家族) / 新規(その他)
```

- 出どころ: 小柳さんの説明「再訪=過去訪問した人へ架電して営業本人がアポを切る/新規=お客様の紹介かご家族」
- 目的: 再訪と新規は決まり方がまるで違うため、**混ぜた平均の申込み率は改善判断に使えない**
- 注意: この区分は「リードがどこから来たか」の属性であり、リードを管理する側が持つのが自然

### 紹介元(任意入力・自由記述)

- 「◯◯様のご紹介」と書ける1行。新規のときだけ入力欄を出す設計にしていました
- 目的: 誰の紹介が成約につながっているかを後から辿る(御礼・次の紹介依頼に使える)
- 注意: 紹介元は**お客様のお名前**が入るため、公開リポジトリに実データを置かない前提が必要

### 集計ロジック(参考実装)

`buildBreakdownStats_` という共通処理で、任意の軸(種別・温度感など)ごとに
「訪問実施(実施済+申込み)を母数、申込みを分子」として率を出しています。
必要であれば `apo-kanri/src/apoCore.js` の該当箇所をそのまま持っていってください
(母数0のとき率を `null` にして「0%」と断定しない作りにしてあります)。

## 3. こちらで踏んだ落とし穴(同じ穴に落ちないために)

同じGAS+スプレッドシート構成なら、そのまま効くはずのものです。**ここが本メモで一番価値がある部分**だと思います。

| 落とし穴 | 内容 |
|---|---|
| **認証で全員締め出し** | GAS Web Appのデプロイで実行ユーザーを「自分」にすると、個人Gmail運用では `Session.getActiveUser().getEmail()` が空になり、**所有者以外の全員がログイン不可**になる。「ウェブアプリケーションにアクセスしているユーザー」にすること(CLAUDE.md §技術構成に規律として追記済み) |
| **テスト全パスでもバグは残る** | 純ロジックのテストだけではGAS層(シート読み書き・通知の結線)が素通りする。独立レビューで10件出た。スプレッドシートとSlackをモックした統合テストを別途書くと捕まる |
| **通知を増やすと全部読まれなくなる** | 通知は5種に限定した。中身の薄い定期配信を足すと「この通知は読まなくていい」学習が起き、肝心の緊急連絡の既読率まで下がる |
| **数値の人事評価利用** | 転換率・稼働率は**チーム全体のみ**表示し、個人別には出していない。画面にも「評価目的では使いません」と明記。人が見られていると感じた瞬間に入力が歪む |
| **少件数の率は嘘をつく** | 率には必ず母数を併記し、母数10件未満は「参考値」と明示している |
| **自動で決めない** | 遅れそう連絡は後続アポの時刻を自動変更しない。代打候補も自動アサインしない。判断と顧客連絡は人が持つ |
| **手貼りセットアップの事故** | claspを使わない人向けに全ソースを1ファイルへ連結した `dist` を生成し、**CIで元ソースとの同期ずれを検出**している。再生成忘れで古いコードが手貼りされる事故を防ぐため |
