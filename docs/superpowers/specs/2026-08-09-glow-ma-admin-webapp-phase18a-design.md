# glow-ma Phase 18a: 管理画面Web App化(企業一覧・詳細の閲覧) 設計書

**日付**: 2026-08-09
**背景**: 既存の「GLOW企業リレーション台帳(glow-ma) 管理画面デモ」Artifact
(`https://claude.ai/code/artifact/82c8d21d-4b76-490f-ba92-8821c6801151`)は
クライアントサイドのみのモック(固定配列`COMPANIES`をブラウザ内メモリで操作するのみで、
`fetch`・`google.script.run`等の外部呼び出しは一切ない)。小柳さんの意向により、この画面を
今後の全機能(スコアリング反映・レター送付・CSV出力・連絡アラーム・対応履歴・現場連携)の
「軸」として、実際に稼働中のGoogleスプレッドシート(GLOW企業リレーション台帳、
scriptId `1ETmIVwC2A71ta9VlpUTZSPelTeTFIYs0tirjGtbjknyonz2cFXSFMmFk`)と接続した本物の
Web管理画面にする。

デモの機能は多いため、Phase 16までと同じく段階的に実装する。本設計はその第一段階
**Phase 18a: 企業一覧・詳細の閲覧(読み取り専用)** のみを対象とする。書き込み系
(関係メモ編集・対応履歴ログ入力)、スタッフ共有(Slack DM)、手紙URLモーダル、
KPIカード・今日のキュー・担当者別ワークロードは、それぞれ Phase 18b/18c/18d として
別途設計する。

**Phase 18b以降の区切り・順序は暫定案**であり確定事項ではない(2026-08-09三名体制レビュー
裁定4「保留」)。特に(a) 18b「書き込み系」は関係メモ編集と対応履歴ログ入力の実装難易度差が
大きく、さらに分割する可能性がある、(b) KPIカード(18d)は経営管理上の価値の高さから
18c(スタッフ共有・手紙URLモーダル、既にスプレッドシート版が稼働中で緊急性は相対的に低い)
より先に出す案も検討に値する。Phase 18aの実装・実機確認が終わった時点で、たかしくん・
小柳さんと相談のうえ改めて確定する。

## 1. 検討した3方式と採用理由

| 方式 | 概要 | 採用しない理由 |
|---|---|---|
| A. 単一GASプロジェクト内でWeb App化(**採用**) | 既存`TrackingWebApp.gs`の`doGet`にページ分岐を追加し、新規Web Appデプロイ(別URL・別アクセス設定)を作成。UIは`HtmlService`、データ取得は`google.script.run`。 | — |
| B. 別ホスティング + Google Sheets API直接連携 | デモのHTML/JSをGitHub Pages等の外部サイトで公開し、ブラウザから直接Sheets APIで読み書き。 | OAuthクライアント登録・APIキー管理など新しい認証基盤が必要で開発・保守コストが大きい。既存GASロジック(スコアリング・アラート判定等)と別実装になり、将来ルール変更時に両者がズレるリスクがある。 |
| C. GASをJSON APIサーバー化 + 外部ホスティングのフロント | GASの`doGet`/`doPost`をJSON APIとして使い、外部サイトの静的フロントから`fetch`で呼ぶ。 | GAS Web AppはCORS・認証まわりに既知の落とし穴が多く、Bと同等以上のコストがかかる割に、Aが持つ「既存ロジックをそのまま呼べる」利点を失う。 |

方式A採用の理由:
- 追加インフラ・追加費用がゼロ(Google純正機能内で完結)
- 既存のRunner群(schema.js・scoring.js・dashboard.js等)をそのまま呼び出せるため、
  スプレッドシート側とWeb画面側でロジックが二重管理にならず、将来の仕様変更時に
  食い違いが起きない(絶対ルール1「正確性最優先」と整合)
- 認証もGAS標準機能(`Session.getActiveUser()`)の範囲で完結できる
- 段階的に小さく作れる(Phase 18a→18b→18c→18dの積み上げが自然)

トレードオフとして受け入れる点:
- 見た目の自由度は`HtmlService`の制約を受ける(通常のHTML/CSS/JSはほぼそのまま使えるため実際の制約は小さい)
- 7000件を一度に画面へ出す設計は実行時間・データ量の面で無理があるため、絞り込み表示を前提にする

## 2. アーキテクチャ

```
[小柳・福田・嶺井のブラウザ]
        │ 管理画面用Web AppのURLにアクセス(Googleアカウントでログイン)
        ▼
[GAS doGet(e) — 既存TrackingWebApp.gsに分岐追加]
        │ e.parameter.page === "admin" のとき
        ▼
[許可リストチェック: Session.getActiveUser().getEmail() が
 「スタッフ」タブの登録メールアドレスに一致するか]
        │ 一致すれば
        ▼
[AdminApp.html(HtmlService) を返す]
        │ 画面内のJSが google.script.run で呼び出す
        ▼
[AdminRunner.gs の各関数が企業マスタ・対応履歴ログを読み取り]
```

新規ファイル:
- `glow-ma/src/AdminApp.html` — 画面(企業一覧・詳細ドロワー)
- `glow-ma/src/AdminRunner.gs` — サーバー側関数(データ取得・許可リスト照合)
- `glow-ma/src/adminAccess.js` — 許可リスト照合・絞り込み条件の純粋ロジック(UMD、Node側でテスト)

既存ファイルへの変更:
- `glow-ma/src/TrackingWebApp.gs` — `doGet(e)`に`page`パラメータでの分岐を追加。既存のトラッキング処理(id パラメータ)はそのまま維持し、ロジックの実体は変更しない
- `glow-ma/src/schema.js` — `STAFF_HEADERS`の末尾に`"メールアドレス"`列を追加
- `glow-ma/src/SheetSetup.gs` — スタッフタブの列追加に伴う調整(ensureTab_の見出し行上書きで自動対応、ロジック変更は不要な想定。実装時に確認)

## 3. Phase 18aのスコープ

**作るもの:**
- 企業一覧: 検索(会社名/代表者名)・絞り込み(ランク、現在ステージ、担当者)
- 企業詳細: 概要(基本情報・初期スコア/反応スコア/総合スコア/ランク・関係メモの表示のみ、編集不可)
- 対応履歴の表示: 対応履歴ログを日付降順で一覧表示(入力不可)

**作らないもの(後続フェーズ):**
- 関係メモ編集・対応履歴ログ入力(Phase 18b)
- スタッフ共有(Slack DM)・手紙URLモーダル(Phase 18c)
- KPIカード・今日のキュー・担当者別ワークロード(Phase 18d)

一覧は「絞り込み条件を最低1つ指定」を基本とし、未絞り込み時は`次回アクション予定日`降順の上位100件のみ表示する(全7000件の一括表示はしない)。

## 4. 認証・アクセス制御

- 「スタッフ」タブ(`STAFF_HEADERS`)の末尾に**「メールアドレス」列を追加**する(既存の「氏名」「Slack User ID」「有効」列はそのまま、途中への挿入はしない)。小柳・福田・嶺井の3名分のGoogleアカウントのメールアドレスを登録する。
- 新規Web Appデプロイを追加作成する: 実行ユーザー「自分」、アクセスできるユーザー「Googleアカウントを持つ全員」。既存のトラッキング用デプロイ(実行ユーザー「自分」、アクセス「全員」)とはURLもアクセス設定も別。
- `doGet(e)`が`page=admin`のとき、**`Session.getActiveUser().getEmail()`**(実際のアクセス者のメールアドレス)を取得し、スタッフタブで「有効」かつ「メールアドレス」が一致する行があるかを照合する(`adminAccess.js`の`isAllowedEmail(email, staffRows)`として純粋関数化しテストする)。
  - **`Session.getEffectiveUser()`は使わない**(実行ユーザー=常に自分を返すため、誰がアクセスしても同じ値になり許可リストチェックとして機能しない)。
  - `getActiveUser().getEmail()`が空文字を返すケース(環境依存の既知の弱点)は「未認証」として拒否する。この挙動は実機デプロイ後に必ず検証する(本番投入前チェックリストに追加)。
- 一致しなければアクセス拒否の案内画面(`HtmlService`)を返す。エラーにはしない(想定内の操作として扱う)。
- 個人Gmail運用(Workspaceドメインなし)のため、ドメイン制限は使えない。この許可リスト方式が確実。
- **多層防御**: 許可リストチェックは`doGet`の初回だけでなく、`getCompanyList_`・`getCompanyDetail_`など公開される各サーバー関数の冒頭でも個別に行う。デプロイを分けたこと自体は安全性の根拠にはならない(トラッキング用デプロイは「アクセス:全員」のままであり、`?page=admin`を付けられても許可リストチェックだけが最後の砦になるため)。

### `doGet`分岐の規律

`TrackingWebApp.gs`の`doGet(e)`は**ルーティングと許可リストチェックのみ**を行い、実処理(データ取得・HTML組み立て)は完全に`AdminRunner.gs`側の関数へ委譲する。将来Phase 18b以降やLINE要約連携(`doPost`)が追加されても、`doGet`/`doPost`自体は薄いルーターのまま保つ。

## 5. データ取得(サーバー側関数)

`AdminRunner.gs`に実装し、いずれも読み取り専用(`getValues()`のみ、書き込みなし):

- `getCompanyList_(filters)` — 企業マスタを読み、`filters`(検索語・ランク・ステージ・担当者)で絞り込んだ結果を返す。未絞り込み時は`次回アクション予定日`降順で上位100件。絞り込み判定ロジックは`adminAccess.js`側に切り出しNode側でテストする。
  - **返すフィールドは一覧表示に必要な最小限**(企業ID・会社名・ランク・現在ステージ・次回アクション予定日・担当者)に絞る。携帯番号・関係メモ・所在地などの機微情報は含めない(通信に流れる機微情報量を最小化する)。
- `getCompanyDetail_(companyId)` — 企業マスタから1社分の全項目(携帯番号・関係メモ・所在地を含む) + `対応履歴ログ`から企業IDが一致する行を日付降順で返す。詳細を開いた本人にのみ機微情報が渡る設計にする。
- 既存の`readCompanyRecords_`(`ShareRunner.gs`)と同等の読み取りロジックを共通関数として切り出し、両ファイルから再利用する(重複実装を避ける)。
- `getCompanyList_`・`getCompanyDetail_`いずれも、冒頭で`isAllowedEmail(Session.getActiveUser().getEmail(), staffRows)`を呼び、許可されていなければ例外を投げる(4章の多層防御)。

## 6. エラーハンドリング

- 許可リスト外アクセス: 案内画面を表示するのみ(ログ・通知は不要)
- `getCompanyList_`/`getCompanyDetail_`実行中の例外: クライアント側で「読み込みに失敗しました。再読み込みしてください」を表示。自動リトライはしない(閲覧機能のため、ユーザー操作での再試行で十分と判断)
- 存在しない企業IDが指定された場合: 空状態を返し「該当する企業が見つかりません」と表示

## 7. テスト方針

- `AdminRunner.gs`本体はGAS依存(`SpreadsheetApp`/`Session`/`HtmlService`)のため、既存の他Runnerと同様に`node --test`の対象外。
- 許可リスト照合(`isAllowedEmail`)・絞り込み条件の適用(`applyCompanyFilters`等)は`adminAccess.js`にUMD形式で切り出し、Node側(`tests/glow_ma_adminAccess.test.mjs`)でテストする。
- 実機での動作確認手順(新規デプロイ作成・スタッフタブへのメールアドレス登録・許可リスト外アカウントでのアクセス拒否確認)を`docs/glow-ma_本番投入手順書_統合版.md`に追記する。

## 8. 三名体制レビュー裁定(2026-08-09)

総合裁定: **採用(条件付き)**。反映済みの条件:
1. 認証は`Session.getEffectiveUser()`ではなく`Session.getActiveUser().getEmail()`を使う。空文字が返るケースは「未認証」として拒否し、実機で必ず検証する(→9章のチェックリストに反映)。
2. 許可リストチェックは`doGet`だけでなく、公開される各サーバー関数の冒頭でも個別に行う(多層防御)。
3. `doGet`はルーティング+許可リストチェックのみとし、実処理は完全に`AdminRunner.gs`へ委譲する。「デプロイを分けたから安全」という前提は置かない。
4. `getCompanyList_`が返すフィールドは一覧表示に必要な最小限に絞り、携帯番号・関係メモ・所在地は`getCompanyDetail_`でのみ返す。
5. 本番投入前チェックリストに「Web管理画面での個人情報相当データ閲覧範囲拡大について守り部へ申し送る」項目を追加する(→9章)。
6. Phase 18b以降の区切り・優先順位は暫定案として明記し、Phase 18aの実機確認後に改めて確定する(反映済み、本文冒頭)。
