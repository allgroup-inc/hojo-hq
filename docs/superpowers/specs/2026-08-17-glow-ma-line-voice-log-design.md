# glow-ma: 現場訪問ログ LINE音声記録システム 設計書

作成: 2026-08-17 / 小柳さんの承認により実施

## 背景

現場ヒアリング(ブレインストーミング論点4、`docs/superpowers/specs/2026-07-31-glow-ma-feature-brainstorm-triangle-review.md` 参照)の結果、現場担当者から以下の回答を得た(2026-08-17):

1. 訪問後の記録タイミングは、その場(スマホ)と後でPCから、どちらも同じくらい。訪問時にログを取ってそのままLINEで送り、見込企業の情報に反映される仕組みを希望
2. 現状(PCのスプレッドシート入力)で、記録が後回しになって忘れる・面倒に感じることが「あると思う」
3. スマホから簡単に記録できる仕組みがあれば「使いたい」

これを受け、訪問直後に音声メッセージをLINEで送るだけで、対応履歴ログ(必要なら企業マスタ)に反映される仕組みを設計する。

### 参考にした既存事例(kachitalk)

ALLGROUP内の別事業(エンライフ)向けに、LINE音声受付→Azure AI Speechでの文字起こし→自作査定エンジンでの分析、という仕組み(kachitalk、`https://github.com/allgroup-inc/kachitalk`)が既に稼働している。本設計はこのパターン(LINE Webhook受信・署名検証・即時ACK・非同期処理)を参考にしつつ、以下の理由で**インフラ・実装は完全に独立させる**(2026-08-17 小柳さん確認):

- glow-ma全体がGoogle Apps Script + スプレッドシートで完結する設計であり、Azureを新たに持ち込むとglow-maの運用がGAS単独からAzure併用に変わり、複雑性・管理コストが増す
- kachitalkは営業品質の査定(点数化・NGワード検出)と個人情報マスキングが目的だが、本機能は「訪問記録を楽に残し、見込企業の情報に正しく反映すること」が目的であり、要件の性質が異なる

## 1. スコープ

**作るもの:**

- GLOW実務チーム専用のLINE公式アカウント(新規開設)
- 音声メッセージを送ると、Gemini APIで文字起こし・構造化データ抽出を行い、LINE上のボタン操作で確認・確定できる仕組み
- 確定した内容を、既存の「対応履歴ログ」タブ(および必要に応じて「企業マスタ」タブへの新規行追加)に書き込む機能

**作らないもの(スコープ外):**

- 営業品質の査定・スコアリング機能(kachitalkの査定エンジンに相当する部分)
- 個人情報の自動マスキング処理(社内CRMとして正しく企業情報を記録することが目的のため、kachitalkとは逆の要件)
- LINE上での自由記述による内容訂正(確定後の修正は、既存の管理画面の関係メモ編集と同様の仕組みで行う。将来必要になれば別途検討)
- 1回の訪問で複数音声をまとめて送るケースの特別対応(1音声メッセージ=1対応履歴ログとして扱う。複数送りたい場合は、1件ずつ確定してから次を送る)
- テキストメッセージでのログ送信(今回は音声のみ。現場ヒアリングで音声を希望する回答だったため)

## 2. 全体アーキテクチャ

```
現場担当者(LINEアプリ)
  → GLOW専用LINE公式アカウント(新規)に音声メッセージを送信
  → LINEプラットフォームがGAS Web App(doPost)へWebhook通知
  → GASがリクエストの形式(destinationフィールドがBotのユーザー IDと一致するか等)を確認
    (※ `destination` はBot自身のユーザー ID(`U`+32桁)であり、Basic settingsページの
    数字だけの「チャネルID」ではない。2026-08-17 最終レビューで実装が後者を比較していた
    誤りを検知し、スクリプトプロパティ名も `LINE_BOT_USER_ID` に修正した)
    (※ GAS Web Appの`doPost`はHTTPヘッダーを読み取れない既知の制約があり、
    LINEが送る`X-Line-Signature`ヘッダーでの暗号学的な署名検証はGAS単体では実装できない。
    2026-08-17 プラン作成中に判明し、小柳さんに確認のうえ、Webhook URL自体の推測困難性
    +リクエスト形式チェックという一段弱いセキュリティモデルで進めることを承認済み。
    既存のTrackingWebApp.gsのdoGetが「全員」アクセス可でURL自体が唯一の防御である
    設計と同水準のリスク受容)
  → 形式チェックOKなら「音声ログ処理状況」シートに新規行を記録(ステータス=受信済み)
  → LINEへ即時ACK返信(「録音、届きました。少々お待ちください」)
  → (ここでdoPostの処理を終了。LINEの応答時間制限に対応するため、重い処理はしない)

時間主導型トリガー(1分間隔)
  → 「音声ログ処理状況」シートの「受信済み」行を1件ずつ処理:
      1. LINE Content API(`https://api-data.line.me/v2/bot/message/{messageId}/content`)で音声データを取得
      2. Gemini APIに音声を渡し、以下を1回のAPI呼び出しで抽出:
         - 話した会社名(テキスト)
         - 種別候補(面談実施/電話/入電 等、既存のINTERACTION_TYPESに寄せる)
         - 対応相手候補(オーナー社長本人/経理・総務等の窓口担当/未接触)
         - 内容メモ(要約)
         - 次回アクション
      3. 企業マスタの「会社名」列と抽出した会社名を照合(完全一致→部分一致の順)
      4. 照合結果に応じてLINEへ確認メッセージ(ボタン付き)を送信し、ステータスを更新
```

## 3. LINE会話フロー(状態管理)

1人につき同時に1件のみ処理中とする(前の処理が確定/破棄されるまで、次の音声は「音声ログ処理状況」シートに積まれたまま待機し、LINEには「前の記録が完了していません」と案内する)。

**ステータス遷移:**

`受信済み` → `文字起こし済み` → (`企業選択待ち` または `新規企業確認待ち` または スキップ) → `最終確認待ち` → `確定` または `破棄`

- **企業選択待ち**(候補が複数の場合): LINEのQuick Replyボタンで候補企業(最大5社、照合スコアの高い順)+「見つからない」を提示する
- **新規企業確認待ち**(候補がゼロの場合): 「企業マスタに見つかりませんでした。新規企業として登録しますか?」とYes/Noボタンを提示する
- **最終確認待ち**: 抽出した内容(会社名・種別・内容メモ・次回アクション)をテキストで表示し、「この内容で記録する」「取り消す(録音し直す)」の2択ボタンを提示する
- **確定**: 対応履歴ログへの書き込み(新規企業の場合は企業マスタへの行追加も)を実行し、「記録しました」と返信する
- **破棄**: 何も書き込まず、「取り消しました。もう一度録音してください」と返信する

**新規シート「音声ログ処理状況」の列構成:**

```
処理ID, LINEユーザーID, LINEメッセージID, ステータス,
受信日時, 会社名候補(JSON文字列), 企業ID(確定後),
種別候補, 対応相手候補, 内容メモ, 次回アクション, エラー内容
```

このシートは`ensureLedgerTabs`実行時に自動作成する(既存の全タブと同じパターン)。1行=1件の音声ログの処理状態を表し、確定・破棄後も記録を残す(後から「未処理のまま放置されていないか」を確認できるようにするため)。

## 4. データ項目のマッピング

| Geminiの抽出項目 | 書き込み先 |
|---|---|
| 話した会社名 → 企業マスタと照合した「企業ID」 | 対応履歴ログ「企業ID」 |
| 種別候補 | 対応履歴ログ「種別」(`GlowSchema.INTERACTION_TYPES`の値に正規化。一致しない場合は「面談実施」を既定値とする) |
| 対応相手候補 | 対応履歴ログ「対応相手」(`GlowSchema.RESPONDENT_TYPES`の値に正規化) |
| 内容メモ(要約) | 対応履歴ログ「内容メモ」 |
| 次回アクション | 対応履歴ログ「次回アクション」 |
| (自動) 送信日時 | 対応履歴ログ「日付」 |
| (自動) LINEユーザーIDから「スタッフ」タブを逆引き | 対応履歴ログ「担当者」 |

新規企業登録時は、企業マスタに「企業ID」(自動採番)・「会社名」(抽出値)のみを最小限で書き込み、他の列は空欄とする(詳細は後で通常の編集フローで補完する)。

**スキーマ変更: 「スタッフ」タブに列を追加**

現状の「スタッフ」タブ(`STAFF_HEADERS`: 氏名/Slack User ID/有効/メールアドレス)には、LINEユーザーIDを引くための列がない。既存の`Slack User ID`列と同じ考え方で、末尾に「LINE User ID」列を追加する(既存データの列位置がズレないよう、末尾への追加とする。ShareRunner.gsのSlack連携で確立済みの、氏名・IDの登録パターンをそのまま踏襲する)。LINEユーザーIDの調べ方は、担当者が最初にLINE公式アカウントへ音声を送った際、GAS側でそのユーザーIDをログ出力し、人間が「スタッフ」タブへ手動転記する(LINE公式アカウントの管理画面から事前に一覧取得する方法がないため)。

**スタッフ未登録者からの音声を受信した場合**: LINEユーザーIDが「スタッフ」タブに見つからない場合は、対応履歴ログへの自動反映は行わず、「担当者が特定できませんでした。管理者に「スタッフ」タブへの登録を依頼してください」と返信して処理を終了する(誰の記録か分からないまま対応履歴ログに書き込まない、CLAUDE.md絶対ルール1に基づく)。

## 5. 障害隔離・エラー処理

- 音声データが取得できない・Gemini APIが失敗した場合、「音声ログ処理状況」シートのステータスを「エラー」にし、LINEへ「うまく処理できませんでした。もう一度録音してください」と返信する(既存のLetterRunner.gs等と同じ、1件の失敗が他の処理を止めない設計)
- 企業マスタとの照合・書き込み処理でエラーが起きた場合も同様にエラーステータスとし、担当者に再送を促す
- リクエストの`destination`フィールドがBotのユーザー ID(スクリプトプロパティ`LINE_BOT_USER_ID`に設定)と一致しない等、
  LINEからの正規のWebhookと形式が異なるリクエストは、ログに記録した上で何も返さず終了する
  (前述のとおり暗号学的な署名検証ではなく形式チェックによる簡易な防御)

## 6. 新たに発生する費用・契約

- LINE公式アカウントの新規開設(GLOW実務チーム専用)
- Gemini APIの利用料(音声処理1件あたりの従量課金)

金額規模の見積もりは実装時に確認するが、契約・予算の最終承認は小柳さんの決裁事項とする(CLAUDE.md絶対ルール5)。

## 7. テスト方針

- 企業名照合ロジック(完全一致・部分一致の判定)、種別・対応相手の正規化ロジック、対応履歴ログ行の組み立てロジックは、既存パターン(`shippingContent.js`等)と同様にGAS非依存の純粋ロジックとして切り出し、Node側で`tests/glow_ma_*.test.mjs`により検証する
- LINE Webhook受信・署名検証・Gemini API呼び出し・LINE返信送信はGAS依存のため、本番投入前の目視確認で担保する(既存の「本番投入(実データ運用開始)前チェックリスト」に本機能の動作確認を追加する)
