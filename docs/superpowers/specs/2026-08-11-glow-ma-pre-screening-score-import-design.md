# glow-ma: 事前選定スコア・ランクの取り込み 設計書

作成: 2026-08-11 / 小柳さんの承認により実施

## 背景

Phase 18b(関係メモ編集)の本番検証中に、企業一覧の「ランク」列が多数の企業で空欄になっていることが判明した。
調査の結果、外部で事前に選定作業(建設業許認可情報や福祉事業所指定情報等をもとにしたTier/仮ランク判定)が
完了しているリスト(「第1弾1500社」建設業リスト、「福祉総合リスト_全1711法人」)が既に企業マスタへ
取り込まれていたが、`importCompaniesFromStaging`の`IMPORT_COLUMN_MAP`が「仮ランク」「仮スコア」列を
マッピング対象にしていなかったため、これらの評価情報が取り込み時に失われていたことが原因と判明した。

glow-ma自体の「ランク」は`scoring.js`が業種・規模・代表者年齢等から独自に算出するものであり、
外部の事前選定評価とは計算方法も評価軸も異なる別物である。対応履歴が全く無い新規取り込み企業では
glow-ma独自のランクはほぼ空欄・低評価になってしまうため、外部の事前選定評価を活かせる仕組みが必要。

## 1. スコープ

**作るもの:**
- 企業マスタへの「事前選定ランク」「事前選定スコア」列の追加
- 既存約3,200社への遡及反映機能(`applyPreScreeningScores`)
- 今後の新規取り込み時のマッピング対応(`IMPORT_COLUMN_MAP`拡張)
- スコア計算式への事前選定スコアの組み込み

**作らないもの(スコープ外):**
- 会社名のあいまい一致(表記ゆれ吸収)。前後・全角スペースの除去のみ行い、それ以外は完全一致とする
  (誤って別会社に反映するリスクを避けるため。曖昧一致は次フェーズで検討)
- 未一致企業の自動新規登録(今回は「既存企業への反映」のみ。新規登録が必要な場合は
  `importCompaniesFromStaging`を別途使う)
- 手紙のQRコード化(本セッションで話題に上ったが、別件として今後検討)

## 2. スキーマ変更(schema.js)

`COMPANY_MASTER_HEADERS`の末尾に追加(既存列の並び順は変更しない):
```
"事前選定ランク", "事前選定スコア"
```

## 3. 名寄せ(dedupe.js)

新2列を既存の「初期スコア」「反応スコア」「総合スコア」「ランク」と同じ`SCALAR_FIELDS`(統合時、
複数レコードのうち最初に見つかった非空値を採用する方式)に追加する。これらはスコア系の列であり、
将来的に再計算で上書きされる性質を持つため、既存のスコア系列と同じ扱いとする。

## 4. 遡及反映機能(新規)

### 4.1 「事前選定リスト」タブ

新規タブ「事前選定リスト」を作成する(取り込み専用。列構成が既存の「インポート待ち」タブ
(`importCompaniesFromStaging`用)と異なるため別タブとする)。1行目に見出し、2行目以降に
元データを貼り付けて使う。

### 4.2 マッピング設定

`IMPORT_COLUMN_MAP`と同様の考え方で、専用の`PRE_SCREENING_COLUMN_MAP`を設ける:
```javascript
var PRE_SCREENING_COLUMN_MAP = {
  // 左が企業マスタの列名、右が「事前選定リスト」タブの見出し文字列。
  // 実データの見出しに合わせてここを書き換えてから実行する。
  "会社名": "正式商号",
  "事前選定ランク": "仮ランク",
  "事前選定スコア": "仮スコア"
};
```
今回のように見出しが異なる複数のファイルを扱う場合、1ファイルごとに`PRE_SCREENING_COLUMN_MAP`を
書き換えて`applyPreScreeningScores`を複数回実行する運用とする(「第1弾1500社」用に1回、
「福祉総合リスト」用に1回)。

### 4.3 `applyPreScreeningScores()`関数

1. 「事前選定リスト」タブの全行を読み込む
2. 各行の会社名(前後の空白・全角スペースを除去して正規化)を企業マスタの「会社名」(同様に正規化)と
   突き合わせる
3. 一致した行の「事前選定ランク」「事前選定スコア」のみを更新する(他の列は一切変更しない)
4. 一致しなかった件数を`Logger.log`に出す(例:「128件が企業マスタと一致しませんでした」)。
   会社名の一覧までは出さない(今回のご要望通り)
5. 既存の`importCompaniesFromStaging`と同様、`LockService`で企業マスタへの排他制御を行う

## 5. 今後の新規取り込み対応(ImportRunner.gs)

`IMPORT_COLUMN_MAP`に「事前選定ランク」「事前選定スコア」も追加できるようにする(取り込み元に
これらの列がある場合は、`importCompaniesFromStaging`の時点で最初から反映される)。

## 6. スコア計算式の変更(ScoringRunner.gs)

`recalculateAllScores`内の初期スコア算出部分を変更する:

```javascript
var preScreeningScore = Number(record["事前選定スコア"]) || 0;
var initialScore = GlowScoring.calculateAttributeScore(record)
  + preScreeningScore
  + GlowScoring.calculateRouteBonus(record["流入ルート"]);
```

`scoring.js`自体(業種・規模・年齢の計算式)は変更しない。「事前選定スコア」が空欄・非数値の企業は
0として扱われ、既存の計算結果に影響しない。

## 7. エラーハンドリング

- 「事前選定リスト」タブが存在しない場合: エラーを投げて中断する
- `PRE_SCREENING_COLUMN_MAP`の見出しが実際のタブの見出しと一致しない場合:
  `importCompaniesFromStaging`と同様、見つからない見出しを列挙してエラーを投げる
- 会社名が完全一致しなかった行: エラーにはせず、未一致件数としてログに残し処理を継続する

## 8. テスト方針

- 会社名の正規化ロジック(空白・全角スペース除去)、突き合わせロジックは純粋関数として切り出し、
  Node側でテストする(`dedupe.js`または新規ファイルに実装し、既存のUMDパターンを踏襲)
- `applyPreScreeningScores`本体はGAS専用(`SpreadsheetApp`依存)のためNode単体テスト対象外
  (`updateCompanyMemo`等の既存パターンと同じ扱い)
- `ScoringRunner.gs`の計算式変更は、`scoring.js`側のテストで「事前選定スコアを加味した初期スコア」の
  計算をカバーする(初期スコア計算のオーケストレーション自体はNode側で検証できないため、
  加算対象になる値の妥当性は既存の`calculateAttributeScore`等のテストで担保する)
