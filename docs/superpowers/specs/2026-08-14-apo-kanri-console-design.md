# アポ管理コンソール(apo-kanri)設計書

作成: 2026-08-14 / 小柳さんの設計承認により実施(チャット決裁: 別コンソール方式・Slack通知・7名以上・企業マスタ非連携)

## 背景

アポ入れ担当が日々獲得するアポを対面営業メンバーへ連携する業務が、口頭・チャットでバラバラに
行われており、①アポ連携の抜け ②申込み(成約)連携の漏れ ③顧客都合の急な日時変更
④営業の前アポ長引きによる後続アポのずれ ⑤ダブルブッキング等のイレギュラー、を全員が
同じ画面で見られない。これを解決する共有アポ管理システムを作る。

小柳さんの要望: **連携のしやすさ・管理のしやすさ・確認のしやすさ・便利さのすべてで最高の使い勝手**。
→ 設計原則として「主要操作は2タップ以内」「開いた瞬間に今日が見える」「すべての変更が
履歴と通知に自動で残る(手動の二度書きゼロ)」を採用する。

## 決定済み要件(2026-08-14 小柳さん回答)

- 通知: **Slack**(glow-maで実績のあるIncoming Webhook方式)
- 利用者: **7名以上**(アポ入れ係+対面営業)→ 担当者別絞り込み必須
- スマホ操作: **専用Web管理画面**(GAS Web App)
- アポ先企業: **glow-ma企業マスタとは完全に別**。紐づけない(変につながらないことが条件)
- 置き場所: **別コンソール**(専用スプレッドシート+専用Web App。M&A台帳とファイルもURLも分離)

## 1. スコープ

**作るもの(MVP):**
- 新ディレクトリ `apo-kanri/`(hojo-hq内)。スタンドアロンGASプロジェクト+専用スプレッドシート「アポ管理台帳」
- シート4タブ: スタッフ / アポ予定 / 変更履歴 / 設定
- Web App 1画面構成(モバイルファースト): 本日ビュー+週ビュー+登録/編集フォーム+「遅れそう」ボタン
- Slack通知5種: 新規アポ / 日時変更 / キャンセル / 申込み / 遅れそう
- ダブルブッキング警告(同一営業・時間帯重複。警告のみで登録は止めない)
- self-test(tests/apo_kanri_*.test.mjs、既存glow_maテストと同形式)+セットアップ手順書

**作らないもの(スコープ外・見直しはMVP稼働後):**
- glow-ma企業マスタ・対応履歴との接続(完全別。コードも glow-ma のスプレッドシートを一切参照しない)
- 顧客本人への自動連絡(誤送信リスク。社内通知のみ)
- Googleカレンダー同期 / 数値の人事評価利用 / 顧客の電話番号等の連絡先保持(PII最小化)

## 2. データ設計(スプレッドシート「アポ管理台帳」)

列の追加は必ず末尾へ(glow-maと同じ理由: 位置依存の読み書きのため途中挿入禁止)。

- **スタッフ**: 氏名 / Slack User ID / 有効 / メールアドレス / 役割(アポ入れ・営業・両方)
- **アポ予定**: アポID / 日付 / 開始時刻 / 所要分 / 顧客名 / 形式(訪問・来店・オンライン) /
  場所またはURL / 担当営業 / アポ入れ担当 / 温度感(高・中・低) / ステータス / メモ /
  登録日時 / 最終更新日時
  - ステータス: 予定 / 確定 / 実施済 / 申込み / キャンセル(顧客都合) / キャンセル(自社都合) / 再調整中
- **変更履歴**: 履歴ID / アポID / 日時 / 操作者 / 操作(新規・変更・遅延連絡) / 変更内容(旧→新) — Web App経由の全操作を自動追記
- **設定**: キー / 値 / 説明(通知のオンオフ等)

## 3. Web App設計(モバイルファースト)

認証・実装パターンは glow-ma Phase 18a を踏襲: スタッフタブのメールアドレス許可リスト照合を
doGet と **公開関数それぞれの冒頭** で行う多層防御。末尾 `_` なしの公開関数は最小限にする。

- **本日ビュー(初期表示)**: 全員分のアポを時刻順にカード表示(ステータス色・温度感バッジ)。
  上部に「自分のアポ」ワンタップ切替と担当者チップ。件数サマリー(本日◯件・うち未確定◯件)
- **週ビュー**: 今日から7日分を日別に一覧(先の予定の確認・空き把握用)
- **登録/編集**: 1フォーム。営業担当は選択式(スタッフタブの営業役割から)。保存と同時に
  Slack通知+変更履歴追記。時間帯重複時は保存前に警告表示(保存は可能)
- **カード操作(2タップ以内)**: カードをタップ→「確定 / 実施済 / 申込み / 再調整中 / キャンセル /
  遅れそう(+15・30・60分)/ 編集」のアクションシート
- **遅れそう**: 押した営業の本日中の後続アポを自動抽出し、各アポのアポ入れ担当宛に
  Slackメンション通知(「◯◯さん 30分遅れ見込み。15:00 △△様のアポに影響の可能性」)。
  後続アポの時刻自動変更はしない(判断は人間。通知のみ)

## 4. Slack通知設計

- Script Property `SLACK_WEBHOOK_URL`(コードに書かない)。resilience.js の withRetry
  (最大3回・429/5xxのみ)で送信。未設定時はスキップしてログのみ(glow-maと同じ)
- 文面は「何が・いつ・誰の担当か」が通知一覧で読み切れる1〜3行。担当者はスタッフタブの
  Slack User ID があれば `<@U...>` メンション
- 通知失敗でもシート保存は成功扱い(保存が正・通知は従。失敗は変更履歴に記録)

## 5. エラー処理・壊れにくさ

- シート書き込みは LockService で直列化(glow-ma LetterRunner と同様)
- アポIDは `APO-` + タイムスタンプ+乱数で採番(重複チェック付き)
- シート直接編集は運用上禁止(READMEに明記)。ただし壊れた行があっても一覧描画は
  その行をスキップして継続する(1行の不正で全画面が死なない)

## 6. テスト

- 純ロジック(UMD形式 .js)をNodeテストで検証: スキーマ整合 / 本日・週ビューの絞り込みと
  ソート / 重複判定 / 遅延通知の対象抽出 / 通知文面 / 変更履歴の差分生成 / 許可リスト照合
- GAS層(SpreadsheetApp等)は薄いランナーに限定しロジックを持たせない(既存方針踏襲)
- UIはHTML生成のスモークテスト+目視確認用のプレビューを納品時に添付

## 7. 三名体制レビュー(2026-08-14)

### 論点: 別コンソール新設の構成と「遅れそう」自動化の範囲

**スイシン**: glow-maの実証済み部品(認証・resilience・UMD+Nodeテスト)の流用で、新規リスクは
アポ固有ロジックのみに限定できる。7名運用の要である「遅れそう」ワンタップは自動通知まで
やってこそ価値がある。

**ウタガイ(反対必須)**: ①後続アポの時刻を自動で後ろ倒しする案は、顧客と合意していない時刻が
システム上の「正」になり事故のもと。②同一リポジトリに置く以上、glow-maのシートIDや関数を
うっかり参照する混線リスクがある。③シート直接編集を完全には防げず、変更履歴が「全変更の記録」
だと過信すると監査に穴が開く。④Slack通知が多すぎると読まれなくなり、肝心の遅延通知が埋もれる。

**ベッカイ**: そもそもGoogleカレンダー共有で足りるのでは。→ ステータス管理(申込み・温度感・
変更履歴)と役割別通知はカレンダーでは実現できず、要件の中心がそこにあるため不採用。ただし
「カレンダーで済む部分を作り込まない」原則として採用(リマインダー等は作らない)。

**裁定**: 採用。ウタガイ①を全面採用し時刻の自動変更はしない(通知のみ)。②はコード規約として
「apo-kanri/ から glow-ma/ への参照禁止・SpreadsheetApp.getActiveSpreadsheet() のみ使用
(IDハードコード禁止)」を明記。③はREADMEに「直接編集禁止・履歴はWeb App操作の記録」と明記。
④は通知を5種に限定しリマインダー系を作らない。見直し期限: 2027-02-14。

## 8. 受け入れ条件

- 登録→担当営業へSlack通知→日時変更→再通知が、スマホ画面だけで1分以内に完了する
- 「遅れそう」ワンタップで後続アポのアポ入れ担当に通知が届く
- 全Nodeテストがパスし、既存テスト(glow_ma_* 等)を壊さない
- セットアップ手順書(README)を見て、小柳さんが自力で本番投入できる
