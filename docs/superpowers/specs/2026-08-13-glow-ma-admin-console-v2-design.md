# glow-ma: 管理画面リッチ化(コンソールv2) 設計書(プロジェクトA)

作成: 2026-08-13 / 小柳さんの承認により実施

## 背景

2026-08-05〜07にかけて、本セッション内でGLOW企業リレーション台帳の管理画面デモ
(`glow-ma-console.html`、Claudeアーティファクトとして作成)を何度も反復して作り込んでいた。
その後 Phase 18a(2026-08-09)で実際にApps Script Web Appとして実装した管理画面
(`adminApp.js`)は、このデモよりずっと簡素な内容(企業一覧+詳細ドロワーのみ)にとどまっていた。

利用者(小柳さん)が本番稼働開始後、このデモの内容(KPIサマリー・流入ルート表示・
ネクストアクション優先順位・担当者別ワークロード・Slack連携・レター下書き確認)を
本番の管理画面でも使いたいという要望があり、本設計書でその反映範囲を定める。

## 1. スコープ

**作るもの:**
- デモのビジュアルデザイン(コーポレートカラー・光るGLOWロゴ・カード型KPI・緊急度表示等)の本番移植
- 企業一覧テーブルの列拡張(流入ルート・提案商品を追加)・ソート・絞り込み拡張
- KPIサマリー行(6項目、クリックで内訳モーダル)
- 「本日のネクストアクション」パネル(優先度順、最大8件)
- 「担当者別ワークロード」パネル(素の集計値のみ。フラグ表示は見送り)
- ドロワー内の🤝連携ボタン(既存`shareCompanyWithStaff`を呼び出すSlack共有)
- レター下書きプレビュー(その企業への最新下書き本文を表示)

**作らないもの(スコープ外):**
- プロジェクトB(通話録音→文字起こし→専用LINE経由送信→対応履歴自動記録)。別途、完了後に設計する
- パートナー一覧(紹介パートナー開拓状況)画面のリッチ化。今回は企業一覧側のみを対象とし、
  パートナー側は既存のまま維持する(将来必要になれば別途検討)
- ランク別接触サイクル日数や紹介料率など、既存のスコアリング・アラート発報ロジック自体の変更。
  今回はあくまで「画面上の表示・優先順位付け」であり、AlertRunner.gs等の実発報ロジックには触れない
- 担当者別ワークロードの「要偏り確認」フラグ(三名体制レビュー2026-08-13論点2により見送り。
  初期データ安定後に別途検討)
- ランク別に緊急度日数閾値を変える仕組み(同論点1でYAGNIと判断)

## 2. 三名体制レビューでの決定事項(2026-08-13)

- **論点1(緊急度閾値)**: 次回アクション予定日が本日以前=`overdue`、3日以内=`soon`、
  それ以外=`ok`という基本閾値を採用。加えて、**次回アクション予定日が未設定の企業は
  `untouched`(未着手)という独立区分とし、KPI・ネクストアクション一覧の両方でoverdueと
  同等以上の優先度で表示する**(未着手の新規リードを緊急度「none」扱いにして埋もれさせない
  ための修正)。ランク別の閾値差別化は見送り。見直し期限2027-02-13。
- **論点2(ワークロード偏り判定)**: 3役の意見が割れたため保留・小柳さんへ上申。
  ワークロードパネル自体は実装するが、「要偏り確認」フラグは表示しない
  (今回の一括インポート直後は大半が未着手のため、絶対値基準では機能しない)。
  見直し期限2026-11-13。

これらの閾値は**画面表示上の優先順位付けにのみ使う**。Slack通知等の実際のアラート発報は
既存のAlertRunner.gs(P3)が別途担っており、本プロジェクトでは変更しない。

## 3. ビジュアルデザイン

デモ(`glow-ma-console.html`)のCSS変数・配色・アニメーションをそのまま移植する:
- コーポレートカラー: ネイビー(`--navy: #00335c`系)× 金(`--kin: #F88800`系)
- ヘッダーのGLOWロゴに光るアニメーション(`logoGlow` keyframes、3.2秒サイクル。
  `prefers-reduced-motion: reduce`時はアニメーション無効化、デモの実装をそのまま踏襲)
- ロゴ画像はデモに埋め込まれているbase64データURIをそのまま使う(外部ホスティング不要)
- ダークモード対応(`prefers-color-scheme`および`data-theme`属性の両対応、デモの実装を踏襲)
- カード型KPI・ランクバッジ(A/B/C/D色分け)・緊急度ドット(赤/黄/緑/グレー)

adminApp.jsは現状「UMD形式のHTML/JS文字列組み立て」という構造を維持し、STYLE/HEADER/TABLE/
DRAWER等の定数を全面的にデモの内容に合わせて書き換える形で実装する(構造自体は変えない)。

## 4. 企業一覧テーブル

列: 会社名/代表者名 ・ 業種/所在地 ・ 流入ルート(バッジ表示) ・ 現在ステージ ・ 提案商品(バッジ表示) ・
ランク ・ 次回アクション(緊急度ドット+日付)。列見出しクリックでソート(会社名/業種/流入ルート/
ステージ/商品/ランク/次回アクション、昇順・降順トグル)。

絞り込み: 既存の検索窓(会社名・代表者名)に加え、ランク・現在ステージ・担当者(既存)・
流入ルート・提案商品(新規)のプルダウンを追加する。`getFilterOptions()`を拡張し、
流入ルート・提案商品の選択肢も企業マスタの実在値から動的に作る。

## 5. KPIサマリー行

新規関数`getKpiSummary()`(AdminRunner.gs)を追加し、`requireAdminAccess_()`で保護する。
企業マスタ全件を`readCompanyRecords_`で読み、以下6項目を計算して返す:

| key | ラベル | 計算方法 |
|---|---|---|
| total | パイプライン企業数 | 全企業数 |
| untouchedOrOverdue | 本日の掘り起こし対象 | urgency が `overdue` または `untouched` の企業数(論点1の裁定) |
| hot | 即時アラート | 本日日付の対応履歴ログがある企業数(`種別`問わず、`日付`が本日) |
| rank | ランク内訳 | A/B/C/Dそれぞれの件数 |
| deal | 提案中・案件化 | 現在ステージが「提案中」または「案件化」の企業数 |
| stale | 長期検討企業 | dashboard.js(Phase 12)の長期検討判定ロジックを流用 |

各カードクリックでモーダルを開き、該当企業の一覧(会社名・ランク・簡易情報)を表示、
行クリックでドロワーを開く(デモの`openKpiModal`の挙動を踏襲)。

## 6. 緊急度判定ロジック(urgency)

新規の純粋ロジックモジュール`adminAccess.js`に`computeUrgency(company, todayString)`を追加する
(Node側でテスト可能にするため、既存のUMD構成に合わせてadminAccess.jsに置く):

```javascript
function computeUrgency(company, todayString) {
  if (company["連絡不要"]) return "none";
  var nextDate = company["次回アクション予定日"];
  if (!nextDate) return "untouched";        // 論点1の裁定
  var diffDays = daysBetween(todayString, nextDate);
  if (diffDays <= 0) return "overdue";
  if (diffDays <= 3) return "soon";
  return "ok";
}
```

`untouched`は掘り起こし対象KPI・ネクストアクション一覧の両方で`overdue`と同格(最優先)として扱う。

## 7. 「本日のネクストアクション」パネル

`getKpiSummary()`と同じ企業配列から、以下条件で最大8件抽出しサイドパネルに表示する:
本日反応あり(hot) OR urgency が overdue/untouched/soon。並び順: 反応あり→untouched→overdue→soon。
各項目クリックでドロワーを開く。新規関数は不要(`getCompanyList`の絞り込み結果を流用するか、
`getKpiSummary()`のレスポンスに含める形で実装する。実装時にどちらが自然か判断してよい)。

## 8. 担当者別ワークロードパネル

新規関数`getOwnerWorkload()`(AdminRunner.gs)を追加。担当者ごとに「担当企業数」「urgency
overdue+untouchedの件数」を集計して返す(論点2の裁定により、フラグ・警告表示は行わない)。

## 9. 🤝連携ボタン(Slack共有)

ドロワーに共有ボタンを追加し、クリックでスタッフ選択+一言メモのモーダルを開く。
スタッフ一覧は既存の「スタッフ」タブ(Slack User ID列)から取得する新規公開関数
`getShareableStaffList()`(AdminRunner.gsの既存`readActiveStaff_`と同等のロジックを、
末尾`_`なしの公開関数として追加。既存の非公開版とロジック重複するが、呼び出し元
[スプレッドシートメニュー vs Web App]が異なるため許容する)。送信自体は既存の
`shareCompanyWithStaff(companyId, staffIds, note)`(ShareRunner.gs)をそのまま呼び出す
(変更不要)。

## 10. レター下書きプレビュー

新規関数`getLatestLetterDraft(companyId)`(AdminRunner.gs)を追加。「レター下書き」タブ
(`LETTER_DRAFT_HEADERS`)から該当企業IDの最新行(`生成日時`が最も新しいもの)を1件返す。
ドロワーに「下書きを見る」ボタンを追加し、モーダルで本文(`本文`列)を表示する。
下書きが存在しない企業では「下書きなし」と表示する。

**デモからの変更点**: デモではこの部分は追跡ページ(トラッキングURL遷移先)のiframeプレビュー
だったが、実際に運用上役立つのは「その企業に何を送ったか(下書き本文)」であるため、
本設計ではレター下書き本文の表示に変更する。

## 11. データフロー・関数一覧まとめ

新規追加(AdminRunner.gs): `getKpiSummary()` / `getOwnerWorkload()` / `getShareableStaffList()` /
`getLatestLetterDraft(companyId)`
新規追加(adminAccess.js、Node側テスト対象): `computeUrgency(company, todayString)` /
KPI集計・ワークロード集計の純粋ロジック部分(AdminRunner.gsからは薄いラッパーとして呼ぶ)
変更(adminApp.js): STYLE/HEADER/TABLE/DRAWER等のHTML/CSS/JS定数を全面書き換え
変更なし: ScoringRunner.gs / AlertRunner.gs / ShareRunner.gs / LetterRunner.gs のロジック自体

## 12. テスト方針

adminAccess.jsに追加する純粋ロジック(`computeUrgency`・KPI集計・ワークロード集計)は
既存のNode側テスト(`tests/glow_ma_adminAccess.test.mjs`)に追加する。AdminRunner.gsの
薄いラッパー関数(GAS依存)は既存パターン通りNode側では検証せず、本番投入前の目視確認で担保する。
adminApp.jsのHTML/JS文字列組み立ては既存の構造面テスト(`tests/glow_ma_adminApp.test.mjs`)に
新規マークアップ・呼び出しの存在チェックを追加する。
