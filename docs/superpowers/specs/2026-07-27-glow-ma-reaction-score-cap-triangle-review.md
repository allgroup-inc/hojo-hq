# glow-ma 三名体制レビュー記録: 反応スコアの上限設計

実施日: 2026-07-27 / スキル: `glow-ma-triangle-review` / 起点: Phase 2最終レビュー(Opus)の指摘
対象: `docs/superpowers/specs/2026-07-26-glow-ma-relation-system-design.md` 6章(反応スコア)

## 背景

Phase 2実装の最終レビューで、反応スコアが対応履歴ログの行数に比例して無制限に加算される設計上の欠陥が実証された:
- 「電話5回(すべて対応相手=オーナー社長本人)」→ 反応スコア75点 → ランクA
- 「レターURLアクセス14回」→ 反応スコア70点 → ランクA

属性スコアには45点の上限があるが、反応スコアには上限がなく、同一イベントの水増しでランクを操作できる状態だった。これはコードの実装ミスではなく、設計書6章の計算式自体の欠陥(コードは仕様通りに実装されていた)。

## 論点

反応スコアの上限設計(同一イベントの繰り返し発生による不当なランク昇格を防ぐ)

### スイシン(推進)

- 反応スコアは「関係の深まりの証拠」を測る指標なのに、現状は同じイベントを何度でも積み増せるため、実態のない量産(同じ人が電話を繰り返す、同じURLに何度もアクセスする)でランクが動いてしまう。企業ごと・種別ごとに上限を設けるべき。
- シンプルな実装案: 「種別ごとに、企業につき初回発生時のみ加点」にする。意思決定者ボーナスも「企業につき1回のみ」にする。

### ウタガイ(懐疑)

- 「初回のみ加点」にすると、本当に複数回の面談・複数回の資料請求がある「熱心な」企業の温度感を過小評価するのではないか。真剣な企業ほど複数回接触するのは営業実態として自然。
- 反応スコアに一律の上限点数を設ける案もあるが、その上限値をいくらにするかがまた恣意的になり、属性スコア上限(45点)との整合性を考えずに数値だけ決めると"たたき台"を重ねるだけになる。
- 「電話5回で75点」の内訳は実は「対応相手=オーナー社長本人」ボーナス(+15×5)が効いた結果。「本人と5回話した」という事実自体は評価に値するのでは、という論点も残る。

### ベッカイ(別解)

- そもそも「対応履歴ログの行数×単価」で反応スコアを計算するモデル自体が、営業実態(捕まるまで何度も電話する、開封されるまで何度もURLを送る)とスコアリングの意図(初動の温度感を測る)がズレている根本原因。
- 「イベントの発生回数」ではなく「そのイベント種別を経験したことがあるか(YES/NO)」で加点する設計に変えれば、量産インフレと複数回接触の評価不足を同時に解決できる。意思決定者ボーナスも同様に「企業につき1回のみ」のYES/NO加点にする。
- 詳細な温度感(何度も接触している等)は、対応履歴ログをそのまま見れば分かる。スコアは一次スクリーニングの目安、履歴ログは詳細把握、という役割分担にすればよい。

### 結論(裁定)

- 採否: **採用(ベッカイ案)**
  1. 反応スコアは「種別ごとに、企業につき初回発生時のみ加点」する方式に変更(同じ種別の2回目以降は加点しない)
  2. 意思決定者ボーナス(オーナー社長本人)も「企業につき1回のみ」加点(対応履歴ログに何度現れても+15点は1回だけ)
  3. これにより反応スコアの理論上限が固定される: 5(レターURLアクセス)+15(返信)+25(ゆんたく相談実施)+25(面談実施)+10(資料請求)+15(意思決定者ボーナス) = 95点。属性スコア上限45点との合計理論上限140点に対し、Aランク閾値70点は十分な位置にある
  4. ウタガイの「複数回接触の評価が下がるのでは」という懸念は、対応履歴ログの閲覧で担保する(スコアは一次スクリーニング、詳細な温度感は履歴ログで補う役割分担)
- 理由: ベッカイ案は量産インフレを構造的に防ぎつつ実装もシンプル(企業ごとの発生済み種別の集合を作り、含まれる種別の点数を合算するだけ)。ウタガイの懸念は役割分担の明確化で解消できる。
