# glow-ma: レター発送 個別QRコード生成 設計書

作成: 2026-08-13 / 小柳さんの承認により実施

## 背景

手紙発送業者との調整の結果、以下の制約が判明した:

- 本文はロボット代筆(業者側で対応可)
- 署名・追伸を代表本人が直筆する場合、その部分は空欄で納品を受け、GLOW側で記入する必要がある
- 送付先企業ごとに異なるQRコード(個別トラッキングURL)を使う場合、業者側で宛先と照合・紐付けする対応はできない

これを受け、業者に「照合して物理的に貼ってもらう」のではなく「QRコード入りの追加ページを、こちらが用意する差し込み印刷用データで印刷してもらう」という依頼に切り替える方向で業者に確認中。ただし、この確認の結果(差し込み印刷可否)によらず、「企業ごとのQRコード画像を生成する」機能自体は、GLOW内製で貼付する場合・業者に差し込み印刷データとして渡す場合のどちらでも共通して必要になるため、先行して実装する。

QRコードの中身は、既存のレター追跡の仕組み(Phase 4: TrackingWebApp.gs / letterContent.js の `buildTrackingUrl`)がすでに生成している企業ごとのトラッキングURL(`<Web AppのURL>?id=C000001`)をそのまま使う。新しいURL体系は作らない。

## 1. スコープ

**作るもの:**
- 発送日を指定すると、その日に発送予定の企業ごとにQRコード画像(トラッキングURL埋め込み)を生成し、Google Driveに保存する機能
- 生成結果の一覧(企業ID・会社名・トラッキングURL・QR画像へのリンク)をシートまたはCSVとして出力する機能
- 既存の「発送日でCSV出力」(Phase 16, ShippingRunner.gs)と同じ操作感の新規メニュー項目

**作らないもの(スコープ外・保留):**
- 印刷して切って貼る用のラベルシート(Googleドキュメント)などの物理作業前提の出力形式。業者が差し込み印刷に対応できるかどうかで要不要が変わるため、業者の回答が出てから別途検討する
- 業者への差し込み印刷データの実際の受け渡し方法・フォーマット調整(業者側のシステム要件が分かってから別途設計する)
- レター下書き生成(LetterRunner.gs)自体の変更。QR生成は発送日が確定した時点(既存のPhase 16 CSV出力と同じトリガー)で行い、下書き生成時には行わない

## 2. QRコード生成方式

Google Apps ScriptにはQRコード生成のネイティブ機能がないため、外部QR生成API(`UrlFetchApp`経由)を使う。**`api.qrserver.com/v1/create-qr-code/`(APIキー不要・無料・GET一発でPNGを返す)を採用する**。呼び出し形式:

```
GET https://api.qrserver.com/v1/create-qr-code/?size=300x300&data=<encodeURIComponent(trackingUrl)>
```

レスポンスはPNGバイナリで、`UrlFetchApp.fetch(url).getBlob()`でそのままDriveに保存できる。手紙の発送規模はロット単位(数社〜数十社)であり、無料枠の呼び出し上限を問題にする想定はない。

トラッキングURL自体は元々手紙に印字して公開する情報であり、外部サービスに渡しても機密性の懸念はない(2026-08-13 小柳さん確認済み)。障害時の挙動: API呼び出しが失敗した行はスキップし、生成結果一覧に「QR生成失敗」の旨を記録して処理を継続する(1社の失敗で全体を止めない。既存のLetterRunner.gs等の「1社ごとの障害隔離」方針を踏襲)。

## 3. データフロー・関数一覧

### 新規ファイル: `glow-ma/src/qrContent.js`(UMD形式、Node側テスト対象)

`glow-ma/src/shippingContent.js`と同じ「発送日ベースで対象を絞り込む」ロジックを踏襲し、QR生成対象の一覧(純粋データ)を組み立てる。

- `buildQrManifestRows(letterDrafts, companies, targetDate, baseUrl)` →
  `[{ 企業ID, 会社名, trackingUrl }]`(発送日が一致し、企業マスタに存在する行のみ。`GlowLetterContent.buildTrackingUrl`をそのまま呼ぶ)
- 既存の`GlowShippingContent`の対象絞り込み(`発送日`一致判定・`GlowAlerting.toDate`利用)と重複するロジックは、`shippingContent.js`側の絞り込み部分を直接呼び出す形にはせず(呼び出し元の関心が「CSV行組み立て」と「QR対象抽出」で異なるため)、同じ絞り込み条件を`qrContent.js`側にも実装する。既存の`buildShippingCsvRows`とは独立した関数として持つ(将来的な共通化は本設計のスコープ外)

### 新規ファイル: `glow-ma/src/QrRunner.gs`(GAS実行層、Node側テスト対象外)

- メニュー「GLOW台帳」→「発送日でQR出力」から実行する新規公開関数(既存のCSV出力メニューの実装パターンをそのまま踏襲)
- 発送日をプロンプトで受け取り、`GlowQrContent.buildQrManifestRows`でQR生成対象一覧を取得
- 各行についてQR生成APIを`UrlFetchApp`で呼び出し、返ってきたPNG画像をGoogle Driveの発送日別フォルダ(例:「QR_2026-08-20」)に、企業IDが分かるファイル名(例:「C000001.png」)で保存
- 生成結果一覧(企業ID・会社名・トラッキングURL・Drive画像へのリンク)を、新規シート(例:「QR生成結果」タブ、都度クリアして書き込み)に出力する
- **既存のScript Properties `TRACKING_BASE_URL`(Phase 4で設定済み)をそのまま使う。新しい設定項目は増やさない**

### 実行時間についての注意

GASの1回の実行には6分の制限がある。手紙の発送はロット単位(数社〜数十社程度)を想定しており、通常は問題にならない見込みだが、念のため「対象社数が多い場合は分割実行が必要になる可能性がある」ことをREADMEに注記する。自動分割の仕組み自体は本設計のスコープ外(実際に問題になった場合に別途対応する)。

## 4. テスト方針

`qrContent.js`の`buildQrManifestRows`(純粋ロジック、発送日絞り込み・トラッキングURL組み立て)は、既存の`tests/glow_ma_shippingContent.test.mjs`と同様のパターンで新規`tests/glow_ma_qrContent.test.mjs`を作成しNode側で検証する。`QrRunner.gs`(外部API呼び出し・Drive操作・シート書き込み)はGAS依存のため、既存の`ShippingRunner.gs`等と同様にNode側では検証せず、本番投入前の目視確認で担保する。
