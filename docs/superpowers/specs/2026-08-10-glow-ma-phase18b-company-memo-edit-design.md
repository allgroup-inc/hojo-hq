# glow-ma Phase 18b: 管理画面からの「関係メモ」編集 設計書

作成: 2026-08-10 / 小柳さんの承認により実施

## 背景

Phase 18a(企業一覧・詳細の閲覧)・紹介パートナー開拓状況ビューにより、管理画面Web Appは
読み取り専用の機能を持つに至った。`docs/superpowers/specs/2026-08-09-glow-ma-admin-webapp-phase18a-design.md`
では、書き込み系(関係メモ編集・対応履歴ログ入力)をまとめてPhase 18bとする暫定案を示していたが、
「実装難易度差が大きく、さらに分割する可能性がある」と明記していた(同ドキュメント裁定4)。

本ドキュメントでは、Phase 18bの範囲を**企業詳細ドロワーの「関係メモ」欄の編集のみ**に絞り、対応履歴
ログ入力は後続フェーズ(Phase 18b-2、仮称)として切り出す。関係メモ列の由来は
`docs/superpowers/specs/2026-08-06-glow-ma-relationship-memo-triangle-review.md`を参照。

## 1. スコープ

**作るもの:**
- 企業詳細ドロワーの「関係メモ」欄に「編集」ボタンを追加し、管理画面から直接書き換えられるようにする

**作らないもの(後続フェーズ):**
- 対応履歴ログの新規入力(Phase 18b-2)
- 関係メモ以外のフィールド(次回アクション内容・現在ステージ・担当者等)の編集
- 楽観的ロック(保存時の競合検知)。今回はlast-write-winsを採用し、次フェーズで再検討する(4章参照)

## 2. UI(adminApp.js)

- 企業詳細ドロワーの「関係メモ」欄の横に「編集」ボタンを表示する
- 「編集」を押すとテキストエリアに切り替わり、「保存」「キャンセル」ボタンが表示される
- 「保存」を押すと`google.script.run`で`updateCompanyMemo(companyId, memo)`を呼ぶ
  - 保存中はボタンを無効化し「保存中...」を表示する
  - 成功時のみ「保存しました」を一時表示し、閲覧モードに戻す(`.withSuccessHandler`が呼ばれた場合のみ)
  - 失敗時は「保存に失敗しました。もう一度お試しください」を表示し、編集モードのまま入力内容を保持する
    (`.withFailureHandler`。自動リトライはしない。失敗時に誤って「保存しました」と表示しないことを
    三名体制レビュー2026-08-10で確認済み)
- 「キャンセル」を押すと編集前の内容に戻し、閲覧モードに戻る
- **未保存の変更がある状態で、ドロワーを閉じる操作・別企業の詳細を開く操作をした場合、
  `confirm()`で「保存されていない変更があります。破棄しますか?」と確認する**
  (三名体制レビュー2026-08-10、論点2の裁定により追加)

## 3. サーバー関数(AdminRunner.gs)

`updateCompanyMemo(companyId, memo)`を新設する。

```
function updateCompanyMemo(companyId, memo) {
  requireAdminAccess_();
  // 1. 企業マスタから該当企業IDの行を探す。見つからなければ例外を投げる
  // 2. 更新前の「関係メモ」の内容を取得しておく
  // 3. 対応履歴ログに1行追加する:
  //    種別="関係メモ更新", 内容メモ="関係メモを更新しました(更新前の内容: <旧内容>)"
  //    (旧内容が空の場合は「(更新前は未記入)」とする)
  // 4. 企業マスタの「関係メモ」列を新しい内容で上書きする
  // 5. 3→4の順で行う(対応履歴への記録が失敗したら関係メモも更新しない。
  //    記録なき上書きを避けるため)
}
```

- 冒頭で`requireAdminAccess_()`を呼ぶ(Phase 18aから続く多層防御パターン)
- 関数名の末尾に`_`を付けない(Phase 18a最終レビューで発見したGASの落とし穴。`google.script.run`から
  呼べなくなる)
- `SpreadsheetApp`の`LockService`は使わない。関係メモ1件の単純な上書きであり、企業マスタ全体を
  書き直す`writeCompanyRecords_`のような処理ではないため、既存の`ImportRunner.gs`のロックパターンは
  過剰と判断(YAGNI)

## 4. 対応履歴ログへの自動記録(三名体制レビュー2026-08-10 論点1・3の裁定)

関係メモの上書きにより過去の記載内容が消える問題(ウタガイの指摘)に対処するため、専用の変更履歴
テーブルは作らず、**保存の直前に、更新前の関係メモの内容を対応履歴ログへ1行自動記録する**。

- `schema.js`の`INTERACTION_TYPES`に新しい種別`"関係メモ更新"`を追加する
- この自動記録により、関係メモが上書きされても対応履歴ログを遡れば過去の内容を復元できる
- 対応履歴ログの「担当者」欄には、`Session.getActiveUser().getEmail()`から特定できる氏名
  (「スタッフ」タブの氏名列と突き合わせる)を入れる。特定できない場合は「不明」とする

## 5. 競合方針(三名体制レビュー2026-08-10 論点4の裁定: 保留・次フェーズ再検討)

同時編集時はlast-write-wins(後から保存した内容が勝つ)とする。楽観的ロック(保存前に最新内容と
読み込み時の内容を比較し、食い違っていれば警告する)は今回見送るが、4章の自動記録により
上書きされた内容も対応履歴ログから復元可能なため、実害は限定的と判断する。次フェーズ(対応履歴
ログ入力)の設計時に、同時編集対策をまとめて再検討する。

## 6. エラーハンドリング

- 該当企業が見つからない場合(削除済み企業を編集しようとした場合など): サーバー側で例外を投げ、
  クライアント側は「保存に失敗しました。もう一度お試しください」を表示する(詳細なエラー内容は
  区別しない。Phase 18aの一覧読み込み失敗時と同じ方針)
- 許可リスト外アクセス: `requireAdminAccess_()`が例外を投げ、上記と同じエラー表示になる

## 7. テスト方針

- `updateCompanyMemo`はGAS専用(`SpreadsheetApp`依存)のためNode単体テスト対象外
  (`getCompanyDetail`等の既存パターンと同じ扱い)
- クライアント側の状態遷移(編集モード切り替え・保存中表示・成功/失敗表示・離脱確認)は
  `adminApp.js`のNodeテスト(`tests/glow_ma_adminApp.test.mjs`)で検証する

## 8. 本番投入前チェックリストへの追加事項

`docs/glow-ma_本番投入手順書_統合版.md`に以下を追記する:
- 関係メモを編集・保存し、対応履歴ログに「関係メモ更新」種別の行が自動追加されることを実機確認
- 保存失敗時(例: 意図的に企業IDを不正な値にして実行するなど)に、誤って「保存しました」と
  表示されないことを実機確認
- 未保存の変更がある状態でドロワーを閉じようとした際、確認ダイアログが出ることを実機確認
