# glow-ma 管理画面: 紹介パートナー開拓状況ビュー 設計書

**日付**: 2026-08-09
**背景**: `docs/superpowers/specs/2026-08-09-glow-ma-partner-development-design.md`(三名体制レビュー済み)
で確定した沖縄県内M&A紹介パートナー開拓の3層データ構造(紹介パートナーマスタ・パートナー対応履歴
ログ・紹介実績ログ)を、Phase 18a(企業一覧・詳細の閲覧)と同じ管理画面上で可視化・管理できるように
する。企業一覧と切り替えて見られる「紹介パートナー開拓状況」ビューを追加する。

読み取り専用から始める(Phase 18aと同じ段階的アプローチ)。パートナー候補の新規登録・対応履歴の
入力・紹介実績の入力は後続フェーズとし、当面はスプレッドシートを直接編集する運用とする。

## 1. アーキテクチャ

Phase 18aで作成済みのWeb App・許可リスト認証をそのまま使う、単一ページ内の画面切り替え方式を
採用する。新しいWeb Appデプロイや新しいURLは作らない。

```
[小柳・福田・嶺井のブラウザ]
        │ 既存の管理画面URL(?page=admin)にアクセス
        ▼
[AdminApp(adminApp.js)] ── 画面上部の切り替えタブ
        │                        │
        ▼                        ▼
   企業一覧ビュー            紹介パートナー開拓状況ビュー(新規)
   (Phase 18a・既存)          │ google.script.run
                              ▼
                    [AdminRunner.gs: getPartnerList / getPartnerDetail]
                              │ requireAdminAccess_()(既存の許可リストと同じ)
                              ▼
                    [紹介パートナーマスタ・パートナー対応履歴ログ・紹介実績ログ]
```

認証・許可リストはPhase 18aと完全に同じ(小柳・福田・嶺井の3名)。紹介実績ログの紹介料率・契約
内容メモという金額情報についても、この3名は全項目を閲覧できる(2026-08-09ブレインストーミングで
小柳さんが直接決裁。福田さんも含めて3名とも閲覧可)。

## 2. スコープ

**作るもの:**
- パートナー一覧: 紹介パートナーマスタの全件表示(件数が少ないため絞り込み必須・100件上限は
  設けない。企業一覧とは異なる設計判断)。各行に対応履歴の件数(対応回数)を表示する
- パートナー詳細: 基本情報(名称・種別・担当者名・関係性ランク)・対応履歴(日付降順)・紹介実績
  (紹介料率・契約内容メモ・成約有無)の3ブロックを1画面で表示

**作らないもの(後続フェーズ):**
- パートナー候補の新規登録
- 対応履歴・紹介実績の画面からの入力
- KPI集計(既存のダッシュボードのパートナー別サマリーとの統合)

## 3. データ構造(新規タブ2つ)

`glow-ma/src/schema.js`に追加し、`ensureLedgerTabs`(`SheetSetup.gs`)で既存8タブと合わせて自動
作成されるようにする。

- **パートナー対応履歴ログ**(`PARTNER_INTERACTION_LOG_SHEET_NAME`): `履歴ID・パートナーID・
  日付・対応者・内容メモ・次回アクション`(既存の企業向け`対応履歴ログ`と同じ並び)
- **紹介実績ログ**(`REFERRAL_RECORD_SHEET_NAME`): `実績ID・パートナーID・紹介日・対象企業ID・
  紹介料率・契約内容メモ・成約有無`

## 4. サーバー関数(`AdminRunner.gs`に追加)

- `getPartnerList()`: `readPartnerRecords_`(`DashboardRunner.gs`、既存)を再利用して紹介パートナー
  マスタ全件を読み、パートナーIDごとにパートナー対応履歴ログの件数(対応回数)を集計して返す。
  `requireAdminAccess_()`を冒頭で呼ぶ
- `getPartnerDetail(partnerId)`: 該当パートナーの基本情報+対応履歴(日付降順、
  `GlowAdminAccess.sortInteractionsByDateDesc`と同じ並び替えロジックを再利用)+紹介実績を返す。
  該当パートナーが見つからない場合は`null`を返す。`requireAdminAccess_()`を冒頭で呼ぶ
- どちらもPhase 18aの`getCompanyList`/`getCompanyDetail`と同じ命名規則に従う(**末尾にアンダー
  スコアを付けない**。Phase 18a最終レビューで実際に発生した「`google.script.run`から呼ぶ関数が
  private扱いになりサイレントに失敗する」不具合を再発させないため)

## 5. 画面(`adminApp.js`を拡張)

- ページ上部に「企業一覧」「紹介パートナー開拓状況」の切り替えタブを追加する(Phase 18aの詳細
  ドロワー内タブ切り替えと同じ実装パターンを流用する)
- パートナー一覧: 名称・種別・関係性ランク・対応回数のテーブル。行クリックでパートナー詳細を表示
- パートナー詳細: 既存の企業詳細ドロワーと同じ構造(概要・対応履歴の2ペイン)に、紹介実績ペインを
  追加した3ペイン構成

## 6. エラーハンドリング・テスト方針

Phase 18aと同様の方針を踏襲する。
- 読み込み失敗時: 「読み込みに失敗しました。再読み込みしてください」を表示
- 該当パートナーなし: `getPartnerDetail`が`null`を返し、「該当するパートナーが見つかりません」を表示
- 対応履歴・紹介実績ログの日付は`Date`オブジェクトで返る可能性があるため、Phase 18a最終レビューで
  追加した`GlowAdminAccess`の日付正規化ロジック(`normalizeDateForDisplay_`)を再利用し、
  文字列比較の不具合を再発させない
- 純粋ロジック(対応回数の集計、日付正規化・並び替えの再利用)は`adminAccess.js`にNode側で
  テストする。GAS専用部分(`AdminRunner.gs`・`adminApp.js`のUI部分)は静的チェック+手書き
  トレース+実機検証とする

## 7. 見直し期限

2026-11-09(最長6ヶ月)。パイロットの進捗次第で、書き込み機能(候補登録・対応履歴入力)の要否を
再検討する。
