## 1. 改善点(目標達成確率への影響が大きい順)

### ① 独立監査が週次レポに繋がっていない【実施済み】

- **対象**: `scripts/weekly_report_integrated.py` / `docs/運用規程_やり切り実行計画_2026-08.md` G2
- **何が不十分だったか**: 規程に「統合週次レポに監査所見欄+無作為3件点検の運用開始」と書かれてから**2週間、1行も実装されていなかった**。`監査所見` の語はリポジトリ内の規程・議事にしか存在せず、週次レポ生成器のどこにも無い。つまり**タダスさん(独立監査)は名前だけで、週次に何も見ていない**状態
- **使ったスキル**: `resilient-agent-design`(決定性・べき等)/ `hojo-triangle-review`(点検の3観点)
- **どう作り直したか**: 統合週次レポに **§4「監査所見 — 今週の無作為点検」** を新設。パッチではなく機能として追加
  - 点検対象プール = cron定期実行ワークフロー(L3/L4自動運転)+ 決裁キューの未チェック項目
  - **週番号をシードにした決定性抽出**。同じ週なら何度生成しても同じ3件(べき等)、週が変われば入れ替わる。実行時刻依存の乱数にしない
  - 点検の観点を3役(スイシン=動いているか / ウタガイ=壊れても気づけるか / ベッカイ=そもそも必要か)で固定
  - **「所見が2週連続で未記入なら監査が名前だけになっている合図」**という自己検知条件を明記
  - 自己テスト11件を追加(決定性・重複なし・週で入れ替わる・プール空・パス不正)。`--self-test` は41チェック全通過
- **効果**: 全部門の品質を外から見る目が、週1回・自動で対象付きで立ち上がる。「監査しているつもり」が数字で検出できる

### ② `/go/` の計測イベントがKGIを水増ししうる【実施済み・面談予約表に直結】

- **対象**: `.claude/skills/go-link-discipline`(新規作成)/ `scripts/generate_go_pages.py`
- **何が不十分だったか**: `generate_go_pages.py` `generate_card.py` ほか計6ファイルが `go-link-discipline 準拠` と書いているのに、**スキルの実体が存在しなかった**。規律が人の記憶とREADMEにしか無い状態
- さらに実害: 現行テンプレートは計測イベント名が **`line_redirect` 固定**。面談予約表で `/go/yoyaku/` を足すとき、そのまま流用すると**予約クリックがLINE登録として集計され、KGI(1,000社)の現在地を見誤る**。次の作業で確実に踏むところだった
- **使ったスキル**: `go-link-discipline`(作成したもの)
- **どう作り直したか**: スキルを新規作成し、「転送先がLINEでない場合はイベント名と文言を必ず切り替える」を独立セクションで明記。判断基準を「この数字はどのKPIに積まれるべきか」に固定。CV単一ルールとの関係(チャネル追加≠導線追加の許可)も明記
- **効果**: KGIの数字の信頼性を守る。数字が汚れる事故はリンク切れより発見が遅れる分たちが悪い

### ③ Lighthouse Issueが triage スキルに繋がっていない【実施済み】

- **対象**: `.github/workflows/lighthouse.yml`
- **何が不十分だったか**: 閾値割れで自動起票されるIssue本文が「スコア詳細とレポートはArtifacts参照」で終わっていた。**Claude Code環境からは本番URLもArtifactsも開けない**ことが多く、`hojo-lighthouse-triage` はまさにそれを前提にローカル再現手順を用意しているのに、Issueからそこへの導線が無い。対応者が毎回同じ場所で詰まる
- **使ったスキル**: `hojo-lighthouse-triage`
- **どう直したか**: Issue本文に「対応する人へ(AIエージェント含む)」節を追加し、着手前にスキルを読むこと・ローカル実測から始めることを明記
- **効果**: 再発時の初動が速くなる。スコア低下の放置期間が縮む

### ④ 議事が企画書に埋没し、一覧から漏れていた【実施済み】

### ⑤ 出荷ゲートの通過記録が成果物に残っていない【2026-08-17 実施済み】

- **対象**: `posts/` `outbox/` 配下の対外文面、および各投稿生成ワークフロー

- **どう作り直したか**(議事: `docs/議事_20260817_出荷ゲート通過記録.md`): 単純なスタンプではなく**二層構造**にした
  - **機械が検査する層**: 禁止表現(「締切7日前」「必ずもらえる」等の断定)/ lin.ee直貼り / 記録の鮮度。**申告があっても違反なら落とす**

  - 突然止まらないよう76日で警告・90日で停止の二段にし、停止時は失敗時LINE通知が飛ぶ
- **残り(正直な記録)**: LINE配信・note・メール・もらいわすれ堂側は**未適用**。同じモジュールを呼ぶだけで広げられるが、誤検知の有無をミカタのSNSで1〜2週間見てから拡大する
- **限界**: humanizerの自然さは依然として申告。仕組みでは埋まらないため、週次の無作為点検で見る

## 2. 組織編成の点検

### このチャットの体制

**体制化していない(1人称で進行)。** 部門分担はせず、意思決定時に `hojo-triangle-review` の3役(スイシン/ウタガイ/ベッカイ)を自分の中で回す形で代替しています。
面談予約表の規模(既製ツール1週間の検証)に対して部門分担は過剰と判断。**この判断は妥当**と考えます。

### リポジトリ全体の体制(検証できた範囲)

- **役割定義**: `.claude/agents/` に21体(統括・6部門・note編集部・独立監査・ニドナシ機構3体・フクギイロ5部門)
- **検証したもの**: 独立監査(kansa.md)の実効性のみ
  - → **名前だけになっていた**(週次レポに所見欄が無く、無作為3件点検も動いていなかった)。①で是正
- **検証していないもの**: 他20体が実際に動いているか、役割の重複・空白があるか。**このチャットの守備範囲を超えるため未実施**(統括アカリさんの週次レポ側で見るべき事項)。誤って「点検済み」と記録しないためここに明記します

### 意思決定の質

- 直近の議事5本すべてに `ウタガイ` の記載あり(`docs/議事_20260812_読み心地総点検.md` は「ウタガイの反対理由(記録・議事有効性要件)」節を持つ)。**形式は守られている**
- ただし④のとおり、**議事ファイル名の規則から外れた議事が1本あった**(今回是正)。形式が守られていても置き場所が外れると点検対象から消える
- 全会一致の連続(視点の同化)は、①の週次点検が回り始めれば検出できるようになる
