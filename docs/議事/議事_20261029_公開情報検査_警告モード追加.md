# 議事: 公開情報検査(警告モード)の追加 — P1-1(ドラフト・決裁待ち)

> このファイルはドラフト(決裁待ち)。承認と実施の経過(いずれも 2026-10-29、小柳さんの限定承認):
> 実装とローカル検証 → 作業ブランチへの commit・push → main 宛ての Draft PR(allgroup-inc/hojo-hq#542)の作成。
> Draft の解除・取り込み(マージ)・止めるモードへの切り替えは未承認。採用されたら `status: adopted` に改める。

## なぜ(背景)

GLOW 全体統括の調査(2026-10-28〜29)で、公開リポジトリ hojo-hq の `docs/` に、管理画面の入口URL・
台帳への直接リンク・スタッフ個人のメールアドレスが載っていることが分かった。既存の公開NG検査
(`scripts/check_repo_scope.py`)は家計の見直しやさん関連の語だけを見ており、メールアドレス・電話番号・
内部URLは見ていない。最新のファイルから値を消しても過去の版には残るため、消すより先に
「これ以上増やさない」見張りが要る(P1 安全対策の最初の単位)。

## 前提

- 本リポジトリは公開。Actions のログも誰でも読める。したがって検査は**一致した値そのものを出力しない**
- 既存の検査には足さない。既存の検査は Baseline Debt(`docs/wikiskill/baseline-debt.json`)で
  「違反0件」として固定されており、項目を足すと既存の一致で即座に赤になって「新しい赤を増やさない」規律に反する。
  また既存の検査ファイルは CODEOWNERS の Trust Boundary にある
- 既存の一致は件数だけを `scripts/public_exposure_baseline.json` に記録し、**増えた分だけを新規**として報告する。
  記録した既存の一致は「過去の版にも残っている一致」であり、安全になったとは扱わない
- 検査しないファイル(画像・PDF等、`data/`、`.claude/experience/`、大きすぎる・文字コード不明)は
  「未検査」として件数を毎回報告する。未検査は「問題なし」ではない
- 外部AI・外部サービスには何も送らない。`pull_request_target` と secrets は使わない。権限は読み取りのみ

## 代替案

1. 既存の `check_repo_scope.py` に規則を足す → 既存の一致で即赤・Trust Boundary の変更になるため不採用
2. 外部の秘密情報検査ツール(OSS)を入れる → 外部の部品の取り込み(版とハッシュの固定・deps-pin-check への登録)が
   既存ファイルの変更を伴う。日本の携帯番号・会社ドメインの個人名アドレスは標準では拾わない。今回は不採用(将来の併用は可)
3. いきなり止めるモード(`--strict`)で入れる → 既存の一致125件で毎回赤になり、無関係の変更まで止まるため不採用

## 三名体制の議論

- **スイシン(推進)**: 新しいファイルだけで入り、本番・記憶・既存の検査に触れない。値を出さない・既存と新規を分ける・
  未検査を数える、の3点で公開リポジトリでも安全に回せる。P1-2(文書の置き換え)の進み具合も「減少」で見える
- **ウタガイ(懐疑・反対理由。必須)**: 警告モードは止めないので、注記を誰も見なければ増えても素通りする
  (2026-10-06 FK-006「赤でも後続が止まらない」と同型)。件数ベースの判定なので、既存の一致を1件消して別の値を1件
  足すと「増えていない」と判定され見逃す。形の決まらない個人情報(氏名・住所)は拾えない。`data/` を未検査にしたことで、
  そこに個人の携帯番号が紛れても気づけない。架空とみなす形(同じ数字の繰り返し等)に偶然一致する実在の番号は見逃す
- **ベッカイ(別解・前提を疑う)**: そもそも公開リポジトリに業務文書(担当者とのやりとり・設定手順)を置く運用自体が
  原因で、検査は対症療法。業務文書の置き場を非公開側へ寄せる方針(CLAUDE.md「判断に迷う置き場所は、先に非公開側へ」)
  の徹底と組み合わせないと、件数は減らない

## 裁定

(決裁待ち。以下は起案者の提案)

- 警告モードで導入する。ウタガイの指摘への手当て:
  - 素通り対策: P1-2(文書の置き換え)完了後、議事を改めて `--strict`(新規があれば失敗)へ切り替える。期限の目安は導入から1か月
  - 入れ替わりの見逃し: 件数判定の限界として残す。`--strict` 移行時に、PR の差分の行だけを見る判定の追加を再検討する
  - `data/` の未検査: 別途、公的データの点検(収集部・守り部)で扱う。未検査の件数は毎回表示する
- BASELINE(件数表)を増やす書き直し・規則を緩める変更・止めるモードへの切替は、いずれも議事を要する

## 未解決事項(2026-10-29 時点)

- **BASELINE の125件(36ファイル)は暫定値**。既存の一致を「新規」と区別するための件数であり、
  これらが安全であること・公開してよいことの承認を意味しない(過去の版にも残っている)
- **要確認1件**: `glow-ma/src/LineVoiceLogRunner.gs` の使い方の例(447行目付近)に、LINE の利用者IDの形をした
  文字列がある。架空の形(同じ文字の繰り返し・連番)ではないため、実在のIDかどうかを小柳さんが確認する(値はここに書かない)
- 既存の wikiskill-tests は main で失敗が続いている。本変更とは無関係で、別の課題として対応する
  - CI(Python 3.11): main と本変更のどちらでも、同じ**5件**が失敗(`tests/integration/test_wikiskill_wiki_e2e.py`、`scripts/wiki_validate.py` の V09)
  - ローカル(Python 3.13): 上の5件に、Python の版の差で `tests/scripts/test_check_experience_privacy.py` の1件が加わり**6件**。本変更の前後で同じ

## 見直し条件

- 導入から1か月、または P1-2 完了の早いほうで、`--strict` への切替を再議論する
- 新規の一致が警告されたのに対応されなかった事例が1件でも出たら、その時点で再議論する
- 誤検知が規則ごとに月3件を超えたら、その規則の形を見直す
