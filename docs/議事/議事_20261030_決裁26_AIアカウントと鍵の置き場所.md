# 議事: 決裁26 追補 — AI用アカウントと自動処理の鍵の置き場所(2026-10-30)

決裁26(`docs/議事/議事_20261008_決裁26_Rulesets段階導入.md`)の S7b「Claude 用アカウント(outside collaborator・Write)」について、**Write を渡す前に満たす条件**を追加する。本議事で決めたのは方針だけで、鍵の移し替え・workflow の変更・アカウントの招待は未実施。それぞれ別の承認を要する。

## なぜ(背景)

- 2026-10-30、公開の試験用リポジトリ `allgroup-inc/auth-sandbox`(無料プラン)で、決裁26 と同じ形の branch ruleset と AI 用アカウント `allgroup-ai-agent-01`(outside collaborator・Write)を使い、段階 A の試験を行った。
  - 期待どおり: main への直接 commit・自分の PR の承認・承認の無い PR の統合・承認後の AI による統合を、すべて拒否。承認後に書き足すと承認が取り消された。小柳さんはバイパス(PR のみ)で統合できた
  - **期待外れ**: Write の AI 用アカウントが、Actions の repository secret を**追加・削除できた**
  - 未実施: main の強制上書き・削除(パソコンからの試験)
- 調査の結果、より大きな穴が分かった。**Write があれば、自分の作業用の枝に workflow を置くだけで、repository secret を読み出せる**(GitHub の security hardening の文書にも「書き込み権限のある人は、すべての secret を読めるのと同じ」とある)。main の ruleset では防げない。
- hojo-hq の workflow は、`GITHUB_TOKEN` 以外に **44 種類の secret** を参照している(LINE・SNS・メール送信・AI API など。66 本中 47 本が参照。2026-10-30 の main で計測)。いま `environment:` を使うのは `sns-approval` の 1 本だけ。App の秘密鍵は S3 で Environment `app-push`(Deployment branches = main のみ)に置いてある。

## 前提

- hojo-hq は公開・無料プラン。公開リポジトリでは、無料でも Environment と「Deployment branches(main のみ)」が使える。Environment の secret は、許された枝で動く job にしか渡らない。
- 組織の secret は、無料プランでは非公開リポジトリに届かない(公開リポジトリには届く)。
- Environment の設定変更は admin の操作で、Write では変えられない(画面上の扱い。Write が Environment の secret を追加・削除できるかは**未確認**。試験用リポジトリで確かめる)。

## 代替案

| 案 | 内容 | 採否 |
|---|---|---|
| **A 鍵を Environment へ移してから Write(採用)** | 44 種類の secret を、Deployment branches = main のみの Environment へ移し、参照する workflow に `environment:` を付ける。移し終えるまで AI 用アカウントに Write を渡さない | **採用** |
| B 組織の secret にする | 公開リポジトリには届くが、枝の制限が無く、Write の枝の workflow から読める | 不採用(穴が塞がらない) |
| C 有料プラン(Team) | 非公開リポジトリでも Environment が使える | hojo-hq は公開なので不要。不採用 |
| D AI 用アカウントには Write を渡さず、fork から PR を出させる | secret は fork の PR に渡らない | 不採用(S7b の前提「Write」を変える大きな変更。案 A が不成立のときの再上申候補) |
| E いまのまま(小柳さんのアカウントで Claude が動く) | — | 不採用(人と AI の区別がつかない状態が続く) |

## 決定内容(2026-10-30 小柳さん決裁: 「上の表の方針で進める」)

1. **S7b で AI 用アカウントに hojo-hq の Write を渡すのは、workflow が参照する secret をすべて Environment(Deployment branches = main のみ)へ移し、repository secret を 0 件にした後とする。**
2. 移し替えは、決裁26 の S5(App トークンへの切替)と同じ workflow を触るため、S5 と同時か直後に行う。段階の名前は「S6 鍵の Environment 移行」とする(旧 S6 は削除済みのため番号を再利用する)。実施は別の承認。
3. 移し替えの受け入れ: ①repository secret が 0 件(画面で確認)②secret を参照する workflow がすべて `environment:` を持つことを機械検査(S5 の検査テストに追加)③main 以外の枝で動いた試験の workflow が secret を受け取れないこと。
4. 他のリポジトリの扱いは、そのリポジトリ側で記録する(本議事は hojo-hq だけを決める)。

## 三名体制の議論

- **スイシン(推進)**: 鍵の穴は試験で実際に見つかった。Environment は無料で使え、`app-push` で手順も確かめ済み。S5 で同じ workflow を触るので、手戻りが少ない。
- **ウタガイ(懐疑・反対理由。必須)**:
  1. 44 種類の secret を 47 本の workflow で移し替えるのは大きい。1 本でも `environment:` を付け忘れると、その自動処理は secret が空のまま動き、沈黙して失敗する(`note-magazine-automation` の前例)。
  2. Environment を付けた job は、実行のたびに「deployment」の記録が増え、画面が読みにくくなる。
  3. Write が Environment の secret を追加・削除できるかは未確認。できるなら、7b・7c の穴(追加・削除)は残る。
  4. 移し替えの間、同じ値の secret が repository と Environment の両方にある期間ができる。古いほうの消し忘れで穴が残る。
  5. Write の AI は、main 向けの PR の中で workflow を書き換えられる。統合は人が行うが、見落とすと secret を外へ送る workflow が main に入る。鍵の置き場所だけでは防げない。
  6. 段階 ②(強制上書き・削除)の試験が未実施のまま方針を決めている。
- **ベッカイ(別解・前提を疑う)**:
  1. secret を使う処理を、そもそも hojo-hq から外す(例: 送信は Power Automate 側に寄せ、リポジトリは成果物を作るだけ)。
  2. AI 用アカウントは fork から PR を出す形にし、Write を渡さない(代替案 D)。
  3. 使われていない secret があれば、移さずに消す。

## 裁定(部門長)

- 案 A を採用。ウタガイ 1 は採択: 受け入れ②の機械検査(`environment:` の付け忘れを赤にする)を必須にする。ウタガイ 3 は採択: 試験用リポジトリで Write による Environment secret の追加・削除を確かめ、結果を本議事の見直し条件に反映する。ウタガイ 4 は採択: 受け入れ①で repository secret 0 件を確認する。ウタガイ 5 は採択: いま CODEOWNERS に入っている workflow は 4 本だけ(2026-10-30 確認)なので、S6 で `.github/workflows/` 全体を CODEOWNERS に加え、S7b の Code Owner 承認で workflow の変更に人の確認を必須にする(CODEOWNERS の変更は Trust Boundary のため別の承認)。加えて、workflow を変える PR は統合前に secret の送り先を確かめることを S8 の文書に明記する。ウタガイ 2 は不採択(表示の問題で、安全性に影響しない)。ウタガイ 6 は一部採択: 段階 ② の結果は S7a の前提として扱い、方針は先に決める。
- ベッカイ 1 は Phase 3 以降の構想として記録。ベッカイ 2 は案 A 不成立時の再上申候補。ベッカイ 3 は採択: S6 の作業で、参照の無い secret を一覧にして、小柳さんの確認後に削除する。

## 見直し条件

- 見直し期限: 2027-04-28。
- Write が Environment の secret を追加・削除できると分かったときは、期限を待たずに再議論する。
- S6 の受け入れ③(main 以外の枝で secret を受け取れない)が満たせないときは、AI 用アカウントへの Write を保留し、代替案 D を再上申する。
- GitHub の提供条件が変わったとき。
