# 議事: 決裁キュー #26 main 保護の段階導入(2026-10-08)

本議事は、WikiSkill Phase 2 の Gate G1 で未設定のまま分離された「main の保護」(決裁キュー #26)について、2026-10-08 に小柳さんが決裁した **基本方針(案 B・段階導入)・S0 実装前確認の条件付き合格・詳細設計 v1.1 の変更方針・S1 の実施計画** を正式な Decision として残すもの。調査書(S0 v1・v2)と詳細設計(v1・v1.1 差分)の要点を本文に統合した。

**本議事の時点で実施済みなのは調査と設計だけ**である。S1 のコード実装・GitHub App 作成・Secret 登録・Workflow 変更・Rulesets 有効化・アカウント変更・Phase 3 は未着手で、それぞれ別の承認を要する。

## なぜ(背景)

- Phase 2 で `.github/CODEOWNERS`(`docs/wiki/` と Trust Boundary 19 パス)を入れたが、main は未保護・ruleset なしのため、CODEOWNERS は「運用上の約束」にとどまる。Official Wiki の「人の承認」も、AI セッションが main に直接 push しないことも、機械では保証されていない。
- Claude Code の GitHub 連携は小柳さんのアカウントそのものである(PR #441・#442 の作者もマージ実行者も同一)。このままでは「Code Owner の承認必須」を入れても、承認者 = 作者 = AI の操作主体が同一アカウントになり、本人 PR が詰まるか、admin の bypass で AI も素通りする。
- 32 本の自動処理 workflow が既定の `GITHUB_TOKEN` で main に直接 push している(直近 20 日で 180 commit・1 日約 9 回)。`GITHUB_TOKEN` は Rulesets の bypass actor に指定できないため、PR 必須を先に掛けると自動処理が全停止する。
- 直近 20 日で、Claude セッションが main をチェックアウトして直接 commit した例が 33 件、`.claude/experience` だけを直接 push した `record:` commit が 5 件ある。

## 前提

- 本リポジトリは Organization `allgroup-inc` 配下の **public**。プランは **Free**(2026-10-08 小柳さん画面確認)。
- 2026-10-08 の画面確認で確定した事実: 組織 Rulesets は Team 以上 / リポ単位の Branch Rulesets は作成可 / **Push Rulesets は項目なし(public では提供されない)** / **Evaluate モードは Enterprise 限定** / PR 必須・Code Owner 承認・必須 status check は設定可 / bypass 候補は 組織管理者・リポジトリ管理者・Deploy Key・**Write**・GitHub App 等 / `GITHUB_TOKEN` の既定は読み取り専用 / 「Actions による PR 作成・承認」は**無効でグレーアウト(組織ポリシー)** / 外部投稿者の workflow は初回投稿者のみ承認が必要。
- API(proxy 経由)で実測: Rulesets 0 件・classic protection なし・`git push` を含む workflow は 32 本(main へ 30・ブランチへ 2)で、全 32 本が `actions/checkout` に `token:` を指定していない・`pull_request_target` を使う workflow はゼロ・`.github/workflows` を書く自動処理はゼロ・Trust Boundary と `docs/wiki/*.md` 直下を書く自動処理はゼロ。
- `GITHUB_TOKEN` による PR 作成は既に失敗している: `ai-update-watch.yml` の 2026-09 分 PR #353 は小柳さんが手動作成、2026-10 分はブランチ `auto/ai-update-watch-2026-10` が push されたまま PR が無い(run は warning で success)。`knowledge-extract.yml` は GitHub 上で 0 回実行で、動かしても同じ理由で PR を作れない。
- CI の現状: `repo-scope` のジョブは `check` 1 つで、置き場所の検査(Baseline 9 件・#22)が常時赤。常時起動かつ常時緑の check は存在しない。check-run 名 `validate` は 3 workflow、`test` は 2 workflow で重複している。
- この作業コピーは shallow clone(境界 2026-09-18)であり、履歴の統計は 20 日間の値。境界の commit を「異常な巨大 commit」と誤報した調査(v1)は撤回済み。

## 決定内容(2026-10-08 小柳さん決裁)

### 1. 基本方針(承認済み)
1. 案 B(Rulesets 段階導入)。
2. 人間の承認者アカウントと Claude Code の GitHub 認証を分ける。**Claude 側を新設の低権限アカウント(outside collaborator・Write)へ移し**、小柳さんの現アカウントを承認者・admin として残す。Claude 用アカウントには admin も bypass も与えず、将来の追加には議事と決裁を要する。
3. 自動処理の認証は GitHub App を第一候補とする。権限は Metadata Read / Contents Read & write / Pull requests Read & write のみ。**Issues と Workflows は付けない**(Issue 起票 9 本は `GITHUB_TOKEN` のまま。Workflows を付けないことで App トークンが CI 定義を書き換える経路を塞ぐ)。install 先は hojo-hq のみ。秘密鍵は repo secret(org secret にしない)。トークン発行は `actions/create-github-app-token` を commit SHA で固定。
4. Experience は E1(セッションは main で作業しない。記録は普段の PR に同梱)から始める。E2(自動取り込み)は App 導入後の別案件。
5. 32 本の自動処理を止めない。順序は **App → カナリア → 全数切替 → ruleset** を固定する。
6. 各段階で守り部の審査と Rollback を用意する。S3(App 作成)の守り部審査は省略不可。

### 2. S0 実装前確認の結果(条件付き合格)と、それに伴う設計変更
- **設計変更 1**: Push Rulesets は public では使えないため、Official Wiki の機械的保護は **W1(branch ruleset の Code Owner 承認)+ CI の `wiki-guard`**(昇格ファイル `docs/wiki/*.md` 直下を含む PR の作者が Claude 用アカウントなら赤)に一本化する。**S7b(アカウント分離)は「任意の強化」ではなく「Official Wiki 保護の必須条件」**とする。
- **設計変更 2**: App トークンの push は `on: push` の workflow を起動する(`GITHUB_TOKEN` の push は起動しない仕様)。全 workflow の起動条件と書込先を突き合わせた結果、自分の出力で自分が起動する workflow も、push する workflow 同士の循環も無い。bot の push ごとに `repo-scope` が起動する等、1 日約 10 本の run が増えるが、public リポの Actions 分数は無料。`[skip ci]` は最後の手段とし、既定では付けない。
- **App の必要性の追加根拠**: 組織ポリシーにより `GITHUB_TOKEN` では PR を作れないため、App は bypass のためだけでなく **`ai-update-watch` と `knowledge-extract` の PR 作成を復旧するためにも必要**。
- **Evaluate の代替(試験ブランチ方式)**: ruleset を対象 `refs/heads/ruleset-test/**` で Active 作成し、試験行列(直 push 拒否・force push 拒否・必須 check・App bypass)を `ruleset-test/main-sim` で実施、合格後に対象だけ `main` へ変更して 48 時間監視する。
- **bypass の表現**: Rulesets の bypass は個人を指定できない(ロール・チーム・App・Deploy key)。小柳さんの bypass は **Repository admin ロール・For pull requests only**(S7b 以降に追加。S7a の時点では admin bypass 無し)。**「Write」ロールは絶対に bypass に入れない**。repo admin は小柳さん 1 人に保つ。
- **必須 check**: `repo-scope.yml` を 2 ジョブに分割し(`repo-scope-guard` = Experience 公開可否・Wiki 検査・議事検査 / `repo-scope-check` = 置き場所の検査・Baseline 赤のまま)、`wikiskill-tests.yml` を全 PR で起動して対象外なら即 success にする(`wikiskill-tests-all`)。必須にするのは `repo-scope-guard` と `wikiskill-tests-all`。名前は一意にし、「Require branches to be up to date」は OFF。
- **`note-magazine-automation.yml`**: 唯一 `permissions:` 未宣言で、既定が読み取り専用のため push に到達しても失敗する設計。S5 で App 化と同時に `permissions: contents: read` を明示する。直近 6 回の投稿ステップ失敗と `|| echo` による沈黙失敗の是正は別件。

### 3. 変えない設定(決定事項)
1. 組織の「Allow GitHub Actions to create and approve pull requests」は無効のまま(12 リポへ波及するため)。PR 作成は App で行う。
2. Workflow permissions の既定は読み取り専用のまま。書込が要る workflow は `permissions:` を明示する。
3. Fork PR の承認設定は「初回投稿者のみ」のまま(「全ての外部協力者に承認」に変えると Claude 用アカウントの全 PR の CI が止まる)。
4. Rulesets の bypass に「Write」ロール、または Claude 用アカウントを含むチームを入れない。
5. App の秘密鍵は repo secret に限定する。
6. Claude 用アカウントに bypass・admin を与える変更は、本議事の見直しと小柳さんの決裁なしに行わない。

### S1 の内容・受け入れ基準・Rollback(承認済み・実装は別承認)
- 成果物(1 PR): `scripts/direct_push_watch.py`(純粋関数 `classify(changed_files, has_pull_request)` + `--selftest`。対象パスは `.github/CODEOWNERS` から読む + `docs/wiki/*.md` 直下)/ `.github/workflows/main-direct-push-watch.yml`(`on: push: branches: [main]` + `workflow_dispatch(sha)`。`permissions: contents: read, issues: write` を明示。`GITHUB_TOKEN` のまま。PR 経由でない commit が対象パスを変えたら Issue(ラベル `direct-push-watch`・同一 commit の重複起票なし)+ LINE)/ `tests/scripts/test_direct_push_watch.py` / README 1 段落。
- 挙動: `GITHUB_TOKEN` による bot の push では起動しない(仕様)。S5 以降は bot の push でも起動するが、bot は対象パスを書かないので起票されない(書いたら異常として起票)。「作者 = マージ実行者」の統計は起票せず週次レポの欄に出す(S8)。
- 受け入れ: ①selftest と pytest が緑 ②`workflow_dispatch` で PR 経由の Trust Boundary commit(例 `1e19530df`)は起票されない ③ブランチ上で作った試験 commit の sha を dispatch すると起票される ④同じ sha を 2 回 dispatch しても Issue は 1 件 ⑤既存 CI(`repo-scope-check` 以外)が緑・Baseline `--compare` が SAME ⑥Issue 本文に commit message と変更パス以外(個人情報・秘密)を載せない。
- Rollback: workflow ファイルを削除(試験 Issue はクローズ)。本番設定には触れないため、他段階に影響しない。

### 5. S7a の安全性と、S7b に移行できない場合の停止条件
- S7a が保証するのは「直 push・force push・削除の拒否」と「必須 check 2 本」。**アカウント分離(S7b)前は「AI がマージできない」は運用上の約束のまま**(退行はしない)。その間、Claude セッションは小柳さんの明示的な「マージ承認」の文言なしに `merge_pull_request` を呼ばない。
- S7a 有効化から **30 日**以内に S7b が完了しない場合の停止条件: ①claude.ai の GitHub 接続を新アカウントに切り替えられない → S7a は維持、#26 を「G1 未完(運用上の約束)」と明記し、承認用の第 2 人間アカウントを再上申 ②新アカウントで Skill 配布(12 リポ)が止まる → 配布リポにも Write を付与できるまで保留 ③bypass・自己マージの記録が週 2 件を超える → 三名体制で再議論 ④自動処理の push 失敗が原因不明で 2 回以上 → S7a を Disabled に戻して原因究明。停止中は、機械保証を前提とする Phase 3 の機能(自動昇格・自動統合の類)を承認しない。

## 三名体制の議論

- **スイシン(推進)**: 現状は CODEOWNERS が約束にとどまり、Phase 2 の G1 が未完である。App 先行 → ruleset 後の順序なら自動処理は止まらず、各段階は独立に戻せる。画面確認 10 項目は設計の前提と整合し、App の必要性は PR 作成の復旧でも裏付けられた。S0 合格、S1 へ。
- **ウタガイ(懐疑・反対理由。必須)**:
  1. 規模が不釣り合い。防ぎたい事象(`record:` 5 件・直接 commit 33 件)に実害は出ておらず、workflow 32 本 + 新 secret + 新アカウント + ruleset は大きすぎる。案 A(検知 + ルール)で足りるのではないか。
  2. App の秘密鍵は新しい攻撃面である。公開リポの secret を使ってどの workflow でも bypass 可能な write トークンを発行でき、`pip install anthropic`(未固定)やサードパーティ action 経由で workflow が汚染されたら、今の `GITHUB_TOKEN`(ruleset で止まる)より悪化する。
  3. 運用の摩擦が設計を壊す。Claude がマージできなくなると小柳さんの手数が増え、いずれ「Claude のアカウントにも bypass を」となれば目的が消える。
  4. check 名の重複(`validate`・`test`)で、必須 check が別 workflow の緑で通る穴がある。
  5. Claude は proxy のため Rulesets・App・secrets を読めない。受け入れはスクリーンショットと試験 PR に依存し、設定ミスを機械で検知できない。
  6. Free のリポ単位 ruleset は admin が外せる。S7b が完了するまで「機械の保証」は無く、S7b は claude.ai の connector 切替に依存して Claude 側から検証できない。
  7. Evaluate も Rule Insights も無いので、本番 ruleset の誤設定は自動処理が止まって初めて分かる。試験ブランチ方式は本物の main と条件が同じではない。
  8. App の導入動機が増えたことで S3 を急ぐ圧力が掛かり、守り部審査を省略する誘惑になる。
  9. `ai-update-watch` 10 月分の放置は、失敗を warning で握りつぶす設計の結果であり、App 化しても沈黙失敗は残る。
  10. 前回調査(v1)は shallow clone に気づかず「異常 commit」を報告した。同じ調査の他の数字も鵜呑みにできない。
- **ベッカイ(別解・前提を疑う)**:
  1. push ruleset だけで Trust Boundary と `docs/wiki/*.md` を守り、PR 必須も App も入れない(workflow 変更ゼロ)。
  2. 自動処理は `bot/data` ブランチへ push し、Pages はそこから配信する。main には人と Claude の PR だけ。
  3. Claude 側の新アカウントではなく、承認用の第 2 人間アカウントを足す。
  4. App ではなく deploy key。
  5. 組織ポリシーの PR 作成を有効にすれば App なしで ai-update-watch は復旧する。
  6. PR 作成だけ Claude 用アカウントの fine-grained PAT で行う。
  7. 試験ブランチ方式ではなく、main に bypass = Repository admin(Always)付きで先に入れ、問題が出たら admin で逃げる。
  8. S1 の検知を Issue ではなく週次レポの固定欄にして騒音を減らす。

## 裁定(部門長)

- **案 B を採用**。ウタガイ 2・4・5・6・7・8・9・10 を採択し、設計と受け入れ基準に取り込んだ: App の権限を Contents/Metadata/PR に限定し Issues・Workflows を付けない、`create-github-app-token` は SHA 固定、S5 で `pull_request_target` 不在と App トークン使用箇所を機械検査(ウ2)/ 必須 check を一意名に(ウ4)/ 各段階の受け入れに設定画面のスクリーンショットと試験 PR の URL を必須に(ウ5)/ S7b を必須条件にし、ruleset History の週次点検を S8 に追加(ウ6)/ 試験ブランチ方式 + 48 時間監視 + Disabled 1 操作(ウ7)/ S3 の守り部審査を省略不可とし、順序 S1 → S2 → S3 を変えない(ウ8)/ S5 で `ai-update-watch`・`knowledge-extract` の PR 作成失敗を `exit 1` + Issue に(ウ9)/ v1 の誤報を撤回し、shallow clone の確認を再発防止候補に(ウ10)。
- ウタガイ 1(規模)は**不採択**: 目的は「AI がマージできない」の機械保証(Phase 2 G1 の未完項目)であり、案 A では達成できない。規模のリスクは段階と順序で抑える。ウタガイ 3(摩擦)は**採択**: 「Claude のアカウントに bypass を与えない」を決定事項とし(§3-6)、摩擦は「小柳さんが UI で Approve → Merge」の 1 操作に限定する。
- ベッカイ 1 は不採択(public で不可。可能でも Claude の修正 PR を塞ぐ)。2 は Phase 3 以降の構想として記録。3 は不採択だが S7b 不成立時の再上申候補。4 は不採択(PR 作成不可・鍵管理)。5 は不採択(12 リポへ波及し bypass にならない)。6 は不採択(個人依存・bot 識別の不一致)。7 は不採択(S7a 期間に Claude = admin が bypass できてしまう)。8 は一部採択(起票は Trust Boundary・`docs/wiki` の直接 commit に限定し、それ以外は週次レポの欄だけに出す)。
