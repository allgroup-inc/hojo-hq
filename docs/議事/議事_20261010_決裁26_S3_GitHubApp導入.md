# 議事: 決裁 #26 S3 GitHub App 導入の設定完了と受け入れ(2026-10-10)

本議事は、決裁キュー #26「main 保護の段階導入」(議事 D20261008-rulesets-staged)のうち **S2「CI 準備」の完了受け入れ(2026-10-09)と、S3「GitHub App 導入」の設計承認(2026-10-09)および GitHub 側設定 A〜E の実施・受け入れ(2026-10-10)** を正式な Decision として残すもの。

**本議事の時点で実施済みなのは、S2 の 7 PR のマージと、S3 の GitHub 設定(App 作成・Environment・変数・秘密鍵・install)まで**である。App の認証動作は未検証(App を参照する workflow は 0 本)で、依存固定 PR・S4(カナリア)・S5a/S5b・S7a/S7b・S8 は未着手であり、設計上の検討・承認(S5 の分割方針など)と実施の承認を区別し、実施はそれぞれ個別承認を要する。本議事を含む台帳反映 PR #466 は 2026-10-10 の G-2 承認で作成済みで、マージは別途承認(G-4)を要する。

## なぜ(背景)

- 自動処理 workflow 32 本は既定の `GITHUB_TOKEN` で main へ直接 push している。S7a で branch ruleset(PR 必須)を入れると、`GITHUB_TOKEN` は ruleset の bypass actor に指定できないため、自動処理が全停止する。bypass actor に指定できるのは App・ロール・チーム・deploy key のみ。
- 組織ポリシーで「Actions による PR 作成・承認」が無効のため、`GITHUB_TOKEN` では PR を作れない(`ai-update-watch` の 2026-10 分がブランチのまま滞留)。
- したがって、自動処理の認証主体として **GitHub App** が必要(議事 D20261008-rulesets-staged 設計変更 1)。S3 はその App を作り、workflow から安全に使える置き場所を整える段階である。

## 前提

- S2「CI 準備」完了(2026-10-09 小柳さん受け入れ承認・main `7189d4887`)。内訳: PR-A1 #455(repo-scope を check/guard に分割・Baseline 比較)/ A2 #456(wikiskill-tests を全 PR で起動・対象外は skip 緑)/ C #458(CODEOWNERS に S1 一式・`/.gitignore`・`wiki_guard.py`)/ D #460(Experience の ignore・追跡状態検査)/ D2 #461(S1 workflow の bash 回帰テスト 10 件)/ D3 #462(追跡済み記録全件の ignore 判定)/ B #463(wiki-guard の休眠投入。`HOJO_CLAUDE_LOGIN` 未登録の間は step skipped)。
- S3 最終設計(2026-10-09 小柳さん承認): Environment 方式(`app-push`・Deployment branches = main のみ)/ 依存固定は S4 前の独立 PR / S5 を S5a(定期・PR 作成 22 本)と S5b(dispatch 9 本)に分割 / variable 名は `HOJO_APP_CLIENT_ID`。
- `actions/create-github-app-token` v3.2.0 = commit `bcd2ba49218906704ab6c1aa796996da409d3eb1`。`action.yml` 8〜14 行で実測: `client-id` が正式入力、`app-id` は deprecated(`client-id` は v3.1.0 以降にのみ存在)。`owner`/`repositories` 未指定なら現在のリポジトリのみ、`permission-*` で job ごとにトークンの権限を縮小、post step でトークンを revoke。
- 監査基準: `origin/main` = `6b974f543a31a767364960452459fc8f98beee4e`(2026-10-10)。S3 の設定は本セッション(Claude)から API で検証できない(Environment・secrets・variables・installation の取得は proxy で 403/401)ため、受け入れは小柳さんの画面画像の照合に依存する。

## 代替案

| 案 | 内容 | 採否 |
|---|---|---|
| PAT(個人アクセストークン) | 小柳さんのアカウントのトークンで自動処理を動かす | 不採択(個人アカウント依存・bypass 対象が人になり S7b の目的と矛盾) |
| deploy key | 鍵ペアで push だけ許可 | 不採択(PR を作れない。`ai-update-watch`・`knowledge-extract` の PR 作成を復旧できない) |
| App を 2 つに分割(push 用・PR 用) | 権限を用途ごとに分ける | 不採択(鍵が 2 本に増え、漏えい面と運用が増える。`permission-*` で job ごとに縮小すれば足りる) |
| データ用ブランチ分離 | 自動処理の出力を main 以外へ | 本段階では不採択。Phase 3 構想として維持 |
| S3 と S4 を同日に実施 | 設定とカナリアを一気に進める | 不採択(認証の初回発行を単独で観察できなくなる) |

## 決定内容(2026-10-09〜10 小柳さん決裁)

1. **採用 4 項目**: Environment `app-push` 方式 / 依存固定の独立 PR を S4 の前提にする / S5 の S5a・S5b 分割 / variable 名 `HOJO_APP_CLIENT_ID`(`client-id` 入力に渡す)。
2. **S3 ステップ A〜E の設定値と受け入れ結果**(小柳さんが GitHub UI で実施。画像照合は ChatGPT の独立レビューと三名体制で実施し、設計との不一致なし。その報告を受けて 2026-10-10 に小柳さん本人が S3 設定の受け入れを承認。App の認証動作は未検証のまま):

| ステップ | 設定 | 受け入れ |
|---|---|---|
| A Environment | `app-push`(hojo-hq)。Required reviewers なし・Wait timer なし・管理者の回避なし・Deployment branches = `main` のみ | 2026-10-10 画像確認 PASS |
| B App 作成 | `hojo-hq-automation`(所有者 `allgroup-inc`・App ID 5257258)。Repository permissions: Metadata R / Contents RW / Pull requests RW、他は No access。Organization/Account 権限なし。Webhook 無効。Only on this account | 画像確認 PASS |
| C 変数 | `app-push` の Environment variable `HOJO_APP_CLIENT_ID` 1 件(App の Client ID。Repository variables には置かない) | 画像確認 PASS |

| E install | hojo-hq のみに install(Installation ID 169968461) | 画像確認 PASS |

3. **認証動作は未検証**。App を参照する workflow は 0 本で、登録値の正しさ(鍵の貼り間違いを含む)は S4 の初回トークン発行まで分からない。
4. **秘密鍵の運用**: 鍵は GitHub 側で復元不可(紛失時は新しい鍵を追加して差し替え、旧鍵を Delete)。漏えい疑い時は installation の Suspend → 鍵 Delete → 点検 → 新鍵 → Unsuspend の順。鍵の Delete は新規発行を止めるだけで、発行済み installation token は最長 1 時間残る前提で扱う。PEM の中身はチャット・画像・AI・文書のいずれにも載せない。
5. **S4 の初回トークン発行は、明示承認後の `workflow_dispatch` 1 回に限定**し、その後に定期実行 3 回を観察してから S5a へ進む。
6. `note-magazine-automation.yml`(R9)は S5 で個別審査する。
7. **S3-E(install)は事前承認手順を経ずに実施された**。事実として記録し、受け入れは事後の画像照合で行った。S4 以降は承認ゲートを省略しない。
8. 本議事を含む台帳反映 PR #466 は 2026-10-10 の G-2 承認で作成済み。マージは G-4 の個別承認を要する。

## 三名体制の議論

- **スイシン(推進)**: 権限を Contents/PR/Metadata に限定し、トークン発行時は `permission-*` でさらに縮小できる。Environment(Deployment branches = main のみ)により、同一リポジトリの PR ブランチからはトークンを発行できない。段階(S3 → 依存固定 → S4 → S5a/S5b)はそれぞれ 1 操作で戻せる(secret Remove・鍵 Delete・uninstall・Environment Delete)。
- **ウタガイ(懐疑・反対理由。必須)**: ①秘密鍵は新しい攻撃面であり、main で動く workflow が汚染されれば、今の `GITHUB_TOKEN`(ruleset で止まる)より悪化する。Environment は PR 経路だけを塞ぎ、main の schedule/dispatch 経路は塞がない。②App 経由の push は Trust Boundary・正式 Wiki も変えられる(S1 は事後の記録のみで、止めはしない)。③設定は本セッション(Claude)から検証できず、受け入れは画像照合に依存する。④認証動作が未検証のまま S3 を完了扱いにした(鍵の貼り間違いは S4 まで潜む)。⑤S3-E が事前承認手順を省略して実施された。⑥`pip install` が未固定のまま S4 に進めば①の面が残る(依存固定 PR を S4 の前提にした理由)。⑦本議事と決裁キューは公開リポジトリに置く。秘密の混入は自動検査では検出しきれない(パターン外の形式・分割・言い換え)ため、人手の全文確認なしにマージしてはならない。
- **ベッカイ(別解・前提を疑う)**: OIDC + 外部 secret manager(本規模には過剰)/ S4 を省いて PR 2 本だけ先行(カナリアの意味が失われる)/ 鍵を手元に残して貼り間違いに備える(漏えい面が延びる。作り直しは 5 分で済む)→ いずれも不採択。データ用ブランチ分離は Phase 3 構想として維持する。

## 裁定

S3-A〜E を「設定と証跡の確認を完了(認証は S4 で検証)」として採用する。ウタガイ①②は権限限定・action の SHA 固定・`pull_request_target` 不使用・依存固定で攻撃面を狭め、残りは S7a/S7b と S1 の記録で補う。③は画像照合に加えて S4 の run で実証する。④⑤は事実として記録し、S4 では承認ゲートを省略しない。⑦は台帳反映 PR の検査(自動検査 + 人手の全文確認)で担保する。

## 見直し条件

次のいずれかに該当したら、期限を待たずに再議論する。

- (a) S4 で App トークンによる push が 1 回でも失敗する。
- (b) 期待外の workflow が起動する(App の push が `on: push` の連鎖を起こす)。
- (c) App の push が S1(main-direct-push-watch)に起票される。
- (d) 鍵の漏えい疑い。
- (e) **S7a 有効化日を起算日として 30 日以内に S7b が完了しない場合**は、議事 D20261008-rulesets-staged §5 の停止条件①〜④(①claude.ai の GitHub 接続を新アカウントに切り替えられない ②新アカウントで Skill 配布が止まる ③bypass・自己マージの記録が週 2 件を超える ④自動処理の push 失敗が原因不明で 2 回以上)に従う。停止の対象は「機械保証を前提とする Phase 3 の機能(自動昇格・自動統合の類)の承認」であり、S3 で設定した App・Environment を止めるものではない(④に該当した場合のみ S7a を Disabled に戻す)。現時点で S7a は未有効化のため、この 30 日は未起算。S7a 有効化から 30 日後の中間レビュー(bypass 使用件数・push 失敗件数・詰まった PR 件数・直接 commit 検知件数)は同議事の見直し条件に従う。
- 見直し期限: 2027-04-08(D20261008 の見直し期限 2027-04-06 と同じ週)。
