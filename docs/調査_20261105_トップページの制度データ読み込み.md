# 調査: moradou.jp のトップページが制度データを読めていなかった件(2026-11-05)

対象: もらいわすれ堂(株式会社フクギイロ・moradou.jp)のトップページ(`site/fukugiiro/index.html`)。
状態: 修正は Draft PR で提出(小柳さん承認 2026-11-05)。**統合・本番反映は未実施**。

## 症状

PR #572・#573 のマージ後に本番を確認したところ、moradou.jp のトップで次の3か所が初期表示のままだった(配信リポジトリ allgroup-inc/moradou の `1f6f116` を手元の実ブラウザで表示して確認)。

- 「検証済み」の件数が「—」
- 「掲載○件のうち○%を公式ページと照合済み」の一文が出ない
- 「たとえば、こんな制度を掲載しています」のカードが「制度情報を準備中です」のまま

診断ページ・申請準備シート・場面別ページは正常に表示されていた。

## 原因

トップは `fetch("../data/fukugiiro/seido.json")` で制度データを読んでいた。

| 配信先 | トップの位置 | 読みに行く先 | 結果 |
|---|---|---|---|
| 旧URL(github.io) | `/hojo-hq/fukugiiro/` | `/hojo-hq/data/fukugiiro/seido.json`(`update.yml` が `cp -r data site/data` で置く) | 読める |
| moradou.jp | `/` | `/data/fukugiiro/seido.json` | **404**(`deploy_moradou.py` は `site/fukugiiro/` だけを配信し、`data/` は配信しない) |

読み込みの失敗は `catch` で握りつぶす作りだったため、画面のエラーにはならず、初期表示が残った。2026-11-02 の診断ページの障害(`../../data/fukugiiro/seido.json`)と同じ形。11/2 は診断ページだけを直し、トップは見落としていた。

- 配信中のトップの読み込み先は 11/3 の配信でも同じだった。11/4 の統合で起きたものではない。いつからかは未特定
- PR #572 でトップに足した「公式ページを確認中」の表示も、このためmoradou.jpでは効いていなかった。PR #572 のテストは旧URLの構成でデータを返していたため、気づけなかった

## 修正

- 読み込み先を `seido.json`(ページと同じフォルダ)に変えた。旧URLでは `/hojo-hq/fukugiiro/seido.json`、moradou.jp では `/seido.json` になり、どちらも診断ページが読むのと同じ公開用の制度データ(公開を保留する仕組みを通ったもの)を指す
- 読み込みの応答が 200 以外のときは失敗として扱う(404 のページを JSON として読もうとしない)
- 旧URLでの影響: これまでは `data/fukugiiro/seido.json` を読んでいた。公開用の `site/fukugiiro/seido.json` と中身は同じ(2026-11-05 の main で sha256 一致)。公開の保留中は公開用のほうが正しい

## 受給報告の台帳(jukyu_reports.json)

- トップは `../data/fukugiiro/jukyu_reports.json` も読む。moradou.jp には配信していないので 404 になる
- 表示は「検証済み10世帯以上」から(2026-08-10 小柳さん決裁)。いまは0世帯なので、**読めても読めなくても表示は変わらない**。この PR では読み込み先を変えず、注記だけ残した
- moradou.jp で表示するには、台帳そのものではなく集計値だけを配信する方法を決める必要がある(台帳には報告の明細がある)。公開範囲の変更にあたるため、10世帯が近づいた時点で別途決める

## 再発防止

`tests/top_page_layouts.test.mjs`(新規・CI の `source-link-selftest` で実行)

- `deploy_moradou.py` で配信ツリーを組み立ててルートで配信する構成(moradou.jp)と、`site/` を `/hojo-hq/`・`data/` を `/hojo-hq/data/` に置く構成(旧URL)の両方で、トップと診断ページを実ブラウザで開く
- トップ: 件数・照合率の一文・制度カード4枚が、配信される制度データどおりに出ること。読めなかったデータファイルが無いこと(台帳の1件だけは理由つきで例外)
- 診断ページ: 15分監視と同じ条件で診断して結果が出ること
- 公式ページが無いと確かめた出典が、moradou.jp のトップでも「公式ページを確認中」になること
- 配信ツリーの全ページの `fetch("…")` を解決し、配信されていないファイルを読みに行くページが無いこと
- 修正前のコードに戻すと、moradou.jp の構成の3件とツリー検査が失敗することを確かめた

## 外部監視(UptimeRobot)でトップを見る方法

UptimeRobot のキーワード監視は JavaScript を動かさないため、画面に件数が出たかは見られない。次の2つを合わせて「トップが制度データを読めること」を見る。

| 監視 | 確かめる文字列 | 見つけるもの |
|---|---|---|
| `https://moradou.jp/`(新規) | `fetch("seido.json")` | 読み込み先が配信構成と合わない形に戻ること・トップの消失 |
| `https://moradou.jp/seido.json`(設定済みの予定) | `"fk-kuni-jidoteate"` | 制度データの消失・破損 |

- **トップの監視は、この修正が moradou.jp に配信されてから登録する**。修正前の配信には `fetch("seido.json")` が無いので、先に登録すると必ず鳴る(誤通知)
- 画面に件数が出たかまで見るには、実ブラウザで動く15分監視(`scripts/diagnosis_monitor.mjs`)にトップの検査を足す(別の PR)
