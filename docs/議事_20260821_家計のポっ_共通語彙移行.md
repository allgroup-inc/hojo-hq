# 議事: 家計のポっ(❷)を5システム共通語彙へ移行する

- 日付: 2026-08-21
- 対象: `apo-kanri`(❷ 営業アポスケジュール管理システム)
- 前提: 軸(🌟総合管理システム🌟)の裁定「軸の裁定_訪問スケジュール管理からの3点_2026-08-21」
- 区分: **不可逆な変更**(ステータスというルールの変更)。CLAUDE.md 三名体制 規程8①②に該当するため議事必須
- 裁定者: 軸(3点とも裁定済み)。本議事は❷側の実装判断を記録するもの

## 背景

5システム共通の約束【4】「ステータスの言葉を言い換えない」に対し、❷は独自語彙
(予定/確定/実施済/申込み/キャンセル2種/再調整中)を使っており抵触していた。
軸へ3点上申し、いずれも裁定を得た。

| 上申 | 軸の裁定 |
|---|---|
| ① 参照キーは KM- か アセンドの顧客id か | **正は KM-**。ただし今は焼き付けない。当面の保存はアセンドid、KM- は読み取り時に resolve API で引く。カットオーバーで焼き付けてから不変 |
| ② ファネルを外してよいか | **外さない**。「入力」を「表示」に変える。ただし**❷が独自に数えない**。定義は軸が一元管理 |
| ③ キャンセル理由を残してよいか | **残す**。ステータスは共通語彙のまま、理由は別項目。**人事評価に使わない** |

## 三名体制の議論

### スイシン(推進)

共通語彙に寄せれば、❶❸❹との突き合わせが名前だけで成立する。本番未投入の今なら
データ移行がゼロで、費用はコード修正だけ。**今やらなければ、投入後に全行を書き換える
羽目になる。**移行の最良のタイミングは今日しかない。

### ウタガイ(懐疑・反対)

**反対理由を3点記録する。**

1. **「実施済」を「訪問済」に変えるのは、単なる言い換えではなく持ち場の移動を伴う。**
   ❸が結果を返す仕組みは**まだ存在しない**。裁定どおり❷を編集不可にすると、その日から
   誰も訪問結果を入れられず、ファネルは0件のまま真っ暗になる。「見込みが埋もれるのを
   防ぐ」という目的に対して、むしろ埋もれる側へ動く。
2. **旧「再調整中」の統合で、枠の扱いが黙って変わる。**
   再調整中は枠が空く扱いだったが、スケジュール調整中は枠を押さえる。同じ現場の操作が
   別の結果を生むのに、画面には何の説明も出ない。**リハーサルで必ず「あれ?」が出る。**
3. **ファネルの定義を「軸が一元管理」と言うが、その定義はまだ届いていない。**
   届くまでの間、❷は暫定の数え方で数字を出す。暫定と書いてあっても、画面に出た数字は
   独り歩きする。「数えるな」と言われた側が数え続けるのは、裁定の趣旨に反する。

### ベッカイ(別解・前提を疑う)

そもそも❷が結果ステータスを**保持する**必要があるのか。枠が埋まっているかどうかだけ
分かれば、❷の仕事(スケジュールを回す)は成立する。訪問結果は❸から**読むだけ**にして、
❷のシートには持たない案もある。ただし❸のAPIが無い今は絵に描いた餅なので、
**「持つが、持ち主は❸である」と明示する形**が現実解。

## 結論(❷側の実装判断)

軸の裁定に従い共通語彙へ移行する。ウタガイの反対1・2・3はいずれも**採用**し、
以下のとおり裁定の実装に条件を付けた。

| 決めたこと | ウタガイのどの指摘に応えたか |
|---|---|
| ステータスを共通語彙9種へ移行(`OWNED_STATUSES` / `HANDED_OFF_STATUSES` に二分) | — |
| ❸❹が持つステータスの書き換えは `RESULT_INPUT_MODE` で塞げるようにし、**❸連携が通るまでは "許可"**。連携実装と同じリリースで "禁止" に倒す | 反対1(暗転を避ける) |
| スケジュール調整中は**枠を押さえる**と決め、コードにも試験にも理由を書き残す。流れたら差し戻しで明示的に空ける | 反対2(黙って変えない) |
| ファネルの数え方を `VISITED_STATUSES` / `SIGNED_STATUSES` の2定数に集約し、**画面に「この定義は暫定です」と明示**。軸から正式定義が届き次第そこだけ差し替える | 反対3(独り歩きさせない) |
| 差し戻し理由は独立列(顧客都合/自社都合)。理由なしの差し戻しは通知に「理由未記入」と出す | ③の裁定 |
| KM- 形式の列は**作らない**。試験で「作っていないこと」を固定 | ①の裁定 |

**ベッカイの案**は将来の姿として妥当だが、❸のAPIが無い現時点では採らない。代わりに
`HANDED_OFF_STATUSES` という名前で「持ち主は❸❹である」ことをコード上に明示した。

## 積み残し(軸へ)

1. **ファネルの正式定義**(どのステータスを「訪問に至った」「申込に至った」と数えるか)
2. **resolve API の仕様**(アセンドid → KM- を引く手段。URL・認証・応答形式)
3. **❸からの結果連携の仕様**(これが決まれば `RESULT_INPUT_MODE` を "禁止" に倒せる)
