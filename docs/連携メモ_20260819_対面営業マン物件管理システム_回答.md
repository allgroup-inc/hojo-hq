| # | 先方の決定 | こちらへの影響 |
|---|---|---|

**「紹介元を持つ理由は集計ではなく架電の中身が変わるから」**という理由づけは、こちらが書いた
「集計のため」より本質を突いています。同じ項目でも、**その情報が無いまま電話をかけること自体が事故**
という捉え方は、こちらの通知設計にも効く視点でした。

## 1. ご依頼①: 顧客IDを保持できるか → **できます。実装しました**

`アポ予定` の**末尾に `顧客ID` 列を追加**しました(2026-08-19・本番投入前のため既存データへの影響なし)。

**フォームには出していません。**理由は、そちらの機能追加基準「タップ数が減るか」に反するためです。
①(営業本人が両方入力)の期間に営業へ顧客IDを手入力させるのは、二重入力の上にさらに転記を
足すことになります。**②の自動連携が通るまでは空のまま**とし、先方から登録が来た時点で埋まる想定です。

- 実データ(顧客ID・顧客名)はスプレッドシート側のみに保持。リポジトリには一切コミットしません
- ①期間に登録されたアポは顧客IDが空になります。②開通後に遡って埋める必要があるかは、
  そちらの運用次第(必要なら突き合わせ方法を相談させてください)

## 2. ご依頼②: 「ご家族」を独立区分にする必要があるか → **こちらの都合では不要です**

理由は3つ。

1. **こちらは種別別の集計を持ちません**。前便でお渡ししたあと、家計のポっからは種別の概念ごと
   撤去しました。種別別の申込み率は、結果がそちらへ戻る以上、**そちらで計算するのが筋**です
   (リードの出自を知っているのはそちらなので、分類の精度もそちらが上です)
2. **紹介元の自由記述で足ります**。「大城様のご家族」と書けば、カンペにも出るし検索でも辿れます。
   独立区分にしなくても、架電の中身は変わりません
3. **そちらの基準に照らして落ちます**。「かけ漏れが減るか/約束に遅れなくなるか/タップ数が減るか」の
   3つのうち、ご家族フラグはどれにも当たりません。ワンタップ選択を足す案は、**紹介元入力に
   1タップ増える**ので、基準を自ら曲げることになります

ただし、**ご家族を厳密に取りたい理由がそちら側にある場合**(例: ご家族への架電は時間帯の配慮が
必要、世帯単位で提案を束ねたい)は話が別です。その場合は「集計のため」ではなく
「**架電の中身が変わるから**」という、そちらが紹介元で示した基準で判断されるのが一貫すると思います。

## 3. 結果返信(❸)の実装について — 受け口の仕様が決まってから着手します

送信側はこちらで実装します。**ただし今は作りません。**送信先が決まっていない状態でコードを書くと、
仕様確定後に必ず作り直しになるためです。以下が決まり次第、着手します(実装は1〜2時間程度の見込み)。

### 決まったら教えてほしいこと

| # | 項目 | 補足 |
|---|---|---|
| 1 | エンドポイントURL | Supabase REST のテーブル/RPCどちらか |
| 2 | 認証方式 | APIキーならGASのスクリプトプロパティに置きます(コードには書きません) |
| 3 | リクエストボディの形 | 送れるもの: 顧客ID / アポID / 日付 / 開始時刻 / 担当営業 / ステータス / 更新日時 |
| 4 | 送信タイミング | 「実施済・申込みになった瞬間」を想定。キャンセルも要りますか(二重架電防止なら要る気がします) |
| 5 | 冪等性の扱い | 同じアポIDで複数回届いても壊れない設計にしてほしい(リトライで重複送信が起こり得るため) |

### こちら側で担保する予定のこと

- **リトライは最大3回・一時エラー(429/5xx)のみ**。権限エラー等は即諦める(既存の resilience 実装を流用)
- **送信失敗しても台帳の保存は成功扱い**。失敗は変更履歴に記録します(保存が正・送信は従)
- 送信は**アポIDを添えて冪等**に。同じ結果が2回届いてもそちらが壊れない前提で設計します
- **顧客IDが空のアポは送信しない**(①期間のアポ)。突き合わせ先がないため

## 4. 落とし穴7件へのご返答について

- **4番(数値を人事評価に使わない)**: 別々に同じ結論へ辿り着いたとのこと、心強いです。
  そちらの「順位づけは指導ではなく晒しになる」という言語化は、こちらの画面注記より的確なので、
  次に文言を直すときに使わせてください
- **1番(認証)**: そちらの「所属未設定だと0件表示 → データが消えたと誤解されて二重登録」は、
  同型でありながらこちらが見落としていた角度です。**0件と権限なしを区別して表示する**という
  原則として受け取りました。家計のポっの「本日のアポはありません」も、権限や絞り込みの結果と
  区別できているか点検します
- **6番(自動で決めない)への反論**: 「不在→翌日を自動で置く」は妥当だと思います。
  こちらが言いたかったのは「**人が知らないうちに確定してしまう**のを避ける」ことで、
  上書き可能な下書きなら趣旨に反しません。「自動で入った値と分かる表示」にされるなら、
  それがまさに求めていた形です
