# Feature Factory(役割分担で機能を作る)

AIを"速いキーボード"で終わらせず"チーム"として使うためのスキル。1つの会話に
調査・設計・実装・検証を全部詰め込む(Vibe Coding)と、思い込みが連鎖し、
同じロジックが散らばり、新機能が旧機能を壊す。**役割を分けて渡すと、
ミスが増幅しにくくなる。**

## Vibe Codingの限界(なぜ役割分担が要るか)

よくある詰まりの原因:
1. 同じロジックが3か所に散らばる
2. 前に決めたルールを忘れる
3. 新機能で旧機能が壊れる
4. テストが浅く、漏れが出る

AIがダメなのではなく、ワークフローがダメ。1会話に全部詰め込むと、思い込みが
連鎖し修正コストが積み上がる。**"作る人"と"確かめる人"を分けると品質が上がる。**

## 7つの役割(必要な分だけ使う。フルセット必須ではない)

| # | 役割 | やること | 人の承認 |
|---|---|---|---|
| 1 | Codebase Researcher | 書く前に調べる専門役。関連ファイル・役割の洗い出し、既存パターンの発見、リスクと更新すべきテストの整理(Read/Grep/Globのみ、書き込みしない) | なし |
| 2 | Story Writer | 曖昧な要望を実装可能なユーザーストーリー(1文で定義)に変える。受け入れ条件・境界条件を明文化。不明点は推測せず質問として残す | **ここで承認①** |
| 3 | Spec Writer | 承認された要件を実装の青写真にする。データモデル/API変更、画面変更、必要テスト、変更ファイルを列挙。リスク・未解決点を明示 | **ここで承認②** |
| 4 | Backend Builder | サーバー側処理・API・DB・ジョブを実装。フロントには触れない。ユニットテストも同時作成。型チェック/lint/テスト完了で返す | なし |
| 5 | Frontend Builder | UIだけを担当。BackendのAPI契約に合わせて実装。画面・状態管理・ローディング/エラー状態・UIテスト | なし |
| 6 | Test Verifier | ユニットテストでなく受け入れテストを書く。受け入れ条件を外側から検証、足りない基準を報告。**コード修正はしない** | なし |
| 7 | Implementation Validator | 実装と仕様のズレを重大度つきで指摘する。認可・権限分離・秘密情報の混入を確認、仕様漏れや一貫性を確認。問題なければ「問題なし」と返す | **ここで承認③(PR)** |

止まるのは判断が必要なところ(承認①②③)だけ。あとはチェーンで前に進む。

## このリポジトリの既存スキルとの対応

このリポジトリ(または本店hojo-hq)には、この役割分担を実行するための部品が
既に揃っている場合が多い。フルセットを新規に作らず、まず既存スキルで代替できるか確認する。

- 役割1(調査): `brainstorming`(要件を固める前の壁打ち)
- 役割2〜3(ストーリー・仕様): `writing-plans`(実装計画の作成)
- 役割4〜7(分業実装・レビュー): `subagent-driven-development`
  (タスクごとに新規サブエージェントを立てて実装→タスクレビュー→最終レビューという、
  このリポジトリで既に定義済みの実行エンジン。バックエンド/フロントエンドのような
  レイヤー分割は、そこに渡す個々のタスクの粒度で表現する)
- テスト: `test-driven-development`

**つまり、このスキルは「新しい実行エンジンを作れ」ではなく「調査→ストーリー→仕様→
(既存の分業実行エンジン)→検証、という順番と承認ゲートの置き方」を示すもの**。
既存スキルが無いリポジトリでは、この7役割を素朴に(サブエージェント無しでも)
順番通りに自分でこなすだけでも効果がある。

## 実行フロー(1つの依頼からどう自走するか)

```
調査 → ストーリー(人が承認①) → 仕様(人が承認②)
  → Backend → Frontend → 受け入れテスト → 検証(PR作成・人が承認③)
```

例: 「7日以上未払いの請求書にリマインドを送る」のような1行の依頼から、
この順で自走させる。

## 土台: CLAUDE.mdが工場を安定させる

CLAUDE.md(またはこのリポジトリの相当ファイル)に書くべきこと:
- 技術スタック
- 実行コマンド(テスト・lint・ビルド等)
- 設計ルール
- やってはいけないこと

なぜ効くか: 毎セッション0から始まる記憶を補う。毎回同じ前提で動ける。AIがミスしたら
それをルールとして蓄積できる(このリポジトリで同じミスが2度起きたら、CLAUDE.mdに
一行足す、という運用が最も費用対効果が高い)。

**Context Driftへの注意**: 小さな誤字はその場で修正する。大きな前提ミス(違う設計方針で
進んでいた等)に気づいたら、その場で軌道修正しようとせず**会話を捨てて最初からやり直す**
方が速い(→ `context-limit-handoff` スキル。作業がgit/CLAUDE.mdに残っていれば会話を
捨てても損しない、という考え方は共通)。「正しい前提を最初に固定する」だけで精度が
大きく変わる。

## 導入手順(週末2〜3時間、小さく試す)

1. Claude Codeを導入(このリポジトリでは導入済み)
2. `.claude`配下の構成を確認(このリポジトリでは`.claude/skills`が既に整っている)
3. CLAUDE.mdを書く/見直す(技術スタック・実行コマンド・設計ルール・禁止事項)
4. 必要な役割だけサブエージェントとして起動できるか確認する
   (`subagent-driven-development`が使えるか、まずそれで試す)
5. 小さな実案件を1つ、この流れで通してみる
6. 詰まった箇所があれば、CLAUDE.mdか該当スキルにルールを1行足す

**完璧を目指すより、1回回してルールを足す方が速い。** 最初は小機能でOK。3〜4回回すと
このリポジトリの「工場」はかなり育つ。

## この10枚の要点(まとめ)

1. まず調査してから書く
2. ストーリーと仕様で思い込みを止める
3. 実装は役割で分業する(バックエンド/フロントエンド/検証)
4. CLAUDE.mdで再現性を高める

Vibe Codingの限界を超える鍵は、エージェントを「役割」で設計すること。
