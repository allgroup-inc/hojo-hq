# user-research-hojo スキル — テストケース

## テストケース概要

このファイルは、user-research-hojo スキルの「ペルソナ鮮度」「リサーチサイクル」「施策～検証の連続性」を検証するテストケース集です。

## テストケース 1: ペルソナ更新日検査

**目的**: ペルソナの最終更新日が 30 日以内に保たれているか確認

### テスト 1-1: ペルソナが最新に保たれている

```
入力:
  ペルソナ最終更新日: 2026-10-05（本日）
  現在日: 2026-10-05

期待値:
  ✅ グリーン（OK）「ペルソナ鮮度: 95/100」

実施方法:
  ├─ docs/ または CLAUDE.md 内の「ペルソナ定義」セクションから最終更新日を抽出
  └─ 更新日から経過日数を計算（30 日以内 → OK / 以上 → NG）
```

### テスト 1-2: ペルソナが 30 日以上未更新

```
入力:
  ペルソナ最終更新日: 2026-08-20
  現在日: 2026-10-05

期待値:
  ❌ レッド（要更新）「ペルソナ鮮度: 35/100」「経過日数: 46 日」

実施方法:
  ├─ 経過日数 = 現在日 - 最終更新日
  └─ 46 日 > 30 日 → 「更新期限切れ」フラグを立てる
     └─ 対応: 月次ペルソナ更新（段階 9）を即座に実施
```

### テスト 1-3: ペルソナ複数セグメントで鮮度がバラバラ

```
入力:
  セグメント A 最終更新日: 2026-10-02（3 日前）→ グリーン
  セグメント B 最終更新日: 2026-09-10（25 日前）→ グリーン
  セグメント C 最終更新日: 2026-08-20（46 日前）→ レッド

期待値:
  ⚠️ イエロー（部分警告）「ペルソナ鮮度: 65/100」
  「セグメント C が 46 日未更新。他セグメントより優先度高」

実施方法:
  ├─ 各セグメントの更新日を個別に確認
  ├─ レッド項目（30 日以上）が 1 個以上 → 警告を発出
  └─ 対応: セグメント C のペルソナを再更新（理由: 新規顧客属性が未反映）
```

## テストケース 2: 施策～検証の連続性検査

**目的**: 実装された施策に対して、KPI 測定と検証記録が残されているか確認

### テスト 2-1: 施策が実装され、検証記録も完全

```
入力:
  施策: 「診断結果に成功事例を埋め込む」
  実装日: 2026-10-15
  検証期限: 2026-11-15
  検証記録: 
    ├─ 2026-10-22: 33%（開始時点）
    ├─ 2026-10-29: 36%
    └─ 2026-11-15: 42% → ✅ KPI 達成（目標 40% 以上）

期待値:
  ✅ グリーン（OK）「施策鮮度: 100/100」「KPI 達成」

実施方法:
  ├─ 施策ID（MST-202610-001）から「実装日」「検証期限」を抽出
  ├─ 検証期限までの「KPI 測定記録」が週次で存在するか確認
  ├─ 検証期限の日に「最終値」が記録されているか確認
  └─ 最終値が KPI を達成しているか確認
```

### テスト 2-2: 施策が実装されたが、検証期限を過ぎても測定なし

```
入力:
  施策: 「LINE 登録ボタンテキスト変更」
  実装日: 2026-10-10
  検証期限: 2026-11-10（期限を過ぎた）
  検証記録: 空（記録がない）

期待値:
  ❌ レッド（検証忘れ）「施策鮮度: 0/100」「経過日数: 25 日（検証期限超過）」

実施方法:
  ├─ 「検証期限」と「現在日」を比較（現在日 > 検証期限 か？）
  ├─ 検証記録ファイルの存在確認（例: `施策_MST-202610-002_検証.md`）
  └─ 記録がない → 「検証期限超過のまま未検証」フラグを立てる
     └─ 対応: 即座に検証を実施（段階 8）
```

### テスト 2-3: 施策が実装されて 1 ヶ月、検証期限は決まっているが期限までのコースは不明

```
入力:
  施策: 「PDF ダウンロード機能」
  実装日: 2026-09-15
  検証期限: 2026-10-15（既に過ぎた）
  検証記録: 部分的（実装直後に 1 回だけ測定）
    └─ 2026-09-20: 15 DL（初期値のみ）
  最終値: なし（期限後も測定されず）

期待値:
  ❌ レッド（継続測定なし）「施策鮮度: 20/100」「検証完了度: 20%」

実施方法:
  ├─ 検証期限までに「週次の KPI 更新」が存在するか確認
  ├─ 検証期限の直前に「最終値」が記録されているか確認
  └─ 記録が途中で途絶えている → 「継続測定の停止」を検出
     └─ 対応: 検証をやり直す（段階 8）、または検証期限を延長
```

## テストケース 3: 営業違和感報告 → リサーチ発動の追跡

**目的**: 営業から出た「違和感」が、その後のリサーチ実施につながったか確認

### テスト 3-1: 違和感報告から 5 日以内にリサーチが開始された

```
入力:
  違和感報告: 2026-10-01「飲食店経営者も新規登録が増えている」
  リサーチ開始: 2026-10-03（2 日後）「新規セグメント調査」

期待値:
  ✅ グリーン（OK）「リサーチ発動: 100/100」「報告～開始: 2 日」

実施方法:
  ├─ 「違和感報告ファイル」から日付を抽出（例: `違和感_20261001_飲食店層.md`）
  ├─ リサーチ開始メモを検索（例: `リサーチ_20261003_新規セグメント.md`）
  └─ 開始日 - 報告日 ≤ 5 日 → グリーン
```

### テスト 3-2: 違和感報告があるが、その後のリサーチ開始記録がない

```
入力:
  違和感報告: 2026-09-10「高齢経営者は電話相談より LINE がいいらしい」
  現在日: 2026-10-05（25 日経過）
  リサーチ開始: なし

期待値:
  ❌ レッド（リサーチ未発動）「追跡状態: 未確認」「経過: 25 日」

実施方法:
  ├─ リポジトリ内を検索（例: `違和感_20260910` に対応する `リサーチ_*`）
  ├─ マッチするリサーチファイルが存在しないか確認
  └─ なし → 「違和感報告が停滞」アラートを発出
     └─ 対応: 3 名体制で「このリサーチは必要か」を判定し、対応を決定
```

### テスト 3-3: リサーチは開始されたが、「完了と実装」への転換がない

```
入力:
  違和感報告: 2026-09-15「セグメント B（飲食店）の申請ニーズが新しい」
  リサーチ開始: 2026-09-18「飲食店向けペルソナ調査」
  リサーチ完了: 2026-09-28（「ジャーニーマップ草案」を作成）
  施策実装: なし（期限から 7 日経過しても実装されず）

期待値:
  ⚠️ イエロー（進行中だが停滞）「リサーチ～施策化: 7 日遅延」

実施方法:
  ├─ リサーチ完了日を確認（例: `リサーチ_20260928_完了.md` の存在）
  ├─ 完了から施策実装（段階 7）までの日数を計算
  ├─ 完了から 5 日以上経過して施策が実装されていない → 警告
  └─ 対応: 即座に「施策実装の三名体制議論」を開始（段階 7）
```

## テストケース 4: ペルソナ更新と新規セグメント追加の検査

**目的**: 新規セグメントが見つかったときに、ペルソナ定義に追加されているか確認

### テスト 4-1: 新規セグメント（飲食店層）が出現し、ペルソナ定義に追加された

```
入力:
  過去 30 日の新規ユーザー属性:
    ├─ 建設業（既知セグメント A）: 45%
    ├─ 製造業（既知セグメント B）: 35%
    └─ 飲食店（新規セグメント C）: 20%
  
  ペルソナ定義:
    ├─ セグメント A: 建設業向け（既存）
    ├─ セグメント B: 製造業向け（既存）
    └─ セグメント C: 飲食店向け（新規追加・2026-10-05）

期待値:
  ✅ グリーン（OK）「新規セグメント検出から追加まで: 期間内」

実施方法:
  ├─ ペルソナ定義ファイルから「セグメント C」の「作成日」を抽出
  ├─ 月次ペルソナ更新（段階 9）の実施記録（例: `ペルソナ更新_20261005.md`）で追加日を確認
  ├─ 新規ユーザー属性の変化を検出した日 ≤ ペルソナ追加日 ≤ その月の月末
  └─ 上記が成立 → グリーン
```

### テスト 4-2: 新規セグメントが検出されたが、ペルソナ追加が遅延

```
入力:
  新規セグメント（飲食店）検出: 2026-09-20（月次ペルソナ更新時）
  月次ペルソナ更新実施記録: 2026-09-30「セグメント C 追加」
  現在（2026-10-05）も、セグメント C のジャーニーマップ・施策がない

期待値:
  ⚠️ イエロー（追加は済みだが、施策化が遅延）「ペルソナ追加: OK / 施策化: NG」

実施方法:
  ├─ セグメント C のペルソナ定義（属性・ニーズ・決定トリガー）が存在するか確認
  ├─ セグメント C 向けの施策（段階 7 の「施策実装タイムライン」）が記録されているか確認
  └─ 施策記録がない → 「ペルソナ追加後、施策化へ進んでいない」を検出
     └─ 対応: 3 名体制での「セグメント C 向け施策検討」を即座に開始
```

## テストケース 5: フィードバックループの発動と完了追跡

**目的**: KPI 未達成時に「ループ発動 → 再リサーチ → 新施策実装」が実行されているか確認

### テスト 5-1: ループが正常に発動・進行している

```
入力:
  施策: 「高齢経営者向け電話相談」
  第 1 ループ期間: 2026-11-20 ~ 2026-12-20
  第 1 ループ結果: ❌ KPI 未達成（CV 数 5 件 < 目標 20 件）
  
  ループ発動記録: 2026-12-20「フィードバックループ開始」
    ├─ 段階 1: 再ヒアリング（2026-12-21）→ 「電話が面倒」という声確認
    ├─ 段階 2: ジャーニーマップ更新（2026-12-25）
    ├─ 段階 4: ユーザーテスト再実施（2026-12-27）
    └─ 段階 7: 新施策「LINE 1:1 チャット」の実装決定（2026-12-30）
  
  第 2 ループ期間: 2027-01-10 ~ 2027-02-10（進行中）

期待値:
  ✅ グリーン（正常）「ループ 1 → ループ 2 への移行が確認できた」

実施方法:
  ├─ フィードバックループ記録ファイル（例: `ループ_MST-202611-003.md`）を確認
  ├─ 第 1 ループが KPI 未達成で終了し、「発動」記録があるか確認
  ├─ 段階 1～10 のいずれかが進行中（または完了）記録があるか確認
  ├─ 第 2 ループが新施策を持って開始されているか確認
  └─ 上記が全て確認できたら → グリーン（ループが正常に回っている）
```

### テスト 5-2: ループが発動されたが、段階が途中で停止している

```
入力:
  施策: 「補助金検索 UI 改善」
  第 1 ループ期間: 2026-11-01 ~ 2026-11-30
  第 1 ループ結果: ❌ KPI 未達成

  ループ発動: 2026-11-30
    ├─ 段階 1: 再ヒアリング（2026-12-02 実施）→ 完了
    ├─ 段階 2: ジャーニーマップ更新（実施なし）← ⚠️ 停止
    └─ 段階 3～10: 未開始

  現在日: 2026-10-05（5 日停止）

期待値:
  ❌ レッド（ループが停止）「ループ進行: 段階 1 / 10（10%）」

実施方法:
  ├─ ループ記録の「最後の実施日」を確認
  ├─ 現在日 - 最後の実施日を計算
  ├─ 3 日以上停止している → 「ループが停滞」フラグを立てる
  └─ 対応: ループの「次の段階」を確認し、責任者に期限を再設定させる
```

## テスト実行スケジュール

| 実行タイミング | テストケース | 実施者 | 備考 |
|---|---|---|---|
| **月次（毎月末金曜）** | 1・4・6（ローカル検証） | 統括 + 部門長 | 月末ペルソナ更新時に同時実施 |
| **施策実装時** | 2-1・2-2 | 施策責任者 | 施策記録テンプレートに自動組み込み |
| **施策検証期限時** | 2-3 | 検証責任者 | 検証レポートで自動チェック |
| **営業から違和感報告あり** | 3 全般 | リサーチ担当 | 報告受け取り時に即座に追跡開始 |
| **KPI 未達成時** | 5 全般 | フィードバックループ責任者 | ループ発動と段階進行を記録 |
| **ペルソナ鮮度アラート時** | 1・6 全般 | 統括 | 期限切迫時に通知発出 |
