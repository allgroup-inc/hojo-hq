# ペルソナ・ユーザーリサーチ（hojo-hq 専用版）

「誰に売るのか」を決めるとき、テンプレート埋め方式（年齢・年収・趣味）は何も決まらない。
このスキルは、営業現場・アプリ利用者・カスタマーサポートが「何に困ったのか」を聞き取り、
施策実装まで落とし込み、効果を検証して、ペルソナを月次で更新し続ける一気通貫の手順。
営業の「あれ、おかしいな」を、形→施策→検証→ペルソナ更新へ繋ぐ仕組み。

## いつ使うか

- 🟠 **新事業の立上げ前**：KAKEHASHI アプリ、もらいわすれ堂の「初期ユーザー像」確定
- 🟠 **LP・プレゼン資料の前**：「誰に何を訴えるか」の土台がないと、文章も配色も決まらない
- 🟠 **離脱が起きたとき**：ミカタの「診断までは来たが、LINE 登録に至らない」→ なぜ？
- 🟠 **営業が『違和感』を感じたとき**：「高齢経営者には紙が必要」の根拠は何か？

## 段階 1: 現場の「違和感」を聞き取る

テンプレートではなく、営業・実装者の「あれ、おかしいな」を形にする。

### **聞き方の原則**

✅ **良い質問**
```
「高齢経営者には紙の資料がいるって、どんな場面で気づきました？」
「診断完了したのに LINE 登録に進まないお客さんて、何が引っかかってるんですか？」
「KAKEHASHI アプリを使ってて、『ここは使いづらい』って感じたことは？」
```

❌ **悪い質問（テンプレ式）**
```
「ターゲットの年齢層は？」
「年収はどのくらい？」
「どんな人格ですか？」
← これでは営業の経験が数字に変わるだけ。判断基準が何も入らない
```

### **具体例（hojo-hq 実例）**

**例 1: ミカタ のペルソナ発見**

過去の営業フィードバック：
```
違和感: 「診断ツールまで来た顧客が、LINE 登録に進まない」

聞き取り:
  ツナグさん: 「診断結果を見て、『次は何すればいい』が分からないんでしょう。
               単に金額や締切が出ても、『申請するぞ』という気持ちにならない」
  
  ウタガイ役: 「実は、診断を見た後『本当に受け取れるのか』という疑い心が働く。
              写真や事例を見ないと、信じられない」

結果: ペルソナの「決定行動」＝ 「信頼できる情報源＋次の一歩が見える」
      → LP は「成功事例 + 次のボタン（LINE）」の 2 点に最適化
```

**例 2: KAKEHASHI 営業アプリの違和感**

営業フィードバック：
```
違和感: 「アプリは使えるが、営業マンが『経営者に見せるのが恥ずかしい』と言う」

聞き取り:
  営業: 「画面がデスク向けで、対面で経営者に『ちょっと見てください』と言いにくい」
  
  現場テスト: 実際に高齢経営者に見せると、「字が小さい」「どこをタッチするのか迷う」

結果: ペルソナの「使用場面」＝ 「対面 → 経営者視点で見やすい」が優先
      → UI は「デスク最適化」から「対面プレゼン最適化」に変更
```

## 段階 2: 違和感を「ジャーニーマップ」に落とす

営業の言葉を、顧客の行動フローに変換する。

### **テンプレート（ミカタ用の例）**

```
顧客ペルソナ: 沖縄県の 50 代経営者
決定行動: 「補助金申請に至るかどうか」

段階 1: 発見
  ├─ Instagram でミカタを見かける
  ├─ 「補助金ってまだ分からん」という感覚
  └─ 痛点: 『制度が複雑すぎて、自分に関係があるのか判断できない』

段階 2: 診断
  ├─ サイトで診断ツール実施
  ├─ 結果: 「あ、うちは対象だ」と初めて気づく
  └─ 痛点: 『診断結果を見ても、次が見えない』
            『本当に自分でできるのか、不安』

段階 3: 申請準備
  ├─ LINE 登録（ここで離脱が起きている）
  ├─ 締切アラート受け取り
  └─ 痛点: 『LINE に入ったはいいが、何をどうすればいいのか』
            『士業に相談するのにいくらかかるのか不透明』

段階 4: 申請実行
  ├─ 士業紹介で申請サポート
  └─ 成功: 『補助金をもらえた』という達成感
```

### **離脱ポイント分析**

```
段階 2 → 段階 3 の離脱が多い理由：

営業の違和感: 「診断は完了したが LINE 登録に進まない」

根本原因（聞き取り結果）:
  ❌ 診断結果が『あなたはもらえます』という確信に変わっていない
  ❌ LINE 登録後の『次のステップ』が見えていない
  ❌ 紙資料を見たい（デジタル完結への違和感）

対策（施策に落とし込む）:
  ✅ 診断結果に「成功事例」を 2-3 件埋め込む
  ✅ LINE 登録ボタンを「締切アラートを受け取る」に言い換える
  ✅ 説明用の PDF（ダウンロード可能）を用意する
```

## 段階 3: ペルソナ別の「心理的ハードル」を洗い出す

同じ行動でも、相手によって「心理的な引っかかり」が違う。営業が感じた違和感から、それを明文化する。

### **例：高齢経営者 vs. 若い経営者**

| 顧客セグメント | 心理的ハードル | 施策 |
|---|---|---|
| **50 代以上の経営者** | 「デジタルが苦手」「だまされるかも」 | 紙資料 + 信頼できる人からの紹介 |
| **30-40 代の経営者** | 「面倒」「時間がない」 | LINE で短く、スマホで完結 |
| **士業・商工会** | 「新しいツールへの信頼」「顧客メリット」 | データ透明性、紹介実績の共有 |
| **金融機関** | 「リスク・コンプライアンス」 | 正確性・原文URLの併記 |

## 段階 4: ユーザーテスト（簡易版）

完成する前に、実際の顧客 3-5 人に試してもらう。

### **テスト対象と質問**

```
対象: ミカタ利用者（診断まで進んだが LINE 登録に至らなかった人）

質問（聞き取り）:
  1. 「診断結果を見た時、どう思いましたか？」
  2. 「LINE 登録しなかった理由は？」
  3. 「もし〇〇だったら、登録していましたか？」

テスト結果から施策に落とし込む:
  例）「診断結果に『次のステップは士業に相談』と書いてあったら登録する」
   → 施策: 診断結果ページに「士業相談は無料」を追加
```

## 段階 5: ペルソナを「セグメント別」に定義する

全員に同じ施策は効かない。ペルソナは複数いる。

### **ミカタの例：3 セグメント**

```
セグメント A: 「補助金について詳しい（会計士・商工会関係者）」
  └─ ニーズ: 「顧客に紹介できる信頼できる情報源」
  └─ LP 上での訴求: データの正確性・更新頻度・API 連携
  └─ 申請経路: 既存顧客への紹介

セグメント B: 「補助金は知ってるが、手続きが分からない経営者」
  └─ ニーズ: 「書類作成のサポート」
  └─ LP 上での訴求: 『士業に相談できる』『締切アラート』
  └─ 申請経路: LINE 登録 → 士業紹介

セグメント C: 「補助金の存在を知らない経営者」
  └─ ニーズ: 「制度を分かりやすく説明してほしい」
  └─ LP 上での訴求: 『何がもらえるのか』『誰でも使えるのか』を最初に
  └─ 申請経路: 診断ツール → LINE 登録
```

---

## 段階 6: ペルソナから「LP / プレゼン」の要素を逆算

ペルソナが決まると、LP の色・文体・構成が自動的に決まる。

```
セグメント A（会計士向け）の場合：
  ├─ 配色: 信頼できる（紺・グレー）
  ├─ 文体: 専門用語で OK、簡潔
  ├─ 構成: データの正確性・更新タイミング → API 仕様 → 価格
  └─ CTA: 「デモを見る」「API ドキュメント」

セグメント C（補助金を知らない経営者）の場合：
  ├─ 配色: 親しみやすい（オレンジ・暖色）
  ├─ 文体: 専門用語を やさしく翻訳
  ├─ 構成: 「こんな人が対象」→ 「実例」→ 「次のステップ」
  └─ CTA: 「診断してみる」「LINE で相談」
```

## 段階 7: 施策実装・タイムラインの決定

ペルソナから出た「対策」を、実装する形に落とし込み、期限・責任者を決める。

### **施策の実装形式（ミカタの例）**

```
対策① 「診断結果に『成功事例』を埋め込む」
  ├─ 実装形式: 診断結果ページ下部に「実例集」セクション
  ├─ 配置: 「あなたはもらえます」の直後
  ├─ 内容: セグメント別の成功事例 2-3 件
  ├─ 責任者: ツナグさん（LINE 部）
  ├─ 開始: 2026-10-15
  └─ 検証期限: 2026-11-15（1 ヶ月後）

対策② 「LINE 登録ボタンのテキスト変更」
  ├─ 実装形式: 「LINE 登録する」→ 「締切アラートを受け取る」
  ├─ 実装先: 診断結果ページ + LP の CTA 全箇所
  ├─ 責任者: ヒロメさん（SNS 部）
  ├─ 開始: 2026-10-10
  └─ 検証期限: 2026-11-10（1 ヶ月後）

対策③ 「説明用 PDF（ダウンロード可能）」
  ├─ 実装形式: 診断結果ページに「印刷用・資料」ボタン
  ├─ PDF 内容: ステップ別の申請フロー + 士業相談の案内
  ├─ 責任者: ツヅルさん（note 編集部）
  ├─ 開始: 2026-10-20
  └─ 検証期限: 2026-11-20（1 ヶ月後）
```

### **三名体制での施策決定（ルール）**

```
施策の意思決定：
  1. スイシン役が施策案を提案
  2. ウタガイ役が「本当に効くか」を疑問（根拠必須）
  3. ベッカイ役が「別の視点」を出す
  4. 部門長が 3 役の意見を踏まえ、採否理由を明記した決定文書を作成
  5. 決定が確定したら、実装タイムラインを施策ごとに指定
```

## 段階 8: 効果検証（KPI 達成まで追跡）

施策を実装したら、期限まで毎週測定し、KPI に達したか確認する。

### **測定項目（ミカタの例）**

```
施策①: 診断結果に成功事例を埋め込む
  ├─ 測定指標: 「診断完了 → LINE 登録率」
  ├─ 対象期間: 2026-10-15 ~ 2026-11-15
  ├─ 現在値（施策前）: 32%
  ├─ 目標値: 40% 以上
  ├─ 実績トラッキング（毎週金曜夜に更新）:
  │   ├─ 2026-10-22: 33% → 仮説は効いているか？ 微差のため継続観察
  │   ├─ 2026-10-29: 36% → 効き始めた。ページ滞在時間も +30 秒
  │   └─ 2026-11-15: 42% → ✅ 目標達成（+10pt）
  └─ 結論: 成功事例の埋め込みが効いた。今後は全セグメント対象に拡張

施策②: LINE 登録ボタンテキスト変更
  ├─ 測定指標: 「ボタン表示 → クリック率」「登録完了率」
  ├─ 対象期間: 2026-10-10 ~ 2026-11-10
  ├─ 現在値（施策前）: クリック率 12% → 登録 8%
  ├─ 目標値: クリック率 15% 以上 → 登録 11% 以上
  ├─ 実績トラッキング:
  │   ├─ 2026-10-17: クリック率 12.5% → 登録 8.2%（微増のみ）
  │   ├─ 2026-10-24: クリック率 13.8% → 登録 9.1%（改善傾向）
  │   ├─ 2026-10-31: クリック率 15.2% → 登録 11.3% → ✅ 目標達成
  │   └─ 2026-11-10: クリック率 15.8% → 登録 12.1%（継続効果）
  └─ 結論: 「登録する」より「アラート受け取る」の方が CV につながる

施策③: PDF ダウンロード機能
  ├─ 測定指標: 「PDF ダウンロード数」「ダウンロード → LINE 登録率」
  ├─ 対象期間: 2026-10-20 ~ 2026-11-20
  ├─ 目標値: ダウンロード数 50 件以上 / 月、そのうち 30% が LINE 登録
  ├─ 実績トラッキング:
  │   ├─ 2026-10-27: 15 DL / 4 登録（26.7%）
  │   ├─ 2026-11-03: 38 DL / 12 登録（31.5%）
  │   └─ 2026-11-20: 65 DL / 21 登録（32.3%） → ✅ ダウンロード数達成 / 登録率目標超過
  └─ 結論: PDF は利用ニーズが高い。次は配信タイミングを最適化
```

### **効果検証で「失敗」した場合のアクション**

```
パターン A: 施策を打ったが数字が動かない
  例: 成功事例を埋め込んだが、LINE 登録率が変わらない
  
  原因の仮説:
    1. ペルソナ定義が外れていた（実際の顧客と違う属性だった）
    2. 施策の形が悪かった（成功事例の位置・デザイン・内容が不適切）
    3. 他の要因がボトルネック（成功事例より、別の痛点が大きい）
  
  対応:
    ├─ 再度現場ヒアリング（段階1に戻る）
    ├─ 実際にペルソナと合致したユーザーを 3-5 人抽出
    ├─ ユーザーテストをやり直す（段階4に戻る）
    └─ 別の施策を試す（優先度順に施策リストを再ランク）

パターン B: ペルソナと実際の顧客が乖離していたことが判明
  例: 「高齢経営者は紙が必要」と決めたが、実はスマホで十分だった
  
  対応:
    ├─ ペルソナの属性を即座に修正
    ├─ ジャーニーマップを更新（新しい痛点を反映）
    └─ 進行中の施策を見直す（紙資料から「スマホ最適化」に振り直す）

パターン C: 施策は効いたが、ペルソナの別の層には逆効果だった
  例: 「成功事例」を見せたら、セグメント A（会計士）には効いたが
      セグメント C（補助金を知らない経営者）には「自信がない」と感じられた
  
  対応:
    ├─ セグメント別に施策を分ける（事例の難度・見せ方を変える）
    ├─ A/B テストで最適版を確定
    └─ セグメント C 向け施策は別途考案
```

## 段階 9: 月次ペルソナ更新（新しい顧客属性・ニーズの反映）

毎月末に「実際に使った顧客の属性」と「定義していたペルソナ」を照らし合わせ、ズレを修正する。

### **ペルソナ更新チェックリスト**

```
毎月末（月末金曜 17:00 に統括・部門長で実施）:

☑ ペルソナ定義の「最終更新日」を確認
  └─ 最後の更新が 30 日以上前 → 要更新フラグ

☑ 過去 1 ヶ月の新規ユーザー属性を集計
  ├─ 年代別・業種別・企業規模別の分布を確認
  ├─ 「想定していたペルソナ」と「実際の顧客」で乖離がないか確認
  └─ 乖離あり → ペルソナの属性を修正する

☑ 営業からの「違和感レポート」を集約
  ├─ 「こんな顧客もいるんだ」という新しい層が見えているか
  ├─ 「前月と異なるニーズ」が出ていないか
  └─ 出ている → 新しいセグメントとして記録 or 既存ペルソナに吸収する

☑ 実施した施策の効果を最終確認
  ├─ KPI 達成した施策：「この施策が有効な顧客セグメント」を記録
  ├─ KPI 未達成の施策：「失敗原因は何か」を明記
  └─ 記録を次月のペルソナ定義に反映

☑ ペルソナごとの「決定行動」を修正
  例: 3 ヶ月前は「成功事例を見たら登録する」だったが、
      実際には「税理士から紹介されたら登録する」ケースが増えた
  └─ ペルソナの「決定トリガー」を更新する

☑ 次月の施策案を検討
  ├─ 「新しく発見した痛点」に対する施策提案を 1～2 個
  ├─ 三名体制での議論（スイシン・ウタガイ・ベッカイ）
  └─ 実装タイムライン・責任者・KPI を決定して記録
```

### **ペルソナ定義の更新テンプレート（例）**

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
セグメント B: 「補助金は知ってるが、手続きが分からない経営者」
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【前月の定義】
  年代: 40-50 代
  業種: 建設業・製造業
  ニーズ: 「書類作成のサポート」
  決定トリガー: 「LINE で締切アラートをもらう」

【今月の更新】
  年代: 35-55 代（35 代の飲食店経営者が増えた）
  業種: 建設業・製造業・飲食店（新規）
  ニーズ: 「書類作成のサポート」+ 「税理士の紹介」（新規）
  決定トリガー: 「LINE での締切アラート」+ 「既存顧客からの紹介」（新規）
  
【施策への反映】
  ├─ 飲食店向けの事例を LP に追加
  ├─ 既存顧客（税理士）への「紹介インセンティブ」を検討
  └─ LINE 配信で「紹介した人へのギフト」を新作成

【ペルソナ鮮度スコア】
  前月: 85/100（30 日前）
  今月: 95/100（本日更新）
  管理期限: 2026-11-05（30 日後、要再更新）
```

## 段階 10: 検証失敗時のフィードバックループ

効果検証で「失敗」または「ズレ」を検出したら、即座に次のリサーチサイクルを発動する（段階 1 に戻る）。

### **フィードバックループの仕組み**

```
[施策実装・検証] →（失敗または新しい違和感を検出）
        ↓
 [段階 1: 再ヒアリング]
   └─ 実際にその施策を使わなかった顧客に聞き取り
   └─ 失敗した施策の「何が」悪かったのか、根本原因を探る
   └─ 新しい「違和感」が出ていないか営業に確認
        ↓
 [段階 2: 新しいジャーニーマップを作成]
   └─ 前月のジャーニーマップを更新
   └─ 新規セグメント or 新規痛点を記録
        ↓
 [段階 3-4: 心理的ハードルと簡易テストを再実施]
   └─ 新しい仮説に基づくテスト
        ↓
 [段階 5-6: ペルソナとセグメント分析を修正]
        ↓
 [段階 7-9: 新しい施策を実装・検証・ペルソナ更新]
        ↓
 [ループ終了 or 継続] ← ここで「効果があった」か「改善が必要」かで分岐
```

### **ループの発動条件（いつ戻るか）**

```
❌ Loop 発動: 以下のいずれかが起きたら、即座に段階 1 に戻る
  ├─ 施策を実装したが、KPI が達成できなかった
  ├─ ペルソナと実際の顧客に乖離が見つかった
  ├─ 営業から新しい「違和感」報告がある
  ├─ 新規セグメントが現れた
  └─ ペルソナの「決定トリガー」が変わった

✅ Loop 終了: 以下を満たしたら、次の施策に進む
  ├─ 同じ施策で 2 ヶ月連続して KPI を達成している
  ├─ ペルソナが 1 ヶ月間ズレなし（ローカル検証で OK）
  └─ 営業からの「違和感」が報告されていない（その施策の層に限定）
```

### **フィードバックループの記録**

```
施策 ID: MST-202610-001（2026-10-15 開始）
施策名: 「診断結果に成功事例を埋め込む」
第 1 ループ (2026-10-15 ~ 2026-11-15): ✅ 成功（+10pt）
  └─ 次施策へ

施策 ID: MST-202610-002（2026-10-10 開始）
施策名: 「LINE 登録ボタンテキスト変更」
第 1 ループ (2026-10-10 ~ 2026-11-10): ✅ 成功（+3pt）
  └─ 次施策へ

施策 ID: MST-202611-003（2026-11-20 開始）
施策名: 「高齢経営者向け電話相談」
第 1 ループ (2026-11-20 ~ 2026-12-20): ❌ 失敗（数字動かず）
  └─ フィードバックループ発動
     ├─ 再ヒアリング: 「電話が面倒」という声あり
     ├─ 新仮説: 「高齢経営者には LINE 後フォローが要る」
     └─ 第 2 ループ (2027-01-10 開始): 新施策「LINE 1:1 チャット」を実装
       └─ KPI 達成見通し: 50%（現在進行中）
```

## 🚨 ペルソナ鮮度低下による失敗パターン（検出・防止）

ペルソナを定義したが、その後更新し続けなかった場合の 5 つの失敗パターン。

### **パターン 1: ペルソナ定義は 3 ヶ月前のまま → 実際の顧客と乖離**

```
症状:
  「ペルソナとして『50 代建設業経営者』を定義した」
  「でも最近の新規ユーザーは『35 代飲食店』が増えた」
  「施策が古いセグメント向けのままで、新規層に効かない」

検出方法 (自動チェック):
  ❌ ペルソナの最終更新日が 30 日以上前
  ❌ 過去 1 ヶ月の新規ユーザー属性が、ペルソナの年代・業種と乖離している
     （例: 年代の平均が 45 才だったが、実際は 38 才）

防止策:
  ✅ 毎月末に「ペルソナ鮮度チェックリスト」を実施（段階 9）
  ✅ ペルソナの属性ズレを検出したら即座に修正
  ✅ 新規セグメント出現時に新しいペルソナを追加定義
```

### **パターン 2: 施策が実装されたが、効果検証を忘れた → ペルソナが古いまま**

```
症状:
  「『成功事例を埋め込む』と決めた施策」
  「実装は完了した」
  「でも、効果を測定していない」
  「1 ヶ月たってる」
  「その間に、実は『成功事例より、士業との連携』が重要だと判明」
  「でも何も修正されず、古い施策が走ったままになっている」

検出方法 (自動チェック):
  ❌ 施策の実装日が 30 日以上前
  ❌ その施策の「効果検証記録」が存在しない
  ❌ 効果検証がないまま、次の施策が開始されている

防止策:
  ✅ 施策を実装したら、必ず「検証期限」を記録（段階 7）
  ✅ 毎週 KPI を測定し、進捗表を更新（段階 8）
  ✅ 検証期限になったら、必ず「効果検証」を締切として扱う
  ✅ 検証結果をペルソナ更新に反映（段階 9）
```

### **パターン 3: 営業が『違和感』を報告したが、リサーチが発動していない**

```
症状:
  「営業から『こういう顧客も多いんですよ』という報告」
  「メモに残したけど、『では次のリサーチ実施』という形に落ちていない」
  「3 ヶ月たって、その『違和感』がペルソナに反映されていない」
  「施策が古いペルソナ向けのままで、機会損失」

検出方法 (自動チェック):
  ❌ 営業からの違和感報告（Slack / 議事）が存在する
  ❌ その報告に対応する「リサーチ発動記録」がない
  ❌ または、リサーチは始まったが、「いつまでに終わる」という期限がない

防止策:
  ✅ 営業からの違和感報告を受けたら、即座に「リサーチ開始メモ」を作成
     （件名: `違和感_YYYYMMDD_<内容>.md`）
  ✅ 3 名体制での議論をして、「本当にリサーチが必要か」を判定
  ✅ 必要ならば、リサーチの責任者・期限を決定し、公開記録する
  ✅ 期限までに完了し、ペルソナ更新に繋ぐ
```

### **パターン 4: ジャーニーマップは作ったが、施策決定で停止**

```
症状:
  「顧客ジャーニーの『この段階で離脱が多い』を分析した」
  「『対策案：施策 A・B・C』と書いた」
  「でも『どの施策をいつ実装するか』という決定がない」
  「『やる』と決まっているのか『保留』なのか、状態が曖昧」
  「時間が経って、何も実装されていない」

検出方法 (自動チェック):
  ❌ ジャーニーマップの「離脱ポイント分析」が存在する
  ❌ 対策案は書かれている
  ❌ でも「施策 A は 2026-11-15 に実装開始」という実装決定がない
  ❌ または決定があっても、その後「実装開始」の記録がない

防止策:
  ✅ 対策案が出たら、3 名体制での意思決定（段階 7）を即座に実施
  ✅ 施策ごとに「責任者・開始日・検証期限」を必ず記録
  ✅ 期限になったら自動で実装タスクが立つ仕組みにする
  ✅ 実装前に「期限延長 / 中止 / 実施」を明記する
```

### **パターン 5: ペルソナ更新が月ずれで発動できず、鮮度が低下**

```
症状:
  「月末に『ペルソナ更新』の議論をするルール」
  「でも 9 月末は案件が立て込んで実施できず」
  「10 月末は『先月やっていないから遅れ取り戻し』と思って後回し」
  「気づいたら 2 ヶ月ペルソナが更新されていない」
  「その間の新規顧客の属性が反映されず、施策がズレた」

検出方法 (自動チェック):
  ❌ ペルソナの最終更新日が 30 日以上前
  ❌ 月次更新スケジュールに「実施記録」がない（未記入がカウント可能）

防止策:
  ✅ ペルソナ更新を「月末金曜 17:00」で固定化し、カレンダーに常時入れる
  ✅ 更新を忘れた月があったら、翌月の更新で「前月分」もまとめて実施
  ✅ ペルソナ更新の「最終実施日」と「次回実施期限」を常時表示
  ✅ 期限の 3 日前に「更新期限切迫」の通知を出す
  ✅ 実施記録（誰が・何を更新したか）を必ず文書化する
```

---

## 注意点

- ❌ 「イメージで決める」（テンプレート埋め方式）は使わない
- ✅ 「営業が感じた違和感」が最初の情報源
- ❌ 1 つのペルソナですべてをカバーしようとしない
- ✅ セグメント AB テスト → 勝った方に施策を集中
- ❌ ペルソナを決めたら、実際の顧客と比べずに施策を打つ
- ✅ 月 1 回はペルソナを現実と照らし合わせ、更新する
- ❌ 施策実装後、効果検証を忘れてペルソナが古いまま
- ✅ 施策と検証は「1 セット」で扱う。検証期限は施策ごとに明記
- ❌ 営業からの違和感報告を受けても、リサーチが発動していない
- ✅ 違和感報告 → リサーチ実施 → ペルソナ更新へ一気通貫させる
- ❌ ペルソナ更新を「最後の仕上げ」としてスケジュール外で実施
- ✅ 月末に「ペルソナ更新」を定期議論として必ず実施する

## ローカル検証：ペルソナ鮮度・リサーチサイクル検査

このチェックリストを「月次」で実施し、リサーチサイクルが停止していないか検査する。

### **チェックリスト（自動 or 手動）**

```
【ペルソナ鮮度スコア】

☑ 1. ペルソナの最終更新日を確認
  └─ 最後の更新が 30 日以内か？
     YES → グリーン（OK）
     NO  → レッド（要更新）

☑ 2. 施策の「実装日～検証期限」が明記されているか
  └─ 実装済みの全施策が「検証記録」を持っているか？
     YES → グリーン（OK）
     NO  → レッド（検証忘れ）

☑ 3. 過去 30 日の営業からの「違和感」報告と「リサーチ発動」の紐付け
  └─ 違和感報告があった場合、対応するリサーチ開始記録があるか？
     YES → グリーン（OK）
     NO  → レッド（リサーチ未発動）

☑ 4. ジャーニーマップの最終更新日
  └─ 最後の更新が 30 日以内か？
     YES → グリーン（OK）
     NO  → レッド（更新遅延）

☑ 5. 段階 9（月次ペルソナ更新）の実施記録
  └─ 当月に「ペルソナ更新議論」の実施記録があるか？
     YES → グリーン（OK）
     NO  → レッド（実施漏れ）

☑ 6. 実装予定の施策と「期限」の同期
  └─ 「決定した施策」と「実装タスク」の期限が一致しているか？
     YES → グリーン（OK）
     NO  → レッド（スケジュール未同期）

☑ 7. フィードバックループの発動記録
  └─ 過去 30 日に「KPI 未達成 → ループ発動」した施策があるか？
     ある場合、ループの「第 N 段階」「期限」が記録されているか？
     YES → グリーン（進行中）
     NO  → レッド（ループ状態不明）

☑ 8. ペルソナ鮮度スコアの推移
  └─ 先月 vs. 当月のスコアが上昇 or 維持されているか？
     YES → グリーン（改善）
     SAME → イエロー（維持。警告）
     NO  → レッド（劣化）
```

### **検査結果の判定**

```
【スコア計算】
グリーン: +10 点
イエロー: 0 点
レッド: -5 点

合計が 70 点以上 → ペルソナ・リサーチサイクルは正常
合計が 50-69 点   → 要改善。来月までに 1-2 項目の修正が必要
合計が 50 点未満  → リサーチサイクルが停止している。即座にループ発動

【レッド項目が出たときの対応】
  ├─ 「ペルソナ最終更新日が 30 日以上前」(項目 1)
  │   → 即座に「月次ペルソナ更新」を実施（段階 9）
  │
  ├─ 「検証期限が来ても効果検証がない」(項目 2)
  │   → 当該施策の検証を即座に実施。未達成なら段階 10 へ
  │
  ├─ 「違和感報告があるが、リサーチ未発動」(項目 3)
  │   → 3 名体制での判定実施。リサーチ開始 or 保留を決定
  │
  ├─ 「ジャーニーマップが 30 日以上未更新」(項目 4)
  │   → 最新のペルソナ・施策結果を反映させて更新
  │
  ├─ 「月次ペルソナ更新の実施漏れ」(項目 5)
  │   → 即座に補実施。翌月は「予定表に自動設定」
  │
  ├─ 「施策の期限がタスクと同期されていない」(項目 6)
  │   → 即座に同期。期限 3 日前に「リマインド通知」を設定
  │
  ├─ 「フィードバックループの状態が不明」(項目 7)
  │   → ループの「現在地」を確認し、「期限」を再設定
  │
  └─ 「ペルソナ鮮度スコアが低下」(項目 8)
      → 全項目を再確認し、赤が多い項目から対応開始
```
