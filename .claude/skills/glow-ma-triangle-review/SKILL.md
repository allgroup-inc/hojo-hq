# 三名体制ディスカッション(トライアングル体制) — glow-ma版

`glow-ma`(GLOW M&A・不動産・法人保険の企業リレーション管理システム)で、
スコアリングモデル・掘り起こしアラートの閾値・提案順序・紹介パートナーとの
料率や逆紹介の取り決めなど、意思決定を伴う検討をまとめるときは、
CLAUDE.md憲法の三名体制(全チーム共通ルール)で議論を構成する。

対象となる典型的な論点の例:
- スコアリングの重み付け(属性スコア・流入ルートボーナス・反応スコアの配分)
- ランク別の標準接触サイクル日数・掘り起こしアラートの閾値
- 保険/経営相談→M&A・不動産という提案順序の適用可否(紹介ルートでの例外扱いなど)
- 紹介パートナーへの紹介料率・逆紹介の条件
- 名寄せ・データ突合のルール変更

## 3役(すべての議論をこの3視点で行う)

- **スイシン(推進)**: 案を前に進める立場。狙い・期待効果・実行手順を出す。
- **ウタガイ(懐疑・反対必須)**: 必ず反対・懸念を出す。リスク・前提の穴・失敗パターンを挙げる。
- **ベッカイ(別解・前提を疑う)**: そもそもの前提を疑い、別の選択肢や枠組みを提示する。

## 議事のまとめ方(この形で出力する)

```
## 論点: <検討テーマ>

### スイシン(推進)
- <推進理由・実行案>

### ウタガイ(懐疑)  ← 空欄不可
- <反対理由・リスク・懸念>

### ベッカイ(別解)
- <前提への疑問・別案>

### 結論(裁定)
- 採否: <採用 / 不採用 / 保留・上申>
- 理由: <3役を踏まえた採否理由>
- 見直し期限: <最長6ヶ月。期限切れは自動で再議論>
```

## 無効になる議事(差し戻し条件)

- **ウタガイ役の反対理由が記録されていない議事は無効**(結論ごと差し戻す)。
- 裁定者は議論の当事者にならない。
- 3役が割れて確信が持てない案件は、たかしくん(GLOW実務)経由で小柳さんへ上申する。
- **予算・提携条件(紹介料率等)・最終決裁は小柳さん。エージェントは提案まで**(CLAUDE.md絶対ルール5)。

# GLOW固有の意思決定ステップ(5～7 Step チェックリスト)

`glow-ma`で検討する意思決定には典型的なパターンがある。三名体制で議論するときは、以下のステップに沿って論点を出す。

## Step 1: 対象の明確化(クリティカルパス確認)

**目的**: 影響範囲と優先度を全員で統一する

**チェック項目**
- [ ] この検討は誰の営業活動に影響するか(個人 / チーム / 全社)
- [ ] 提案中の案件が何件 pending か、実運用中のルールか
- [ ] 変更によって既存データ(登録済み企業など)の再判定が必要か
- [ ] 実装に GAS / スプレッドシート / DB変更 は必要か

**スイシン視点**: 実行すべき理由・タイミング・メリット
**ウタガイ視点**: 影響範囲は正しいか、実装コストは過少見積もりではないか
**ベッカイ視点**: そもそも今 変更する必要があるか、待つ選択肢は？

---

## Step 2: スコアリング設計の再検討(該当時のみ)

**対象となる論点の例**
- 属性スコア(業種・売上・従業員数)の重み付け変更
- 流入ルートボーナス(既存顧客・紹介・検索など)の大きさ
- 反応スコア(問い合わせ・イベント参加)の点数体系
- ランク判定の境界値(例：900点以上=A ⇔ 850点以上=A)

**必須チェック**: Step 1 で「データ再判定が必要」が YES の場合、以下を実行

1. **現在のスコア分布を可視化** → 分布が正規分布に近いか、二峰性でないか
2. **変更後の予想分布を計算** → サンプル 50～100件で試算
3. **営業訪問可能量が範囲内か** → (年間営業時間 / 1社あたり接触時間) の 80% ≦ 提案対象件数

**失敗パターン 1**: スコアリングを高く設定しすぎた結果、有望企業が A/B ランクに集中 → 営業が訪問できない量になる
- 症状: 「毎月の提案リストが 3～5 社だけ」「せっかく紹介が来ても C ランク扱い」
- 対策: ウタガイが試算を要求し、分布図を見てから決定する

**スイシン視点**: 狙う売上水準や業種に沿った重み付けの根拠
**ウタガイ視点**: スコア分布の偏り、営業キャパの確認、試算プロセスの穴
**ベッカイ視点**: スコアそのものが必要か、ランク不要で金額や業種だけで判定できないか

---

## Step 3: 紹介料率・手数料水準の決定

**対象となる論点の例**
- 提携パートナーへの紹介手数料(例：M&A報酬の 5% vs 8% vs 10%)
- 逆紹介時の対価(例：商品手数料の配分)
- 紹介先企業への成約手数料(例：士業送客時の紹介料)

**必須チェック**: 提携先の月間提案件数と想定成約率から売上見積もりを計算

1. **紹介パートナーのインセンティブ最小閾値** → 相手の営業活動が採算に乗る水準か
   - 例：月 1 社成約で時給 1,500 円 / 時間 が報酬の参考値
   - 紹介料が低すぎると相手は本腰を入れない
2. **自社の粗利率** → 紹介料を払った後に利益が残るか
3. **競合紹介料との比較** → 市場水準を調べたか

**失敗パターン 2**: 紹介料率を低く見積もってパートナーが動かない
- 症状: 「提携を結んだが 3 ヶ月提案がゼロ」「他社への紹介に切り替わった」
- 原因: 相手の採算線に達していない
- 対策: 実績に基づき見直し(6ヶ月後の自動再議論推奨)

**スイシン視点**: 料率の根拠、想定成約件数、パートナー確保のメリット
**ウタガイ視点**: インセンティブ最小閾値の試算、自社粗利の確認、試算の独立検証
**ベッカイ視点**: 紹介料形式自体(% vs 定額 vs 段階制)の見直しはないか

---

## Step 4: 提案順序・優先度付けの設計

**対象となる論点の例**
- 初回接触→提案までの優先順位(保険 → 経営相談 → M&A の順など)
- 営業地域による割り当て(営業移動時間を考慮した提案順)
- 案件ステージに応じた優先変更(既存顧客 → 新規紹介の優先度)

**必須チェック**: 営業移動コスト・既存営業負荷を実データで確認

1. **営業移動パターンを地図化** → 沖縄県内の 4 エリア(那覇圏 / 中部 / 北部 / 南部)を想定、1 日の訪問数と時間を試算
2. **既存営業負荷の確認** → 現在の提案ペースと実際の成約率から、キャパシティにゆとりがあるか
3. **提案順序の変更による効果予測** → 移動時間削減 XX 時間 / 月、提案件数 +XX 件などを定量化

**失敗パターン 3**: 提案順序が営業の移動時間を考慮していない
- 症状: 「同じエリア内の A 社と B 社を同じ日に訪問できない」「移動だけで 4 時間」
- 原因: ランク順のみで地理的接近を無視
- 対策: 地域グループ化とエリア内での順序付けを併用

**スイシン視点**: 優先順位の論理(ランク / 地域 / 既存/新規の組み合わせ)
**ウタガイ視点**: 実際の営業移動時間の測定、キャパシティの裏取り、地理的制約の見落とし
**ベッカイ視点**: 提案順序そのもの(リスト管理システムで自動化できないか)の必要性を再考

---

## Step 5: 提携パートナー条件の是非検討

**対象となる論点の例**
- 士業(社労士・行政書士)とのネットワーク条件(紹介規模・対応地域など)
- 商工会・金融機関との OEM 連携(ホワイトレーベル・リード共有)
- 逆紹介の条件(何を条件に対価を払うか)
- データ共有範囲(企業情報・スコアの開示可否)

**必須チェック**: 提携先確保の実現性と継続性

1. **候補先リストの洗い出し** → 手数料や条件を受け入れる可能性のある組織は何社か
2. **条件が厳しすぎないか** → 候補が枯渇するほどの要件になっていないか
3. **逆紹介の実績** → 既に契約している提携先からの逆紹介が月何件か

**失敗パターン 4**: 提携条件を厳しくしすぎてパートナー候補が枯渇する
- 症状: 「この地域は提携先がいない」「要件を満たす士業がいない」
- 原因: 紹介料率が低い / 地域限定が厳しい / 独占条項が強い など
- 対策: 条件の段階化(最小条件 → 推奨条件)と柔軟な地域設定

**スイシン視点**: 提携により獲得できる紹介件数と期待売上、スケーリングの可能性
**ウタガイ視点**: 候補先の現実的な数、条件の厳しさ、継続性の懸念
**ベッカイ視点**: 提携形式自体(直接紹介 vs 紹介料共有 vs 完全独立)の再設計

---

## Step 6: 実装・スプレッドシート同期の確認

**目的**: 議論が確定しても、実装前に運用方法を統一する

**チェック項目**
- [ ] GAS / 関数 / 手動運用の役割分担は誰にも明確か
- [ ] スプレッドシート上の設定値(重み付け・境界値・料率など)は、複数人がアクセスしても衝突しないか
- [ ] 変更ログを記録する仕組みがあるか(だれが・いつ・何を変更したか)
- [ ] 既存データの再判定が必要な場合、実行スケジュールと責任者は決まったか

**実装パターン別**
- 係数・閾値のみ: スプレッドシート設定値の修正 → GAS は自動で参照
- ロジック変更: GAS コード修正 → テスト(サンプルデータで試算) → デプロイ
- データ再判定: 既存企業 XX 件を再計算 → 結果を人が検収 → 本番適用

---

## Step 7: 見直し期限と後続アクション

**目的**: 決定が固定化しないよう、機械的に再議論をトリガーする

**必須設定項目**
- [ ] 見直し期限: 今日から **6ヶ月以内**(最長 6ヶ月が規程)
- [ ] 再検証時期の具体化: 例「2026 年 4 月末に実績確認」「成約 10 件時点で効果測定」
- [ ] KPI(何を測定するか): スコア分布の平坦化 / 紹介件数 / パートナー継続率 など
- [ ] 期限切れ時のプロセス: 自動で「再議論 TODO」が出される

**典型的な見直し期限の設定**

| 意思決定の種類 | 見直し期限 | 再検証トリガー |
|---|---|---|
| スコアリング重み付け | 3～4ヶ月 | スコア分布の確認、営業からの不満 |
| 紹介料率 | 6ヶ月 | 紹介件数 5 件以上・成約 1 件以上で実績確認 |
| 提案順序ルール | 6ヶ月 | 営業訪問時間の実績集計 |
| 提携条件 | 6ヶ月(短期) | 紹介件数ゼロが 3 ヶ月続いたら即見直し |

# よくある質問と対応

**Q: Step 1～7 をすべてやる必要があるか？**
A: いいえ。対象の論点に合わせて該当ステップのみ実行します。例えば紹介料率だけの変更なら Step 3 と Step 7 だけで OK。

**Q: 議事のまとめ方は前セクションと同じ？**
A: はい。前セクション「議事のまとめ方」のテンプレート(スイシン / ウタガイ / ベッカイ / 結論)をそのまま使用します。

**Q: シミュレーションチェックリストで「NO」が出たら？**
A: ウタガイが「不採用・理由：試算が不足」として結論を差し戻します。試算を補完してから再議論。

**Q: 見直し期限を「6ヶ月」にしたら、半年後は自動的に再議論される？**
A: 期限切れは手動でトリガーしてください。統括(アカリさん)の週次チェックリストに「再議論期限切れ」欄があります。
