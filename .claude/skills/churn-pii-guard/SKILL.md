# 顧客データの機密統制(情報統制の生命線)

早期解約リスク保全システム(`scripts/churn/`)は、保険・金融の**機密性の高い顧客個人情報**を扱う。
このデータは規制対象(個人情報保護法・保険業の監督指針)であり、一度漏えいすると回収できない。
コード・設計の"外側"=環境・運用の統制が崩れれば全部が無意味になる。ここは事業の生命線として扱う。

## 事実として押さえておくこと

- 本リポジトリ `allgroup-inc/hojo-hq` は **公開(public)**。コミットした瞬間に全世界へ公開され、git履歴・キャッシュ・フォークに**実質恒久**で残る。
- いま顧客データを守っているのは「gitに上げない」という**運用の1点**だけ。人為ミス1回で公開事故になる高リスク配置である、という前提を忘れない。

## 絶対ルール

1. **PIIを公開リポジトリに絶対入れない**: 顧客の氏名・連絡先・生年月日・契約明細・接触履歴・顧客IDに紐づく個人データ、それらを含むCSV・モデル(`risk_model.json`)・カルテ/一覧/コンソールのHTML出力は、**すべて `private/`(gitignore済)に限定**。コミットするのはコードとPIIを含まない例ファイルのみ。
2. **Issue/PR/Wiki/コミットメッセージにも個人情報を貼らない**: これらも公開される導線。エラー再現用でも本物の顧客値を貼らない(合成データに置き換える)。
3. **匿名化・最小化を保つ**: 分析は顧客IDで扱い、氏名は使わない。年齢は年代にビン化。必要以上の項目を持ち込まない。
4. **実データ投入は守り部審査の後**: 本物の顧客個人情報を入れる前に、**守り部(mamori)＋コジンさん(個人情報)＋監査テキホウさん(適法性)の審査**と**小柳さんの決裁**を必ず通す。AI・エージェントは判定者にならない。合成データでの検証・デモは審査前でも可。
5. **公開と顧客データ処理を分離**: 公開サイト(GitHub Pages)と顧客個人情報の処理を同居させない。実運用のPII処理は**非公開(private)環境・アクセス制御された社内環境**で行う。手元PC任せにしない。

## チェック手順(データ・出力・コミットを触る前に)

1. これから扱う/生成するものに顧客個人情報が含まれるか判定する。含むなら出力先は `private/` か? を確認。
2. `git status` で `private/` の中身や顧客データ(CSV・モデル・カルテHTML)が追跡対象に出ていないか確認する。出ていたら**コミットしない**。
3. `.gitignore` に `private/` が残っているか確認する(誤って外していないか)。
4. 実データ投入・本番運用の相談なら、まず「守り部審査は済んでいるか」を確認し、未了なら**合成データに留める**よう促す。
5. 分離・暗号化・アクセス制御・監査ログ・保持期限など環境側の統制が論点なら、守り部・監査へ上げる(このスキルはコード側の一線を守る係で、環境監査の代替ではない)。

## やってはいけないこと

- 「動作確認だから」と本物の顧客データを公開リポジトリ配下(private以外)に置く/コミットする。
- 守り部審査・小柳さん決裁の前に実データを本番投入する。
- 顧客個人情報をIssue・PRコメント・コミットメッセージ・チャット共有に貼る。
- 「セキュリティは大丈夫」と自己判定して安心させる(判定は守り部・専門家・小柳さんの領域)。
