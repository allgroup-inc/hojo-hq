# マルチAIクロスチェック(独立ダブルチェックの型)

締切・金額・契約条件など「間違えると信頼を失うデータ」をAIで検証するとき、
1つのAIの判定に頼らず、**別系統のAIで独立に二重判定する**ための設計パターン。
hojo-hq の原文照合(scripts/verify_sources.py)が参照実装(2026-08-06 小柳さん決裁)。

## いつ使うか

- AIによるデータ検証・照合・監査の仕組みを新しく作るとき
- 既存のAI単独チェックの見逃しが心配になったとき
- 「AIが2つあれば安心」という設計案をレビューするとき(過信を正す方向にも使う)

## 4つの原則

**① 独立性: 別系統モデルで、同じ入力を、別々に判定させる**
同じモデルに2回聞いても誤りが相関するので意味がない。別会社・別系統のモデル
(例: Claude + Gemini)に**同一の原文・同一のプロンプト**を渡し、互いの結果を見せずに判定させる。

**② 保守的マージ: どちらか一方でも検知したらNG(要確認)**
両方OKのときだけOK。ただし**AI同士の一致は断定の必要条件であって十分条件ではない**。
最終根拠は常に一次情報(原文URL)であり、一致しても原文照合は省略しない。

**③ 割れたら根拠引用の再確認(誤検知フィルタ)**
判定が割れたときだけ、指摘した側のAIに「原文から根拠箇所をそのまま引用せよ」と再確認させる。
- 引用できない・表記ゆれや略称の見落としだった → 撤回(誤検知として処理、撤回理由も記録)
- 引用できた → NG維持(引用を添えて人間のレビューに回す)
「言及が見つからない」系の指摘は不存在の引用ができないため、表記ゆれ・略称・部分一致の
再走査をさせた上で維持/撤回を判断させる。割れたときだけ動くのでコスト増はほぼない。

**④ 台帳化: 参加率と結果を毎回外部に記録する**
- 補助側AIの障害は「スキップして続行」にする(可用性を外部ベンダーに依存させない)。
  その代わり**参加率(n/m件)を毎回記録**し、参加0が続いたら警告する。
  スキップ方式は恒久障害(無料枠切れ・API廃止)でも黙って単独チェックに戻ってしまう
  「静かな脱落」を起こすため、記録なしの導入は不可。
- 判定結果・撤回・NG理由を履歴JSON等に日次で蓄積(同日再実行は上書きでべき等)。
  NG項目には人間が誤検知(false_positive)/真の不一致(true_mismatch)を記入する欄を設け、
  導入効果の測定と見直し判断の根拠データにする。

## 実装の要点(参照実装: hojo-hq scripts/verify_sources.py)

- 両AIともJSONスキーマ強制で構造化判定させる(自由文の解釈ずれを排除)
- モデル名は固定せず候補リスト方式(`*-latest` 優先)で、404時に次候補へ自動フォールバック
- APIキー未設定なら従来動作(単独チェック)に自動で戻る後方互換にする
- ページ取得は1回だけ行い、同じテキストを両AIに渡す(取得タイミング差による偽陽性を防ぐ)

## やってはいけないこと

- 同一モデル・同一ベンダーでの「自己ダブルチェック」を独立照合と呼ぶ
- 補助AIの障害でパイプライン全体を止める(主従を決め、主が生きていれば続行)
- 参加率を記録せずにスキップ方式を採用する(静かな脱落に気づけない)
- AI一致を理由に一次情報の照合を省略する
- 効果測定の期限を切らずに導入する(コスト増に対する見直し判断ができなくなる)
