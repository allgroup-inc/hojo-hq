# 三名体制ディスカッション(トライアングル体制) — 実行手順

沖縄企業のミカタ/もらいわすれ堂で、企画・施策・方針・コンテンツなど
意思決定を伴う検討をまとめるときは、CLAUDE.md 憲法の三名体制で議論を構成する。

## 3役の定義(すべての議論をこの3視点で行う)

- **スイシン(推進)**: 案を前に進める立場。狙い・期待効果・実行手順を出す。
- **ウタガイ(懐疑・反対必須)**: 必ず反対・懸念を出す。リスク・前提の穴・失敗パターンを挙げる。
- **ベッカイ(別解・前提を疑う)**: そもそもの前提を疑い、別の選択肢や枠組みを提示する。

---

## Step 1: 議論対象の判定 — 三名体制が必須か確認

**実行**: 次の2つに該当するか確認
1. **意思決定を伴う案件か** — 予算・提携・掲載方針・体制・価格・ルール/閾値の変更など
2. **不可逆な変更か** — 公開範囲の変更・データ削除・外部送信・本番設定など

**検証**:
- いずれかに該当 → Step 2 へ進む(議事を記録する)
- どちらにも該当しない → 三名体制は任意。可逆な技術作業や定型業務は議事不要(ただしウタガイの視点は常に意識)

**参照**: CLAUDE.md「三名体制運営規程 ルール8」

---

## Step 2: 3役の議論を促進(スイシン)

**実行**: 次の順序で議論を構成

1. **スイシン(推進)が初期案を提案**
   - 何を、なぜ、どう進めるのか
   - 期待される効果・目標
   - 実行手順(具体的な作業)

2. **ウタガイ(懐疑)に反対意見を明示的に求める**
   - 「ウタガイさん、この案のリスクや問題点は何か」と能動的に引き出す
   - 単なる異論ではなく、**反対理由として成立する具体的な根拠**を求める
   - 「なぜそう思うのか」を必ず引き出す

3. **ベッカイ(別解)に別の視点を求める**
   - 前提を疑う別案・選択肢を問う

**検証**: 3役すべてから意見が出たか確認
- スイシン: 推進理由と手順が明確 ✓
- ウタガイ: 反対理由が具体的で、単なる懸念ではなく説得力のある根拠を持つ ✓
- ベッカイ: 別の視点や枠組みが出ている ✓

**参照**: docs/三名体制運営規程.md「1. すべての議論は3役で行う」

---

## Step 3: 議事ファイルの形式で記録(必須)

**実行**: Step 1 で「議事を記録する」と判定した案件は、次のファイルを作成

**ファイル名**: `docs/議事_YYYYMMDD_<件名>.md`
- 日付: 議論を行った日(YYYYMMDDフォーマット)
- 件名: 30字以内の議題名

**ファイル構造** — 必ずこの順序で記載

```markdown
# 議事 YYYY-MM-DD — <件名>

参加: スイシン/ウタガイ/ベッカイ(トライアングル体制)・裁定=<部門長> / 最終決裁=<決裁者>

## 論点: <検討テーマ>

### スイシン(推進)
- <推進理由・実行案>

### ウタガイ(懐疑) ※反対理由の記録
- <反対理由・リスク・懸念>

### ベッカイ(別解)
- <前提への疑問・別案>

### 結論(部門長の裁定)
- **採否**: <採用 / 不採用 / 保留・上申>
- **理由**: <3役を踏まえた採否理由。ウタガイの懸念をどう扱うか明記>
- **見直し期限**: <最長6ヶ月。期限切れは自動で再議論>
```

**検証 — 記録時チェックリスト**:
- [ ] ファイルが `docs/議事_YYYYMMDD_<件名>.md` 形式か
- [ ] ウタガイ(懐疑)セクションが**空欄ではなく、具体的な反対理由が記載されているか**
- [ ] 結論セクションに「採否」「理由」「見直し期限」がすべて揃っているか
- [ ] 参照ファイル(例: docs/GAS会話ボット_会社情報収集.md)が実在するか確認

**参照**: docs/議事_YYYYMMDD_相談転換の設計.md(テンプレート)

## Step 4: ウタガイの反対理由が「有効」か検証

**実行**: 以下の基準で反対理由の妥当性を判定

### 反対理由が有効な例
- リスク: 「受け皿が先。返信遅延で信頼を毀損する」(具体的で対応可能)
- 前提の穴: 「申請代行に近づくため文言制限が必須」(判断基準を示している)
- 失敗パターン: 「ハードルを下げすぎると冷やかしが増え、真のKPIの質が下がる」(懸念の根拠がある)

### 反対理由が無効な例（差し戻す）
- 「なんか心配」(具体性なし)
- 「前にも似たことで失敗した」(失敗内容・教訓が不明)
- 遠回しで意図が不明: 「そこまで進める必要があるのか」(何が問題かが不透明)
- 「スイシンと同じ意見を別の言葉で言い直した」(実質的な反対ではない)

**検証 — 有効性チェック**:
```bash
# 自動検査(Step 6参照): 
# docs/議事_*.md の「ウタガイ(懐疑)」セクションが空欄でないか確認
grep -A 3 "### ウタガイ" docs/議事_*.md | grep -E "^--$|^$" 
# (空欄があれば差し戻し対象)
```

**判定結果**:
- 有効 → Step 5 へ進む(採否を確定)
- 無効 → 「差し戻し」として、ウタガイへ「反対理由を具体化してほしい」と返す

**参照**: CLAUDE.md「三名体制運営規程 ルール3」

---

## Step 5: 部門長による採否の裁定と記録

**実行**: 部門長が 3役の議論を踏まえて採否を決定

1. **採否を決める**: 採用 / 不採用 / 保留・上申
2. **採否理由を明記**: 3役のどの意見を採用し、なぜ他を採用しなかったのかを説明
3. **見直し期限を設定**: 最長6ヶ月。期限切れは自動で再議論

**検証**:
- [ ] 採否理由が「ウタガイの懸念に対する対応」を明記しているか
  - 例: 「ウタガイの『受け皿が先』は小柳さんへ上申した」(懸念を認識し、別で対応)
  - 例: 「ハードルを下げすぎる懸念は、試験運用で監視する」(試案を示している)
- [ ] 見直し期限が6ヶ月以内か(最長: 180日)
- [ ] 最終決裁が必要な案件(予算・提携など)は、決裁者へ上申されているか

**参照**: CLAUDE.md「三名体制運営規程 ルール2, 4」

---

## Step 6: ローカル検証 — 議事の有効性をチェック

**実行**: 議事を記録した後、以下の検査を実行

### 6-1: ファイルの存在性と形式チェック

```bash
# 検査実行(リポジトリルートで)
python tests/skill_validation/test_triangle_review.py validate_format
```

**検査項目**:
- [ ] ファイル名が `docs/議事_YYYYMMDD_<件名>.md` 形式か
- [ ] YAML front matter がないか(このスキルは Markdown のみ使用)
- [ ] 必須セクション(論点、スイシン、ウタガイ、ベッカイ、結論)がすべて存在するか
- [ ] ファイルサイズが異常でないか(1KB～50KB範囲)

### 6-2: ウタガイセクションの有効性チェック

```bash
python tests/skill_validation/test_triangle_review.py validate_utagai
```

**検査項目**:
- [ ] ウタガイ(懐疑)セクション内容が空でないか
- [ ] 「◆ ※反対理由の記録」コメントが添付されているか(推奨)
- [ ] 反対理由が単なる感想ではなく、具体的な根拠を含むか(段落チェック)
- [ ] 反対理由が最低50字以上あるか

### 6-3: 参照ファイルの存在性チェック

```bash
python tests/skill_validation/test_triangle_review.py validate_references
```

**検査項目**:
- [ ] 議事内で参照される全ての `docs/*.md` ファイルが実在するか
- [ ] リンク記法 `[テキスト](パス)` に誤りがないか
- [ ] URL(http/https)の形式が正しいか

### 6-4: 見直し期限の妥当性チェック

```bash
python tests/skill_validation/test_triangle_review.py validate_deadline
```

**検査項目**:
- [ ] 見直し期限が「最長6ヶ月」ルール内か(180日以内)
- [ ] 期限が過去日付になっていないか
- [ ] 期限形式が YYYY-MM-DD か

**検証結果**:
- 全項目 PASS → 議事は有効。実装に進む
- 1項目以上 FAIL → 該当する差し戻し条件を適用(Step 4参照)

**参照**: tests/skill_validation/test_triangle_review.py

## Step 7: 実装の検証 — 議事の決定が実行されたか追跡

**実行**: 採否が「採用」の場合、実装が開始されたか、または「未実装」と判定されていないか確認

### 7-1: 実装の有無を確認

```bash
# 議事で参照された実装ファイルが、当該議事日付以降に更新されているか
git log --since="<議事日付>" -- <参照パス> | head -5
```

**確認項目**:
- [ ] 採用された案件について、実装フェーズが開始されたか(コミット・PR・Issue作成)
- [ ] 未実装の場合、理由が記録されているか(docs に理由があるか)
- [ ] 保留・上申の案件について、結果が反映されているか

### 7-2: 「議事なしで先行実装」の検出

```bash
# 議事なしでコード変更が進んでいないか確認
# (CLAUDE.md 再発防止メモ: 2026-08-11～13 事例)
git log --grep="議事\|decision\|triangle" --oneline | tail -10
```

**検出項目**:
- [ ] ウタガイ役の意見を無視して実装が進んでいないか
- [ ] 議事なしで本番設定・データ削除・外部連携が行われていないか

## 失敗モード と 検出方法

このスキルで起こりうる失敗と、それを検出・防止する方法:

### 失敗モード 1: ウタガイの反対理由が記録されていない

**症状**: 議事ファイルの「ウタガイ(懐疑)」セクションが空欄、または「特になし」と書かれている

**原因**: 
- ウタガイ役が遠回しで意見を述べ、反対の実質が不明
- 部門長が形式だけ整えて内容を確認しない

**検出方法**:
```bash
# 自動検査
grep -A 2 "### ウタガイ(懐疑)" docs/議事_*.md | grep -E "^--$|なし$|特に$|なし。$"
```

**防止策**:
- Step 2 で「ウタガイさん、反対理由は何か」と**明示的に問う**
- Step 3 で「※反対理由の記録」コメントを反対セクションに必ず付ける
- Step 4 で有効性を検証(無効なら差し戻す)

**参照**: CLAUDE.md「三名体制運営規程 ルール3」

---

### 失敗モード 2: ウタガイが遠回しで、反対理由として成立していない

**症状**: 
- 「そこまで進める必要があるのか」(何が問題かが不透明)
- 「前にもこんなことがあった気がする」(失敗内容・教訓が不明)
- 「スイシンと同じ意見を別の言葉で繰り返す」(実質的な反対ではない)

**原因**: ウタガイが責任を理解していない、または本来の役割を実行していない

**検出方法**:
- Step 4 の有効性チェック(上記「反対理由が無効な例」に該当するか)
- 手動レビュー: 議事ファイルを読んで「これは本当に反対か」と問う

**防止策**:
- Step 2 で、ウタガイに「懸念の根拠を説明してほしい」と求める
- 反対理由が曖昧なら、「それは、具体的には何が起こるリスクか」と掘り下げる
- 議事に「※ ウタガイの真意: 〇〇というリスクが顕在化したときの被害が大きい」と注釈を足す

**参照**: CLAUDE.md「三名体制運営規程 ルール1」

---

### 失敗モード 3: 議事なしで先行実装(判断が記録されていない)

**症状**: 
- 会話では「了解しました、実装します」と言いながら、議事ファイルが作られない
- コミットメッセージに「議論した」と書いてあるが、docs に議事がない
- 決裁者(小柳さん)の決裁が記録されていない

**原因**:
- スピード重視で形式を省略した
- 議事を「後で書く」と思ったまま忘れた
- CLAUDE.md 2026-08-11～13 の再発防止メモ: 複数セッションが同時に同じ案件を編集

**検出方法**:
```bash
# 実装コミットが存在するのに、参照される議事ファイルがないか確認
git log --all --grep="翻訳\|新機能\|変更" --oneline | grep -v "議事\|decision" | head -10
```

**防止策**:
- Step 1 で「意思決定を伴う案件か」を**常に判定**する
- Step 3 で、議事ファイルを必ず実装の**前に**作る
- コミットメッセージに `Refs: docs/議事_YYYYMMDD_<件名>.md` を必ず記載
- 実装前に、決裁者の了承が議事ファイルに記録されているか確認

**参照**: CLAUDE.md「再発防止メモ」2026-08-11～13、2026-08-17

---

### 失敗モード 4: 議事が存在しないファイルを参照している

**症状**:
- 議事に「docs/GAS会話ボット_会社情報収集.md の貼り替え待ち」と書いてあるが、そのファイルが存在しない、または別の名前
- リンク記法 `[テキスト](docs/存在しないパス.md)` がある

**原因**:
- ファイル名を間違えた
- ファイルを作る前に議事を書いた
- ファイルをリネームしたが、議事の参照を更新しなかった

**検出方法**:
```bash
# Step 6-3 で自動チェック
python tests/skill_validation/test_triangle_review.py validate_references

# 手動チェック
grep -o 'docs/[^[:space:]]*\.md' docs/議事_*.md | while read f; do
  test -f "$f" || echo "NOT FOUND: $f"
done
```

**防止策**:
- Step 3 で、参照ファイルがすべて実在することを確認してからファイルを保存
- CLAUDE.md 再発防止メモ: 「案内文書を他者へ送る前に、記載した `docs/*.md` パスが全て解決することを機械的に検査する」
- 参照するファイルは、相対パスで記載(`docs/...` 形式)

**参照**: CLAUDE.md「再発防止メモ」2026-08-17、2026-09-19

上記の失敗モード 1～4 が検出された場合、以下の手順で Issue を自動起票


## 使用例

### 例 1: 新しい施策について議論する場合

```bash
# Step 1: 意思決定を伴うか確認 → 予算・掲載方針 → YES

# Step 2: 3役で議論
# (スイシン: 「SNS予算を50万→80万に」)
# (ウタガイ: 「ROI が下がると懸念。成果が出ない時点での中止ルールを決めるべき」)
# (ベッカイ: 「予算より、ターゲット層を先に決めるべき」)

# Step 3: 議事ファイルを作成
cat > docs/議事_20261005_SNS予算拡大.md << 'EOF'
# 議事 2026-10-05 — SNS予算拡大(50万→80万)

参加: スイシン/ウタガイ/ベッカイ・裁定=SNS部長 / 最終決裁=小柳さん

## 論点: SNS予算を月50万から80万に拡大するか

### スイシン(推進)
- Instagram・TikTok の広告出稿拡大で新規登録者の流入を加速
- 現在リーチ 10,000/月 → 20,000/月 の目標
- 予算拡大は1ヶ月で判定(ROI 3倍未満なら中止)

### ウタガイ(懐疑) ※反対理由の記録
- ROI が下がることへの懸念。現在 1:3 だが、出稿拡大で 1:1.5 になるリスク
- 中止のタイミング(いつまで様子見するか)を先に決めないと、赤字が膨らむ
- ターゲット層が曖昧なまま予算を増やすと、無駄打ちになる

### ベッカイ(別解)
- ターゲット層・メッセージを先に固めてから予算を決める方が効率的
- 既存 300 社基盤への逆流を並行して(新規:既存 = 6:4 の配分)

### 結論(部門長の裁定)
- **採否**: 条件付き採用
- **理由**: ウタガイの「中止ルール」と「ターゲット層の明確化」をまず実装してから拡大予算を配分。ベッカイの逆流は次月以降のクリエイティブで対応
- **見直し期限**: 2027-01-05
EOF

# Step 4: ウタガイの反対理由が有効か検証
# → 「中止ルール」「ターゲット層の曖昧さ」と具体的 → 有効

# Step 5: 部門長が採否を確定
# → 「条件付き採用」と理由に「ウタガイの懸念に対する対応」を明記

# Step 6: ローカル検証実行
python tests/skill_validation/test_triangle_review.py validate_format docs/議事_20261005_SNS予算拡大.md
python tests/skill_validation/test_triangle_review.py validate_utagai docs/議事_20261005_SNS予算拡大.md
python tests/skill_validation/test_triangle_review.py validate_references docs/議事_20261005_SNS予算拡大.md
python tests/skill_validation/test_triangle_review.py validate_deadline docs/議事_20261005_SNS予算拡大.md
# → すべて PASS

# Step 7: 実装を開始し、コミットメッセージに参照を記載
git commit -m "SNS予算拡大の条件設定を実装

- 中止ルール: ROI 1:2 未満で中止
- ターゲット層: 20～40代、経営層

Refs: docs/議事_20261005_SNS予算拡大.md"
```

### 例 2: 失敗を検出した場合

```bash
# Step 6: ローカル検証実行
python tests/skill_validation/test_triangle_review.py validate_utagai docs/議事_20261005_新企画.md

# 出力:
```
