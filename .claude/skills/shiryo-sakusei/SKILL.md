# 資料作成(shiryo-sakusei)

資料は「頼んだ人の記憶」ではなく「読む相手の判断」のために作る。同じ人が同じ内容を
頼んでも、日によって配色・断定表現・構成がブレると、読み手は毎回読み方から学び直す
ことになる。このスキルは、その揺れを止めるための固定の手順。コードは書かない。
実際のファイル生成は既存の形式別スキル(`pptx` `docx` `pdf` `xlsx` `docs`)に任せ、
ここでは「何を・誰に・どの型で・どのゲートを通して」を決める。

## 手順(毎回この順で)

### 1. 目的と読み手を1問で確かめる
分からないときだけ、1問にまとめて聞く: 「誰が読んで、何を決める資料ですか?」
(例: 嶺井さんが紹介先に渡す / 小柳さんが採否を決める / 士業に提携を打診する)。
読み手と判断が決まると、盛る情報の量も語尾も自動的に決まる。会話に既に答えが
あるなら聞かずに進む。

### 2. 形式を選ぶ(用途 → 形式 → 呼ぶスキル)

| 用途 | 形式 | 呼ぶスキル |
|---|---|---|
| 説明・提案・説得(対面や画面共有で見せる) | PowerPoint | `pptx` |
| 報告・稟議・議事・手順(読んで残す) | Word | `docx` |
| 配布・印刷・添付(改変されず届ける) | PDF | `pdf`(Word/スライドを作ってから変換でもよい) |
| 数値・一覧・比較(並べ替えて使う) | Excel | `xlsx` |
| 共同編集・コメントで育てる下書き | 共有ドキュメント | `docs` |

迷ったら「読み手がその場で編集したいか」で決める。編集したいならWord/Excel、
見せるだけならPDF/スライド。

### 3. 事業ブランドを当てる(混同は禁止)

| 事業 | 配色 | フォント | トーン |
|---|---|---|---|
| 沖縄企業のミカタ(株式会社GLOW) | ネイビー#00335C × オレンジ#F88800 | Meiryo(Webは Noto Sans JP 可) | 専門用語をやさしく翻訳する |
| もらいわすれ堂(株式会社フクギイロ) | 朱#B9502F × 黄#F2B705、背景 漆喰#FFFBF4、本文 墨#1F2A2E | 丸ゴシック系 | やさしい日本語・断定しない・主語は「あなた」 |
| 家計のポっ(家計の見直しやさん・社内ツール) | 黄#F9C93F × 墨#221D11 | — | 社内向け・簡潔 |

上記に無い事業(GLOW M&A・ゆんたく・hikari等)は、そのリポジトリのCLAUDE.mdか
ブランドガイドを先に読む。無ければ「配色の指定はありますか」と1問で確認し、
勝手に決めない。**別事業の色・名称・ロゴを同じ資料に混ぜない**(CLAUDE.md
「混同表記をしない」)。

### 4. 品質ゲートを通す(4つ)
1. **正確性**: 締切・金額・要件は原文URLを併記し、不明なら「要確認」と書いて
   断定しない(絶対ルール1)。数値には出典(週次レポ・台帳・原文)を添える
2. **個人情報**: 顧客の氏名・連絡先・個別の相談内容は資料に載せない。件数・割合に
   丸める。載せる必要があるときは、資料は公開リポジトリに置かず受け渡しのみにする
3. **文面**: 対外向け(顧客・提携先・県)の文章は `humanizer` で仕上げ、定型の
   書き出し/結び・過剰な強調・単調な語尾を除く
4. **見た目**: `taste-skill` の考え方で、AIが作りがちなテンプレ感(全部同じ余白・
   意味のないアイコン・3列カード乱発)を避ける。1枚1メッセージ、余白で読ませる

### 5. 構成の型
- **結論を先に**(1行) → 根拠(3つまで) → 次のアクション(誰が・いつ・何を)
- スライドは「表紙 → 結論 → 根拠 → 次の一手 → 補足」。1枚に1メッセージ、
  文字は箇条書き5行以内。細かい表は補足に回す
- 報告書(Word)は「要約(5行以内) → 現状 → 課題 → 提案 → 依頼事項」。
  決裁用なら冒頭に「決めてほしいこと」を3択以内で置く(決裁キューと同じ型)
- 週次レポート等の定型データを資料化するときは、数字をそのまま並べず
  「先週との差」「目標との距離」の2つを必ず添える(kgi-ksf-kpi-cascadeの検算)

### 6. 出力先を決める
- 公開リポジトリ(hojo-hq等)に置いてよいのは、個人情報・営業数値・顧客接点情報を
  含まないものだけ。機密区分は各リポジトリのCLAUDE.mdに従う
- それ以外は生成してユーザーへ渡す(`SendUserFile`)に留め、リポジトリには残さない
- 作ったファイル名は `<事業>_<内容>_<YYYY-MM-DD>.<拡張子>` で統一
  (例: `ミカタ_週次レポート_2026-09-21.pptx`)

## 依頼と対応の例

**例1**: 「今週の週次レポをスライドにして嶺井さんに見せたい」
→ 読み手=嶺井さん・判断=次週の打ち手 / 形式=pptx / ブランド=ミカタ /
「取得不可」の項目はそのまま「未接続」と明記し数字を作らない / 表紙→今週の結論
→数字(先週比・目標比)→次の一手、の4枚+補足

**例2**: 「士業向けの提携提案書を作って」
→ 読み手=士業事務所・判断=提携に乗るか / 形式=docx(先方が持ち帰るため)+PDF /
humanizerで仕上げ / 紹介手数料の表現は「士業法に抵触しない定額掲載料型」の範囲で
書き、報酬体系の断定は避けて小柳さん確認へ

**例3**: 「決裁キューの今週分を小柳さん用に1枚にまとめて」
→ 読み手=小柳さん・判断=採用/不採用/保留 / 形式=docx 1枚 / 冒頭に
「決めてほしいこと」を上から順に、各項目は3択+一言で答えられる形に

## 気をつけること
- 「それっぽく埋める」のが一番危ない。データが無い欄は空欄か「未取得」と書く
- 資料の中で新しい方針・価格・提携条件を決めない。決めるべきことは決裁キューへ
- 会話の中で既に決まっていることを、資料で勝手に言い換えない(名称・数値・日付)
- 長くなりそうなら、本編を短くして補足に逃がす。読み手の時間が一番高い

## 関連スキル
- `pptx` / `docx` / `pdf` / `xlsx` / `docs` — 実際のファイル生成
- `humanizer` — 対外文面の仕上げ
- `taste-skill` — テンプレ感の排除(LP向けだが考え方は資料にも効く)
- `hojo-accuracy-check` — 制度データを載せるときの原文照合
- `kgi-ksf-kpi-cascade` — 数値を目標との距離で語るとき
