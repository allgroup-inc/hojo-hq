# 構成設計・ナラティブ（プレゼン資料）— hojo-hq 専用版

## 原則：「誰が何を決めるのか」から逆算

資料を作る前に、以下 3 つを確認する：

```
1. 「読む人は誰か」
   例: 小柳さん（決裁者）、嶺井さん（営業責任者）、経営者（見込み客）

2. 「その人は何を決めるのか」
   例: 「この提携に乗るか」「今月の広告予算をどう配分するか」

3. 「決断に必要な情報は何か」
   例: 「根拠となる数値」「成功事例」「リスク」
```

これが決まると、構成が自動的に決まる。

---

## ステップバイステップ手順：ナラティブ設計 → 根拠検証

ナラティブ設計を「1 アクション = 1 ステップ」に細分化。各ステップで検証可能にする。

### **Step 1: ペルソナ定義・決定事項の明確化**

資料作成の**出発点**。ここが曖昧だと後の全ステップが無駄になる。

```
☐ 読む人（ペルソナ）を 1 人以上 3 人以下に絞る
  例）小柳さん（決裁者）/ 経営者 A さん（見込み客） 
  ※ 複数ペルソナ: 後の Step 6 で分岐検証

☐ ペルソナが「何を決めるのか」を 1 文で書く
  例）「この提携に乗るか乗らないか」「今月の予算配分を決める」
  ※ 「検討する」「考える」は決定事項ではなく NG

☐ 決定に必要な情報は何か（3 つまで）を列挙
  例）「導入後の売上増加 margin」「実装期間」「リスク」
  ※ 4 つ以上は読み手が迷う → 3 つに絞る
```

**チェック：この 3 つが揃ったか確認してから次へ。**

---

### **Step 2: 根拠の収集・検証（原文 URL 照合）**

根拠は「社内都合」ではなく「読み手の意思決定に必要な事実」。

```
各根拠について以下を確認：

☐ 根拠は「数値」「事例」「リスク」のいずれか
  ❌ 「当社は〇〇を得意としています」← 社内都合
  ✅ 「導入企業の平均申請件数が 3 件 / 月 増加」← 事実・事例

☐ 根拠に「出典 URL」が付いているか
  例）「月 252 件」← 「https://github.com/allgroup-inc/hojo-hq/ ... 
        制度 DB から集計」と明記
  ※ 社内資料・聞きかじり NG → 必ず原文を当たる

☐ 根拠の日付は 7 日以内か
  ❌ 「去年のデータ」「前月の成績」← データが古い
  ✅ 「今月の実績」「最新の DB」← 最新・信頼できる

☐ 複数根拠がある場合、相互矛盾していないか
  例）「月 100 社が登録」と「月 50 社が登録」が同じ文面に → 要確認
```

**チェック：根拠 URL を実際に開いて、記載内容が正確か確認してから次へ。**

---

### **Step 3: ナラティブ設計（結論 → 根拠 → 次アクション）**

構成を「読み手の心理」に合わせて設計。

```
資料の流れ：

（a）結論・決めてほしいこと（最初の 30 秒で勝負）
    ❌ 「沖縄企業のミカタについて」← 何それ
    ✅ 「補助金情報を毎日自動配信する機能を追加したい」

（b）読み手の痛点・疑問（共感）
    例）「顧問先が締切を見落とし、受給機会を失っている」
    ※ 相手の言葉で書く。社内用語・専門用語 NG

（c）解決策または選択肢（根拠 3 つまで）
    例）「毎日自動配信」「LINE で締切アラート」「申請サポート不要」

（d）次のアクション（誰が・いつ・何を）
    例）「小柳さんが月末までに『採用 / 不採用』を決定」
    ※ 「ご検討ください」「お気軽にお問い合わせ」は NG

```

**チェック：この流れが「読み手の判断を迷わせない」か確認。迷う点があれば根拠を追加するか、結論を言い換える。**

---

### **Step 4: 構成・流れの妥当性チェック**

資料全体の「脚本」が正しいか検証。

```
☐ 決定事項が目立つポジションにあるか（冒頭か見開き左上）
  ※ 読み手は最初の 10 秒で「何を決めるのか」を判定する

☐ 根拠 3 つが「優先度」の高い順に並んでいるか
  例）「実績数値」→「コスト」→「リスク対策」（順序例）
  
☐ 根拠と結論に因果関係があるか（「だから採用」と繋がるか）
  ❌ 「予算が月 5 万円」← 決定の判断材料ではない
  ✅ 「競合製品の同機能は月 20 万円。当社は月 5 万円」← 判断材料

☐ ページ数・スクロール数は読み手に適切か
  決裁資料: 1 ページ（A4 縦 1 枚に全て収まる）
  営業提案: 5-8 ページ（スライド + note 記事）
  説明資料: 1 スクロール = 1 セクション（LP 基準）

☐ 図表・写真は必須か（盛った図表 NG）
  ※ テンプレート画像（シンプルな矢印、ジェネリック写真）は NG
     実績数値、成功事例の写真は ✅
```

**チェック：この段階で「何かおかしい」と感じたら、Step 2 の根拠検証に戻る。**

---

### **Step 5: テンプレート感払拭 & リアリティ検査**

AI 生成感・テンプレート感を全文から消す。

```
禁止表現（以下のいずれかが 2 回以上出てきたら NG）：

❌ 「〇〇市場で成長」「〇〇業界が拡大」「急速に変化」
❌ 「当社の強みは」「当社は〇〇です」「貴社のビジネスを加速」
❌ 「今後さらに」「一層の」「今注目されている」
❌ 「課題を解決」「革新的」「最先端」（根拠なし）
❌ 「ご不明な点は」「お気軽にお問い合わせください」

許可表現：
✅ 「〇〇さんから『締切を見落とした』との声を 5 件 / 月 受けている」
✅ 「導入した 5 事務所では、紹介件数が平均 3 件 / 月 増えた」
✅ 「通常 2 週間かかる実装を 5 日で提供できる」

禁止テンプレート表現チェック（自動化可能）：
$ grep -E "(市場で成長|業界が拡大|当社の強み|加速させる|革新的)" <file>
```

**チェック：禁止表現が 2 回以上出てきたら全文を言い換える。必ず「具体例」と「数値」で根拠を示す。**

---

### **Step 6: 複数ペルソナ対応の検証（分岐が正しいか）**

複数ペルソナ向けに同じ構成を流用するとどちらにも刺さらない。

```
複数ペルソナがいる場合、以下を確認：

☐ ペルソナごとに「決定事項」が異なるか
  例）
  • 小柳さん（決裁者）→「この機能を採用するか」
  • 経営者（見込み客）→「この製品を契約するか」
  → 異なる決定事項なので、資料を分けるべき

☐ ペルソナごとに「根拠」が異なるか
  例）
  • 小柳さんは「ROI」「実装期間」「リスク」を知りたい
  • 経営者は「使いやすさ」「申請成功率」「料金」を知りたい
  → 異なる根拠なので、資料を分けるべき

☐ 同じ資料で複数ペルソナに対応する場合、明示的に分岐しているか
  例）「決裁者向け」「利用者向け」と見出しで明記
  ※ セクション混在は NG。必ず物理的に分割

複数ペルソナ対応が必要なら、実質 2 つ以上の資料と考える。
構成が異なれば、ファイルも分ける。
```

**チェック：複数ペルソナに同じ構成を流用していないか確認。流用していたら分割する。**

## ナラティブ設計の失敗パターン 5 つ

同じミスが 2 度起きたら再発防止として記載（CLAUDE.md 連携）。

### **❌ パターン 1: 「当社は〇〇です」（社内都合中心）**

例）「当社は補助金情報を自動収集しています」「当社の強みは」

**問題**: 読み手は「だからお前の何なんだ」と感じる。読み手の視点がない。

**修正方法**:
- 読み手の痛点から始める
- 「〇〇という課題を抱えている見込み客」に訴える

✅ 修正例）「顧問先が補助金の締切を見落とし、受給機会を失っている」

---

### **❌ パターン 2: 複数ペルソナ向けに同じ構成を流用**

例）決裁者向けと見込み客向けで同じ構成、同じスライドを使い回す。

**問題**: どちらにも刺さらない。表面的な説得力を失う。

**修正方法**:
- ペルソナごとに「決定事項」が異なるか確認
- 異なれば、資料を分ける
- 同じ資料で対応する場合は、セクションで明示的に分岐

✅ 例）「決裁者向け（ROI・リスク）」「見込み客向け（料金・使いやすさ）」と見出しで区切る

---

### **❌ パターン 3: 根拠が社内都合で、顧客メリットが欠ける**

例）「実装期間 2 週間」「月額費用 5 万円」← これだけでは判断材料ではない

**問題**: 読み手は「他と比べて?」「そのコストで何が得られる?」と感じる。

**修正方法**:
- 根拠に「比較」か「効果」を加える
- 「同業他社は月 20 万円（比較）」
- 「導入後、紹介件数が月 3 件増加（効果）」

✅ 修正例）「競合製品は月 20 万円。当社は月 5 万円で同機能を提供」

---

### **❌ パターン 4: テンプレート感が残る（生成感が強い）**

例）「市場が成長している」「革新的なソリューション」「当社は業界の最先端」

**問題**: AI や ChatGPT で自動生成したような印象。信じられない。

**修正方法**:
- 禁止表現を全削除（grep で機械的に検出可能）
- 具体例・数値・事例で置き換える
- 「沖縄県内の補助金制度は毎月平均 15 件新規追加される。当社は 24 時間以内に DB へ反映」

✅ 修正例）「導入した 5 事務所では、紹介件数が平均 3 件 / 月 増えた」

---

### **❌ パターン 5: ペルソナのニーズと提案がズレている**

例）決裁者は「ROI」を知りたいのに、「ビジョン・ミッション」の話をする。

**問題**: 読み手の意思決定に必要な情報がない。説得力がない。

**修正方法**:
- Step 1 で「ペルソナが何を決めるのか」を明確化
- Step 2 で「決定に必要な情報 3 つ」を列挙
- その 3 つだけ根拠として提示

✅ 例）決裁者向け: 「ROI」「実装期間」「リスク」に絞る（ビジョン不要）

## 構成タイプ別テンプレート

### **Type A: 決裁資料（小柳さん向け）**

読む人: 決定者（小柳さん）  
決定事項: 「採用 / 不採用 / 保留」

**構成（1 ページ A4 を推奨）**:

```
┌──────────────────────────┐
│ タイトル                  │
│ （決めてほしいこと 1 文） │
└──────────────────────────┘
        ↓
┌──────────────────────────┐
│【決めてほしいこと】       │
│ □ A 案（推奨）           │
│ □ B 案                  │
│ □ C 案                  │
│ □ その他                │
└──────────────────────────┘
        ↓
┌──────────────────────────┐
│【根拠（3 つまで）】       │
│ ✅ 成功事例 / データ       │
│ ✅ コスト・スケジュール    │
│ ✅ リスク・対策           │
└──────────────────────────┘
        ↓
┌──────────────────────────┐
│【次のアクション】         │
│ • 誰が（小柳さん）        │
│ • いつまでに（明日）      │
│ • 何を（決定）           │
└──────────────────────────┘
```

**実例: ミカタ 新機能追加の決裁**

```
【決めてほしいこと】
□ AI 質問機能を追加する（推奨）
□ 次月延期

【根拠】
✅ ユーザーから「診断後の相談先が分からない」との声（5 件/月）
✅ 実装: 2 週間、追加コスト月 5 万円
✅ リスク: AI の誤った回答 → mamori が事前チェック

【決定後】
• 小柳さんが月末までに決定
• 決定後、実装部門へ連携
```

---

### **Type B: 営業提案資料（見込み客向け）**

読む人: 見込み客（経営者・士業など）  
決定事項: 「提携に乗るか / 契約するか」

**構成**:

```
表紙
  ↓
01. 「こんな課題、ありませんか？」
    └─ 相手の痛点を、相手の言葉で表現
    
02. 「私たちができること」
    └─ 解決策（1-2 つに絞る）
    
03. 「実績・事例」
    └─ 『同じような企業』の成功例（写真・数値）
    
04. 「料金・条件」
    └─ 透明性が信頼につながる
    
05. 「次のステップ」
    └─ 「デモを見ますか」「相談日を決めますか」
```

**実例: ミカタ の士業向け提案資料**

```
表紙: 「沖縄企業のミカタ — 顧問先の補助金情報を自動配信」

01. 課題
    「顧問先が補助金の締切を見落とし、受給機会を失っている」

02. 解決策
    「補助金情報を毎日自動配信 + LINE で締切アラート」
    「貴事務所は『申請サポート』に集中できる」

03. 実績
    「月 252 件の補助金を追跡」
    「導入事務所の紹介件数が平均 3 件/月 増加」

04. 料金
    「初期費用: 0 円」
    「月額: 定額 2 万円（初年度は 1 万円）」

05. 次
    「来月 1 日から試してみませんか」
```

---

### **Type C: 説明資料（顧客向け LP・note など）**

読む人: 一般ユーザー（経営者・県民など）  
決定事項: 「使ってみるか」「登録するか」

**構成**:

```
ビジュアル大きく（何ができるのか一目で）
  ↓
「こんな悩みありますか？」（相手の言葉で）
  ↓
「3 ステップで解決」（シンプルに）
  ↓
「実は簡単」（事例・写真）
  ↓
「今すぐやってみる」（ボタン）
```

**実例: もらいわすれ堂 の LP**

```
Hero: 「あなたが受け取れる給付金を、自動で探す」
      [イメージ画像: 家族が happy]

問題: 「給付金って、複雑で分かりません」
     「もらい忘れている制度、たくさんあります」

解決: 「3 ステップで分かる」
     ① 診断（1 分）
     ② 該当制度を確認
     ③ 受け取り手続き

事例: 「〇〇さんは月 3 万円の給付金を新たに受け取れました」

CTA: 「診断してみる」[LINE で始める]
```

## ローカル検証：根拠・ナラティブ妥当性テスト

実装の品質を機械的に検査。以下は自動化可能。

### **Test 1: 根拠 URL が実在するか（verify-sources 型）**

```bash
# 根拠に記載された全 URL を抽出・検証
# 実装例（自動化テスト）:

for url in $(grep -oE 'https?://[^\s]+' <ファイル>); do
  curl -sI "$url" | head -1 | grep "200\|301" || echo "NG: $url"
done
```

**チェックポイント**:
- 記載している全 URL が 200 / 301 を返すか
- 404 / 403 は NG（参照不可）
- URL が最新の状態か（git log で日付確認）

---

### **Test 2: テンプレート表現の検出**

```bash
# 禁止表現をグレップで検出
grep -in "(市場で成長|業界が拡大|当社の強み|加速させる|革新的|最先端)" <ファイル>

# 出力例:
# 15: 当社は業界の最先端を行っています ← 禁止表現
# 42: 市場が急速に成長しています ← 禁止表現
```

**チェック**: 禁止表現が出てきたら 0 件になるまで言い換える。

---

### **Test 3: 複数ペルソナ分岐の検証**

複数ペルソナがいる場合、分岐が正しく適用されているか。

```
確認項目:

☐ ペルソナごとに見出し / セクションで明示的に分けられているか
  例）「## 決裁者向け」「## 見込み客向け」
  
☐ 各ペルソナセクションで「決定事項」が異なるか
  チェック: grep -A 5 "決裁者向け" | grep "決める"
  
☐ 同じ根拠を複数ペルソナで繰り返していないか
  繰り返し = 「どちらにも刺さらない」の兆候
```

---

### **Test 4: 社内都合表現の禁止リスト**

以下のパターンが出てきたら社内都合表現の可能性（shipping_gate.py 連携）。

```bash
# 禁止パターン検出
grep -in "(当社は|当社が|当社の|弊社は|弊社が|弊社の)" <ファイル> | grep -v "当社のミカタ\|当社の実績"
```

**許可される場合**:
- 「当社のミカタ」← サービス名（許可）
- 「当社の実績: 導入 5 事務所、紹介件数 3 件 / 月 増」← 具体例＋数値（許可）

**NG の例**:
- 「当社は〇〇を提供しています」← 社内視点
- 「当社の強みは」← 読み手視点がない

---

### **Test 5: 根拠 vs 結論の因果関係確認**

根拠と決定事項に「本当に繋がるか」検証。

```
例）
決定事項: 「この機能を追加するか」
根拠 1: 「実装期間 2 週間」
根拠 2: 「追加コスト月 5 万円」
根拠 3: ???

問題: 「期間」と「コスト」だけでは判断できない。
      「なぜこの機能が必要か」がない。

修正: 根拠 3 に「ユーザーからの要望」「導入後の効果」を加える
例）「ユーザー 5 件 / 月 から『相談先が分からない』との声」
```

**チェック方法**:
- 各根拠について「これがあれば決めやすくなるか」と問う
- ノーなら、その根拠は削除または別の根拠と置き換える

## 構成のチェック（毎回ここを通す）

```
□ 読み手が「何を決めるのか」が 1 文で書いてあるか
  └─ 書いてなければ、資料の目的が曖昧

□ 根拠が「3 つ以下」に絞られているか
  └─ 4 つ以上あると、読み手が迷う

□ 『次のアクション』が『誰が・いつ・何を』で書いてあるか
  └─ 「ご検討ください」「お気軽にお問い合わせ」は NG

□ ページ数は適切か
  └─ 決裁資料: 1 ページ
  └─ 営業提案: 5-8 ページ
  └─ 説明資料（Web）: 1 スクロール = 1 セクション

□ 数値に「出典」が付いているか（shiryo-sakusei）
  └─ 「月 252 件」← 「制度 DB から集計」と書く

□ 禁止表現（テンプレート感）が 0 件か（grep で検査）
  └─ 「市場で成長」「当社の強み」など 2 回以上出たら言い換え

□ 複数ペルソナ対応の場合、分岐が明示的か
  └─ 見出しで「決裁者向け」「見込み客向け」と分割

□ 根拠と結論に因果関係があるか
  └─ 「だからこの判断ができる」と繋がるか確認
```

## ナラティブの工夫（「テンプレ感」を消す）

### **NG パターン**

❌ 「当社は〇〇を提供しています」  
   → 読む人は「でお前の何なんだ」と思う

❌ 「貴社のビジネスを加速させます」  
   → 根拠がない、信じられない

### **OK パターン**

✅ 「あなたの顧問先が、補助金の締切を見落としたことはありませんか」  
   → 相手の痛点から入る、共感

✅ 「導入した 5 事務所の紹介件数が平均 3 件 / 月 増えました」  
   → 数値 + 成功事例で信じられる

## よくある質問（FAQ）

**Q: 「複数ペルソナ 1 つの資料」で対応できる？**
A: できますが、セクションで明示的に分岐してください（例「決裁者向け」「見込み客向け」）。分岐なしで同じ構成を使い回すと、どちらにも刺さりません。判断に迷ったら資料を分ける（コストより説得力）。

**Q: 根拠が「2 つ」だけでもいい？**
A: OK。根拠 3 つはあくまで「上限」です。「2 つで十分」なら 2 つでいい。大切なのは「根拠があるか」「正確か」です。

**Q: 「数値」がない場合は？**
A: 「事例」「リスク対策」で代替できます。ただし「出典 URL」は必須。「聞きかじり」は NG。

**Q: 根拠の日付は「何日以内」が目安？**
A: 7 日以内推奨。1 ヶ月以上古いデータは「最新」と言えません。月次レポは「先月末時点」と明記してください。

**Q: テンプレート表現って、どこまで NG？**
A: 2 回以上出たら NG。根拠のない抽象表現は全削除。具体例・数値で置き換えてください。

**Q: 「次のアクション」が「検討」でもいい？**
A: NG。「〇〇さんが △△までに『採用 / 不採用』を決定」と、具体的な人・日時・決定内容を書く。「検討」は行動が曖昧です。
