# データ分析・インサイト抽出（hojo-hq 専用版）

## 使うべきタイミング

営業・マーケティング・運用のデータが蓄積されているが、
「今、何が起きているのか」が見えていない場合。
データは「過去の記録」ではなく「改善の羅針盤」に変える。

### 違和感シーン（なぜデータが活用されないのか）

❌ **Before（データが眠っている状態）:**
```
状況:
  • KAKEHASHI: 営業マン 12 人の通話データ（月 1,000 通話以上）
  • glow-ma: 顧客接触履歴（月 500 件以上の営業活動）
  • ミカタ: LINE 登録→配信→アラート（月 50-100 人の新規登録）
  • もらいわすれ堂: 診断ツール実施記録（月 200-300 件）

現実:
  • 「今月の成約数は?」と聞かれて、手作業で Excel 集計（1 時間）
  • 「なぜ先月より登録者が減った?」という質問に、
    答えられない（原因が分からない）
  • 失注理由 TOP3 は「知っている気」だが、数値で根拠がない
  • YouTube は「150 ビュー」だが、「昨月比でどう?」は不明
  • 営業マン別の成績差が激しいが、「教育すべき点」が曖昧

運用者の感覚:
  「データってあるはずなのに、意思決定に使えない」
  「毎月同じ質問（成約数、登録数）に答えるだけ」
```

✅ **After（データが生きている状態）:**
```
自動ダッシュボード（毎日朝 8 時に更新、3 分で全体把握）:

┌─────────────────────────────────────────┐
│ KAKEHASHI 営業チーム（昨日との比較）    │
├─────────────────────────────────────────┤
│ 通話数: 25 件 (↑ 前日比 +12%)           │
│ 平均通話時間: 24 分 (↓ 前日比 -2 分)    │
│ 成約数: 3 件 (↑ 昨月平均日 +1 件)       │
│ 成約率: 67% (↑ 目標 60%)                │
│ 失注トップ理由: 「支払が心配」× 5 件    │
│           → 対応フレーズ: 「3ヶ月回収」 │
│              を使っているのは営業 A-D、 │
│              使っていないのは営業 E-F   │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│ ミカタ LINE 登録（昨月同時期との比較） │
├─────────────────────────────────────────┤
│ 新規登録: 18 人 (↓ 昨月同時期 -22%)     │
│ 原因分析:                               │
│   ├─ Instagram 投稿: 4 本 (↑ 前月 +2)   │
│   ├─ SNS エンゲージ: 280 (↓ 前月 -35)   │
│   ├─ クリック→診断率: 65% (↓ 昨月 72%) │
│   └─ 診断実施者: 30 人 (↓ 昨月 38)      │
│ 仮説: 「投稿数は増えたが、クリック率が │
│        落ちた → 投稿内容の見直し必要」  │
│ 改善案:                                 │
│   ├─ 「人気が高い投稿 Top3」を再分析   │
│   └─ 次週の投稿内容を変更予定          │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│ もらいわすれ堂 診断→登録（リアルタイム）│
├─────────────────────────────────────────┤
│ 診断実施: 8 人 (今日)                   │
│ 診断完了率: 75% (目標 80%)              │
│ 登録率: 25% (昨日 40%)                  │
│   ↑ 「診断完了→登録」のステップで      │
│     離脱が多いことが判明               │
│ 改善案: ページの説明文を見直し（本日）  │
└─────────────────────────────────────────┘
```

結果:
  • 朝会（15 分）で「今日何をすべきか」が明確
  • 「支払懸念」対応の営業 E-F に即座に研修を実施
  • 診断ページの説明文変更で翌日の登録率が回復（25% → 45%）
  • データ分析が「月 1 回の定期報告」から「日次改善」へ
```

## 原則: 「データ → 異常 → 仮説 → 改善」のサイクル（1 日で完結）

### サイクルの 4 ステップ

```
Step 1: データ取得・集計（自動）
  ├─ ソース: Sheets API / GA4 API / Zoom API
  ├─ 更新頻度: リアルタイム（5-15 分ごと）
  ├─ 出力: JSON + Google Sheet（バージョン履歴で過去データ保持）
  └─ 例: 昨日の通話 25 件、成約 3 件、失注理由 5 つを自動集計

Step 2: 異常検知（自動 + 人間の判定）
  ├─ 機械的ルール:
  │   • 前日比 ±20% 以上 = 異常フラグ
  │   • 移動平均との乖離 ±3σ = 異常フラグ
  │   • 「失注理由 1 位」が先月 5 位以下 = 異常フラグ
  ├─ 例:
  │   • 通話数 25 件（昨日比 +40%）= 異常
  │   • クリック率 55%（昨月比 -40%）= 異常
  │   • 新規に「法務的懸念」が失注理由 1 位に = 異常
  └─ 出力: Slack アラート「今日の異常 3 件」+ リンク

Step 3: 原因仮説（人間 + AI の協力）
  ├─ 質問を立てる（運用者が考える）:
  │   「なぜクリック率が落ちたのか?」
  │   「失注理由が変わったのはなぜ?」
  ├─ AI が仮説を提案（Claude の分析）:
  │   • Instagram 投稿数は増えても「クリック誘導文」がない
  │   • 失注理由の変化 = 先週公開した「新機能説明」が
  │     顧客に『法的リスク』に見えている可能性
  └─ 運用者が判定: 「その仮説、あり得そう」か「違う」か

Step 4: 改善実行（その日のうち）
  ├─ 改善案を立案（運用者）
  │   例 1: Instagram 投稿に「診断ボタンまで 30 秒」と明記
  │   例 2: 法務部に確認、新機能ページの説明を修正
  ├─ 実行（その日～翌日）
  │   • 投稿内容を変更 + 次の投稿から適用
  │   • 説明ページを修正 + リアルタイムで効果測定
  └─ 結果確認（翌日の朝会）
      「クリック率が 55% → 68% へ改善」と共有
      → チーム全体で「改善が効いた」という確信が生まれる
```

## Stage 1: KPI と異常の閾値を定義

### KAKEHASHI 営業チーム向けの KPI 例

```
Primary KPI（評価対象）:
  ├─ 月次成約数（チーム全体）
  │   └─ 目標: 月 100 件以上
  │       異常: 月単位で前月比 -20% 以上
  │
  ├─ 個人別成約率（営業 1 人あたり）
  │   └─ 目標: 60% 以上
  │       異常: 個人の成約率が 40% 以下が 1 週間続く
  │
  └─ 失注理由 Top3（チーム全体）
      └─ 注視: 先月の Top3 に「新しい理由」が入った
            = 提案内容 / 市場環境 / 顧客層の変化をシグナル

Secondary KPI（プロセス指標）:
  ├─ 平均通話時間（営業 1 人あたり）
  │   └─ 標準: 20-30 分
  │       異常: < 15 分（急ぎすぎ） or > 40 分（長すぎ）
  │
  ├─ 通話数（営業 1 人あたり / 日）
  │   └─ 標準: 2-3 件
  │       異常: 0 件（営業していない） or > 5 件（他の質が落ちる）
  │
  └─ 初回ヒアリングから成約までの回数
      └─ 標準: 1-2 回
          異常: > 3 回（顧客が迷っている = 提案に問題）

定性指標（定期的に手動確認）:
  ├─ 顧客満足度（3ヶ月ごとにアンケート）
  ├─ 営業マンの心理状態（「やる気が落ちている営業」を早期発見）
  └─ 提案資料の「時代遅れ」度（デザイン・事例・数値）
```

### ミカタ LINE チャネル向けの KPI 例

```
Primary KPI:
  ├─ 新規 LINE 登録数（月）
  │   └─ 目標: 月 50 人以上
  │       異常: < 30 人 が 2 ヶ月続く
  │
  └─ LINE → 診断実施率（登録者中）
      └─ 目標: 60% 以上
          異常: < 40% （登録後に離脱）

Conversion Funnel（診断までの離脱分析）:
  ├─ Instagram → クリック（CTR）
  │   └─ 目標: 8% 以上
  │       異常: < 5%（投稿内容を見直す合図）
  │
  ├─ クリック → ランディングページ到着
  │   └─ 目標: 80% 以上（ブラウザ離脱）
  │
  ├─ ランディングページ → 診断スタート
  │   └─ 目標: 65% 以上
  │       異常: < 50%（ページのUX問題 = 修正必要）
  │
  ├─ 診断開始 → 診断完了
  │   └─ 目標: 75% 以上
  │       異常: < 60%（設問が複雑か、時間がかかりすぎ）
  │
  └─ 診断完了 → LINE 登録
      └─ 目標: 50% 以上
          異常: < 30%（ユーザーが「登録のメリット」を感じていない）

フロー分析（どこで一番離脱が多いか）:
  例（実績）:
    Instagram: 1,000 インプレッション
      ↓ (CTR 7%)
    クリック: 70 件
      ↓ (LPO 85%)
    ランディングページ: 60 件
      ↓ (診断開始率 60%)
    診断スタート: 36 件
      ↓ (完了率 72%)
    診断完了: 26 件
      ↓ (LINE 登録率 35%)
    LINE 登録: 9 人 ← 1,000 インプレッションから 0.9%

改善すべき箇所:
  最大離脱は「診断完了 → LINE 登録」（65% 離脱）
  改善案:
    • 診断結果ページに「タイムリーな情報が LINE で届く」と明記
    • LINE 登録後の「最初の 3 つのメッセージ」を改善
      (登録者が「これなら価値ある」と実感できるもの)
```

### KAKEHASHI 営業データの統合

```
データフロー:

┌──────────────────┐
│ Zoom Phone API   │ (1 時間ごとに自動取得)
│  - 通話ログ      │  └─ 通話者 / 通話時間 / 通話結果
│  - 録音ファイル  │
└────────┬─────────┘
         │
         ↓
┌──────────────────┐
│ glow-ma Sheets   │ (Apps Script で自動更新)
│  - 通話 ID       │
│  - 成約 / 失注   │
│  - 失注理由      │
└────────┬─────────┘
         │
         ↓
┌──────────────────┐
│ 分析 Sheet       │
│ (リアルタイム    │ (SQL-like QUERY 関数)
│  ダッシュボード) │  └─ 営業別成績 / 失注理由 Top3
└────────┬─────────┘   └─ 通話時間の平均・バラツキ
         │
         ↓
┌──────────────────┐
│ Slack アラート   │ (異常検知）
│  「失注理由が     │  └─ Slack Bot が毎日 8 時に Webhook 送信
│   変わりました」 │
└──────────────────┘

実装例（Apps Script）:

function fetchZoomCallLogs() {
  const zoomApiKey = PropertiesService.getScriptProperties()
    .getProperty('ZOOM_API_KEY');
  
  const today = new Date();
  const yesterday = new Date(today.getTime() - 86400000);
  const fromDate = Utilities.formatDate(yesterday, 'JST', 'yyyy-MM-dd');
  const toDate = Utilities.formatDate(today, 'JST', 'yyyy-MM-dd');
  
  const headers = {
    'Authorization': `Bearer ${zoomApiKey}`,
    'Content-Type': 'application/json'
  };
  
  const response = UrlFetchApp.fetch(
    `https://zoom.us/v2/report/daily?from=${fromDate}&to=${toDate}`,
    { headers, muteHttpExceptions: true }
  );
  
  const data = JSON.parse(response.getContentText());
  
  // glow-ma Sheet に追記
  const sheet = SpreadsheetApp.getActiveSpreadsheet()
    .getSheetByName("CallLog");
  
  data.meetings.forEach(meeting => {
    sheet.appendRow([
      new Date(),  // 取得日時
      meeting.user_id,  // 営業 ID
      meeting.duration_minutes,  // 通話時間
      null,  // 成約/失注（別途手動入力 or CRM 連携）
      null   // 失注理由（別途手動入力）
    ]);
  });
  
  // 次のトリガー（毎日 9 時に実行）を設定（初回のみ）
  ScriptApp.newTrigger('fetchZoomCallLogs')
    .timeBased()
    .everyDays(1)
    .atHour(9)
    .create();
}

function analyzeCallMetrics() {
  // 昨日の通話データを集計
  const sheet = SpreadsheetApp.getActiveSpreadsheet()
    .getSheetByName("CallLog");
  const data = sheet.getDataRange().getValues();
  
  const yesterday = new Date(new Date().getTime() - 86400000);
  const yesterdayStr = Utilities.formatDate(yesterday, 'JST', 'yyyy-MM-dd');
  
  const yesterdayData = data.filter(row => 
    Utilities.formatDate(row[0], 'JST', 'yyyy-MM-dd') === yesterdayStr
  );
  
  // 集計
  const metrics = {
    totalCalls: yesterdayData.length,
    avgDuration: yesterdayData.reduce((sum, row) => sum + row[2], 0) / yesterdayData.length,
    contracts: yesterdayData.filter(row => row[3] === '成約').length,
    contractRate: (yesterdayData.filter(row => row[3] === '成約').length / yesterdayData.length * 100).toFixed(1)
  };
  
  // 異常検知
  const dashboardSheet = SpreadsheetApp.getActiveSpreadsheet()
    .getSheetByName("Dashboard");
  const previousDayData = data.filter(row => 
    Utilities.formatDate(row[0], 'JST', 'yyyy-MM-dd') === 
    Utilities.formatDate(new Date(new Date().getTime() - 86400000*2), 'JST', 'yyyy-MM-dd')
  );
  
  const previousMetrics = {
    totalCalls: previousDayData.length,
    avgDuration: previousDayData.reduce((sum, row) => sum + row[2], 0) / previousDayData.length
  };
  
  // 異常フラグ（20% 以上の変化）
  const callsChange = ((metrics.totalCalls - previousMetrics.totalCalls) / previousMetrics.totalCalls * 100).toFixed(1);
  
  if (Math.abs(callsChange) > 20) {
    sendSlackAlert(`通話数が前日比 ${callsChange}% 変化しました`);
  }
  
  // ダッシュボード更新
  dashboardSheet.getRange('A1:D1').setValues([[
    `${yesterdayStr} の実績`,
    `通話: ${metrics.totalCalls} 件`,
    `成約: ${metrics.contracts} 件 (${metrics.contractRate}%)`,
    `平均時間: ${metrics.avgDuration.toFixed(1)} 分`
  ]]);
}

## Stage 3: 異常検知ルール（パターン別）

### パターン 1: 時系列の急変（前日比）

```
ルール:
  前日の同じ指標と比較して ±20% 以上の変化 = 警告

例:
  昨日: 通話 25 件、成約 3 件（成約率 60%）
  今日: 通話 15 件、成約 1 件（成約率 33%）
  
  異常フラグ:
    • 通話数: 25 → 15 (-40%) ← 警告
    • 成約数: 3 → 1 (-67%) ← 警告
    • 成約率: 60% → 33% (-45%) ← 警告

仮説:
  ├─ 営業マンが 1-2 人休み?
  ├─ 営業のやる気が低下?
  ├─ 顧客側の購買ニーズが減退?
  └─ システム障害（電話がつながらない）?

対応:
  → 朝会で営業マネージャーに確認
     「昨日の通話が少なかった理由は?」
```

### パターン 2: 移動平均との乖離（トレンドの裂け目）

```
ルール:
  過去 7 日間の移動平均から ±3σ（標準偏差 3 倍）の乖離 = 警告

例:
  過去 7 日の成約率: [60%, 62%, 58%, 61%, 59%, 63%, 60%]
  移動平均: 60.4%
  標準偏差: 1.8%
  許容範囲: 60.4% ± 3×1.8% = 54.8% ～ 65.8%
  
  今日の成約率: 45%
  → 45% < 54.8% = 警告（異常に低い）

仮説:
  成約率が異常に下がった理由
  ├─ 新しい顧客層が増えた（単価の低い案件）
  ├─ 営業が「新しい提案内容」を試している（習熟度不足）
  ├─ 競合他社が出現した
  └─ 顧客が慎重になった（市場全体の変化）

対応:
  → 失注理由を詳しく見てみる
     「何で成約しなかったのか」を分類
```

### パターン 3: カテゴリー別の比率変化（質的な異常）

```
ルール:
  失注理由のランキングが「先月 Top3」から大きく変わった = 警告

例:
  先月の失注理由 Top3:
    1. 「支払が心配」× 38% (12 件)
    2. 「検討が必要」× 25% (8 件)
    3. 「他社と比較」× 19% (6 件)
  
  今月 1 週目の失注理由:
    1. 「支払が心配」× 35% (7 件)
    2. 「法務的な懸念」× 30% (6 件) ← 先月は 5%未満
    3. 「検討が必要」× 20% (4 件)
  
  異常フラグ:
    「法務的な懸念」が 5% → 30% へ増加 = 警告

仮説:
  ├─ 先週公開した「新機能説明」が
  │  顧客に『法的リスク』に見えている
  ├─ 競合他社が「法務リスク」を強調した営業を開始
  └─ 実際のコンプライアンス変化があった

対応:
  → 法務部 (mamori.md) に即座に報告
     「顧客が『法務的懸念』を言い始めました。
      新機能説明が原因か、市場変化か、確認してください」
```

## Stage 4: ダッシュボード設計（毎日 3 分で把握）

### 設計原則

```
❌ NG（よくあるミス）:
  Google Sheet でグラフを 20 個作成
  → 「見るべきグラフ」と「参考情報」が混在
  → 朝 8 時に「さて、グラフを見るか」と思っても 15 分かかる
  → 「今日の行動」が決まらない

✅ OK（3 分で意思決定できるダッシュボード）:
  1. 最上部（15 秒で目に入る）: 「今日と昨日の比較」
     └─ 成約数 / 成約率 / 通話数（3 つの数字だけ）
  
  2. 次段（1 分で確認）: 「異常の有無」
     └─ 「何が異常なのか」を文章で説明
        （単なる数字でなく、「原因の仮説」を含める）
  
  3. その次（1 分で確認）: 「改善すべき Top3」
     └─ 昨日との差異から「今日実行すべき改善」を提案
  
  4. 参考情報（必要に応じて掘り下げ）: 詳細グラフ
     └─ 営業別成績 / 失注理由の詳細分類
```

### 実装例: KAKEHASHI チーム向けダッシュボード

```
【今日（10/01）のサマリー】

┌─ リアルタイム指標（最新更新: 08:15）─────────────┐
│                                                     │
│ 通話数: 12 件                                       │
│   ├─ 目標: 20 件/日 → 進捗 60%                    │
│   └─ 前日同時刻: 18 件 → 比 -33% ⚠️ アラート      │

## Stage 5: データ検証と信頼性確保

### 「データが間違っていないか」を検証する仕組み

```
❌ NG（信頼性が低い）:
  「営業が手動入力した成約/失注」がそのまま集計に使われる
  → 営業が「失注理由」を忘れて「検討中」のままにしてから 3ヶ月
  → 実際には失注なのに、「検討中」として計上される
  → 成約率が見かけ上、高くなる

✅ OK（信頼性が高い）:
  複数ソースから検証
  
  方法 1: 音声記録との照合（transcription-analysis-hojo 連携）
    「営業が『成約』と言ったが、実際の通話では『検討が必要』と顧客が返答」
    → 営業の入力ミス or 顧客の「その場での返事」が後で変わった可能性
    → 音声で事実を確認
  
  方法 2: 複数 AI での独立検証（マルチAI連携）
    失注理由 TOP1 が「支払が心配」と判定されたら、
    Claude + Gemini の 2 つで独立判定
    → 両者が一致 = 信頼度 95%
    → 片方だけ = 信頼度 60%（要確認）
    → 全く違う = 再分析
  
  方法 3: サンプリング検査（月 1 回）
    月末に「先月の成約・失注 30 件」を無作為抽出
    → マネージャーが「本当にそうなったのか」を通話記録で確認
    → 90% 以上一致 = 入力ルールが機能している
    → 80% 未満 = 営業教育 / ルール改善が必要

方法 4: データの時系列一貫性チェック
  「昨日 5 件の失注」で掲載したのに、
  「今日のレポート」では「先月失注は 20 件」と言っている
  → 「見かけ上の一貫性」を機械的にチェック
```

## チェックリスト

```
□ KPI が「ビジネス目標」と連動しているか
  └─ 「成約率」は分かるが、「最終的には何が儲かるのか」と繋がっているか

□ 異常の閾値（何%変化したら警告するのか）が決まっているか
  └─ 「20% 変化」は恣意的か、実績ベースか

□ ダッシュボードが「3 分で意思決定できる」設計か
  └─ グラフが 20 個あるダッシュボードは NG

□ データソースが複数あり、「片方が間違っていても」検証できるか
  └─ 音声記録 / Sheets / GA4 から独立検証

□ 「異常を発見」したら「即座に改善」できる体制か
  └─ 朝会で確認 → 昼間に改善 → 翌日に効果測定

□ データが「過去の記録」でなく「改善の羅針盤」として機能しているか
  └─ 「先月のデータ」を確認するだけではなく、
     「何が変わったか」から「明日何をすべきか」が導き出せるか
```
